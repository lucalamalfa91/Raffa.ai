# task-01-honest-invite-pane — The invite contract, the three-outcome pane, and accept in one click

## Coding objective

Publish the invite half of the API contract and render it. In
`web/openapi/raffa-api.v1.json` declare `identityProvisioned`,
`deliveryOutcome` and — the part that matters most — a **502 response** for
`POST /api/workspaces/{tenantId}/invites` carrying `failureReason`. Regenerate
the typed client, then anchor a typed `failureReason` on
`InviteWorkspaceMemberResult` (`client.ts:160-170`) exactly as `InvitedMemberBody`
is anchored to the 201 at `:150-151`. Replace `memberViewModel.ts:166-173`'s
boolean discriminated union with a three-arm union on the server's outcome
string, and render ADR-020 w15 §3's copy. Finally, make
`handleContinueWithEntra` (`invite/accept/index.tsx:172-183`) await its own
`loginPopup` promise and continue into the accept — its comment currently reads,
verbatim, *"Success needs no handling here"*, and that is why A15-4 dies today on
a mandatory second click.

The 502 declaration is not paperwork. `renderOperation` renders **every** status
key under `responses` (`generate-api-client.mjs:135-143`), so a declared 502 is
typed for free and an **undeclared** one leaves the pane string-matching server
prose through `error` (`client.ts:160-170`, its own comment calling it a
"plain-language failure reason") — a client inference of a server fact that
breaks on any copy edit.

- **Architecture decisions in force**: **ADR-020** w15 §3 (every string below);
  **ADR-012** w15 §7, §8, §13.1–§13.3; **ADR-026** w14 clause 3 and w15 §8–§9;
  **ADR-019** — no new semantic row, token or component.
- **Design ref and anchor**: `inputs/design/prototypes/raffa-v2/screens-v2.md:147-154`
  (§10 Members table and invite form) for the pane's structure, and the **ADR-020
  w14 footer §10.1** for the delivery copy, which was pre-decided *"so it is not
  re-opened"* (`ADR-020:280-287`) and is **confirmed verbatim here**. The 502
  reason copy and the identity sentence have no export and are decided in ADR-020
  w15 §3. The export is **pre-rebrand** — it says "Raffa", the product says
  "Raffa.ai" — so copy strings from the code, never by retyping the export.
- **Copy, verbatim.** 201 states: *"Invitation sent to {email}."* ·
  *"Invitation created, but the email could not be sent."* ·
  *"Invitation ready for {email}."* The identity line: *"They will get a one-time
  code from Microsoft the first time they sign in."* Every 502 row carries
  *"No invitation was created."* as `.micro-meta`, and `consent_missing` names
  **"a tenant administrator"**, not "you" — a Raffa.ai workspace Admin is usually
  not the Entra tenant admin, and telling them to fix a permission they do not
  hold is worse than telling them nothing.
- **Why "Try sending again" does not ship**, so no reviewer restores it: the
  server cannot re-send the original link (the token is stored only as a SHA-256
  hash), so any retry is a **re-issue** that mints a new token and kills the link
  the Admin is looking at — and `ADR-020:284-287` already forbids telling the
  Admin to invite again from this pane. The link block is the remedy; the roster
  row's **"Send a new invitation"** with its confirm and its "The link you already
  shared stops working." line remains the only re-issue path.
- **`identityProvisioned === false` means *not configured*, never *failed*.** The
  pane must not invent a warning from it. With the abort rule, a failure is a 502
  and never a 201.
- **Do not touch the Documents screen, the shell, Ask or the contracts routes** —
  `E16/F03/US01/T01` owns every one of those files this phase. Do not add a route (ADR-018: none
  moves this wave). Do not add a member status — the roster answers "who can get
  in"; a delivery outcome is a *pane* fact about the last action. Do not write a
  fourth outcome arm. Do not change `composeAcceptLink`. Do not convert the
  auto-continue into a `useEffect` on `accounts` — it would silently auto-join a
  visitor who was already signed in and remove the one consent step state 3
  exists for.
