# task-01-priority-by-claim — Priority by claim: the column, the service, the endpoint, the Worker's queue-jump

Built by hand on 2026-09-14, after the first real twenty-file batch on `dev`
(see `docs/waves/w15-acceptance.md` §0.2).

## Coding objective

Give the web one thing it cannot do on its own: move a document ahead of its
FIFO position in the Worker's queue. Service Bus is fixed at exactly one
subscription (OQ-w15-012 — "a design constraint, not an accident"), so the
move happens on the `extraction_job` row, not on the broker. Add one nullable
column (`extraction_job.prioritised_at`), a service that stamps it
idempotently, an endpoint any live member may call, and four lines inside
`ExtractionRequestedHandler.HandleAsync` that let a delivery claim and run a
prioritised job in its own tenant before its own — bounded to one per
delivery, reusing ADR-027 §C6's `ClaimLost` settlement for the prioritised
job's own, now-superseded message.

## Parent story AC covered

- AC-5 (Worker takes the prioritised job first, bounded, no duplicate run)
- AC-6 (endpoint contract: idempotent, 204/400/401/404, one audit row)
- AC-7 (reprocess clears stale priority)

## Context the implementer needs

**Why the row, not the broker.** OQ-w15-012 (`reports/architecture/waves/w15.md:52`)
fixed exactly one Service Bus subscription: "a second subscription would
silently process every document twice." There is therefore no broker-level way
to reorder a message that already left the topic queued behind others. The
document moves on its own `extraction_job` row instead, and the Worker reads
that row before it reads its own delivery.

**The claim is the same CAS every delivery already uses.**
`InMemoryExtractionJobClaimStore`/the production claim store both do
`UPDATE … WHERE status = 'Queued' AND claimed_at IS NULL` — a prioritised job
is claimed with the identical statement, never a bespoke path. When the
prioritised job's own message later arrives on its own delivery, that same
claim affects zero rows (the job is already `Processing`/terminal), and
`ExtractionHandleOutcome.ClaimLost` → `ExtractionSettlement.Decide` already
completes it, never redelivers, never dead-letters (ADR-027 §C6, unchanged —
**do not add a new settlement outcome**).

**Bound the work-steal at one per delivery.** Three replicas × four calls in
flight already lets a dozen opened documents start at once; every extra job a
delivery carries widens the message-lock exposure, since a delivery holds its
own lock for the whole run (`ServiceBus__MaxAutoLockRenewalMinutes = 30`,
ADR-005 §7). `MaxPrioritisedPerDelivery = 1` is a named constant on the
handler, not a magic number.

**Tenant isolation is structural, not a review note.** The prioritised-job
query runs inside `tenantContext.BeginScope(tenantId)` — the *message's* tenant
— exactly like every other query in this handler (ADR-009). It never reads
across tenants; there is no ask here to relax that.

**The endpoint is any live member's, not Admin-only.** Unlike `reprocess`
(Admin, R-DOC-07) and `delete` (Admin, R-DOC-10), prioritising is not a
destructive or privileged act — whoever opened the document is the one
waiting for it. `ICallerContext.ResolveTenantAsync`'s order still applies:
401 (no identity) → 400 (malformed tenant header) → 404 (no membership or no
such document) — **never 403** (ADR-025 Rule B1, the same rule every other
tenant-scoped route in this wave follows since the NW-05 gate).

**Idempotent because the caller calls it blindly.** The web calls this once,
unconditionally, every time a user opens a document that is not yet terminal
(task-02's own contract) — it never first checks whether calling is worth it.
`DocumentPriorityService.PrioritiseAsync` must therefore be a true no-op,
including its audit write, whenever there is nothing left to stamp: already
claimed, already prioritised, or already terminal.

**Do not touch `ExtractionSettlement.cs` or `ExtractionSettlementTests.cs`** —
C6's disposition table is unchanged; this task only adds a caller of the
existing claim store, not a new outcome. **Do not add a second Service Bus
subscription, topic, or Terraform resource** — `infra/modules/servicebus/`
is out of scope and untouched. **Do not widen `MaxPrioritisedPerDelivery`
without recording the reason in the same doc comment that states it today.**
