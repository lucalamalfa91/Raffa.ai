# task-01-async-processing-schema — Additive migration: claim columns, attempt count, refusal record, `Rejected`

## Coding objective

Add one EF Core migration to `Raffa.Documents.Contracts` that gives
`extraction_job` a claim (`claimed_at`, `claimed_by`) and an `attempt_count`,
and gives `document` the nullable columns the refusal record needs (the
rejection **reason code** and its timestamp — a code from the closed set
`AdmissionDecision` already defines, never a sentence). Add the `Rejected`
member to `DocumentProcessingStatus`. Regenerate the checked-in
`documents-contracts.sql` so the script and the model agree, and add the
conditional-`UPDATE` claim method the worker will use in us-02.

Every column is **nullable or defaulted**. Nothing is dropped, no type changes,
and no existing column becomes `NOT NULL` — that is what makes a code revert
safe without a schema rollback, and it is a load-bearing property of the wave's
rollback plan, not a style preference.

`Rejected` needs **no DDL**: `processing_status` is
`character varying(30) NOT NULL` with no CHECK constraint, no enum type and no
default — `backend/src/Raffa.Documents.Contracts/Migrations/Scripts/documents-contracts.sql:110`
is its only occurrence in the script.

## Parent story AC covered

- AC-1 `extraction_job` gains `attempt_count` (defaulted), `claimed_at` (nullable) and `claimed_by` (nullable); `document` gains the three nullable columns the async path needs. **No column is dropped, no type is changed, and no `NOT NULL` is added to an existing column.**
- AC-2 The previous API image runs unchanged against the new schema — the migration is purely additive, so a code revert needs no schema rollback.
- AC-3 `Rejected` joins `DocumentProcessingStatus` **with no DDL**.
- AC-4 A conditional `UPDATE` claim is expressible and proven.
- AC-5 The regenerated `documents-contracts.sql` is idempotent and re-runnable, and `extraction_job` keeps its RLS settings and `tenant_isolation` policy untouched.

table.

- **Architecture decisions in force**: **ADR-027 §D1, §D6** (the row is the
  work; the message is a pointer; the rejection reason is persisted);
  **`none — ADR-021`**, recorded at the table — the new status value needs no
  DDL and `documents-contracts.sql` is already in **both** `backend.yml` arrays,
  so neither array moves and `backend.yml` is not opened; **ADR-009** —
  `extraction_job` carries `FORCE ROW LEVEL SECURITY`, which is precisely why no
  poller and no sweeper may exist, so do not add an index or a column whose only
  purpose is to enable one; **ADR-003** — one migration regenerates one
  checked-in script.
- **The rejection reason is a code, not a sentence.** ux-ui-designer's round-3
  finding: a user-facing sentence supplied by the API has no oracle behind it
  and cannot be edited without a deploy. Persist a code from the closed set at
  `backend/src/Raffa.Documents.Contracts/Application/Admission/AdmissionDecision.cs:23-32`;
  the screen chooses the words (ADR-020 w15 §6). *A server field may select the
  sentence a user reads; it may never supply it.*
- **`Rejected` is a wire and storage value; "Not added" is what the screen
  says.** Do not introduce "Not added" anywhere in the backend.
- **Do not touch**: the `ExtractionStage` vocabulary or
  `DocumentProcessingStageMap.cs:20-39` — the six stage strings are the design
  oracle verbatim and are unchanged this wave. Do not add a CHECK constraint to
  `processing_status`; adding one would turn AC-3's "no DDL" into a breaking
  change and would make the previous image fail on rollback.
