## 1. NW-07 — conversation `user_id` is the token subject

**Scope: IN, reduced** — the keying seam closed in w15; what remains is a *data
disposition*, which I reduce from "migrate" to "record".

- **Decision**: pre-w15 rows are **left in place, never remapped, never deleted**;
  the retirement is *recorded*, not executed. Ratifies OQ-w16-001.
- **Why**: a blind email→`oid` remap needs a directory lookup the product has no
  batch path for (`Raffa.Chat/Migrations/` holds only `Initial` + RLS), and a
  *wrong* remap hands one user's threads to another — a breach of R-CONV-01 AC-1,
  strictly worse than the loss it repairs. Deleting is equally out: the rows are
  the customer's (ADR-001 w15 clause 4's shape).
- **Against my own ADR-001 w15 clause 7** ("must not *silently* drop a fact the
  user is entitled to"): satisfied — the drop is recorded and bounded, not silent.
  **Constraint to preserve, not to build**: no surface may *count* a conversation
  it cannot open. The list filters on the same key, so an orphan never appears as a
  phantom row; a task must not regress that.
- **Pilot impact: none** — a pilot workspace is fresh. The ruling exists so a `demo`
  walker does not read an empty rail as a w16 regression.

**A16-1, reworded** (I ratify the intake's wording and add clause 3). On `dev`:
1. User A creates a conversation, reloads → readable by A.
2. User B, a member of the same workspace, can neither list nor read it (R-CONV-01 AC-1).
3. A pre-w15 conversation is not listed and not counted anywhere; opening it is a
   clean 404 — never a 500, never another user's thread.
4. The disposition is in the PR description and `reports/open-questions.md`
   (task DoD `:72`).

**The promoted task carries a poisoned acceptance line.**
`task-01-conversation-user-is-the-subject.md:69` requires *"a conversation created
under `User@Example.com` is readable by the same subject presenting
`user@example.com`"*. The key is `oid`, and `CallerIdentity.cs:60-68` records
**not** lower-casing as deliberate. Satisfying that line forces an implementer to
**re-introduce the exact normalization ADR-010 rejected** — not merely vacuous,
actively harmful. Raw §0.4 forbids rewriting the body, so the corrected wording
lives in the ADR-001 w16 footer and `waves/w16.md`, and **the decomposer must carry
it into the story row and the slice**, never DoD line 69.

- **Priority**: head of wave, `should`, unchanged. **Never narrowed**: clause 2 —
  per-user isolation is a tenancy promise.
- **ADR action**: `amend ADR-001` (w16 footer, clause 1). `OQ-askv2-005` retires
  with the item, but ADR-024 is software-architect's to amend.

## 3. NW-13 — Contract 360 step ticks are server state

**Scope: IN, as scoped.** Three product rulings; the module and table are
software-architect's (OQ-w16-006's other half).

1. **The four named steps are canonical** — *Notify · Request revised pricing ·
   Counter with the market benchmark · Sign or send non-renewal notice*
   (`screens-v2.md:106-107`). Four, no more; a fifth is a product change.
2. **Stored by stable step key, never array index** (ratifies OQ-w16-006). The
   reason is mine rather than the architect's: two of the four labels are
   **parameterized** (`contract360ViewModel.ts:211-218`; the tracker header is
   literally `"close by {{ cancel }}"`, `screens-v2.md:105-106`). The row stores the
   **key**; **the rendered label stays client-side**. Freezing a supplier name or a
   cancellation deadline into a persisted row makes the record assert a fact that
   later changes — ADR-001 w14 clause 3.
3. **Per contract, one live negotiation per contract** — matching `renewal_action`'s
   unique `(tenant_id, contract_id)` (`RenewalActionConfiguration.cs:41`) and the
   design, where the tracker appears *after* "Start negotiation now" and its status
   is "shared with the Contract 360 tracker (`racts`)" (`screens-v2.md:105,130`).
   **Not** per renewal cycle: no cycle entity exists, and per-cycle tick *history*
   would be a new capability — out for V1, and asked for by no oracle.

**A16-7** — on `dev`: tick 2 of 4 on contract X → reload **and** second browser →
the same 2 ticked; contract Y unaffected; the step keys the API returns match the
four names; no `sessionStorage["raffa.contract360.steps.*"]` is a source of truth.

- **Priority**: `should`, last of theme B before W16-01. Release valve #3 (§6).
- **ADR action**: `amend ADR-001` (footer clause 3). ADR-002/003/021 are
  software-architect's.

## 4. NW-21 — quote outcome updates Savings

**Scope: IN, not expanded, with one fence.** OQ-w16-005 is mine alone.

**Ruling: A16-8 closes on the status move.** I ratify the intake's assumption — but
its stated reason (the design column is "Estimate") is not load-bearing. The real
one, which I verified:

- **No surface renders a realized money figure.** `buildKpiCells`
  (`savingsViewModel.ts:83-112`) builds exactly three cells — Contracts analyzed ·
  Upcoming renewals · Savings **identified** — matching the oracle exactly
  (`screens-v2.md:134-135`, which has **no realized tile**). Realized appears only
  as a **count** (`:110`), as the module's own comment says (`:78-82`).
- **The realized amount is already stored and already on the wire** per opportunity
  (`RealizedSavings.cs:45`, written `SavingsOpportunityService.cs:300-308`, exposed
  as `realizedAmount` `schema.ts:551`). **No fact is dropped from the row.**
- So the estimate-summed `Realized` **range** (`SavingsKpiCalculator.cs:101-106`)
  is a latent **API-shape** defect that reaches no screen.

**Correction to OQ-w16-005, on the record.** It frames the amount fix as "an ADR-001
capability change and the head of W17". It is **neither a capability change nor a
new item**: it is an **unmet AC of an existing, still-`active` story** —
`E04/F03/US01` (`us-01-savings-kpis.md:6`; AC-1 `:18` unchecked, naming "realized")
— whose implementing code documents the gap and names the record task that did ship
(`SavingsKpiCalculator.cs:45-54` → `E04/F02/US02/T02`, `status: live`). It needs no
ADR-001 amendment and no new epic; it needs a **priority ruling: head of W17**,
recorded so it is not lost a third time. Spec `:447` defines the tile as
"**Verified** negotiated/implemented savings".

**Fence binding this wave (zero cost)**: no w16 task may render
`SavingsKpiSummary.Realized` as a **money amount**; the only realized figure a w16
surface may show is the per-opportunity `realizedAmount`, which is correct. Grounds:
ADR-001 w14 clause 3. *The defect is already live, not dormant* —
`PATCH /api/savings/{id}` is routed (`SavingsEndpointExtensions.cs:37`) and already
flips status and stores the amount (`SavingsOpportunityService.cs:287-308`), so
**NW-21 widens that path, it does not create it.**

**May an outcome be *resolved* to an opportunity rather than *naming* one? Yes —
but it must never guess.** The link is explicit, or derived from a fact the system
holds (the quote's contract / supplier). With no unambiguous opportunity the outcome
is recorded **unlinked**, `savingsPropagated` stays `null`, nothing moves — an honest
omission, never a nearest-match. Grounds: ADR-001's own driver ("a fabricated number
is not [acceptable]") and `NegotiationOutcome.cs:127-131`, which already states no
derivable link exists.

**A16-8** — on `dev`: record an outcome linked to an opportunity → its status is
`Realized` and its `realizedAmount` equals the outcome's `realizedSaving`; the
Savings realized **count** increments; a second browser agrees; an outcome with no
unambiguous opportunity is still recorded, is visibly unlinked, and moves no KPI.

- **Priority**: `should`, with or after NW-12 (§5 constraint 5). **Never narrowed**:
  the fence.
- **ADR action**: `amend ADR-001` (footer clause 4). The link column and migration
  are software-architect's.
