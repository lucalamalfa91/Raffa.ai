## The one rule under all four items

ADR-001's w14 footer **clause 3** — *"The screen must not assert a fact the
system does not hold"* — was written for "Invitation sent." with no mail. This
wave applies the same rule to three new surfaces, and adds its mirror:

> **The system must not silently drop a fact the user is entitled to.**

Both halves are the same promise. It is why a refused file must become a row
(NW-27), why a processing document may not render as an empty contract
(NW-61), why an invite may not return a "ready" link that cannot be used
(NW-67), and why "Invitation sent." may only appear on a confirmed send
(NW-68). I will defend this as one rule, not four preferences.

## NW-27 — `POST /api/documents` returns once the file is stored

| `product-spec.md` §7.1 (`:296`) | `uploaded` = "Document stored; **processing not started**" | unreachable as a returned state today |
| `product-spec.md` §16.1 (`:745`) | "**Async queue / worker**" is **P0** | never delivered |

### The product ruling — OQ-w15-004, the admission gate

This is the decision that costs something, so I state the reasoning, not just
the verdict.

The gate does **two** different jobs, and the intake treats them as one:

| Half | Cost | Can it hold a 2 s budget? |
|---|---|---|
| (a) **Format + size**: a `.zip` renamed `.pdf` → 415; > 50 MB → 413 | header sniff, no AI, no I/O beyond the stream | **yes**, trivially |
| (b) **Content**: parse/OCR + Foundry `classify` → "not a contract" → 422 | `DocumentAdmissionGate.cs:110-112`, `:136-138`, live Foundry | **no** — and "no mocks on `dev`" is standing |

**Ruling: the gate splits.**

- **(a) stays synchronous, in the request.** A file that is not even a document
  is refused before anything is stored, exactly as today. `us-01-documents-v2`
  AC-1's *415 half survives intact*, and this preserves the honest promise
  that Raffa does not store a family photo.
- **(b) moves to the Worker**, and a refused file becomes a **terminal
  `Rejected` row**.

**Why (b) must become a row — from acceptance, not from architecture.** The
design oracle calls the "Not added" card *session-only, never counted*
(`screens-v2.md:75`). That rule is only coherent while the refusal is
**synchronous** — the person who dropped the file sees the card in the same
interaction. Once classification is asynchronous, "session-only" means:

- a refusal that arrives after the user closed the browser is **never shown to
  anyone** — which directly contradicts A15-1's own "each reaches a terminal
  state **with the browser closed**";
- "All documents · 15" would show 15 at t≈2 s and silently become 14, and a
  **second browser** would never see the file at all — contradicting A15-1's
  reload and second-browser clauses;
- the user is left believing Raffa holds a document it silently discarded.

That is the mirror of clause 3: **a fact the user is entitled to, dropped
silently.** A rejected file is an outcome of an act the user performed. It must
survive the session.

So: **`Rejected` is a terminal, persisted, visible state.** Three consequences
I own and will write:

1. **A `Rejected` document is never askable and never enters Ask's corpus.**
   ADR-024's grounding rule is untouched: Ask answers only from facts that
   passed validation. `Rejected` is not "validated with zero facts" — it is
   outside the corpus entirely. No task may relax this to make a count add up.
2. **The count must be honest and the askable count must not inflate.** A
   rejected file *is* a document the tenant uploaded, so it belongs in "All
   documents · N". It must **not** appear in `kbSummary`'s "M askable" nor in
   the "K waiting for your review" queue. The exact copy and placement are
   **ux-ui-designer's**, not mine; the arithmetic rule is mine.
   > **⚠ CORRECTED AT THE TABLE (2026-09-13) — do not build to the sentence
   > above.** The clause "it belongs in 'All documents · N'" is **withdrawn**:
   > a rejected row is **never counted**. See "Correction at the table" at the
   > end of this file, and `reports/architecture/waves/w15.md` OQ-w15-004.
3. **No new removal capability.** A rejected row is removed by the `DELETE
   /api/documents/{id}` path that already exists (AC-5, Admin). Nothing new.

**What this costs, stated plainly so the table can price it:** a sixth
`processing_status` value beyond spec §7.1's five, a migration (ADR-021), an
ADR-024 amendment, a recorded override of `screens-v2.md:75`, and the
supersession of two ACs of a live story. I judge that cheaper than a product
that loses a user's file without telling them. If the table prefers to keep the
content gate synchronous instead, it must say so knowing that A15-1's 2 s
budget then depends on live Foundry latency — and I will vote `PROPOSE`, not
`OBJECT`, because that is a defensible trade; what I will **not** accept is
async classification *plus* a session-only refusal, which is the only
combination that loses data.

### Acceptance — observable on `dev`, refining A15-1 / A15-2

Every clause below is checkable by one person with a browser on `dev`.

**A15-1a — the drop returns immediately.** Drop 15 PDFs on `/documents`.
Within ~2 s of the last file, **15 rows exist server-side**: the list shows
"All documents · 15", and each row shows a server stage, not a client
animation. `POST /api/documents` p95 < 2 s across the batch.

**A15-1b — the rows are server facts.** Hard-reload → the same 15 rows. Open a
**second browser** (different session, same Admin) → the same 15 rows, same
statuses. Nothing depends on `sessionStorage`.

**A15-1c — the work continues without the browser.** Close the tab
immediately after the drop. Re-open ≥ 5 minutes later → **every one of the 15
is terminal**: `Needs review`, `Completed`, `Failed` or `Rejected`. None is
stuck in `Uploaded`/`Processing`.

**A15-1d — the rail agrees.** After the drop, the rail Documents badge equals
the list count (this is NW-10's fold-in). No fresh-session zero-badge.

**A15-2 — durability under restart.** Restart the API **and** the Worker
mid-batch. No document is lost, no document is silently stuck: every row
reaches a terminal state, and no file is processed twice into duplicate facts.

**A15-1e — the refusal is honest (new; this seat's clause).** Include one
obvious non-contract (a recipe PDF) in the 15. It becomes a **`Rejected`
row that survives a reload and is visible in the second browser**, carrying
the reason. ~~It is counted in "All documents",~~ **not** in askable, **not** in
the review queue. A `.zip` renamed `.pdf`, by contrast, is refused **in the
request** with nothing stored.
> **⚠ CORRECTED AT THE TABLE (2026-09-13).** The struck clause is withdrawn.
> The row is **visible and persistent but never counted** — so "All documents"
> reads **14**, plus one visible, self-explaining refusal. A count that drops
> 15 → 14 with the row *vanishing* is the dishonest case; a count that reads 14
> beside a persistent refusal notice is not. See "Correction at the table".

### Priority I defend

1. **NW-27 is the wave.** It is the only item that closes a **P0** backlog line
   (§16.1 "Async queue / worker") and it unblocks NW-61. It is not cuttable and

3. **The narrowing I refuse**: shipping async upload **without** the terminal

## NW-61 — Upload feels instant; details only when the document is ready

### Scope decision — **reduced to the completeness contract**

The intake's audit is right and it narrows this item usefully: the client half
(optimistic row, server-driven stage, 2 s poll) is **already built**, and two of
its three defects (the poll predicate never firing, the counters reading zero)
**disappear the moment NW-27 makes the server row appear**. Neither needs a
product decision.

What remains is the part no one has built and that is genuinely mine:

| Sub-capability | Decision | Why |
|---|---|---|
| A **server-side completeness signal** on the Portfolio / Contract 360 aggregates | **IN** | Today Contract 360 reads no `processingStatus` at all. The screen cannot tell the truth about a fact it is never given. |
| Ask's off-state reads a **real status** instead of inferring from counts | **IN** | Today it infers from `kbReady` + `totalCount > 0` (`ask/index.tsx:93`, `:99-105`). An inference is not a fact. |
| "Still processing" state on Portfolio, Contract 360, Ask | **IN** | A15-3. |
| New copy for that state | **OUT — the oracle already has it** | `screens-v2.md:28-29` already ships the sentence, verbatim, at `askViewModel.ts:254`. Reuse it; do not invent a second vocabulary. |
| Poll predicate + a request timeout on the upload call | **IN**, but it is a **client-architect** call, not a product one | I only require the observable: a killed request never silently becomes a permanent `failed` row that contradicts the server. |
| A global "processing" banner / progress dashboard | **OUT** | No oracle asks for one; `screens-v2.md` §3's state list is per-row. |
| Blocking navigation to Ask/Portfolio while anything is processing | **OUT, and I will object to it** | The pilot explicitly says the user "**può lasciare la pagina**" (`percorso-pilota-v1.md:54`). Gating ≠ blocking. |

### The product rule

> **"Still processing" outranks "empty".** Where a screen cannot distinguish
> *nothing exists* from *not ready yet*, it must say *not ready yet*.

An empty Contract 360 during processing is a **fabricated fact**: it asserts
"this contract has no clauses" when the truth is "Raffa has not read them yet".
That is spec §2 ("AI is not the database … canonical facts live in structured
storage") and §8.4's evidence requirement, expressed on a screen. It is also
clause 3 again.

Two "not ready" states exist and the oracle already distinguishes them —
**still processing** (transient, resolves itself) and **waiting for your
review** (waiting for a human). `screens-v2.md:28-29` covers both in one
sentence: *"Your document is still processing **or waiting for review**. Ask
only answers from facts that passed validation — so it never guesses."* The two
must not collapse into one string: the first needs patience, the second needs
**action**, and the pilot's minute 6–11 is exactly that action
(`percorso-pilota-v1.md:122`).

**Askable = validated, not merely `Completed`.** `percorso-pilota-v1.md:55-56`
is explicit: `completed` = "fatti canonicali", "Ask si accende", and **Mark as
validated** is unlocked only when the weak fields are decided. The completeness
signal must key on that, not on the processing status alone. This is the same
number NW-24's w14 ruling already made the rail and the picker agree on.

### Acceptance — observable on `dev`, refining A15-3

**A15-3a — Ask.** With one document mid-processing and **no** validated
contract, open Ask → the off-state shows the *processing* reason
(`screens-v2.md:28-29`), not the generic "Upload a contract first", and the CTA
is "Go to Documents". Ask returns **no answer** derived from that document.

**A15-3b — Contract 360.** Open the contract of a document that is still
processing → the screen says it is still processing. It does **not** render an
empty Overview, an empty Clauses tab, or a zeroed commercial term.

**A15-3c — Portfolio.** A processing document's contract either does not appear
as a complete row or appears **marked as not ready**. It never appears with
blank/zero commercials that read as extracted facts.

**A15-3d — the transition is observable.** When that document reaches
validated, the same three screens switch to real content **without a manual
refresh** (the 2 s poll already exists), and the `justValidated` hook
(`screens-v2.md:70-71`) fires.

**A15-3e — no fabricated fact, restated as a check.** At no point during
processing does any of the three screens display a number, date or clause for
that contract that is not yet a validated extracted fact.

### Priority I defend

1. **NW-61 is `must` and lands in the same wave as NW-27.** Shipping NW-27
   alone makes the product *less* honest, not more: 15 rows appear instantly
   and Ask/Portfolio/Contract 360 will confidently render them as empty. Async
   upload without the completeness gate is a regression in truthfulness.
2. **Order inside the item**: Ask first (it is the pilot's minute 11–15 and the
   only surface with the copy already written), then Contract 360 (the citation
   destination), then Portfolio. If the cap forces a cut inside NW-61, cut
   **Portfolio's** marker last-in/first-out — it is a triage inventory, not a
   proof surface.
3. **I refuse** any implementation that satisfies A15-3 with a second **client**
   heuristic. ADR-012's w14 rule ("a client store never stands in for a missing
   GET") extends here: *a client must not infer a server state it can be told.*

- **`none` for ADR-001** beyond the single footer clause recording the rule

- Co-decider, not writer: **ADR-012** (the inference clause) — client-architect;

## NW-67 — Raffa provisions the invitee's Entra B2B guest at invite time

### Scope decision — **IN, and ADR-001's w14 footer already committed us**

Clause 1 of the w14 footer reads: *"A wave that ships an invite an invitee
cannot act on has not delivered §20."* w14 shipped a copyable link — and the
invitee **still cannot act on it**, because signing in requires an identity the
tenant does not have and the authority forbids `common`/`organizations`
(`write_web_runtime_config.py:80-82`). w14 papered over this with an *operator
prerequisite* ("create a second Entra account by hand",
`reports/audit/w14-hitl.md:302`). An Azure-portal step the customer must
perform is not a product. NW-67 is therefore the **completion of clause 1**,
not an expansion of it.

**Against §1.2 — this is not a non-goal.** The two that a careless reader might
invoke:

- *"Supplier onboarding"* — the invitee is a **colleague** joining the
  customer's own workspace (§20 Day 1: "invite **Procurement users**"; §3.1's
  role table is entirely internal). Supplier onboarding means bringing a
  *counterparty* into a procurement process. Different party, different
  purpose.
- *"Autonomous supplier communication without human approval"* — nothing here
  is autonomous (an Admin clicks Invite) and nobody here is a supplier.

The pilot path's §7 table makes the same distinction in the customer's own
words: `:153` lists "Outreach supplier, RFQ, CLM, firma" as **"Non-goal
prodotto"**, while `:152` lists email/production-Entra merely as "non servono a
mostrare il processo".

### The scope statement I am asked to make

> **Inviting a colleague creates, as a side effect, a guest identity in the
> customer's directory for that address — and never anything more.**

Three fences, all mine, all product-scope not implementation:

1. **Raffa creates a guest; it never deletes or blocks one.** (This answers
   **OQ-w15-007**.) Rationale beyond the technical one: a directory object is
   the **customer's**, not Raffa's, and the same guest may belong to other
   workspaces — removing a member from workspace A must not disable a person in
   workspace B. Raffa's scope is the **workspace roster**, not the identity
   lifecycle; becoming an identity-lifecycle manager is adjacent to §1.2's
   "supplier onboarding" and is not a capability any oracle asks for. An Admin
   who wants the guest gone does it in Entra. **No directory-deletion path is
   built.** Removal of *membership* stays immediate, exactly as ADR-025 ruled.
2. **One guest per invited address, idempotent.** Re-inviting, or inviting
   someone already in the tenant, creates nothing new (A15-5). Raffa never
   duplicates a person in the customer's directory.
3. **No directory reads beyond what provisioning needs.** Raffa does not list,
   search, enumerate or sync the customer's directory. Inviting is a write of
   exactly one object. Anything else is a new item in a later wave.

### The conflict the intake did not flag — ADR-001 w14 footer **clause 7**

Clause 7 deferred the "invite email must match the workspace domain" rule *"to
the wave that lands ADR-010 (real token claims)"*. **NW-05 lands ADR-010 in
this wave.** Read literally, clause 7 fires now — and **A15-4 invites a gmail
address**. Enforcing the restriction would fail the wave's own acceptance on
the first click.

**Ruling: the domain restriction stays helper text and is *not* enforced. The
deferral does not convert into an obligation.** Three reasons, in order:

1. **It contradicts the mechanism this wave chooses.** A B2B *guest* is by
   definition an identity from outside the tenant's verified domain. An item
   whose whole point is inviting an external address cannot ship a block on
   external addresses.
2. **It would make acceptance unverifiable** — the same argument as w14, now
   stronger: in w14 the second account merely *happened* to be on another
   domain; in w15 the product itself provisions it.
3. **It was never a requirement.** It is prototype helper text
   (`screens-v2.md:150`). It is not in §20, not in §3.1, not in the pilot path.

The w15 footer must say this explicitly, because clause 7's wording would
otherwise be read as a standing instruction by the next implementer or
reviewer. If the workspace-domain restriction is ever wanted, it returns as its
own item with its own justification — not as a side effect of a wave that
lands JWT.

### Acceptance — observable on `dev`, refining A15-4 / A15-5 / A15-7

**A15-4 (the end-to-end walk).** Admin invites an address the tenant has never
seen (a personal mailbox the operator controls) as **Procurement**. Then, with
**no Azure portal at any point**:
- the address receives a Raffa-branded mail **within 1 minute** (NW-68);
- the link in that mail opens and sign-in completes via the one-time passcode;
- the invitee lands **inside that workspace**, as **Procurement**;
- **no second "Join" click** is required after the popup resolves;
- the Members roster shows that address **Active** with role Procurement, after
  a reload and from a second browser.

**A15-5 (idempotence).** Invite an address that is already a guest in the
tenant → same flow completes, **no duplicate guest**, roster correct. Re-invite
the same address twice → still one guest, and the second invite does not
corrupt the first.

**A15-7 (the honest failure — the clause I will not trade).** With the Graph
permission **not** consented, invite someone →
- the invite pane shows a **named** error saying provisioning failed and what
  the invitee still lacks (an account on the tenant);
- an **audit row** records the failure;
- **no mail claims the invitation is ready**, and no "ready" accept link is
  presented as usable;
- the Admin is not left believing an invitation is outstanding when it is not.

**A15-4d (the guard on the domain rule — new; this seat's clause).** The gmail
address in A15-4 is **not** rejected for being off-domain. No server-side
domain block exists on the invite form.

### Priority I defend

1. **NW-67 before NW-68's acceptance.** A mail whose link leads to a sign-in
   the invitee cannot complete is A15-4's *failure*, not a partial pass. The
   intake ordered this correctly; I restate it because if the cap binds, the
   tempting cut is "ship the mail, defer the guest" — that ships a worse
   product than w14, because w14 at least did not *promise* the link worked.
2. **A15-7 is not narrowable.** The whole reason this item exists is that a
   "ready" link that cannot be used is the defect. A failure path that only
   writes an audit row and shows the Admin a success pane has not delivered it.
3. If NW-05 slips inside the wave, **NW-67 must not ship an accept path built
   on `X-User-Id` that NW-05 then rewrites** (intake §5; I endorse and will
   hold the table to it).

### ADR action

- **`amend ADR-001`** (same single w15 footer): the guest-provisioning scope
  statement and its three fences; **clause 7 is resolved as "not enforced"**.
- Co-decider, not writer: **ADR-010** (tenant provisions guests; authority
  stays single-tenant) — security-architect; **ADR-015** (the application
  permission) — cloud-architect/security-architect; **ADR-025** (new audit
  verbs; removal never deletes the guest) — security-architect; **ADR-026**
  (the invite response gains a provisioning outcome) — software-architect.
  I sign only the scope and failure-contract clauses.
- **`none`** on which identity calls Graph and whether Terraform manages the
  consent (**OQ-w15-005**) — cloud-architect + security-architect. I take one
  position only: **admin consent must be a one-time operator act, never a
  runtime prompt shown to an Admin using the product.**

## NW-68 — Raffa sends the invitation email (ACS Email)

### Scope decision — **IN. The deferral ends; scope never changed.**

This answers **OQ-w15-002**, which is mine alone per the wave skeleton. The
question "is email in scope, given the pilot path excludes it?" rests on a
misreading, and the pilot document **refutes it in its own words**:

### The truthfulness rule, now that a transport exists

Clause 3 was written as "the UI must not say 'Invitation sent.' while no mail

> `mailDelivered` stays a **server fact** — never a client optimism, never a
> default `true`, never "we called the API so presumably it worked".

link is copyable, the Admin can still deliver it by hand. The failure copy is

only confirm that the `true` path may not overstate.

### Acceptance — observable on `dev`, refining A15-4 / A15-6

controls → a **Raffa-branded** mail arrives **within 1 minute**, containing an

- the pane shows ADR-020's pre-decided failure copy plus **"Try sending

**A15-6c — re-send is real.** "Try sending again" performs an actual send
attempt and updates the state from the server. It does not merely re-render.

**A15-4 (shared with NW-67)** is the true end-to-end: mail → link → passcode →
inside the workspace as Procurement, **no Azure portal, no "Join" click**.
