## 1. W14-01 — the wave base

### Decision

**The wave branches from `origin/main` at a commit that contains `87b7976`
(the `Raffa.*` → `Raffa.*` rebrand), and the rebase is an operator act at
HITL, before `register_wave.py` and before fan-out. It is not a fan-out task.**

Concretely, the order at HITL is:

1. Operator merges/rebases `helix/next-wave-process` onto `origin/main`
   (`≥ 25b10da`). This is a **merge, not a fork**: the process branch carries
   `.helix/raffa-next-process.yaml` (`54cbd27`) which `main` does not have,
   and `origin/main` carries the rename which the process branch does not.
   Neither side is a subset of the other.
2. Operator re-runs the path translation over
   `reports/context/waves/w14-requirements.md` and, once written,
   `reports/plan/slices/w14.yaml` (`Raffa.X` → `Raffa.X`,
   `inputs/design/prototypes/raffa-v2/` → `raffa-v2/`).
3. Operator proves the base green **before** the first task (W14-A1 below).
4. Only then `./run.ps1 -Max -Slice w14`.

### Why this is an ADR amendment and not a bookkeeping note

I read ADR-014 end to end. Its body fixes the flow at `:90` — "Every task
branch is created from `main` and merged to `main` via a required PR with CI
green" — and stops there. Three things it does not cover, all of which bit this
wave and will bite every future wave of the next-wave process:

- **The Helix process branch diverges from `main` by construction.** `.helix/`
  lives in the repo (`ADR-014:97-98`: "`.helix/` stays inside the repo and is
  not its own git toplevel"), so the artefact branch and the product branch
  drift apart and must be reconciled *before* a wave, not after.
- **`integration` is not in ADR-014 at all** — the word does not occur in the
  file. Yet `wave-close-e13.md:7` reports "PR #67 (`integration → main`) was
  merged after the build was reconciled by hand (`50b38a7`)", and `:20`
  names the `wave/E13-*` task branches. That is a real two-level structure
  (task branch → `integration` → PR → `main`) the ADR body never describes. It
  should be recorded now, not re-derived next wave.
- **A rename can cross the CI ↔ cloud ↔ *identity* boundary.** See below;
  ADR-014 has no rule that a base must be proven green before a wave starts.

`## Amendment (2026-09-10, wave w14)`, adding a "Wave base and integration

## 2. NW-58 — infrastructure, secrets and order

### 2.1 The hard constraint: infra cannot be delivered by a fan-out wave

`infra.yml`'s apply is a no-op; HCP Terraform owns apply from its own VCS
connection (`infra.yml:104-135`). So a Terraform change:

- takes effect only after **merge to `main`**, and then only when the **HCP run
  reaches `CURRENT`** — which happens outside GitHub Actions, outside the wave
  branch, and outside anything a fan-out task can observe or wait on;
- must be repeated per environment, and `demo`'s is reviewer-gated;
- cannot have its secret **value** promoted. Two independent sources say so:
  `ADR-016:79-80` ("Promotion moves **code/artifacts only**; never copies a
  database, storage account, or secrets between environments") and
  `demo-promote.yml:43-50` ("no step here or in
  infra.yml/backend.yml/web.yml copies a database, storage account, or secret
  *value* between environments. Keep it that way — do not add such a step").

A new Azure mail resource for NW-58 is therefore not one task. It is: a
`modules/mail` Terraform module + a wire-up in **two** environment roots + a
Key Vault secret per env + a **`modules/containerapps` change** (env vars are
enumerated literally, `main.tf:66-163`; the single `dynamic "env"` at `:165-174`
is bound by ADR-004's amendment to per-role model ids and is not a general
hatch) + a role assignment + two out-of-band HCP applies the wave cannot see +
only then the backend task that reads the setting + only then a web task. With
one wave capped at 20 tasks and 5 phases, and the apply barrier sitting in the
middle of it, that does not fit.

**Pre-empting the shortcut.** Someone will propose skipping Terraform by adding
`--set-env-vars` to `backend.yml`, or by stuffing the value into
`var.ai_gateway_model_env`. Both are drift: `backend.yml:196-208` deliberately
only rolls `--image`, and the next HCP apply reverts anything CI sets behind
Terraform's back. The apply barrier is not a convention I am defending; it is
how this repo is wired.

### 2.2 Recommendation on OQ-w14-002 (the ruling is PO + cloud-architect's)

**Delivery-side recommendation: no mail transport in w14.** My reasons are
scheduling reasons, offered alongside — not in place of — the product reason:

- the apply barrier above makes it undeliverable inside the wave's own CI;
- `inputs/percorso-pilota-v1.md` §2 lists **email** under *"Non è onboarding"*,
  so the pilot path does not need it (product-owner rules on this, not me);
- the locked "cheapest tier, nothing idle-expensive" rule argues against
  standing up a mail resource in two environments for a path the pilot excludes.

So w14 lands **token → accept → join → remove → re-invite** behind
`IInvitationMailer`, with the **copyable accept link** as the shipped path and
a null/logging mailer as the default binding. The UI must not say
"Invitation sent." (NW-58's own must #1, and ux-ui-designer's row).

**I am not ruling this — I am constraining it.** §3 gives the decomposer both
orderings so the wave is safe whichever way the table votes.

### 2.3 The accept link needs a per-environment origin — and nothing supplies one

The finding that decides NW-58's infra footprint:

- the API container app has **no** web-origin env var
  (`containerapps/main.tf:66-174` — every block enumerated, none of them a
  frontend URL);
- config flows API → SPA only: `web.yml:141-205` writes `apiBaseUrl`,
  `oidcAuthority`, `oidcClientId`, `oidcRedirectUri` and the two API scopes into
  the SPA's `config.json`. There is no reverse channel;
- the SWA hostname *is* available — the module exposes `default_host_name`
  (`staticwebapp/outputs.tf:11-14`) and CI already resolves it live
  (`web.yml:170-176`) — but it is resolved **inside `web.yml`'s deploy job**,
  and the API's env vars are set by **Terraform**, not by CI (`backend.yml`
  never sets one). Availability is not plumbing.

Two ways to build `https://<swa-host>/invite/accept?token=…`:

| | Option A — SPA composes the URL | Option B — `Web__BaseUrl` on the API |
|---|---|---|
| API returns | the token / a relative path | an absolute URL |
| Infra change | **none** | `modules/containerapps` + both env roots + HCP apply ×2 |
| Works on localhost | yes (`window.location.origin`) | needs a third config value |
| Promotion risk | none | a `demo` promote before `demo`'s apply is `CURRENT` ships a `dev` link into `demo` — the exact cross-env leak ADR-016`:79-80` exists to prevent |
| Fits w14 | yes | no (see §2.1) |

**Decision: Option A for w14.** The API's invite response carries the token (or
a relative accept path); the Members screen composes the absolute link from its
own origin and offers it to copy. This removes the infra dependency from NW-58
**entirely**, which is what lets NW-58 fit in this wave at all.

**Recorded for later**: Option B is a *prerequisite* for any real mail
transport — a server sending an email cannot ask a browser for its origin. When
the transport item is scheduled (W15/W16), it must carry `Web__BaseUrl` with
it, per environment, applied before the backend revision that reads it.

This decision touches client-architect (who composes) and software-architect
(the response shape) → reconciliation in §6.

**ADR action: `amend ADR-016`** — footer
`## Amendment (2026-09-10, wave w14)`: what NW-58 adds to the per-environment
config contract (nothing, in w14, by construction), and the ordering a future

Once NW-02 makes membership the key to seeing a workspace, and NW-01 lists
workspaces **by membership**, then on `demo`:

> the ADR-022 fixture tenant `00000000-0000-0000-0000-000000000001` is seeded by
> **SQL** (`backend/scripts/demo-fixture-seed.sql:60-67`, run by
> `seed-demo-fixture.yml:132-135`), not by `POST /api/workspaces`. It can
> therefore **never** receive a membership row from NW-02's new code path.

I verified this two ways. The seed inserts `workspace`, `contract` and three
`savings_opportunity` rows and **nothing else** — no `workspace_user`, no
`workspace_membership`. And a repo-wide grep for
`workspace_membership|workspace_user` across every `*.sql`/`*.yml`/`*.yaml`
returns **exactly one file**: `identity-workspace.sql`, the migration that

Result: promote w14 to `demo` as-is and the demo user signs in,
`GET /api/workspaces` returns `[]`, and the picker offers "create a workspace" —
on the stakeholder-facing environment. The same applies to every workspace
already created on `dev`.

This is mine, and it is **mandatory regardless of how the table rules on
OQ-w14-002 or on a "claim this workspace" product path**, because the fixture
tenant has no interactive creator to claim it.

## 3. Ordering constraints for the decomposition (`depends_on` hints)

Three mechanical hazards drive this section, all of which cost e13 real work:

- **`check_single_writer.py` refuses a slice whose same-phase tasks claim one
  file, creation included** (`wave-close-e13.md:82`, verbatim). It runs as a
  start hook — a violation kills the run, it does not warn. The script is on
  disk at `.helix/scripts/check_single_writer.py`.
- **The union-merge defect** that shipped a broken build in e13 phase 3 was two
  tasks writing one C# file. "Union is now limited to prose; code goes to
  `conflict-fixer`, then abort" (`:63-66`) — so a same-file collision now
  *fails the wave* instead of corrupting it.
- **`depends_on` is now load-bearing, not advisory.** The process sets
  `require_delivery: true` and `task_failure_markers: ["HALTED:"]`
  (`:73-74`), so a task that halts is *recorded as failed and blocks its
  dependents* — where in e13 it was silently "finished". Good change; it means
  a wrong dependency edge now stops the wave rather than producing a lie.
