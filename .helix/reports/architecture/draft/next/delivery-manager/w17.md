## NW-73 — bulk whole-tenant reprocess console

ADR-016 clause 31 (`:770-784`) already fixed the shape and scheduled it here.
This lane does not re-derive it; it resolves the three things clause 31 left
**owed** and adds the two constraints clause 31 could not have known.

### D1 — the RBAC change, priced exactly

Verified on `d3d2d24`. Every `azurerm_role_assignment` in `infra/`:
`acr.acr_pull`, `foundry.workload_ai_services_user` / `_openai_user` /
`operator`, `keyvault.workload_secrets_user` / `deployer_secrets_officer` /
`ci_secrets_user`, `servicebus.workload_servicebus_sender` (`:71-73`) /
`_receiver` (`:89-91`). **The CI principal holds exactly one**:
`keyvault.ci_secrets_user` (`modules/keyvault/main.tf:66-68`). `modules/servicebus`
takes no CI input at all — `variables.tf` has four variables and no
`ci_deploy_principal_id`. The intake (§2) and clause 27 are both confirmed.

**The change is four files, not one**: `modules/servicebus/variables.tf` (new
`ci_deploy_principal_id`), `modules/servicebus/main.tf` (a **third** assignment),
and **both** env roots. Both roots already resolve the object id and already pass
it to `modules/keyvault` — `environments/dev/main.tf:223-225,236` and
`environments/demo/main.tf:245-247,258` — so each root gains **one line**, and no
new data source.

**Sender only, never Receiver.** The Worker is the only consumer; a CI principal
with Data Receiver could take messages off the subscription the Worker needs.
Clause 31 says "Send"; this records *why* the symmetric grant is refused.

**Wire both roots in the same change, and make the variable required.** If it is
required and only `dev` is wired, `demo`'s root fails `terraform validate` /
`plan` — and `demo-promote.yml:128-136` calls `infra.yml` with
`target_environment: demo`, so **the promotion path breaks on a dev-only wiring**.
That failure appears one tag later, in the job nobody runs weekly. Required +
both roots keeps `validate` green for both and preserves the dev/demo symmetry
`modules/servicebus/variables.tf:22-28` states as a rule.

### D2 — an argument for security-architect that is stronger than the inclination

OQ-w17-008 asks whether a CI principal may hold a Send right. Beyond clause 31's
recorded *yes*: `backend.yml:251` states that `raffa-sp-<env>` has **Contributor
on the resource group** (the message exists to explain why Contributor is *not*
enough for Key Vault data-plane). Contributor is control-plane, so it cannot
send — but it **can** call `az servicebus namespace authorization-rule keys list`.
So the SAS-key shortcut clause 30 forbids is not merely tempting, it is
**mechanically available today**. An explicit, topic-scoped, auditable
`Azure Service Bus Data Sender` is therefore *narrower* than the capability the
principal already carries ambiently, and it makes the forbidden path the
anomalous one. Granting it **reduces** the surface; refusing it does not.

### D3 — where the console runs, and the alternative that is refused

**On the GitHub runner, `dotnet run`** — not as a Container Apps Job.

- `backend.yml:66-74` runs `dotnet restore/build/test` on **`Raffa.slnx`**, so a
  new console project registered there is built and tested **with no `backend.yml`
  edit**. (`Raffa.slnx` is XML; `AuthenticationSeamAbsenceTests.cs:92` confirms the
  `.slnx` name is load-bearing. A `*.sln` glob finds nothing — intake §2's
  mechanical note.)
- `backend.yml:130-144` builds exactly two Dockerfiles (Api, Worker). A console is
  **not** containerised, **not** pushed to ACR, **not** a Container App. Zero
  deploy-path change.
- **Refused alternative — a Container Apps Job.** It would need *no new role*
  (the workload identity already holds Send, `servicebus/main.tf:71-73`), which is
  its one genuine attraction. It is still refused: it costs a new Terraform
  resource, a third image, a third deploy path, and it leaves a permanently
  triggerable mutation surface in Azure. One topic-scoped role on a principal that
  only exists inside CI is the smaller standing surface. Recorded so W18 does not
  re-open it as "the cheaper option".

### D4 — the console workflow is bound by a CI gate clause 31 does not name

**`AuthenticationSeamAbsenceTests` scans `.github/workflows/**`** —
`AuthenticationSeamAbsenceTests.cs:62-68` (`backend/src`, `web/src`, `infra`,
`.github/workflows`) — and it runs inside `backend.yml`'s **`dotnet test`**, the
required check on `main`. **My file set is inside a backend test.** A red `main`
is no `dev` deploy (ADR-014 w15 clause 3), so a careless workflow line kills the
wave's deploy, not just its own job.

What the scanner flags (`AuthenticationSeamAbsenceSelfTests.cs:113-128`): a key
that **disables authentication**, a path returning a **fixed passcode/token**, and
a **branch keyed on an environment name that skips a credential check**. It does
**not** flag connection strings — `:146` is a Postgres string *with a password*
asserted clean. So:

> **Rule: the console workflow copies `verify-tenant-corpus.yml`'s credential
> idiom verbatim** — `./.github/actions/azure-login` (`:67-72`) → `az keyvault
> secret show` (`:112`) → `scripts/pg_connection_string_env.py` → masked `PG*`
> (`:119-134`). That idiom is **proven green** against this scanner today. Any
> `if [ "$TARGET_ENVIRONMENT" = ... ]` branch that skips a credential step is
> shape 3 and turns `main` red.

### D5 — the two jobs compose; do not duplicate the worklist

`verify-tenant-corpus.yml:147-169` already computes the worklist — `Failed`, or
an `embedding` still starting with `%PDF`. That **is** the console's input set.
**The console must run the same predicate**, not a second one, or "what needs
reprocessing" and "what got reprocessed" drift apart silently. This also makes
A17-S2 self-proving: run verify → console → verify again, and the worklist goes
to 0 with `%PDF` gone (`:171-184`), which is the acceptance sentence already.

Unchanged from clause 31 and restated only as binding: the console calls
`DocumentReprocessService.ReprocessAsync`; it **never** replicates
`RequeueClassificationJobAsync`'s reuse-and-reset (`:161-173`), because the
`ClaimedAt = null` reset is what makes the Worker's compare-and-swap re-deliver.
The three shortcuts of clause 30 stay refused.

### D6 — the console workflow is `workflow_dispatch` only, and never joins promotion

`demo-promote.yml` calls only `infra.yml`, `backend.yml`, `web.yml` (`:128-158`).
The console is an operator job: `workflow_dispatch` with `target_environment`
(`dev`/`demo` choice) + `tenant_id`, `environment:` set so `demo`'s required
reviewers gate it — exactly `verify-tenant-corpus.yml:17-52`. **It is not added to
`demo-promote.yml`**, whose header (`:43-50`) forbids adding steps that move data.

## Process — the wave's shape, and two residuals that did not execute

### D7 — **the two-PR shape fires this wave.** It did not in w16

ADR-014 w15 clause 5 splits a wave that changes `infra/` into **PR 1
(infrastructure) → PR 2 (the wave)**. w16 explicitly escaped it (zero `infra/`
delta, ADR-014 w16 clause 2). **w17 does not**: D1 is a real four-file `infra/`
change, and §5 confirms it is the wave's only one. So:

1. **PR 1** — the Terraform task **alone**. Merge to `main`.
2. **HCP applies it.** `infra.yml`'s apply job deliberately does not apply
   (`:114-135`: "Apply not allowed for workspaces with a VCS connection") — HCP's
   VCS run does. **CI green is not the role existing.**
3. **PR 2** — the rest of the wave.

**A17-S2 cannot pass before step 2.** The console will authenticate and then fail
to send. That is an *operator sequencing* fact, not a task: record it in
`reports/audit/w17-hitl.md` and in the acceptance doc, or the first run reads as
a broken console. This is the same class of trap as ADR-016 clause 33 — and note
that clause 33's own pending apply (PR #118) may **still** be outstanding, so the
w17 gate confirms **two** applies, not one.

### D8 — `w16.hitl-ok` is missing. Third occurrence, and the remedy stops being a one-off

Verified: `reports/plan/gates/` holds `e01…e13`, `readiness-gaps`, `w14`, `w15`
— **no `w16`**. `check_slice_prereqs.py` requires `<previous>.hitl-ok`, and

document carries it by construction instead of the next intake rediscovering it.

### D9 — my own w16 clause 3 did not execute, and it was unenforceable as written

ADR-014 w16 clause 3 ruled: the close record is `wave-close-<w>.md`, written
after the merge. **On disk: `reports/execution/` holds `wave-close-e13.md`,
`wave-close-r0-a.md`, `wave-close.md` — there is no `wave-close-w16.md`**, and
`wave-close.md:1-3` is still the w15 file stamped `2026-09-14T02:53:30Z` listing
delivered tasks as undelivered. w16 merged (PR #129, `d3d2d24`) and the record was
never written. The w17 intake needed a banner to neutralise it (§1) — **exactly
the cost clause 3 existed to remove**.

**Root cause, stated honestly against my own clause**: that file is written by the
**execution engine**, not by an agent or a wave task — its shape
(`wave-close.md:1-8`: generated header, `Product repo`, `Origin`, per-task
delivery table) is engine output. **A council rule cannot rename an engine
artefact**, so clause 3 bound nobody. Renaming it is a process/engine change and
belongs in its own PR, never mixed into a wave PR.

**Enforceable replacement (this is what ADR-014 w17 should say):** the engine's
generic `wave-close.md` is a **fan-out delivery report, not the wave record**; it
is never cited as current and its staleness is expected, not a defect to banner.
**The wave record is `docs/waves/<w>-acceptance.md`** (product tree, written by
final integration — it exists for w14/w15/w16) plus `reports/audit/<w>-hitl.md`.
That binds *readers*, which the process can actually enforce.

## Ordering constraints for the decomposition (`depends_on` hints)

Intake §5's ten constraints stand. Mine add to them:

1. **The Terraform task is alone and is PR 1** (D7). Nothing in the wave
   `depends_on` it at build time; **A17-S2 depends on its *apply*.**
2. **NW-73 console+workflow is one task** — sole claimant of
   `.github/workflows/**` (§5 c10) *and* of the new console project. It
   `depends_on` nothing in the wave; do not chain it behind a web phase.
3. **`web/src/api/client.ts` (§5 c7): NW-72 and NW-63 must not share a phase.**
   Resolved below by putting NW-72 in P2 and NW-63's viewer in P4.
4. **`documents-contracts.sql` (§5 c9): NW-71's migration and NW-63's must not
   share a phase.** P2 and P3 below.
5. **`contract360ViewModel.ts` (§5 c3) has three writers — NW-62, NW-65, NW-66.**
   NW-62 in P3; **NW-65 + NW-66 as one task** in P4.
6. **New collision, in no constraint list: NW-66's viewer deep-link vs NW-63's
   viewer web task.** NW-66 adds an anchor in `contract360/`
   (`WhyClauses.tsx`/`ClauseHighlight.tsx`), which is where NW-63's clause→page
   navigation also lands. **Either the deep-link belongs to the NW-65+66 task and
   NW-63 exposes only the route, or they are phase-separated.** Unresolved in §5.
7. **`FactTable.tsx` is claimed by no task** (ux-ui-designer's lane names it as
   `getConfidenceTag`'s sixth consumer; §5 c1 lists five). **It needs an owner
   before fan-out** or NW-65's gate ships on part of screen 5.
8. **Final integration alone in the last phase.**

**Recommended skeleton — a hint, not a ruling** (≤ 5 phases, ≤ 20 tasks; **≈ 15**,
which leaves headroom if NW-63 splits into two under OQ-w17-001):

- **P1** — **NW-73 Terraform (alone → PR 1)** · NW-20 backend · NW-22 backend ·
  NW-26 renderer seam
- **P2** — **NW-72 full-stack** (sole writer of `raffa-api.v1.json` *and*
  `client.ts` this phase) · **NW-73 console + workflow** · NW-71 server rule +
  migration
- **P3** — **contract-B** (NW-71's decision + NW-26/63 preview/evidence) ·
  NW-71 web (sole writer of `semantics.ts`) · NW-62 web (sole writer of
  `contract360ViewModel.ts`) · NW-63 backend (geometry/page anchors, sole writer
  of `documents-contracts.sql` this phase)
- **P4** — NW-63 viewer web (sole writer of `client.ts` this phase) · NW-64 ·
  **NW-65 + NW-66 combined** (sole writer of `contract360ViewModel.ts`)
- **P5** — final integration, alone

Two contract tasks, not five (§5 c6): **contract-A folds into NW-72's P2 task**
and contract-B is P3. Every phase has at most one writer of the contract file, of
`client.ts`, of `semantics.ts`, of `contract360ViewModel.ts` and of
`documents-contracts.sql`. NW-71 web (P3) precedes NW-64/65/66 (P4), satisfying
§5 c1 by phase rather than by hope.
