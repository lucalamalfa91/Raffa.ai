## 1. W15-01 — the wave base

### Decision

**The wave base is `helix/w15` with `origin/main` merged into it, by the
operator, at HITL, before `register_wave.py` and before fan-out.** This is not a
new rule — ADR-014's w14 footer clause 1 already fixes it ("a wave base is
produced by **merging** `origin/main` into the process branch at HITL, never by
branching afresh"; `ADR-014:118-124`). W15-01 produces **no fan-out task**, for
the same reason W14-01 produced none (clause 5, `ADR-014:164-167`): its
enforcement *is* the gate.

### 1.2 `integration` has diverged from `origin/integration`

**FACT** (loose refs): local `integration` is `8ed3af1a`; `origin/integration`
is `271c3ae1`. They are **not the same commit**, and neither is a descendant of
the other by inspection of the refs alone.

This matters because ADR-014 w14 clause 2 makes `integration` the wave's single
merge path (`ADR-014:126-132`) and the wave's task branches merge into it. A
wave that starts on a diverged `integration` either resurrects an old wave's
commits into its PR or loses its own. e13 recorded the same class of hazard —
"Never touch `integration` or the clone's HEAD while a wave runs"
(`wave-close-e13.md:84-86`).

**Decision: `integration` is re-created from the wave base at the gate**, not
merged into. It is a wave-scoped branch with no protection of its own
(`ADR-014:129-131`), so re-creating it is free and reconciling it is not.
Operator prerequisite 5 below.

### 1.3 What the intake's W15-A1 is missing, and why it matters this wave

The intake's W15-A1 checks that the base "contains `origin/main` @ `3c89d35`",
that two files resolve, and that "one `dev` deploy is green". Two halves are
absent, and both bit the **last** wave:

**(a) The merge must leave a zero product-tree delta.** Five files differ
between the two sides (`w15-requirements.md:1044-1047`): two exist only on
`origin/main` (`docs/waves/w14-acceptance.md`, `web/e2e/invite.spec.ts`) and

`helix/w15` side **silently reverts w14's README sweep and its e2e work** — and
no build, no test and no deploy would notice. So the check is mechanical and
exact:

> after the merge, `git diff --stat origin/main..HEAD -- backend web infra
> .github docs scripts` is **empty**.

Nothing weaker proves it. "The two files resolve" proves two of five.

**(b) `main` must be green *at the base commit*, on the test job, not only on a
deploy.** `w15-requirements.md:70-72` records that w14 closed as HITL issue #94

`dev`… is green", which is *not* the same check: the deploy job is
`needs: build` (`backend.yml:83`), so a red test job means the deploy never runs
at all — the operator sees "no deploy", not "red tests", and the honest reading
of a missing deploy is ambiguous. State it directly: **a red `main` means no
`dev` deploy, which means no wave.** The fixture class is known and must be read
as a fixture gap, never as a flake to re-run.

## 2. The apply barrier, with three applies instead of zero

This section is the wave's delivery core. Everything in §4 follows from it.

### 2.1 What is actually true about an apply

`infra.yml` never applies (`:106-109`). HCP owns apply, from its own VCS
connection, for **both** workspaces, both watching `infra/`
(`../infra/README.md:8-12`, `:45-50`). Three consequences the decomposer must be
told in those words:

- **An apply is triggered by a push to `main`, not by a task, not by a phase,
  and not by `integration`.** No fan-out task can wait for it, observe it, or
  retry it. ADR-016 w14 clause 3 already says this ("An infra change's effect is
  **not observable by the wave that wrote it**, so it is a HITL gate, never a
  `depends_on`", `ADR-016:133-135`). w15 is the wave that has to live with it
  three times over.
- **The GHA deploy and the HCP apply race.** The same push to `main` starts
  `backend.yml`'s deploy (`:16-23`, `:86`) *and* the `raffa-dev` HCP run. Which
  finishes first is not ordered by anything in this repo. So for a window of
  minutes after the wave merges, **`dev` runs the new image against the old
  environment variables**.
- **`demo` gets w15's infrastructure at merge time, before `demo` has the
  code.** This is the finding w14's zero-delta rule hid. `raffa-demo` is
  VCS-connected on the same prefix, so merging the wave's Terraform to `main`
  moves the *stakeholder-facing* environment's infrastructure while it is still
  serving w14's images. (`../infra/README.md:88-91` notes `raffa-demo` does not
  auto-plan *from GHA*; that is about `infra.yml` planning `dev` only on that
  path, and says nothing about HCP's own VCS run. The operator confirms the
  `raffa-demo` run state either way — that confirmation is the gate.)

### 2.2 The rule I want recorded: required keys vs optional keys

A wave that ships Terraform **and** the code that reads it can only be safe one
of two ways. Name both, forbid the third:

| | **Optional key** (fail-soft) | **Required key** (fail-closed) | ~~Fail-open~~ |
|---|---|---|---|
| Absent value means | a documented, shipped fallback | the feature refuses, loudly | the old, weaker path still works |
| Merge-time race | harmless | a bounded, honest outage on `dev` | **silent regression** |
| w15 items | NW-27 (queue), NW-68 (mail), NW-67 (guest) | **NW-05 only** | — |

**Every new configuration key in w15 ships with a documented absent-value
behaviour, and no key may fail open.** Concretely:

- **NW-27** — no Service Bus connection configured → the existing in-process
  path (`Raffa.Worker/Queue/InMemoryQueueConsumer.cs`) stays the binding, so a
  pre-apply `dev` still functions. The repo already uses exactly this shape for
  Foundry (`AiGateway:Endpoint` empty → fixture gateway, `../infra/README.md:194-196`).
- **NW-68** — `Invitations__Mail__Enabled` false or `Invitations__AcceptUrlBase`
  empty → `mailDelivered: false` and the copyable-link path, which is **today's
  shipped behaviour** (`NullInvitationMailer`, `w15-requirements.md:480-489`).
  Nothing regresses; the pane simply keeps taking the path it takes now.
- **NW-67** — the Graph permission missing → a **named** provisioning failure on
  the pane plus an audit row, never a "ready" link. That is not a fallback I am
  inventing: it is **A15-7, an acceptance criterion of the item**
  (`w15-requirements.md:461-462`). The absent-key behaviour and the acceptance
  test are the same thing.
- **NW-05** — no authority/audience configured → the API **must not** fall back
  to `X-User-Id` / `X-Tenant-Id`. That fallback is the vulnerability the item
  exists to remove (`w15-requirements.md:654-657`: a forged header is full
  impersonation). Fail **closed**: the authenticated routes answer `401` until
  the env vars arrive. Fail **closed**, not **crash**-closed — the API must
  still boot, because a boot-crash loop on `dev` costs the wave its only
  acceptance environment and looks identical to a bad image. When the HCP run
  reaches `CURRENT`, Terraform's env-var change rolls a **new revision**, and
  the environment self-heals without a human.

That last row is the only place where a w15 merge degrades `dev`, it is bounded
by one HCP run, it is honest, and it is strictly better than the alternative.
I want it written down before someone "helpfully" adds a header fallback.

### 2.3 `demo` stays inert between the apply and the promotion

Because of §2.1's third bullet, the per-environment flag is no longer a
nicety — it is what stops a stakeholder environment from acquiring live
behaviour it has no code for. ADR-005's w14 footer already proposed
`var.invitation_mail_enabled` mirroring `ai_gateway_wired`
(`w15-requirements.md:513-516`); I am making the pattern **mandatory for every
w15 key whose feature can act on the world**, and stating who flips it:

| Key / resource | `dev` root | `demo` root at merge | Flipped when |
|---|---|---|---|
| `Invitations__Mail__*` (ACS) | `true` | **`false`** | the one-line PR that precedes the `demo-v*` tag |
| Graph guest provisioning | `true` | **`false`** | same PR (if the council gates it per environment — OQ-w15-005) |
| Service Bus wiring | `true` | `true` (inert — the w14 image ignores unknown env vars) | n/a |
| Worker `min_replicas` / scale rule | see §4.1 | **unchanged until promotion** (cost) | same PR |
| `AzureAd__*` (NW-05) | `true` | `true` (inert — the w14 image reads no such key) | n/a |

**The flag flip is itself a Terraform change and therefore a second merge to
`main`.** That is not a new invention either: `ai_gateway_wired` is flipped

carries the live-Foundry backend**" (`../infra/README.md:278-279`). So the w15
promotion runbook gains one step before the tag (§7 step 4), and it is a

### 2.4 Pre-empting the shortcuts (three this time)

Recorded because each will be proposed, and each is drift:

## 3. Per-item delivery decisions

### 3.1 NW-27 — the worker that never wakes up

**The blocker no other seat is looking at.** `ca-raffa-<env>-worker` has
`min_replicas = 0`, `max_replicas = 1`
(`../infra/modules/containerapps/main.tf:231-232`), **no ingress**
(`outputs.tf:20-22`) and **no scale rule of any kind** — a grep of all of
`../infra` for `scale_rule|azure_queue_scale_rule|custom_scale_rule|http_scale_rule`
returns nothing. A container app with zero minimum replicas, no ingress and no
scaler has **no activation source**. Today that is harmless: the worker's hosted
service only drains an in-process `ConcurrentQueue` and dispatches nothing
(`w15-requirements.md:191-194`). The moment NW-27 makes it the thing that
processes every uploaded document, it is the wave's single point of failure, and
it fails **silently** — uploads return 201 in under 2 s and never progress.

Two shapes, and the choice is cloud-architect's; the **consequence** is mine:

| | `min_replicas = 1` | Service Bus KEDA scale rule, `min_replicas = 0` |
|---|---|---|
| Cost | one always-on Consumption replica per environment, ×2 | scales from zero on queue depth |
| Locked rule | tension with "cheapest SKUs, nothing idle-expensive" | aligned |
| New Terraform | one integer | `custom_scale_rule` (type `azure-servicebus`) + its trigger authentication |
| A15-2 (restart mid-batch, nothing lost) | provable | provable, **plus** it proves the scaler |

**My requirement, whichever is chosen:** the scaling decision is part of the
**same** Terraform task and the same apply as the queue wiring (§4.1) — a wave
that wires a queue and forgets the scaler ships an acceptance failure that looks
like a code bug. And **A15-2 must be walked on deployed `dev` with the worker
scaled as it will run in `demo`**, not with a locally pinned replica.

**Ordering.** Terraform (queue env vars on both hosts + scaling) is phase 1 and
is inert without the code; the producer/consumer code follows in phase 2; the
endpoint's return-shape change follows the consumer. See §4.

**Workflow decisions.** `backend.yml` needs **no change**: the worker image is
already built (`:138-144`) and deployed (`:203-208`) in the same job as the API,
API first. The new/changed migration extends an **existing** module's checked-in
script, so **neither** ADR-021 array is touched (`:276-286`, `:308-318`) — the
arrays only change when a *new module* appears, and NW-27 adds none. If
software-architect's claim/retry model turns out to need a new .NET module with
its own `Migrations/Scripts/*.sql`, **both** arrays change and `backend.yml`
joins the planned set — tell me at the table, because it moves §5's assertion
from "zero files" to "one file".

**ADR action**: `amend ADR-016` (the w15 footer, §9) for the apply ordering and
the demo-inertness rule. The queue contract itself is ADR-002/ADR-005, not mine.

### 3.2 NW-68 — the first per-environment API key

This is the exact case ADR-016's w14 footer clause 2 was written to pre-empt
(`ADR-016:108-118`): a new API environment variable can arrive **only** through
Terraform plus an HCP apply. Three decisions from this seat:

1. **`Invitations__AcceptUrlBase` is composed inside `modules/containerapps`
   from `var.spa_host_name`, which already exists there** (`variables.tf:59`,
   consumed at `main.tf:189` for CORS). No new variable in either environment
   root, no new value for a human to type, and structurally impossible to point
   `demo` at `dev`'s host — each root already wires its own
   `module.staticwebapp.default_host_name` (`w15-requirements.md:502-506`).
   **Never hardcode a hostname in either root**: that is precisely the
   cross-environment leak `ADR-016:79-80` exists to prevent, and it would ship a
   `dev` link into a `demo` invitation email — an email you cannot recall.
2. **The `acs-connection` secret follows the existing Key Vault → container-app
   handle pattern** (`postgres-connection`/`pg-cs`, `storage-connection`/`st-cs`
   — `w15-requirements.md:492-495`). No secret value is ever promoted
   (`ADR-016:79-80`; `demo-promote.yml:43-50`), so each environment's secret is
   created by its own apply. Nothing new for me to decide; recorded so nobody
   proposes copying it.
3. **`mailDelivered` must stay a server fact.** The delivery-side reason: it is
   what makes the promotion checkable. If the pane can infer "sent", then a
   `demo` whose flag is still `false` will *claim* delivery, and the promotion
   check has nothing to assert against. (Software-architect owns the contract;
   this is my reason for wanting it.)

**Workflow decisions**: none. No workflow mentions `Invitations__` or ACS today
(zero hits), and none needs to — the key arrives by Terraform.

### 3.3 NW-67 — the Graph permission, and the risk it puts on the *other two* applies

Delivery-side, NW-67's danger is not the permission. It is that
**one errored HCP run takes down the wave's other two features.**

Both environments' roots are a single Terraform state each. If the app-role
assignment that grants the workload identity its Graph permission fails to
apply — most plausibly because **the Terraform/HCP identity itself lacks the
directory permission to grant a Graph permission** — then the `raffa-dev` run
errors, and **Service Bus wiring (NW-27) and ACS (NW-68) do not apply either**.
Three features, one failure. And it is a realistic failure: the current design
*deliberately avoids* Graph and records why — "web.yml reads it over ARM so the
deploy job does not need Microsoft Graph (ADR-015)"
(`w15-requirements.md:394-396`), with no Graph `required_resource_access`
declared anywhere.

**My requirement: the Graph grant must not be able to error the shared run.**
Two ways, cloud-architect + security-architect choose (OQ-w15-005):

- **(i) Terraform manages the app-role assignment** → the tenant admin grants
  the HCP/Terraform identity `AppRoleAssignment.ReadWrite.All` (+
  `Application.ReadWrite.All`) **out of band, before the first apply**. That
  becomes operator prerequisite 2 in §1, verified at the gate, not discovered by
  a red run. This is a standing, powerful directory permission held by CI-side
  automation — security-architect's call, and they may well refuse it.
- **(ii) The grant is an out-of-Terraform one-time operator step**, documented
  in `infra/README.md` and in the acceptance doc, with a
  `guest_provisioning_enabled` flag defaulting `false` so the code path stays
  dark until the operator confirms. **This is my default recommendation**: it
  keeps a directory write out of the blast radius of the apply that also carries
  the queue and the mail transport, it needs no new standing permission on CI,
  and A15-7 (named error when provisioning is unavailable) already *requires*
  the code to behave correctly in exactly that state — so option (ii) costs
  nothing that A15-7 does not already buy.

**ADR-015 is the ADR that has to say so**, and it is jointly mine
(`ADR-015:5`). Its body's only statement about runtime identity is
`:82-83` — "The AI Gateway / backend / worker authenticate to Foundry, Key
Vault, and other services using the same managed-identity model at runtime; **CI
identity is only for deploy-time control-plane actions**." NW-67 is the first
runtime call to a *directory* API, so the footer records: the Graph permission
belongs to the **per-environment workload identity**, the **CI deploy identity
gains nothing** (no new federated credential, no new subject claim, no new
secret), and whichever of (i)/(ii) the table picks, the grant is verified at the
gate before the wave's Terraform merges.

**Workflow decisions**: none. No workflow mentions Graph or `User.Invite` (zero
hits), and none should.

### 3.4 NW-05 — the change that can lock everyone out of `dev`

Four delivery decisions:

1. **No scope rename, no new scope.** `web.yml:204-205` hardcodes
   `api://raffa-<env>-api/Raffa.Read` and `…/Raffa.Write` into the SPA's
   `config.json`, and the SPA already requests them
   (`w15-requirements.md:670-674`). NW-05 reuses them **verbatim**. Two
   consequences: the SPA needs **no new config key** for its token acquisition
   (it is code-only on the web side), and §5's "zero workflow files" assertion
   holds. If security-architect needs a different audience or an extra scope,
   `web.yml` joins the planned set and §5 becomes "exactly one file" — that is a
   table decision, not a task-time discovery.
2. **The authority/audience pair is the classic runtime-only failure.**
   `../infra/modules/identity/outputs.tf:7-17` exposes `api_identifier_uri` "as
   audience", but v2 access tokens carry `aud` = the **client id**
   (`identity/main.tf:75`, `requested_access_token_version = 2`). Wiring the
   identifier URI where the client id belongs applies cleanly, deploys cleanly,
   and then **every request 401s in the browser**. The acceptance step must be an
   interactive sign-in returning **200 on a real tenant-scoped route**, not only
   the 401-on-forged-header half of A15-8. Cloud-architect wires it;
   security-architect fixes the validation parameters; I am fixing **what proves
   it**.
3. **Fail closed, not crash closed** (§2.2) — so the merge-time race degrades
   `dev` to 401 for one HCP run instead of a boot-crash loop.
4. **Rollback rehearsal before the promotion.** NW-05 is the one w15 change
   whose failure mode is "nobody can use `dev`". The recovery is the ADR-014
   path — revert PR to `main`, `dev` redeploys the previous image; the env vars
   stay (harmless, unread). The acceptance doc states it as a named step so the
   operator does not have to invent it under pressure. And **A15-8 passes on
   deployed `dev` before the `demo-v*` tag is cut** — never the reverse
   (`ADR-016:169-170`).

**Workflow decisions**: none, under decision 1.

### 3.5 NW-58r — where N3b actually runs (joint with security-architect)

**Decision: no Playwright runner in w15, and no passcode seam in the product,
and no `dev` mail-catcher.** Three refusals, three separate reasons:

- **A `dev` mail-catcher is a fourth apply.** A new resource, a new Terraform

## 4. Ordering constraints for the decomposition (`depends_on` hints)

Three mechanical hazards, unchanged since w14 and still load-bearing:
`check_single_writer.py` **fails** a slice whose same-phase tasks claim one file,
creation included (`wave-close-e13.md:82`); a same-file collision aborts rather
than corrupts (`:63-66`); and `depends_on` is enforced —
`require_delivery: true`, `task_failure_markers: ["HALTED:"]` (`:73-74`), so a
halted task blocks its dependents.

### 4.1 The hard constraint: **one Terraform task for the whole wave**

Four of this wave's items write Terraform, and **they overlap on the same
files**:

| Item | `modules/containerapps/main.tf` | `environments/{dev,demo}/main.tf` | other |
|---|---|---|---|
| NW-27 | queue env vars on **both** hosts + worker scaling | pass `module.servicebus` outputs | — |
| NW-68 | `acs-cs` secret handle + `Invitations__*` env | wire `module.communication` | **new** `modules/communication`, `modules/keyvault` |
| NW-67 | — | — | `modules/identity` (Graph) |
| NW-05 | `AzureAd__*` on the API | pass `module.identity` outputs | — |

Three items claim `modules/containerapps/main.tf` and three claim both
environment roots. Under `check_single_writer.py` that is either **one task**, or
**four serialized phases** — and four phases of Terraform in a five-phase wave
leaves one phase for ten items. So:

> **One task, phase 1, owns every file under `infra/`.** It is the wave's single
> Terraform writer and produces the wave's single HCP apply per environment.

This is mechanically mandatory and it is also *better*: one apply, one operator
confirmation, one blast radius — which is exactly why §3.3's "the Graph grant
must not be able to error the shared run" matters so much. Cloud-architect owns
the content of that task and may legitimately say it is too large; if they split
it, **the split must be by phase, not within a phase**, and the phase budget
has to come from somewhere. I would rather narrow a feature than split the
Terraform.

  This is the mechanical reason, and it is now three reasons.
- **"The HCP run is `CURRENT`" does not prove the messaging path works.** §7 step
  3's confirmation is extended: confirm the **subscription** exists, the **worker
  carries a scale rule (or `min_replicas = 1`)**, and the **role assignments** are
  present. A Terraform apply that creates none of them still succeeds.

The auth choice is cloud-architect's and it is **not** "one integer" as §3.1's
table implied: with no connection string available, a KEDA `azure-servicebus`
scale rule needs **identity-based trigger authentication**, whereas every other
secret in this repo (`pg-cs`, `st-cs`) arrives as a Key Vault connection-string
handle. Two different Terraform designs — pick one **inside the single task**.

### 12.4 Confirmed — and the API is not affected
