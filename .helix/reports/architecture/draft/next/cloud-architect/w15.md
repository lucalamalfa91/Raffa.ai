## 1. NW-27 — `POST /api/documents` returns once the file is stored

### 1.1 What exists and what is actually missing

`module "servicebus"` is instantiated in both roots (`environments/dev/main.tf:98-104`,
`demo/main.tf:119-125`) and creates exactly two resources
(`modules/servicebus/main.tf`, 23 lines): `azurerm_servicebus_namespace "this"`
(`:11-18`, `sbns-raffa-${var.environment}`, **`sku = "Standard"`**) and
`azurerm_servicebus_topic "extraction_events"` (`:20-23`, `extraction-events`).
There is **no queue, no subscription and no authorization rule** anywhere under
`infra/`. Its three outputs (`id`, `name`, `fqdn`) have **one consumer in the
whole repo**: `environments/dev/outputs.tf:77`. `modules/containerapps/variables.tf`
declares no Service Bus input at all (its 16 variables are enumerated in the
scan; none names a queue).

Two facts make this worse than "not wired yet", and both are mine to fix:

1. **A topic with zero subscriptions discards every message it receives.** Not
   "queues them for later" — Service Bus drops a message published to a topic
   that no subscription matches. A producer shipped against today's Terraform
   would report success and lose every document. A15-2 ("restart API and Worker
   mid-batch → no document lost") cannot pass on the resource set that exists.
2. **The worker app can never start.** `modules/containerapps/main.tf:231-232`
   sets the worker `min_replicas = 0` / `max_replicas = 1`, the app has **no
   ingress** (`outputs.tf:20-23` says so), and a case-insensitive grep of the
   whole module for `scale_rule|azapi` returns **zero matches**. A Container App
   with no ingress, no scale rule and `min_replicas = 0` has nothing that can
   ever raise its replica count. Today that is invisible because
   `QueueConsumerHostedService` does nothing; the moment it must drain a durable
   queue, "the worker is deployed" stops being the same statement as "the worker
   runs".

A third, quieter one:

3. **The worker cannot read the blob it is being asked to OCR.**
   `modules/containerapps/main.tf:44-54` gives the **API** two secret handles
   (`pg-cs`, `st-cs`); the worker (`:224-228`) has **only `pg-cs`**, and its env
   list (`:240-306`) carries five `ConnectionStrings__*` — `DocumentsContracts`,
   `Audit`, `Renewals`, `Savings`, `Quotes` — and **no `ConnectionStrings__Storage`**.
   `ConnectionStrings__Storage` is read at `backend/src/Raffa.Api/Program.cs:66`
   with a **fail-fast `?? throw`** (`:67-69`); `Raffa.Worker/Program.cs` does not
   read it at all today. NW-27 moves the file read to the worker, so the worker
   acquires that same fail-fast guard, against a container app where the variable
   does not exist. See the hard ordering in §5.

### 1.2 Decision — resources and SKUs

**SKU: unchanged.** Service Bus stays **Standard** (ADR-005 `:43`). No tier
change, no second queue product (ADR-005 `:76` forbids one).

**Add one subscription, keep the topic.** `azurerm_servicebus_subscription`
`document-processing` on the existing `extraction-events` topic:

| Setting | Value | Why |
|---|---|---|
| `max_delivery_count` | `5` | Bounded retry. On the 5th abandon the message dead-letters; the handler's last attempt is what must flip the row to `Failed` so A15-2's "every row terminal" holds. Coupled to software-architect's handler contract. |
| `dead_lettering_on_message_expiration` | `true` | An expired message lands somewhere inspectable instead of vanishing. |
| `default_message_ttl` | `P1D` | A document not processed within a day is a defect, not a backlog. |
| `lock_duration` | `PT5M` | **The Service Bus maximum.** OCR + classify + extract + embed against live Foundry routinely exceeds it, so the handler must renew — see the coupled key in §1.3. |
| sessions | **not enabled** | See §1.5. |

A **topic + subscription**, not a queue, because: it is purely additive (no
existing resource is destroyed or replaced), it preserves the accepted ADR-005
`:43` rationale for paying for Standard ("Standard gives topics + sessions;
Basic omits topics" — a Standard namespace carrying only a queue would make that
line false), and a second consumer later costs one subscription rather than a
redesign. KEDA's `azure-servicebus` scaler supports `topicName` +
`subscriptionName` natively, so nothing is given up.

**Data-plane auth: RBAC, no secret.** Two `azurerm_role_assignment` resources in
`modules/servicebus`, scoped to the **topic** (`azurerm_servicebus_topic.extraction_events.id`),
principal = `var.workload_principal_id`:

- `Azure Service Bus Data Sender`
- `Azure Service Bus Data Receiver`

This is the path `modules/foundry` already takes for `Cognitive Services User` /
`Cognitive Services OpenAI User` (ADR-008 amendment `:107-110`), and it means
**NW-27 adds no Key Vault secret at all**. `AZURE_CLIENT_ID` is already published
to **both** apps (`containerapps/main.tf:145-148` API, `:277-280` worker), so
`DefaultAzureCredential` resolves to the workload identity with no code
ceremony.

Both roles go on one principal because there **is** one principal: a single
`azurerm_user_assigned_identity "workload"` per environment
(`modules/identity/main.tf:36-46`) is attached to both apps (`containerapps/main.tf:34-37`,
`:214-217`). Splitting it into an api-identity and a worker-identity so that
Sender and Receiver separate is a genuine least-privilege improvement and is
**security-architect's call, explicitly out of this wave's budget** — it would
touch every module that takes `workload_principal_id` (keyvault, acr, foundry,
servicebus) and re-key four role assignments per environment.

New `modules/servicebus` inputs/outputs: variable `workload_principal_id`
(string, required); outputs `topic_name`, `subscription_name`, `topic_id`.

### 1.3 Decision — worker scaling, and the option that is rejected

`modules/containerapps`, worker app:

- `min_replicas = 0` — **unchanged**, and deliberately so (ADR-005 `:54`).
- `max_replicas = var.worker_max_replicas`, **default `3`** (from the hardcoded `1`).
- a new `custom_scale_rule` on the worker:

```
name             = "servicebus-extraction"
custom_rule_type = "azure-servicebus"
metadata = {
  namespace        = <servicebus namespace name>
  topicName        = "extraction-events"
  subscriptionName = "document-processing"
  messageCount     = "5"
}
```

API app: `max_replicas = var.api_max_replicas`, **default `3`** (from `1`),
`min_replicas = 0` unchanged. Not cosmetic: `web/src/routes/documents/uploadPipeline.ts:22`
runs three uploads in flight, A15-1 drops **fifteen** files and asserts
`POST /api/documents` **p95 < 2 s**, and one 0.25-vCPU replica serialising
fifteen multi-MB blob writes is the most likely way that p95 target fails after
the pipeline itself is fixed. Scale-out on a consumption profile is paid only
while it is used.

**Rejected: `min_replicas = 1` on the worker.** It is the obvious way to make a
queue consumer run, and it is forbidden here. One always-on replica is
0.25 vCPU × 2.592 M s ≈ **648,000 vCPU-s** and 0.5 GiB × 2.592 M s ≈
**1,296,000 GiB-s** per month; net of the monthly consumption free grant
(180,000 vCPU-s / 360,000 GiB-s per subscription, which the API already draws
on) that is of the order of **$14 per environment per month, ~$28 across both** —
a **new fixed monthly line**, which is exactly what the locked rule forbids and
what ADR-005 `:54-56` was written to prevent. Recorded so it is not re-proposed
as a "simplification" when the scale rule proves fiddly.

**Prerequisite, proved and not asserted** — the same discipline ADR-005's w14
footer `:211-219` imposed on the ACS resource names. How a Container Apps
`custom_scale_rule` authenticates its queue-length probe must be **read from the
pinned `azurerm ~> 4.0` schema** (`environments/*/main.tf` `required_providers`)
and proved by `terraform validate` in the `infra.yml` PR job (`:73-75`). No
identifier may be copied out of this draft. In preference order:

1. **Workload-identity auth on the scale rule** — if the pinned provider exposes
   it, take it: zero secrets, and it reuses the identity already attached.
2. **Fallback, bounded and named**: `azurerm_servicebus_namespace_authorization_rule`
   `keda-listen` with `listen = true, send = false, manage = false` → its
   `primary_connection_string` → Key Vault secret **`servicebus-listen-connection`**
   → container-app secret handle **`sb-listen-cs`** on the worker, referenced
   **only** by `custom_scale_rule.authentication`, **never** by an `env {}`
   block and never by application code. The application data plane stays
   secret-free either way; only KEDA's probe would hold a listen-only credential.
   A `manage = true` or namespace-wide send rule is rejected outright.
3. If neither is expressible, the item does **not** fall back to `min_replicas = 1`
   — it comes back to this seat.

### 1.4 Config keys, per environment, named exactly

On **both** apps unless stated. All literal (non-secret) except where noted.

| Key | Value / source | API | Worker | Binding shape required |
|---|---|---|---|---|
| `ConnectionStrings__Storage` | `secret_name = "st-cs"` (**new handle on the worker**; `var.storage_connection_secret_id` is already passed to the module from both roots — `dev/main.tf:119`, `demo/main.tf:143` — so **no new module variable and no root change**) | already present `:137-140` | **NEW** | fail-fast, mirroring `Raffa.Api/Program.cs:66-69` |
| `ServiceBus__FullyQualifiedNamespace` | `module.servicebus.fqdn` → `sbns-raffa-dev.servicebus.windows.net` / `sbns-raffa-demo.servicebus.windows.net` | **NEW** | **NEW** | **optional**, like `ConnectionStrings:Market` (`Program.cs:122-128`) |

| `ServiceBus__SubscriptionName` | `document-processing` | — | **NEW** | optional |
| `ServiceBus__MaxAutoLockRenewalMinutes` | `30` | — | **NEW** | optional |

Two rules on that table, both load-bearing:

- **`ServiceBus__*` must bind optionally, never with `?? throw`.** That is what
  makes the infra→code ordering *soft* for these four keys: if the code lands
  first, the absent value degrades to today's in-process `ConcurrentQueue`
  instead of crash-looping the app. It is the difference between a wave that can
  interleave and one that cannot.
- **`ServiceBus__MaxAutoLockRenewalMinutes` is not optional-by-taste.** The
  subscription's `lock_duration` is capped at the Service Bus maximum `PT5M`
  (§1.2); an extraction that outruns five minutes without automatic lock renewal
  is redelivered **while still running**, which is a duplicate-processing bug the
  idempotency model then has to absorb. The infra knob and the SDK knob are one
  decision; naming only one of them is how this goes wrong.

**New `modules/containerapps` variables**: `servicebus_namespace_name`,
`servicebus_fqdn`, `servicebus_topic_name`, `servicebus_subscription_name`,
`worker_max_replicas` (default `3`), `api_max_replicas` (default `3`).
**New root wiring** in both `environments/*/main.tf`: pass
`module.servicebus.*` into `module "containerapps"` — the edge that
§1.1 showed does not exist today — and `workload_principal_id =
module.identity.workload_principal_id` into `module "servicebus"`.

**Not added to the worker, and named so nobody adds them "for symmetry"**:
`ConnectionStrings__IdentityWorkspace`, `ConnectionStrings__Chat`,
`ConnectionStrings__Suppliers`, `ConnectionStrings__Market`. The worker's NW-27
scope is `document` + `extraction_job` + audit rows, and it already holds
`DocumentsContracts` and `Audit`. If software-architect's handler needs a sixth
context, that is a new line on this table, argued on its own merits.

**Foundry needs nothing.** OCR, classify, extract and embed moving to the worker
adds **no role assignment and no deployment**: the worker already carries
`AiGateway__Endpoint`, `AiGateway__ProjectName`,
`AiGateway__DocumentIntelligenceConnection` (`containerapps/main.tf:282-295`)
and the same `dynamic "env"` over `var.ai_gateway_model_env` (`:299-306`) that
the API has, and the shared workload identity already holds
`Cognitive Services User` + `Cognitive Services OpenAI User` on `aisvc-raffa`
(ADR-008 `:107-110`). Recorded because "the AI calls moved, so the AI RBAC must
move" is a plausible and wrong inference.

### 1.5 Two corrections to the record

- **`demo/main.tf:117-118` claims "Service Bus Standard tier (topics + *sessions*
  for extraction events)".** No session setting exists on the topic and no
  subscription exists to carry one. w15's subscription **does not enable
  sessions**, and that is a decision, not an omission: a session-enabled
  subscription serialises every message of a session onto one ordered consumer
  and would silently cap the worker at one effective replica, defeating
  `worker_max_replicas` and slowing a 15-file batch to strictly serial. Recorded
  so the comment is not treated as a requirement to restore.
- **`environments/demo` has no Service Bus output** while `dev` does
  (`dev/outputs.tf:75-78`). Adding the mirror output is free and makes the two
  roots comparable at plan time; it is a nicety, not a requirement.

### 1.6 Cost

**$0.00 new fixed cost.** The Service Bus Standard namespace is **already
provisioned and already billed in both environments** — order $0.0135/hour ≈
**$9.86 per namespace per month**, including 12.5 M operations. w15 adds a
subscription (**free**) and a message volume that at pilot scale (tens of
documents per day → low thousands of operations per month) does not approach the
included allowance. **Wiring a resource the project already pays for is the
cheapest capability in this wave.**

Compute is a **relocation, not an addition**: the same OCR / classify / extract /
embed vCPU-seconds move off the API replica and onto the worker replica. With
`min_replicas = 0` on both and a queue scaler, the worker bills only while a
message is in flight. Net compute delta ≈ **$0.00**; the `api_max_replicas` and
`worker_max_replicas` headroom is paid only when concurrency is actually used.
Retail rates to be confirmed by the infra cost researcher:
**Azure Service Bus Standard**, **Azure Container Apps consumption
(vCPU-second / GiB-second, with the monthly free grant)**.

## 2. NW-68 — Raffa sends the invitation email (ACS Email)

The design is **accepted and not re-opened**: ADR-005's w14 footer `:154-219`
fixes ACS Email + Azure Managed Domain, the four resource types, the rejected
alternatives (custom domain, SendGrid, Graph `sendMail`), one resource per
environment never shared, the `communication → keyvault → containerapps` wiring,
the `acs-connection` → `acs-cs` path, the four config keys, the
`invitation_mail_enabled` flag, and `data_location = "Europe"` (ADR-006 w14
footer `:82`). This wave **applies** it. My lane's job is the exact shape, the
exact keys, and the ordering.

### 2.1 New module `infra/modules/communication`

| Resource | Name | SKU / tier | Region |
|---|---|---|---|
| `azurerm_communication_service` | `acs-raffa-<env>` | **No SKU** — metered per message, no idle charge | **global type**: no `location`, `data_location = "Europe"` |
| `azurerm_email_communication_service` | `acsemail-raffa-<env>` | **No SKU** | `data_location = "Europe"` |
| `azurerm_email_communication_service_domain` | Azure Managed Domain | `domain_management = "AzureManaged"` | — |
| `azurerm_communication_service_email_domain_association` | — | no charge | — |

`tags = { project = "raffa", env = var.environment }` on every taggable resource,
as every other module does (`servicebus/main.tf:4-9`, `keyvault/main.tf:8-13`).

Per ADR-005 `:216-217`, `Invitations__Mail__SenderAddress` comes **from the

### 2.2 Key Vault and the secret handle

`modules/keyvault` gains, following `postgres_connection` / `storage_connection`

### 2.3 Config keys, per environment, named exactly

**API app only.** The worker neither issues nor sends invitations; ADR-005
`:198-200` already forbids giving it these "for symmetry", and this draft
repeats it because §1.4 adds worker keys in the same wave and the two lists will
be read together.

| Key | Kind | `dev` | `demo` |
|---|---|---|---|
| `Invitations__Mail__Enabled` | literal | `"true"` | `"false"` |
| `Invitations__Mail__SenderAddress` | literal, from `module.communication.sender_address` | `DoNotReply@<managed domain>` | same shape, **its own** domain |
| `Invitations__Mail__ConnectionString` | **`secret_name = "acs-cs"`** | Key Vault `acs-connection` | its own vault's `acs-connection` |
| `Invitations__AcceptUrlBase` | literal, `"https://${var.spa_host_name}"` | dev SWA host | demo SWA host |

`var.spa_host_name` is **already** a `modules/containerapps` variable
(`variables.tf:59`) wired from `module.staticwebapp.default_host_name`
(`dev/main.tf:120`, `demo/main.tf:144`) and consumed today only by the ingress
CORS block (`main.tf:188-193`). `Invitations__AcceptUrlBase` is therefore a
**reuse of an existing wire**, not a new discovery — exactly as the intake says.

Three exactness rules the decomposer must carry:

1. **`Invitations__AcceptUrlBase` has no trailing slash.** `https://<host>`, and
   the API composes `{base}/invite/accept#{token}`. The `#` is not a style
   choice: ADR-025 Rule C9 and ADR-005's second w14 footer `:240-266` make the
   token a **fragment**, never a query string, because `staticwebapp.config.json`
   rewrites every non-asset path to `/index.html` and the Static Web Apps
   platform logs the accept path — a query-string token would land a live
   single-use invitation token in platform logs on infrastructure this seat owns.
2. **All four bind optionally**, like `ConnectionStrings:Market`
   (`Program.cs:122-128`), **never** like the nine fail-fast guards — ADR-005
   `:202-204`. That keeps the infra→code ordering soft for NW-68.
3. `Invitations__Mail__Enabled` is a **product** switch, not a provisioning gate.
   Unlike `ai_gateway_wired` — where publishing an endpoint the account could not
   back produced HTTP 500 on every upload (`foundry/outputs.tf:6-12`, commit
   `a750746`) — publishing a *working* mail connection string behind
   `Enabled = false` is harmless. So the resources, the secret and all four keys
   land in **one** apply per environment, with the flag `true` on `dev` and
   `false` on `demo`. **No two-phase apply is needed for mail**, and requiring one
   would buy a second operator-confirmed HCP gate for nothing.

**New root variables**: `invitation_mail_enabled` (bool) — `dev` default
**`true`**, `demo` default **`false`**, mirroring the `ai_gateway_wired`
lifecycle already proven on this tenant (`dev/variables.tf:23-27` = `true`,
`demo/variables.tf:20-24` = `false`). `demo` flips at its own promotion, after
acceptance on deployed `dev` (ADR-016 clause 7: acceptance on `dev` precedes the
tag, never the reverse).

**Root ordering note**: `module "keyvault"` sits *after* `module "containerapps"`
in file order in both roots (dev `:177` vs `:106`; demo `:205` vs `:130`) and
this already works, because Terraform orders by reference and not by position.
`module "communication"` may be placed anywhere; the dependency chain
`communication → keyvault → containerapps` is acyclic and is created by the
`acs_connection_string` / `acs_connection_secret_versionless_id` references.

### 2.4 Why the connection string, and not managed identity

ACS Email can be called with a `TokenCredential`. This seat is **not re-opening**
the decided design, and records the reason so the question is not re-raised at
the table: the Key Vault → `acs-cs` → env-var path is already proven twice in
this module (`pg-cs`, `st-cs`), it satisfies the lock verbatim ("secrets in Key
Vault, never in source or bundle"), and swapping it for Entra data-plane auth
mid-wave would add a role assignment on a resource type nobody here has probed
plus an SDK auth path with no coverage — against a wave that already carries
three applies' worth of Terraform. If a later wave wants it, it is an ADR-011
amendment and one role assignment, not a redesign.

### 2.5 Cost

**Fixed: $0.00 per environment.** All four resource types are **SKU-less** and
metered per message with **no idle charge**, so no third fixed monthly line joins
Service Bus Standard and ACR Basic (ADR-005 `:56`). Variable, to be confirmed at
retail by the infra cost researcher: order **$0.00025 per email** plus
**$0.00012 per MB** (**Azure Communication Services Email**). At pilot volume —
tens of invitations — this **rounds to under $0.01 per environment per month**.

**Deliverability caveat, unchanged from ADR-005 `:217-219`**: an Azure Managed
Domain sends from `…azurecomm.net`, which corporate filters treat harshly.
`demo` is stakeholder-facing, so a custom sender domain is a separate DNS-gated
task (not this wave), and until it lands **the copyable link stays the guaranteed
path** — which is precisely why NW-69's `false` branch must remain reachable and
why A15-6 exists.

### 2.6 ADR action

**amend ADR-005** — the four ACS rows move from *decided* to *applied*; the
resource names, the secret and handle names, the four keys, the per-env flag
values, the one-apply ruling of §2.3(3), and the $0.00 fixed-cost confirmation.
**amend ADR-007** — `infra/modules/communication/` joins the layout block
(`:36-61`), which today lists nine modules and will list ten.
ADR-006: **none** — the w14 footer `:82` already ruled the ACS case; this wave
applies it as written and re-opens nothing.
ADR-011 (security-architect's file): `acs-connection` is the **third** Key Vault

**no new role assignment**; and "no mail body, no accept token and no recipient
address in a log line or an audit row" is theirs to state.

## 3. NW-67 — Entra B2B guest provisioning (Microsoft Graph)

one Graph mention in Terraform is a **negative**: `modules/identity/main.tf:41-42`

Graph (ADR-015)". `modules/identity` declares exactly one
`required_resource_access` block (`:131-143`, the public client's `Raffa.Read` /
`Raffa.Write` scopes on the API app) and **none for Graph**.

What *does* exist and is the right caller: one
`azurerm_user_assigned_identity "workload"` per environment
(`identity/main.tf:36-46`, `id-raffa-<env>-workload`), already attached to both
container apps, already published as `AZURE_CLIENT_ID` to both, with
`workload_principal_id` already exported (`identity/outputs.tf:39-42`). The
`azuread` provider is already required (`~> 3.0`) and already configured
(`provider "azuread"` at `dev/main.tf:30`, `demo/main.tf:46`) — so **no new
provider**.

### 3.2 Decision

`modules/identity` gains:

```
data  "azuread_service_principal" "msgraph"   # client_id 00000003-0000-0000-c000-000000000000
resource "azuread_app_role_assignment" "workload_guest_inviter" {
  count               = var.guest_provisioning_enabled ? 1 : 0
  app_role_id         = <msgraph app_role_ids["User.Invite.All"]>
  principal_object_id = azurerm_user_assigned_identity.workload.principal_id
  resource_object_id  = <msgraph object_id>
}
```

plus variable `guest_provisioning_enabled` (bool, default `false`) and outputs
`graph_app_role_assignment_id` (or `null`) and `tenant_id` (from the
`data "azuread_client_config" "current"` already at `:16`).

**No secret, no app registration, no client credential.** The managed identity
authenticates to Graph with `DefaultAzureCredential` for
`https://graph.microsoft.com/.default`, using the `AZURE_CLIENT_ID` already on
both apps. ADR-011 gains **nothing** for NW-67 — which is what the intake's
OQ-w15-005 assumption predicted, and it holds.

**Least privilege**: `User.Invite.All` is the documented app-only permission for
`POST /invitations`; there is no narrower *application permission*. The narrower
alternative is the **Guest Inviter** directory role
(`azuread_directory_role_assignment`), which confers invitation rights without a
tenant-wide Graph app role. It is a one-resource swap in my Terraform and it
changes the blast radius, so it is **security-architect's ruling, not mine** — I
will implement whichever they name.

### 3.3 The operator act, stated correctly

The intake's assumption says "admin consent granted once by the tenant admin as
an operator step". That is right in substance and wrong in mechanism, and the
difference decides whether the apply succeeds:

**For a managed identity there is no separate "Grant admin consent" click.** The
`azuread_app_role_assignment` **is** the consent — creating it is the grant. What
is genuinely a one-time operator act is upstream of it: the **identity that runs
the HCP apply** (the credentials on the `raffa-dev` / `raffa-demo` workspaces,
which is also this `azuread` provider's identity) must be able to write app role
assignments. It cannot today. It needs one of:

- Graph **`AppRoleAssignment.ReadWrite.All`** + **`Application.Read.All`**
  application permissions, **or**
- the Entra directory role **Privileged Role Administrator** (or
  **Cloud Application Administrator**),

granted once by a tenant admin, **before** the apply. `identity/main.tf:41-42`'s
"the deploy job does not need Microsoft Graph (ADR-015)" stops being true at that
moment, which is why this is an **ADR-015 amendment** and not a runbook line.

**Escape hatch, which is why this can ride the same apply as everything else.**
`guest_provisioning_enabled` defaults to `false`. If the operator's Graph
permission is not in place when the apply runs, the flag stays `false`, the
`count = 0` resource is not created, **the whole w15 apply still succeeds**, and
NW-67 lands on a later one-line flip. Without that gate, one missing directory
permission would block the Service Bus wiring and the mail transport too. If the
operator declines to widen the apply identity **permanently**, the documented
fallback is a Global Administrator performing the single assignment out-of-band
(`az rest` POST to the Graph service principal's `appRoleAssignedTo`), the
Terraform resource staying at `count = 0`, and the deviation recorded with an
`import` path for a later wave. Named so the wave is never blocked on a
permission grant, only degraded.

### 3.4 Config keys, per environment, named exactly

The Graph call sits in the invite transaction. Whether that transaction runs in
the API or is handed to the worker is **software-architect's** call; **the role
assignment does not change either way**, because one workload identity serves
both apps. The keys follow the handler:

| Key | Kind | `dev` | `demo` | App |
|---|---|---|---|---|
| `Invitations__GuestProvisioning__Enabled` | literal, `tostring(var.guest_provisioning_enabled)` | `"true"` | `"false"` | API (or worker, if the call moves) |
| `Invitations__GuestProvisioning__TenantId` | literal, `module.identity.tenant_id` | tenant GUID | **same GUID** | same |

Both bind optionally. **No secret, no endpoint key** — the Graph endpoint is a
constant, not configuration.

**New root variables**: `guest_provisioning_enabled` (bool) — `dev` default
**`true`**, `demo` default **`false`**.

### 3.5 OQ-w15-005, second half — a `dev`-provisioned guest and `demo`

This is my half of the open question; the acceptability ruling is
security-architect's.

**The fact**: both environments authenticate against the **same single Entra
tenant** — `sign_in_audience = "AzureADMyOrg"` on both registrations
(`identity/main.tf:63`, `:118`), and the live `oidcAuthority` recorded for both
SWAs carries the same GUID (`tests/test_check_demo_swa_config.py:32`, `:42`).
"dev/demo isolation is by distinct registration, not by separate Entra tenants"
is written in the module itself (`:41-46` region). A B2B guest is a **tenant
object**. There is **no Azure control that makes a guest environment-scoped**,
and pretending otherwise would be the kind of claim that fails at acceptance.

**Why it is nonetheless contained**: what *is* environment-scoped is workspace
membership — per-env PostgreSQL, per-env RLS (ADR-009), never shared (locked). A
guest provisioned from `dev` who signs in to `demo`'s SPA gets ADR-026's
two-phase discovery over **`demo`'s** database, finds **zero workspaces**, and
receives ADR-025's **404** for any tenant id they name. **Blast radius: can
authenticate to `demo`, can see nothing.** That is the same posture any employee
of the tenant already has, and it is not new surface created by NW-67.

**Why the capability is still per-environment**: the Graph role assignment is on
the **per-environment** workload identity and is gated by
`guest_provisioning_enabled`. With `dev = true` / `demo = false`, only `dev` can
write to the directory in w15. The directory is shared; **the right to write to
it is not**.

**No directory deletion path is built** (OQ-w15-007's assumption): removing a
workspace membership never deletes or blocks the Entra guest. From this seat that
is also the only safe answer — a guest may belong to other workspaces, and a
product that deletes tenant directory objects on a per-workspace action is one
bug away from removing a real employee.

No new Azure resource, no SKU, no meter. For the cost researcher: **Microsoft
Entra External ID (MAU-based, free allowance)**, confirm the allowance still

### 4.2 Config keys, per environment, named exactly

**API app only. Four literal, non-secret values** — ADR-010 `:78-80` requires
exactly this ("injected per environment at runtime from a config value that is
not a secret"). The `__` convention matches `AiGateway__*` / `ConnectionStrings__*`
already in the module.

| Key | Source | `dev` | `demo` |
|---|---|---|---|
| `AzureAd__Authority` | `module.identity.issuer` | `https://login.microsoftonline.com/<tenant>/v2.0` | **same** (one tenant) |
| `AzureAd__TenantId` | `module.identity.tenant_id` (new output) | tenant GUID | **same** |
| `AzureAd__ClientId` | `module.identity.api_client_id` | **dev's** API client id | **demo's** API client id |

`ClientId` **and** `Audience` are both published on purpose: with
`requested_access_token_version = 2` the `aud` claim is the **client id**, while
the SPA requests scopes against the **identifier URI**. Publishing both lets the
API accept either as a valid audience and removes an entire class of
"token acquired, then 401" failure. The exact binding prefix (`AzureAd__` vs
`Authentication__`) is **software-architect's** to confirm — the *values*, their
Terraform sources and the per-environment split are mine, and they do not change
under either prefix.

**New `modules/containerapps` variables**: `entra_authority`, `entra_tenant_id`,
`entra_api_client_id`, `entra_api_audience`. **New root wiring**: four lines in
each `environments/*/main.tf` `module "containerapps"` block, from
`module.identity`. **New `modules/identity` output**: `tenant_id`.

**Worker: none of the four.** The worker has no ingress
(`containerapps/outputs.tf:20-23` states it) and validates no token. Not "for
symmetry".

### 4.3 No `Authentication__Enabled` switch — and why that is the safer answer

NW-05 is, as the intake says, "the change that can lock everyone out of `dev`",
so a runtime kill-switch is the obvious ask. **This seat does not propose one**:

- A key that turns authentication off is a security control in the hands of
  whoever can run an apply, and flipping it back requires **another
  operator-confirmed HCP apply** — the slowest rollback in the repo.
- The rollback that already exists is faster and costs nothing:
  `backend.yml:198-201` deploys the API with `az containerapp update --image`,
  so reverting to the previous image SHA is one command and **no HCP apply**.
- All four keys are inert to any image that does not read them, so **the apply
  can land days before the code with literally zero observable effect** — which
  is the property that makes the hard ordering in §5 cheap rather than risky.

**Recorded rename risk** (ADR-010 w14 clause 4, not re-decided here):
`.github/workflows/web.yml:201-205` hardcodes
`api://raffa-<env>-api/Raffa.Read|Write`, which must stay equal to
`module.identity.api_identifier_uri` plus the `oauth2_permission_scope` `value`s
(`identity/main.tf:79`, `:90`). They match on this tree. A mismatch fails at
**token acquisition in the browser, after CI is green** — it is not a deploy
error. Delivery-manager's surface; named here because the Terraform side of the
equality is mine.

## 5. Apply path and order constraints for the decomposition

### 5.1 One phase, one apply per environment

All four items are `infra/**` changes. `infra.yml`'s path filter (`:11-13`,
`:16-18`) runs `validate` (fmt + `terraform validate`, `:55-75`) and `plan`
against the real HCP workspace (`:80-102`) on the PR. On merge, the `apply` job
(`:114-135`) **does not invoke Terraform**: both workspaces are VCS-connected, so
**HCP itself runs plan/apply from the repo and a human confirms the run in the
HCP UI** (`https://app.terraform.io/app/raffa-platform/workspaces/raffa-dev/runs`).

| Environment | Apply path | Gate |
|---|---|---|
| `dev` | merge the infra PR to `main` → `infra.yml` → confirm the VCS-triggered run in HCP until it reads `CURRENT` | ADR-016, operator-confirmed |
| `demo` | tag `demo-v5` (ADR-016 clause 7 made `demo-v4` w14's) → `demo` GitHub Environment approval → `demo-promote.yml` calls `infra.yml` with `target_environment: demo` → confirm the run on `raffa-demo` | ADR-016 required reviewers + operator-confirmed |

**One Terraform PR, one apply per environment — not three.** The requirements
§5 already say the three applies "should be one phase, not three"; this seat
goes one step further and makes it **one apply**, because three PRs against one
VCS-connected workspace serialise anyway and each buys a separate human
confirmation. The bundling is only safe because **every risky resource is behind
a `count` flag** (`guest_provisioning_enabled`) or is inert when unread (all
`ServiceBus__*`, `Invitations__*`, `AzureAd__*` keys) — so a single missing
directory permission degrades NW-67 instead of blocking NW-27 and NW-68.

**Two shortcuts are named drift and must not be taken** (ADR-016 clause 2,
restated because this is the first wave where the temptation is real): adding
`--set-env-vars` to `backend.yml`, and folding any of these eleven keys into the
single `dynamic "env"` block over `var.ai_gateway_model_env`
(`containerapps/main.tf:168-175`, `:299-306`, bound by ADR-004 to per-role model
ids). The next HCP apply reverts anything CI sets behind Terraform's back.

**One manual, non-Terraform operator act in the whole wave**: granting the HCP
apply identity the Graph write permission (§3.3), **before** the apply. Nothing
else in this lane requires a portal.

### 8.2 A missing worker env var fails **silently**; `backend.yml` stays green

§5.2 calls the worker's `ConnectionStrings__Storage` ordering HARD because the
worker crash-loops. Re-reading `backend.yml` end to end makes it worse, and the
difference decides whether anyone finds out:

- the only per-app loop (`:155-191`, `for APP in api worker`) is a **pre-deploy**
  ACR registry attach, not a health check;
- deployment is `az containerapp update --image` for each app (`:196-208`), which
  returns when ARM **accepts** the revision, not when it is healthy;
- the next step is the ADR-021 schema apply (`:210-218`), whose own comment
  asserts "after both Container Apps above are already **running** the new image"
  — a claim **nothing in the job verifies**;
- there is no `az containerapp revision show` / `runningState` / `healthState`
  assertion anywhere in the workflow.

**A worker that cannot start therefore produces a green `backend.yml` run.** The
API keeps serving, uploads keep returning 201, and documents simply never leave
`Uploaded` — a queue backing up behind a dead consumer looks exactly like slow
processing. Detection today rests entirely on someone opening `dev`.

Consequence for the decomposition: the NW-27 worker task should assert **one**
post-deploy revision state for `ca-raffa-<env>-worker`. That is a `backend.yml`

### 8.3 The worker already proves the optional-binding pattern — and its limit

`Raffa.Worker/Program.cs` fail-fasts on exactly three connection strings —
`DocumentsContracts` (`:16-19`), `Audit` (`:24-27`), `Renewals` (`:31-34`) — and
binds `Market` (`:44`) with **no** `?? throw` and a documented rationale.

So §1.4's "`ServiceBus__*` must bind optionally" is **not a convention I am
introducing**: it is the shape this host already uses for a dependency whose
absence must degrade rather than crash. That is the strongest possible answer to
"why should the queue keys be optional when nine others are not".

The same finding fixes the boundary: **`ConnectionStrings__Storage` must be
fail-fast, not Market-shaped.** A worker that silently cannot read blobs marks
every document `Failed` — a config gap wearing the costume of a product defect,
across a whole environment, with A15-2 ("every row terminal") passing while the
rows are all terminal-`Failed`. Optional binding is correct for the four queue
keys and **wrong** for storage; §5.2's HARD row survives on its merits.

### 8.4 The worker's env list is not evidence of what the worker reads

`Program.cs:49` calls `AddWorkerHost(documentsContracts, audit, renewals)` —
**three** connection strings. The container app publishes **five**:

`Raffa.Worker.Program` does not read ConnectionStrings:Savings/Quotes yet").

Harmless in itself, and **not** a w15 task. Recorded because it defeats the
obvious review shortcut: counting five `ConnectionStrings__*` on the worker and
concluding storage must be among them. It is not, and §8.2 means the mistake is
not caught by CI either.

### 8.5 `module.servicebus.fqdn` is plan-time known — no `(known after apply)`
