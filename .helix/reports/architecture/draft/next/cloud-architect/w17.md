## NW-73 — bulk whole-tenant reprocess console

### CA-1 — one topic-scoped role assignment; no new resource, no SKU move

- `modules/servicebus/variables.tf` — new `variable "ci_publisher_principal_id"`
  (string), description carrying the isolation rule verbatim from the sibling it
  copies (`variables.tf:22-30`): each root passes **its own** principal.
- `modules/servicebus/main.tf` — new `resource "azurerm_role_assignment"
  "ci_servicebus_sender"`: `scope = azurerm_servicebus_topic.extraction_events.id`,
  `role_definition_name = "Azure Service Bus Data Sender"`, `principal_id =
  var.ci_publisher_principal_id`, `skip_service_principal_aad_check = true`, **and
  the same `lifecycle { ignore_changes = [skip_service_principal_aad_check,
  principal_type, name] }`** both existing grants carry (`main.tf:80-86`, `:95-101`).
  ARM rejects in-place updates to a role assignment; omitting that block makes a
  *later, unrelated* apply fail.
- `environments/dev/main.tf:106-116` — one line: `ci_publisher_principal_id =
  data.azuread_service_principal.ci_deploy.object_id`. **The data source already
  exists** (`:223-225`) and already feeds `module.keyvault.ci_deploy_principal_id`
  (`:236`). `environments/demo/main.tf` — same line, own data source at `:245-246`.

**Never** (each already refused by a rule on disk): `Data Owner`, any `Manage`
right, a namespace-wide scope, `Data Receiver` for the CI principal, an
`azurerm_servicebus_namespace_authorization_rule`, or a SAS key in Key Vault —
`modules/servicebus/main.tf:64-70` is the module's own "identity + RBAC, never a
shared key" rule.

**Why this principal.** ADR-015 keeps SPs out of band, so a purpose-made publisher
SP costs an out-of-band creation, a federated credential, a GitHub Environment
variable and a **third** literal client id in source — and both roots warn a stale
literal fails the plan outright (`dev/main.tf:218-222`); w16 ruled "no new identity,
credential, app role or secret". Terraform resolves exactly two principals today:
`module.identity.workload_principal_id` (**already holds Send**, `:71-87`) and
`data.azuread_service_principal.ci_deploy`. The choice is "grant the CI SP" vs
"run under the workload identity" (shape C) — there is no third.

**Blast radius, for security (OQ-w17-008 is theirs).** Whoever can trigger the
workflow inherits publish rights on `extraction-events`. Bounded by topic scope,
Send only (no read, purge or DLQ peek), ids-only messages (`main.tf:66-70`,
ADR-009), and `ReprocessAsync` writing the `document.reprocessed` audit row. **Not**
bounded by tenant — a Send right is tenant-blind; tenant scoping is the console's
argument and the audit row, never the role.

## NW-26 — real page render (conditional seat)

### CA-2 — no new Azure resource; the shared container pair is the live risk

- **Nothing on the AI account renders a page.** Document Intelligence is attached as
  a connection (`containerapps/main.tf:174`, `:448`) and ADR-017 records
  `prebuilt-layout` as available-but-not-called; it returns **geometry, not pixels**.
  If a renderer calls an Azure API for the raster it must **name the operation** and
  I re-price. Absent that: **no model deployment, no capacity, no Foundry change, no
  new resource.**
- **The rasteriser is in-process and Worker-only.** `RenderAndStoreAsync` has one
  caller — `DocumentProcessingPipeline.cs:239`; the API only `LoadAsync`es the stored
  PNG (`DocumentsEndpointExtensions.cs:468`). Memory pressure lands on
  `ca-raffa-<env>-worker`, not the API, while the pipeline stays Worker-hosted.
- **The number that matters: both apps run at 0.25 vCPU / 0.5 GiB per replica**
  (`containerapps/variables.tf:70-80`, consumed `main.tf:76-77`, `:345-346`). An A4
  page at 150 DPI is ≈ 1240×1754×4 B ≈ **8.4 MB per bitmap** before the native
  allocator's buffers, and the Worker runs **`ServiceBus__MaxConcurrentCalls = 4`**
  per replica (`:424-427`) — four concurrent rasterisations plus EF Core, the OCR
  client and embedding buffers inside 0.5 GiB.
- **Binding task constraint (mine, because it decides whether the SKU moves): render
  and store page-by-page, disposing each bitmap, never materialising a document's
  pages as a set.** Multi-page then multiplies the work, not the peak.
- **If a bump is needed it is a *pair* and it is *shared*.** Consumption accepts only
  a fixed ladder (0.25↔0.5Gi, 0.5↔1.0Gi, 0.75↔1.5Gi, 1.0↔2.0Gi) — **memory cannot be
  raised alone** — and the module exposes **one** `cpu`/`memory` pair consumed by
  *both* apps, so bumping the Worker bumps the API. Options: (i) raise the shared
  pair to 0.5 / 1.0Gi; (ii) split into `worker_cpu` / `worker_memory` and leave the
  API at the floor. **Recommended: (ii)** — proportional to the evidence.
- **Cost.** Consumption bills per **vCPU-second** and **GiB-second** above the monthly
  free grant, and `min_replicas = 0` on both apps (`:66`, `:335`) means an idle
  environment bills nothing; a bump changes only the *rate* while a replica is alive.
  **Expected €0.00/month.** Retail lookups owed **only if the bump is taken**:
  Container Apps Consumption vCPU-second and GiB-second, North Europe.
- **Storage.** Per-page previews turn `documents/{id}/preview/page-1.png`
  (`DocumentStoragePath.cs:20-21`) into N objects per document. On **StorageV2 /
  Standard / LRS**, 1,000 docs × 20 pages × ~200 KB ≈ **4 GB ≈ €0.07/month** plus
  cents of transactions — immaterial. One rule: reprocessing must **overwrite by
  deterministic path**, never accumulate a suffix, or the `documents` container grows
  unbounded and nothing deletes it today.

### CA-3 — the Worker **image**, not the SKU, is where a native rasteriser lands

Verified this lane; no seat has priced it. The image is built by ACR Tasks
server-side (`backend.yml:130-144`, `az acr build --file
backend/src/Raffa.Worker/Dockerfile`) — no local Docker daemon, no runner-side
dependency to add.

- **Base is `mcr.microsoft.com/dotnet/runtime:10.0`** (`Raffa.Worker/Dockerfile:29`),
  chosen over `aspnet` **deliberately** (`:25-28`: Generic Host, no Kestrel, "smaller,
  cheaper runtime image"). It is a **slim Debian** layer: **no `libfontconfig1`,
  `libfreetype6`, `libjpeg`, `libpng`, no `libgdiplus`**. A managed-only rasteriser
  needs none; a SkiaSharp/PDFium-class native one does. **This decides whether the
  Dockerfile changes at all**, and it is invisible from the SKU table.
- **`USER $APP_UID` at `:34` is a hard ordering constraint**: any `apt-get`/native
  layer must sit **above** that line or the build fails permission-denied. A task
  appending to the end of the Dockerfile breaks CI.
- **Layer placement is a cost decision**: the native `RUN` must sit **above** `COPY
  --from=build /app .` (`:31`) so it lands in a layer **shared by every `:<sha>`
  tag**. Below it, the libs are re-stored on every commit.
- **ACR is `Basic`** (`modules/acr/main.tf:24`). Native deps add tens of MB **once**
  to the shared layer, so **NW-26 does not move the ACR SKU** — the image ruling is
  €0.00 too.
- **Pre-existing, and I will not smuggle it into this wave**: the module has **no
  `retention_policy`** (unsupported on Basic — a Premium feature) and **no workflow
  purges** (zero `acr purge` / `acr repository delete` across `.github/workflows`),
  while `backend.yml:134,142` pushes `raffa-api:<sha>` **and** `raffa-worker:<sha>`
  per commit against Basic's included 10 GB. Growth is slow because tags share base
  layers, but it is unbounded and nothing reclaims it → **OQ-w17-ca-04**.
- **Config keys: zero.** If the renderer needs a knob (DPI, max pages) it belongs in
  `appsettings` as `Preview__*` with a shipped default, **not** a Terraform-managed
  env var — a render default is not environment-specific, and putting it in the
  module would make every change a Terraform apply.

### ADR action and order constraint

- **`none` on ADR-005/006/007/008**, conditional on an in-process renderer and the
  pair staying 0.25 / 0.5Gi.
- **Pre-authorised contingency with a named ceiling**, so no new council round is
  needed if measurement disagrees: **0.5 vCPU / 1.0 GiB, Worker only**, recorded then
  as an ADR-005 amendment + an operator HCP apply.
- If the council opens a **new ADR for the renderer and the preview contract**, I
  **ratify** it rather than write a competing one, on condition it carries the four
  clauses this lane owns: page-by-page render-and-dispose; deterministic overwrite
  path; the three image constraints in CA-3; the pair unchanged with the contingency
  above. ADR-017 is software-architect's.
- **Order: soft, deliberately.** A renderer that *throws* is absorbed —
  `DocumentPreviewService:56-61` turns it into "no preview" and never fails the
  upload. A renderer that *OOMs* kills the replica, the message is redelivered up to
  `max_delivery_count = 8` (`servicebus/main.tf:53-62`), then dead-letters. **NW-26's
  acceptance must include one 20-file batch on `dev` with zero Worker restarts** —
  otherwise the memory question is answered by hope.
- **Image before renderer, inside NW-26**: if a native dependency is chosen the
  Dockerfile layer must land in the **same task** as the renderer — a renderer merged
  against an image without its native deps fails at runtime with `Unable to load
  shared library`, not at build.
