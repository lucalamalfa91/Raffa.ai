## 1. NW-58 — Invites are email + link (the only item that names this seat)

### 1.1 Decision — the transport is Azure Communication Services Email

The raw requirement is "they must go **by email** … the UI must not say 'sent'
unless the mail left". No mail transport exists anywhere in the tree today: the
intake's grep over `backend/src` + `infra` returned zero files, and I confirm
independently that a grep for `azurerm_communication|azurerm_email_communication|
communication_service` over `../infra` returns **zero files**. So this is a
genuinely new Azure resource — ADR-005's "Concrete services and SKUs" table
(`ADR-005:34-48`, plus the 2026-09-09 AI amendment at `:87-103`) lists none.

| Option | Verdict | Why |
|---|---|---|
| **Azure Communication Services Email + Azure Managed Domain** | **chosen** | Pay-per-message, **no fixed monthly line**, no idle cost; first-party; expressible in `azurerm ~> 4.0` (pinned in both roots — `dev/main.tf:11-14`, `demo/main.tf:27-30`); no DNS, no domain ownership, no manual verification step, so it can land inside this wave. |
| ACS Email + **custom domain** | deferred | Needs DNS TXT/SPF/DKIM records on a domain Terraform does not own and a manual verification wait. Cannot complete inside w14. Re-opened as the `demo` deliverability task (§5, OQ-w14-cl-002). |
| SendGrid (Azure Marketplace) | rejected | Third-party SaaS account + a long-lived API key = a new secret and a new vendor for something Azure does natively; no free tier to lean on. Contrary to "cheapest tier, first-party where it exists". |
| Microsoft Graph `sendMail` | rejected | Requires a licensed M365 mailbox (a per-seat cost, not an Azure meter) and the `Mail.Send` **application** permission, which is tenant-wide unless narrowed by an Exchange application access policy — a PowerShell-only, out-of-band step Terraform cannot own. Blast radius is wrong for an invite mail. |
| No transport (copyable link only) | fallback, kept | OQ-w14-002's fallback. Costs nothing, but fails NW-58's own must. Retained as the **`Enabled = false`** state of the chosen design, not as a separate design — see §1.4. |

**One ACS resource per environment**, in that environment's own
`rg-raffa-<env>` (`dev/main.tf:41-49`, `demo/main.tf:55-63`), never shared.
ADR-008's shared `aisvc-raffa` account is the deliberate single exception to
one-of-everything-per-env and it exists for a cost/quota reason (ADR-005's
amendment calls it out in as many words: "the single deliberate exception to
'one of everything per env'", `ADR-005:95`). Mail has **no fixed cost to
amortise**, so sharing would buy nothing and would blur the environment
boundary inside the recipient's inbox (a `demo` invite indistinguishable from a
`dev` invite). Isolation wins, and it matches `demo/main.tf:52-54`'s existing
"never a target of data-plane promotion" reasoning.

|---|---|---|---|

Tags `project` + `env` on every resource, from the same `locals.tags` shape
every other module uses (verified identical in `../infra/modules/keyvault/main.tf:8-13`
and `../infra/modules/containerapps/main.tf:7-12`).

**Provider-schema discipline.** I have no `Bash` and no provider registry in
this lane, so I name the four resource types as **proposed** and do not assert
their attribute spellings. The infra task must read the exact argument and
attribute names (notably the sender-domain's `from_sender_domain` /
`mail_from_sender_domain`) from the pinned `azurerm ~> 4.0` schema, and must
take `Invitations__Mail__SenderAddress` from the **module output**, not from a
hand-composed string in this document. `terraform validate` in the PR job
(§1.7) is what proves the types exist, and it runs before merge at no cost.
Same rule as §6: read the tree, never copy an identifier out of this draft.

**Region.** ACS and the Email service are **global** resource types with a
`data_location` property; they have no regional deployment and therefore
cannot take the ADR-006 `northeurope` pin. `data_location = "Europe"` keeps the
data in the EU. This is the **same shape as a deviation already in force but
never written down**: `../infra/modules/staticwebapp/main.tf:6-9` states in its
own comment that "Microsoft.Web/staticSites is not offered in North Europe …
This module therefore does NOT inherit the env-root North Europe pin
(ADR-006)", and both roots repeat it (`dev/main.tf:64-65`,
`demo/main.tf:75-76`). ADR-006 itself says the opposite at `:55` ("Do not
introduce a second region for either environment") and carries **no footer
recording the exception**. A global-only resource type is not "a second region"
in the sense ADR-006 forbids — but that reading exists only in a module comment
today. §1.10 closes that gap once, for both cases.

### 1.3 Config keys each environment needs (exact strings)

Published on the **API** Container App only. The worker gets **none** of these:
it neither issues nor sends invitations. Do not add them "for symmetry" —
`ConnectionStrings__Savings` / `__Quotes` were added to the worker for exactly
that reason and the module's own comment concedes the worker does not read them
("even though `Raffa.Worker.Program` does not read
ConnectionStrings:Savings/Quotes yet", `../infra/modules/containerapps/main.tf:257-263`).

| Env var (Container App) | .NET config path | Secret? | Source in Terraform |
|---|---|---|---|
| `Invitations__AcceptUrlBase` | `Invitations:AcceptUrlBase` | no | `"https://${var.spa_host_name}/invite/accept"` — **an input the module already receives** (`dev/main.tf:120`, `demo/main.tf:144`) and already uses for ingress CORS (`containerapps/main.tf:188-193`). Zero new module inputs. |
| `Invitations__Mail__Enabled` | `Invitations:Mail:Enabled` | no | `var.invitation_mail_enabled` (two-phase bool, §1.4) |
| `Invitations__Mail__SenderAddress` | `Invitations:Mail:SenderAddress` | no | `module.communication.sender_address` (module output, per §1.2) |
| `Invitations__Mail__ConnectionString` | `Invitations:Mail:ConnectionString` | **yes** | Key Vault secret `acs-connection` → Container App secret `acs-cs` → env var, resolved by the workload identity |
| `Invitations__TokenSigningKey` | `Invitations:TokenSigningKey` | **yes** | Key Vault secret `invitation-signing-key` → Container App secret `inv-key` → env var |

The two-layer naming above is the existing convention, not an invention: Key
Vault secrets are long-form (`postgres-connection`, `storage-connection` —
`keyvault/main.tf:82,93`) and the Container App secret handles are short
(`pg-cs`, `st-cs` — `containerapps/main.tf:45,51`). `acs-connection`/`acs-cs`
and `invitation-signing-key`/`inv-key` follow it exactly.

`Invitations__Mail__Endpoint` is **not** required in w14: the
`Azure.Communication.Email` client is constructed from the connection string
alone. It becomes required only on the Entra-auth path (§1.5), and only then.

**Two facts the other seats must build against:**

1. **The accept URL cannot be derived from the request.** A grep for
   `SpaHostName|WebBaseUrl|PublicWebUrl|AllowedOrigins|BaseUrl|AcceptUrl|Invitation`
   over `../backend/src` returns **zero files** — the API today has no notion of
   the web origin at all. `HttpRequest` gives the Container App FQDN
   (`ca-raffa-<env>-api…azurecontainerapps.io`, `containerapps/main.tf:23`),
   never the SPA host (`swa-raffa-<env>…`, `staticwebapp/main.tf:18`). A link
   built from the request points at the API and is dead.
   `Invitations__AcceptUrlBase` is the only correct source, and it must be
   **read**, not computed.
2. **The deep link already works on Static Web Apps.** An emailed
   `/invite/accept?token=…` opened cold is a client route with no server file.
   `../web/public/staticwebapp.config.json:2-5` rewrites every non-asset path to
   `/index.html` (`exclude` lists only `/config.json`,
   `/staticwebapp.config.json`, `/assets/*` — `/invite/accept` is not among
   them), so **no hosting change is needed** for the client-architect's new
   route. Recording this so no task invents one.

### 1.4 Two-phase wiring — the flag *is* the OQ-w14-002 fallback

`var.invitation_mail_enabled` (bool, **default `false`**) mirrors the
`var.ai_gateway_wired` pattern ratified in the ADR-008 amendment of
2026-09-09.

**Correction to the previous revision of this draft, and to the intake.** That
revision cited `dev/variables.tf:18-27` as a "default `false`" precedent, and
the intake says the same of NW-40 (`w14-requirements.md:620`: "publication is
still gated by `ai_gateway_wired` (default `false`)"). On **this checkout that
is stale for `dev`**:

- `../infra/environments/dev/variables.tf:23-27` — `ai_gateway_wired` default
  is **`true`**.
- `../infra/environments/demo/variables.tf:20-24` — default is **`false`**.

The precedent is therefore **stronger** than claimed, not weaker: the two-phase
flag is not a nice idea awaiting first use, it has been **exercised end to
end** — `dev` went `false` → live probe → `true`, while `demo` still sits at
`false` awaiting its own promotion (`demo/variables.tf:18-19`: "flipped with
the demo promotion that carries the live-Foundry backend"). That is exactly the
per-environment lifecycle I am proposing for mail, already proven on this
tenant. NW-40 is queued for **W18**, so I record the stale line for that
wave's intake and take no action on it here.

- `false` → the API shows the Admin a **copyable accept link** and must **not**
  say "Invitation sent." This is precisely NW-58's must #1 and OQ-w14-002's
  fallback, expressed as one env var instead of a second code path.
- `true` → the mailer sends and the UI may say it sent.

Consequence for the table: **OQ-w14-002 does not have to be answered "all or
nothing"**. The transport lands as infrastructure in w14; whether `dev` and
`demo` actually *send* is a per-environment flag the delivery-manager flips
after a probe. `percorso-pilota-v1.md` §2's "email is not onboarding" and spec
§20's "invite Procurement users" stop being in conflict, because the product
never claims a mail was sent that was not.

### 1.5 Identity — reconciliation needed with security-architect

**My proposal for w14: the ACS connection string as a Key Vault secret**, read
at runtime by this environment's own user-assigned workload identity. Not
because keys are nicer than Entra — because this is the exact path already
proven end to end in this tree: `azurerm_key_vault_secret.postgres_connection`
/ `.storage_connection` (`keyvault/main.tf:81-101`) → versionless sensitive
outputs (`keyvault/outputs.tf:14-24`) → `secret { name, key_vault_secret_id,
identity }` on the API app (`containerapps/main.tf:44-54`) → `env { secret_name }`.
It needs no new role definition and it survives one apply.

This is ADR-011-compliant as written, and more directly than the previous
revision claimed: ADR-011's own "Implications for the decomposition" says the
API "reads connection strings, Foundry endpoint/key, and **signing config**
from Key Vault at startup" (`ADR-011:95-97`). An invitation token signing key
is signing config; ADR-011 already anticipates it living in the vault. The
locked rule is "no secrets in **code, client bundles, or Terraform source**"
(`ADR-011:6-7`, `:29` — "anything repository-visible is non-secret config"),
and a Key Vault secret materialised only at revision start via managed identity
is the shape ADR-011 chose (Option 1, `:49-51`).

The honest objection, stated for the security-architect rather than hidden:
ADR-008's Foundry account runs **keys disabled, Entra-only** (`ADR-005:95`),
and consistency argues for the same here. I cannot name a *least-privilege*
built-in role for ACS data-plane Entra auth from anything in this tree, and the
coarse role I would otherwise have to grant the workload identity is a
management-plane one — strictly **worse** for blast radius than a vault-scoped
secret. So:

- **w14**: Key Vault secret (deterministic, one apply, no unknowns).
- **Follow-up (recorded, not this wave)**: move to managed identity once the
  correct scoped role is verified against the live tenant. The swap is one
  module change plus `Invitations__Mail__Endpoint`; no application code beyond
  the client constructor.
- If the security-architect rules Entra-only at the table, I do not object —
  but the infra task then carries a **verification step against the live
  tenant** and may not assert a role name from documentation alone.

**Token signing key**: `random_bytes { length = 32 }.base64` (the `random ~>
3.6` provider is pinned in both roots — `dev/main.tf:19-22`,
`demo/main.tf:35-38` — and already used for `random_string.suffix`,
`keyvault/main.tf:15-20`; ADR-007:64 anticipates it) written to Key Vault as
`invitation-signing-key`, generated inside `modules/keyvault` next to the other
secrets. Per environment — structurally distinct, because the vaults are
(`kv-raffa-${var.environment}-${suffix}`, `keyvault/main.tf:23`), so a `dev`
token can never be replayed on `demo`. **Rotation invalidates every outstanding
invitation** — that is the security-architect's expiry story to own, and it
should be recorded next to the token TTL.

**A tension I will not paper over (see §1.10, ADR-007).** ADR-007:66 says
Terraform "never emits a connection string, SAS token, or certificate secret
into state as plaintext-visible app secret". The tree has already diverged from
a strict reading: `module.postgres.connection_string` and
`module.storage.primary_connection_string` are passed through the root into
Key Vault today (`dev/main.tf:182-183`, `demo/main.tf:210-211`), so they
transit HCP state. State is remote, encrypted and per environment (ADR-007
`:63`). My two new secrets follow that same established path and add a third
instance of it. That deserves one recorded sentence rather than silence, and
the ADR-007 footer in §1.10 supplies it. If the security-architect wants the
stricter reading enforced instead, that is a decision about `pg-cs`/`st-cs`
too, not only about mail — and it is a bigger change than this wave.

### 1.7 Apply path

`infra.yml` is path-filtered to `infra/**` and to itself (`infra.yml:8-18`), so
this PR runs `terraform fmt -check -recursive` + `init -backend=false` +
`validate` (`:55-75`), then `terraform plan` against the real HCP workspace
(`:80-102`). **Apply is owned by HCP Terraform, not by CI**: both workspaces are
VCS-connected and a CLI apply from the runner is rejected — the workflow says so
itself, "Apply not allowed for workspaces with a VCS connection", and the
`apply` job only prints the HCP run URL (`:104-135`). So:

- **`dev`**: merge to `main` → HCP `raffa-dev` run → **the operator confirms
  it in the HCP UI** ("Confirm the VCS-triggered run in the HCP UI (or enable
  workspace auto-apply)", `infra.yml:108-109`). Not automatic. This is a HITL
  step inside the wave and the decomposer must schedule it as one.
- **`demo`**: `demo-v*` tag → `demo-promote` calls this same workflow with
  `target_environment: demo` (`infra.yml:19-33`; the `apply` job's condition
  explicitly matches `refs/tags/demo-v*`, `:119`) → HCP `raffa-demo` run,
  behind the `demo` GitHub Environment's required reviewers (`:121`, ADR-016).
  Promotion moves **code and configuration only, never data**
  (`demo/main.tf:12-14`) — a `dev` invitation token is not valid on `demo` and
  no secret crosses.
- `terraform validate` in the PR job is also what proves the four
  `azurerm_communication_*` resource types and their attribute names exist in
  the pinned `~> 4.0` provider (§1.2). That check is free and it happens before
  merge.

### 1.9 Order constraints for the decomposition

Strict. Infra before the code that reads the key.

1. **W14-01** (rebase onto post-rebrand `origin/main`) — delivery-manager, at
   HITL, before any task. Everything below reads the *rebased* env roots.
2. **INFRA-1** — `modules/communication` + the two Key Vault secrets + the five
   API env vars, in **both** roots, with `invitation_mail_enabled = false`.
   PR → `infra.yml` validate+plan → merge → **HCP apply on `raffa-dev`,
   confirmed in the HCP UI**.
   *Must be merged and applied before the NW-58 backend task ships.*
3. **NW-58 backend + web** — software / security / client / ux. The API must
   treat `Invitations__Mail__*` as **optional** (§3): absent or
   `Enabled=false` → copyable link, and the UI never says "Invitation sent."
4. **INFRA-2** — live send probe on `dev`, then flip
   `invitation_mail_enabled = true` by PR → HCP apply. Only after this may the
   UI claim a mail was sent. Same pattern, same order, as the
   `ai_gateway_wired` flip `dev` has already been through (§1.4).
5. **`demo`** — both roots were edited in INFRA-1, so no extra Terraform is
   needed; the apply happens on the `demo-v*` tag under the `demo`
   environment's approval. `demo`'s flag stays `false` until its own probe —
   exactly where `ai_gateway_wired` sits for `demo` today.

## 3. The cross-seat hazard I am raising — and the pattern that answers it

**A new DbContext costs an infra PR, and this has already broken `dev` twice.**

`Raffa.Api.Program` fail-fasts at startup on a missing `ConnectionStrings:*`
key. I verified the shape directly: nine `?? throw new InvalidOperationException`
guards in `../backend/src/Raffa.Api/Program.cs` (`:31-34`, `:38-41`, `:55-58`,
`:65-67`, `:86-89`, `:105-108`, `:154-157`, `:177-180`, `:192-195`). The module's
own comments record the two times a module shipped before its env var did:
`ConnectionStrings__Savings` / `__Quotes` (`containerapps/main.tf:89-95` — "the
live API app has been missing them since those tasks landed") and
`ConnectionStrings__Suppliers` (`:117-121` — "without this env var the
container never starts"). Both were found late, after deploy.

Applied to NW-58:

- **If `workspace_invitation` lives inside `Raffa.Identity.Workspace`**, the
  existing `ConnectionStrings__IdentityWorkspace` covers it. **No infra
  change.** This is my recommendation to the software-architect.
- **If it gets its own module and DbContext**, a *third* infra PR must land and
  be HCP-applied **before** that code deploys, or `dev` goes down at the next
  revision. That PR is not free: it is a merge plus an operator confirmation in
  the HCP UI (§1.7).

**New finding — OQ-w14-cl-003 is already answered by an existing pattern.**
The previous revision asked the software-architect to please not fail-fast on
`Invitations__*`. That is not a favour to ask; it is a shipped convention.
`ConnectionStrings:Market` is deliberately **optional** in the same file —
`Program.cs:122-128` passes `builder.Configuration.GetConnectionString("Market")`
straight into `AddMarketModule(...)` with **no `?? throw`**, and the module
comment states the intent exactly: "Unlike the blocks above this one is optional
in the host -- absent, the API falls back to the in-memory mock projection --
but a deployed environment must have it" (`containerapps/main.tf:127-135`).

So the ask to the software-architect is precise and precedented: **bind
`Invitations__*` the way `ConnectionStrings:Market` is bound, not the way
`ConnectionStrings:Suppliers` is.** Absent or `Enabled=false` → copyable link,
container starts. That is the same behaviour NW-58's must #1 requires anyway,
so the safe wiring and the required product behaviour are the same line of
code. With it, §1.9's ordering is a sequencing preference; without it, step 3
before step 2 is a `dev` outage.
