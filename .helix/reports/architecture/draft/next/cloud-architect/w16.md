## Headline: the condition in OQ-w16-004 resolves to **involved**, whichever repair wins

`w16-requirements.md` §7 OQ-w16-004 puts the assumption in force as the
**re-enqueue path**, "because ADR-027 `:198` already rules that *reprocess
collapses into re-enqueue* on the same publisher, and it needs **no new identity,
no secret and no Terraform** — keeping the wave's cloud delta at zero and
cloud-architect on `PASS`". §5's closing line repeats it: "**No Azure or
Terraform delta is required** unless the council picks the token-bearing repair".

**That is wrong, and it is wrong because of what ADR-027 D5 actually says.**

ADR-027 `:192-201` makes re-enqueue an **internal** property of the API endpoint:
the same handler, with a replace step at its head. `:719` states the operating
model in full — "reprocess **is** a re-enqueue and **an admin inside that tenant**
can drive it". The caller is still an authenticated Admin arriving through
`POST /api/documents/{id}/reprocess`. Making that endpoint publish instead of
parsing inline changes **nothing** about who may call it.

So: if the workflow keeps calling the API, it still 401s at
`reprocess-tenant-documents.yml:202-211` — exactly the failure NW-31 exists to fix
— whether or not the endpoint re-enqueues internally. The re-enqueue only removes
the API-auth problem if **the workflow itself becomes a second publisher to
`extraction-events`**, and that needs a data-plane grant the CI principal does not
have.

**Evidence.** `infra/modules/servicebus/main.tf:71-102` declares exactly two role
assignments — `Azure Service Bus Data Sender` and `Data Receiver` — both scoped to
`var.workload_principal_id`. That is the **container apps' managed identity**. The
module has no CI input at all: both env roots pass only `workload_principal_id`
(`infra/environments/dev/main.tf:106-116`, `demo/main.tf:128-138`). The CI deploy
SP (`raffa-sp-dev` `4886788e-…`, `dev/main.tf:223-225`; `raffa-sp-demo`
`de126866-…`, `demo/main.tf:245-247`) is Terraform-granted **one** role in this
product — `Key Vault Secrets User` (`modules/keyvault/main.tf:66-75`). It has
**no Service Bus data-plane role**.

**A shared key is not the escape hatch.** A management-plane role can list the
namespace's default SAS key, but `modules/servicebus/main.tf:64-70` records the
decision already taken: "identity + RBAC, never a connection string and never the
namespace's default full-access shared key. NW-27 adds NO Key Vault secret because
of these two role assignments." Reaching for the SAS key to dodge Terraform would
reverse a decided rule and add the secret that comment says does not exist.

**And the DB-only variant is closed.** A decomposer might propose "let the
workflow flip `processing_status` in Postgres and let the worker pick it up" — it
already holds a psql session (`reprocess-tenant-documents.yml:292-334`). There is
no such pickup: ADR-027 `:71` lists "worker polls the database for queued jobs" as
**considered option 1 and not chosen**. The worker is broker-driven only. A DB
nudge re-enqueues nothing.

## NW-31 — the three repairs and their cloud delta

| Path | Cloud delta | Terraform | New €/mo | My seat |
|---|---|---|---|---|
| **A · token-bearing identity** | app role / federated credential on the API app registration | `modules/identity` | 0.00 | active |
| **B · CI publishes to the topic** (recommended) | **one** role assignment | `modules/servicebus` + both roots | **0.00** | active |
| **C · Container Apps Job** | **new resource**, new image path | `modules/containerapps` (+ ADR-007) | ~0.00, new surface to own | active |
| **D · workflow retired, no repair** | none | none | 0.00 | returns to `PASS` |

Only **D** leaves the cloud delta at zero. It is delivery-manager's call, not
mine, but it is the only reading under which OQ-w16-004's assumption holds.

### Recommendation — Path B

Cheapest correct repair, and the only one that adds **no new resource, no new SKU
and no new authorization principal class**.

- **Resource / SKU change**: **none**. `sbns-raffa-<env>` stays Service Bus
  **Standard** (`modules/servicebus/main.tf:11-18`, ADR-005 — Standard for topic
  support; Basic omits topics). Topic `extraction-events` (`:20-23`) and
  subscription `document-processing` (`:53-62`) are untouched: `max_delivery_count
  = 8`, `lock_duration = PT5M`, `default_message_ttl = P1D` all stay as w15 set
  them. No capacity, replica or tier movement.
- **Module change**: `modules/servicebus/variables.tf` gains
  `ci_deploy_principal_id`; `modules/servicebus/main.tf` gains a **third**
  `azurerm_role_assignment` — `Azure Service Bus Data Sender`, scoped to
  `azurerm_servicebus_topic.extraction_events.id` (topic-scoped, never
  namespace-wide, per the same file's `:66-68` rule), `principal_id =
  var.ci_deploy_principal_id`. It carries the same `lifecycle { ignore_changes =
  [skip_service_principal_aad_check, principal_type, name] }` block the existing
  two use (`:80-86`) — ARM rejects in-place role-assignment updates.
  **Sender only. Never Receiver**: CI enqueues, the worker consumes; a CI receiver
  grant would let a runner steal messages from the worker's subscription.
- **Root wiring**: one line in each of `infra/environments/dev/main.tf` and
  `demo/main.tf` — `ci_deploy_principal_id =
  data.azuread_service_principal.ci_deploy.object_id`. **The data source already
  exists in both roots** (`dev:223-225`, `demo:245-247`), so nothing new is
  looked up. Each root passes **its own** `ci_deploy`, never the other's — the
  same no-cross-env rule every module in these roots already states.

### Config keys per environment

**No `appsettings` key changes, and no container-app env var changes.** This is
the part most likely to be mis-decomposed, so it is explicit:

- The API and Worker container apps keep exactly the keys w15 set —
  `ServiceBus__FullyQualifiedNamespace`, `ServiceBus__TopicName`
  (`modules/containerapps/main.tf:195-202` API; `:398-405` Worker),
  `ServiceBus__SubscriptionName` (`:407-410`, Worker only),
  `ServiceBus__MaxAutoLockRenewalMinutes = 30` (`:412-415`),
  `ServiceBus__MaxConcurrentCalls = 4` (`:424-427`). **None moves.**
- Replica ceilings stay as PR #118 set them at the `dev` root —
  `api_max_replicas = 3`, `worker_max_replicas = 5` (`dev/main.tf:163-164`);
  `demo` stays at 3 until its own promotion. A reprocess burst rides the existing
  scale-out; it needs no ceiling change.
- The **workflow** is CI, not an app, so it reads no `appsettings`. It needs two
  values, both derivable with no new output and no new variable: namespace
  `sbns-raffa-${TARGET_ENVIRONMENT}` and topic `extraction-events` — both are
  literals of `modules/servicebus/main.tf:12,21`. Resolve the host with
  `az servicebus namespace show -g rg-raffa-${TARGET_ENVIRONMENT} -n
  sbns-raffa-${TARGET_ENVIRONMENT} --query serviceBusEndpoint -o tsv`, in the same
  place it resolves the API FQDN today (`:140-157`). A data-plane token comes from
  `az account get-access-token --resource https://servicebus.azure.net` on the
  login it already performs at `:124-129`. **No new GitHub Environment variable,
  no new secret.**

### Guard — two flags no w16 task may touch

`w16-requirements.md` §1 carries this forward and it lands in my lane because they
are my environment keys: `Invitations__Mail__Enabled` and
`guest_provisioning_enabled` are **`false` on `demo`**
(`modules/containerapps/main.tf:209-212`, `:232-235`; roots' `variables.tf`).
NW-67/NW-68 are delivered; the flags being false is a deliberate `demo` posture,
**not** a defect. **No w16 task may flip either**, and no reviewer may read them
as undelivered work.

### Apply path

`infra/**` is path-filtered to `.github/workflows/infra.yml:8-18`.

1. PR → `validate` (`fmt -check -recursive`, `init -backend=false`, `validate`,
   `:55-75`) then `plan` against the real HCP workspace (`:80-102`). Both are
   read-only; `plan` is visible on the PR.
2. Merge to `main` → **HCP Terraform owns the apply**. The `apply` job runs
   Terraform **not at all** (`:104-135`): both workspaces are VCS-connected, and a
   CLI apply from the runner is rejected outright. The run must be **confirmed in
   the HCP UI** at `app.terraform.io/app/raffa-platform/workspaces/raffa-dev/runs`
   unless auto-apply is on.
3. `demo` is **not** applied by that merge. It applies only through the ADR-016
   promotion path, which calls this workflow with `target_environment: demo`
   (`:19-33`) behind `demo`'s required reviewers.

**Manual step, named so it is not discovered at runtime**: step 2's HCP confirm
is a human action. A merged Terraform change whose HCP run is unconfirmed leaves
the grant absent and the workflow failing with a Service Bus `401`/`403` that
looks nothing like the API `401` NW-31 set out to fix.

**Propagation**: AAD role assignments are eventually consistent — the same
"well-known AAD replication lag" `modules/keyvault/main.tf:46-47` documents. Allow
minutes between the confirmed apply and the first workflow run; a failure inside
that window is not a defect.

### Cost

**€0.00/month.** A role assignment is free; Path B adds no resource, no SKU
change, no namespace and no Key Vault secret. The Standard namespace already
bills as ADR-005 set it — adding a second principal to an existing topic does not
change the line. Message volume is negligible: a reprocess publishes one message
per document (tens, not thousands) against Standard's included operation
allowance. **The wave's total cloud cost delta is zero**, which is the part of
OQ-w16-004's assumption that *is* correct — it is the "no Terraform" half that
fails.

### ADR action

  assignment on `extraction-events`; sender-only; CI deploy SP per env, never
  crossing envs; **no SKU, tier, capacity or replica movement**; cost delta
  €0.00. *(Mine to write, per `next-seats`.)*
- **`none — ADR-007`**: adding a variable and a resource to an existing module is
  not a layout change. `servicebus` is already in ADR-007's module list, remote
  state per env is untouched, no secret enters Terraform source. **If the council
  picks Path C instead, ADR-007 *does* need amending** for the new job resource.
- **`none — ADR-008`**: Foundry account, projects, deployments and `model_roles`
  are untouched this wave (`dev/main.tf:188-213`).
- **`none — ADR-006`**: region unchanged.
- **Reconcile, do not write** — `ADR-011` is security-architect's: they must
  ratify that the CI deploy SP becomes a data-plane **sender**, and re-affirm
  "never the namespace default shared key". `ADR-016` is delivery-manager's: the
  workflow's disposition and the one-wave window. `ADR-027` is
  software-architect's: the envelope a second publisher must emit, and whether the
  `document.reprocessed` audit row still gets written when the API is bypassed —
  see the open question below.

### Order constraint for the decomposition

**Infra before the code that reads it**, and the two must not share a phase:

1. **Phase N — Terraform task.** Owns `infra/modules/servicebus/{main,variables}.tf`
   and the one-line wiring in `infra/environments/{dev,demo}/main.tf`. Merge →
   **confirm the HCP run on `raffa-dev`**.
2. **Phase N+1 or later — the workflow task.** Owns
   `.github/workflows/reprocess-tenant-documents.yml` exclusively (ADR-016 w15
   clause 21). It may not run green before step 1's apply is confirmed.

No single-writer conflict exists between them (disjoint files), so
`check_single_writer.py` will not catch a wrong order — **the ordering must be
expressed as phases, not assumed**. `infra/environments/dev/main.tf` was last
touched by PR #118 and is on `main` at `f0b3436`; no rebase hazard.

If the council takes **Path D**, both tasks vanish, my seat returns to `PASS`, and
NW-31 narrows to the header/contract/prose deletions the other seats already own.

## Open questions from this lane

- **OQ-w16-cloud-01** — *(raised here, closes OQ-w16-004's factual error)*: the
  re-enqueue repair needs **one Terraform role assignment**, not zero. The
  council must pick A / B / C / D explicitly; only D leaves the cloud delta at
  zero. **Assumption in force**: **Path B**. cloud-architect + delivery-manager +
  security-architect.
- **OQ-w16-cloud-02** — under Path B the API is bypassed, so the
  `document.reprocessed` audit row the endpoint writes today is not written
  unless the worker writes it on a re-enqueued message. That collides with
  **NW-32** ("every write names its actor") in the same wave: a CI-published
  message has no user actor at all. **Assumption in force**: the worker writes the
  audit row with an explicit operator provenance string — the honest successor to
  `OPERATOR_USER_ID` (`reprocess-tenant-documents.yml:89-95`) — and NW-32's "no
  `unattributed`" sweep must not simply delete that path's actor. Not mine to
  rule: software-architect + security-architect.

## Table outcome (2026-09-14, council round 2) — **Path B is withdrawn**

Appended after the table so this draft is not read as a live proposal. Everything
above was written before the council ruled; two things in it are now **stale**.

1. **The headline is wrong about the outcome, right about the facts.** It says the
   condition resolves to *involved* "whichever repair wins". The table found a
   repair the four paths did not enumerate: **delete the workflow's API steps**
   (delivery-manager D3) and close NW-31's acceptance through the **product's own**
   Admin reprocess path (`POST /api/documents/{id}/reprocess`, PO's re-worded
   A16-3). That is this draft's **Path D** — "workflow retired, no repair" — so
   **the cloud delta is zero and this seat returns to `PASS`**.
2. **Path B is withdrawn.** The third topic-scoped `Azure Service Bus Data Sender`
   for `raffa-sp-<env>` was conditional on a **runner-side publisher**, and the
   table created none. **No w16 task may open `infra/`; no role assignment is to be
   minted from the §"NW-31 — the three repairs" table above.** The send-right
   question returns in **W17** with the bulk operator console (delivery-manager D5),
   where security-architect rules first on whether a CI principal may hold it.

**What still stands, and is the reason this draft mattered:** the refutation of
OQ-w16-004's zero-cost premise — both Service Bus roles go to
`var.workload_principal_id` only (`modules/servicebus/main.tf:71-102`), the module
takes no CI input, `raffa-sp-<env>` holds only `Key Vault Secrets User`
(`modules/keyvault/main.tf:66-75`), the SAS-key escape is closed by the module's
own rule (`:64-70`), and the DB-nudge variant is closed by ADR-027 `:71`. Three
seats converged on it from independent evidence; it is what made "re-enqueue is
free" fall. Also standing: the **config-keys** section (no `appsettings` or
container-app env key moves this wave), the **guard** on `demo`'s two flags, and
the **apply path** (HCP owns the apply; `demo` only through the ADR-016 promotion).

The **order constraint** section is **void**: with no Terraform task there is no
infra-before-code phase requirement from this seat. Delivery-manager's constraint 8
("no task opens `infra/`") replaces it.

Promoted to disk at the table: the **NW-31 `CA` clause** and the **vote row** in
`reports/architecture/waves/w16.md`, and four entries under "Rulings from the w16
council table (cloud-architect)" in `reports/open-questions.md` — including the
`demo` promotion arithmetic (12 in flight vs `dev`'s 20; 16.7k vs 15k TPM per
in-flight document) that says the promotion needs **no capacity or SKU change**.
