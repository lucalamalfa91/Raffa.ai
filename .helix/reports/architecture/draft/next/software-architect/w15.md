## 0. The two forcing problems

Five of my items follow from two decisions. Neither is a coding detail.

### 0.1 The worker cannot poll for work, and the API cannot reliably publish it

`extraction_job` carries `ENABLE` **and** `FORCE ROW LEVEL SECURITY` with the
ordinary tenant predicate
(`../backend/src/Raffa.Documents.Contracts/Migrations/Scripts/documents-contracts.sql:473-482`,
from `Migrations/20260903080549_AddTenantRowLevelSecurity.cs:47`). `FORCE` means
even the table owner is subject to the policy, and
`TenantRlsConnectionInterceptor` sets exactly one uuid
(`../backend/src/Raffa.SharedKernel/Tenancy/TenantRlsConnectionInterceptor.cs:232-238`).
So **"select every queued job across all tenants" returns zero rows and cannot be
made to return more** without the two exits ADR-009 forbids outright
(`ADR-009:12-13`, `:57-58`).

That kills the obvious design (write the row, let a poller find it) and it also
kills the obvious *recovery* design (a sweeper that re-enqueues rows the publish
step lost). Which in turn decides the publish ordering, because the two orderings
fail differently:

| Ordering | Crash window | Recovery |
|---|---|---|
| commit → publish | row committed, message never sent | needs a **cross-tenant sweep** — forbidden, or a new non-RLS ledger table |
| **publish → commit** | message sent, row never committed | **phantom message**: the handler finds no job, abandons, dead-letters after N. Costs nothing. |

**Publish-before-commit is not merely preferable here; it is the only ordering
compatible with ADR-009 that needs no new isolation axis.** Everything in §1
follows from that.

### 0.2 Whether the admission gate stays on the request thread decides the data model

OQ-w15-004 offers both. The evidence settles it on a second, independent ground
the requirements did not have:

- The gate parses/OCRs (`DocumentAdmissionGate.cs:107-117`) and calls the Foundry
  `classify` role (`:133-148`) — neither can be promised inside 2 s against live
  Document Intelligence.
- **And** `AdmissionDecision.Pages` carries the parsed text in memory
  (`AdmissionDecision.cs:67`), which today lets the upload handler pass the pages
  straight into the pipeline's pages+classification overload
  (`DocumentsEndpointExtensions.cs:265-273`;
  `DocumentProcessingPipeline.cs:174-182`) — **one parse per document**. A message
  cannot carry those pages (Service Bus Standard caps a message at 256 KB). So if
  the gate stays in the request and only extraction moves, the worker must
  **parse/OCR the document a second time**, paying Document Intelligence twice per
  upload, forever.

Keeping the gate in the request is therefore both slower *and* strictly more
expensive. The gate moves. §1.4 says what a refused file becomes, and §7 records
the ADR-024 sentence that has to be superseded to allow it.

## 1. NW-27 — `POST /api/documents` returns once the file is stored

**Decision**: the request keeps every check that is free and deterministic and
gives up every check that needs a model or the OCR service. `POST /api/documents`
answers **201** as soon as the blob and the rows are durable; a Service Bus
message published *before* the commit carries the work to `Raffa.Worker`, which
claims the `ExtractionJob` row that already exists, runs the admission gate and
then the pipeline, and drives the document to a terminal state.

### 1.1 The request/worker split

| Stays in the request (no I/O beyond the blob) | Moves to the Worker |
|---|---|
| form read + `ContentLength`/`MaxFileBytes` → **413** (`DocumentsEndpointExtensions.cs:171-220`) | parse / OCR (`DocumentAdmissionGate.cs:107-117`) |
| `DocumentFormatSniffer.TryDetect` → **415** (`:222-227`) | Foundry `classify` — the admission verdict (`:133-148`) |
| `storage.SaveAsync` + `document` + `document_version` + `extraction_job` rows + `document.uploaded` audit (`DocumentUploadService.cs:80-145`) | staged extraction, supplier link, per-page embedding (`DocumentProcessingPipeline.cs:262-278`) |
| **publish**, then commit (§1.2) | every `processing_status` transition after `Uploaded` |

The 201 body is unchanged in shape
(`DocumentsEndpointExtensions.cs:280-288`) and still carries
`processingStatus: "Uploaded"`.

**`201` is kept, `202 Accepted` is rejected.** 202 reads more correctly, but the
resource genuinely is created and `Location` is genuinely valid, and the change
would move an operation's success code in a hand-written 5 425-line contract
(`../web/openapi/raffa-api.v1.json`) and in the generated client for no behavioural
gain. The honest asynchrony signal is `processingStatus` plus the list's `stage`,
both of which already exist.

### 1.2 The queue contract

**The message is a pointer, never the work.** The durable work record already
exists: `DocumentUploadService.cs:114-121` writes an
`ExtractionJob { Stage = Classification, Status = Queued }` in the same
`SaveChangesAsync` as the `Document` (`:127`), and its own comment already
describes a consumer that was never built. That row stays authoritative.

```
Raffa.SharedKernel/Messaging/
  ExtractionRequested.cs          // sealed record (Guid TenantId, Guid DocumentId,
                                  //                Guid ExtractionJobId, int SchemaVersion)
  IExtractionQueuePublisher.cs    // Task PublishAsync(ExtractionRequested, CancellationToken)
  ExtractionQueueNames.cs         // TopicName = "extraction-events"; SubscriptionName = "extraction-worker"
```

The port lives in `Raffa.SharedKernel` for the reason `IDocumentStorage`
(`../backend/src/Raffa.SharedKernel/Storage/IDocumentStorage.cs:23`) and
`IAuditWriter` (`../backend/src/Raffa.SharedKernel/IAuditWriter.cs:8`) already do:
it is a cross-host port, and `Raffa.Api` cannot see `Raffa.Worker`'s types —
`IQueueConsumer` and `QueueMessage` are `internal` with
`InternalsVisibleTo("Raffa.Worker.Tests")` only
(`../backend/src/Raffa.Worker/Queue/IQueueConsumer.cs`,
`../backend/src/Raffa.Worker/AssemblyInfo.cs:9`).

**Publish before commit, with a small scheduled delay.** `DocumentUploadService`
publishes after building the three entities and **before** `SaveChangesAsync`;
the ids are known because `ExtractionJob.Id` is `ValueGeneratedNever`
(`ExtractionJobConfiguration.cs:14-16`). The message is scheduled a configurable
delay ahead (default **2 s**, matching the client poll) so the common path never
races the commit. If the commit then fails, the message is a phantom: the handler
finds no job, abandons, and Service Bus dead-letters it after `max_delivery_count`.
Nothing is lost and no cross-tenant read is invented (§0.1).

**Idempotency is a database claim, not a broker feature.** Service Bus duplicate
detection is *not* required and must not be relied on. The handler claims inside
the message's own tenant scope:

```sql
UPDATE extraction_job
   SET status = 'Running', claimed_at = @now, claimed_by = @instance,
       attempt_count = attempt_count + 1, started_at = COALESCE(started_at, @now)
 WHERE id = @jobId AND tenant_id = @tenantId
   AND status IN ('Queued','Failed')
   AND (claimed_at IS NULL OR claimed_at < @now - @lease)
```

0 rows affected → a duplicate or late delivery → complete the message, do nothing.
A worker that dies mid-run holds the lease only until it expires, and Service Bus
redelivers the message it never completed, so the crash case needs no sweeper.

**The database, not the dead-letter queue, owns the terminal state.** When
`attempt_count` reaches `MaxAttempts` the handler itself writes
`processing_status = Failed` with the reason and **completes** the message.
`max_delivery_count` on the subscription is set strictly above `MaxAttempts`, so
the DLQ stays empty in normal operation and a non-empty DLQ is an operational
alert rather than a product path. This is what makes A15-2 ("every row terminal")
a property of the schema rather than of the broker.

**One message per document, not one per stage.** The worker runs the whole
pipeline under one claim, advancing `ExtractionJob.Stage` so the six live stage
strings keep rendering (`DocumentProcessingStageMap.cs:20-39`, already
implemented verbatim from `screens-v2.md:59-79`). The SDK processor auto-renews
the lock. Per-stage fan-out is rejected as premature: it would make the Worker a
publisher too and multiply the claim surface by eight
(`ExtractionStage.cs:15-33`) for no acceptance benefit. Recorded as the named
upgrade path if one stage ever outlives a renewable lock.

**Rejected alternative — a non-RLS `extraction_dispatch` ledger + a sweeper.** It
works, and it is the shape ADR-026 kept as its named fallback for a different
problem. It is rejected here because publish-before-commit removes the failure it
exists to catch, at the cost of a harmless phantom message, whereas the ledger
costs a second isolation axis, a dual write on every upload, and a table whose
drift direction is "work silently not done".

### 1.3 The pipeline must replace, not append — this is not optional under retry

`StagedExtractionService.RunAsync` **appends on every run**: a new
`ExtractionJob` row per stage (`StagedExtractionService.cs:341-350`) plus
`ExtractionEvidences.Add` (`:522`, `:911`), `ContractLineItems.Add` (`:670`),
`Clauses.Add` (`:726`), `Obligations.Add` (`:778`), `Risks.Add` (`:832`). There is
no `RemoveRange` / `ExecuteDelete` anywhere in that file. The only delete-then-
replace in the product is for embeddings, and it lives in the *reprocess* service
(`EmbeddingRetrievalService.RemoveChunksAsync:163-181`, called from
`DocumentReprocessService.cs:84-87`), not in the pipeline.

Today nothing retries, so nobody has seen it. **At-least-once delivery makes it
acute**: one redelivery duplicates every extracted fact of a contract. So NW-27
must land a replace step at the head of the handler — delete this document's
prior `extraction_evidence`, `contract_line_item`, `clause`, `obligation`, `risk`
and non-`Classification` `extraction_job` rows, and reuse the existing
`RemoveChunksAsync` for the embeddings — before the pipeline runs.

Two things fall out for free: **reprocess collapses into "re-enqueue"** (the same
handler, the same replace step), and a latent duplicate-facts defect in today's
reprocess path is fixed by the same code. **If the cap binds, this is not the
thing to narrow** — A15-2 is exactly the acceptance it protects.

### 1.4 A refused file becomes a terminal `Rejected` row, and its bytes are deleted

`DocumentProcessingStatus` has five values and no `Rejected`
(`../backend/src/Raffa.Documents.Contracts/Domain/DocumentProcessingStatus.cs`).
It is persisted as the enum **name** into `processing_status character varying(30)`
with **no CHECK, no enum type and no default**
(`documents-contracts.sql:110`, from `20260902205243_Initial.cs:126`), so adding
a sixth value is a **code-only change** — the intake's "a new status value is a
migration" is, on this schema, not true, and ADR-021 needs no amendment for it.

What the worker does on `AdmissionOutcome.Rejected`
(`AdmissionDecision.cs:23-32`: `NotAContract` | `NoReadableText` — the only two):

1. `processing_status = Rejected`, terminal;
2. the rejection reason, detected type and confidence are persisted on the
   `document` row (three nullable columns — **this** is the migration);
3. `storage.Delete…` removes the blob, so the bytes do not persist;
4. **nothing is extracted, no `contract` row is created, nothing enters the
   tenant `embedding` index** — ADR-024's isolation property is untouched;
5. the existing `document.rejected` audit row is written unchanged, hash-keyed
   and content-free (`DocumentAdmissionGate.cs:222-251`).

**"Never store" survives in substance.** D3's rule is about a non-contract's
*content* living in the tenant's corpus; what persists after a refusal is a
content-free record of the refusal, which the audit row already persisted before
this wave. The bytes are transiently in the tenant's own container, written by
the tenant's own user, and are deleted on the verdict. **Security-architect must
ratify that window** (§9).

**`422` leaves `POST /api/documents`.** After the split, the only synchronous
refusals are 413 and 415; `not_a_contract` and `no_readable_text` both need a
parse. The 422 block (`DocumentsEndpointExtensions.cs:242-252`) is deleted and
its operation entry removed from the contract. A dead response code left in a
hand-written contract is worse than a breaking one the client seat is told about.

**Counted or not counted is a server fact, not a client rule.** The design oracle
marks the "Not added" card *session-only, never counted* (`screens-v2.md:72-75`).
That is preserved exactly by **excluding `Rejected` from the `all` count while
still listing the row** (§2.1) — which additionally makes the card survive a
reload and a second browser, which the session-only version cannot. The copy and
the card's treatment stay ux-ui-designer's.

### 1.5 Three things the Worker cannot do today

These are blockers, not chores, and each has a named owner.

1. **`IDocumentStorage` is not registered in the Worker.** The only registration
   in the product is `AddSingleton<IDocumentStorage, AzureBlobDocumentStorage>` at
   `../backend/src/Raffa.Api/Infrastructure/DocumentStorageServiceCollectionExtensions.cs:26`,
   called from `Program.cs:71`; the adapter is `internal sealed` in `Raffa.Api`
   (`AzureBlobDocumentStorage.cs:14`) and `Raffa.Worker.csproj` carries no
   `Azure.Storage.Blobs`. `DocumentUploadService` (`:35`),
   `DocumentReprocessService` (`:39`), `DocumentDeleteService` (`:45`) and
   `DocumentPreviewService` (`:30`) all require it, so the Worker's container
   cannot resolve any of them. **Decision: promote the adapter to a new
   `Raffa.Storage` project** referenced by the two hosts and by nothing else —
   the `Raffa.AiGateway` shape, and the only legal home for code two hosts share.
   Duplicating a tenant-path-guarded storage adapter into `Raffa.Worker` is
   rejected: `DocumentStoragePath` exists precisely because that guard is
   security-relevant (`../backend/src/Raffa.SharedKernel/Storage/DocumentStoragePath.cs:24`),
   and two copies of it will diverge.
2. **The worker container app receives only `pg-cs`.** Every `AiGateway__*` key,
   `AZURE_CLIENT_ID` and `ConnectionStrings__Storage` are on the API app alone
   (`../infra/modules/containerapps/main.tf:66-175` vs the worker block at
   `:205`+). A worker that must call `classify`, `ocr`, `extract` and `embed`, and
   must read the blob, needs them. **cloud-architect's Terraform**, and it is a
   hard prerequisite of the feature, not a follow-up.
3. **`QueueConsumerHostedService` dispatches nothing** — it logs the id and
   completes (`../backend/src/Raffa.Worker/Queue/QueueConsumerHostedService.cs:36-37`),
   with no `IServiceScopeFactory` and no scoped resolution. The scope-per-run
   pattern to copy is `RenewalThresholdSchedulerHostedService`, already in the
   same host.

### 1.6 Transport selection, and why CI stays green

`ServiceBusExtractionQueuePublisher` is registered when the Service Bus
connection is configured; otherwise an **`InlineExtractionQueuePublisher` runs the
handler synchronously in-process**. This is the codebase's own idiom — Foundry
when `AiGateway:Endpoint` is set, fixture otherwise (ADR-024) — and it is what
keeps `dev` laptops and the whole existing test suite working: today
`DocumentUploadEndpointTests`, `R1EndToEndTests` and `R1DocumentsV2EndToEndTests`
assert a processed document immediately after the POST, and with the inline
publisher they still can.

The trap is real and must be closed by the task: an environment that forgets the
connection string silently keeps synchronous uploads and still passes every test.
**The host must log the selected transport by name at startup**, and A15-1 /
A15-2 are acceptance on deployed `dev`, never in CI.

`Azure.Messaging.ServiceBus` lands in exactly two csproj files (`Raffa.Api`,
`Raffa.Worker`). It trips neither guard: `DependencyDirectionTests`'s
`ForbiddenSdkPrefixes` applies only to the fixed domain-module list
(`../backend/tests/Raffa.ArchitectureTests/DependencyDirectionTests.cs:18-33,76-84`),
and `SdkAllowListTests` forbids only `Azure.AI.*` and `Azure.Identity`
(`../backend/tests/Raffa.AiGateway.Tests/SdkAllowListTests.cs:23`) — which is why
the transport authenticates with a **Key Vault connection string**, exactly as
`pg-cs` and `st-cs` already do, and not with `DefaultAzureCredential`.

### 1.7 Infrastructure this decision requires (cloud-architect owns; stated as a contract)

The namespace and topic exist and are wired to nothing
(`../infra/modules/servicebus/main.tf:11-23`; no `ServiceBus*` / `Queue*` env var
in `../infra/modules/containerapps/main.tf`). What the design needs:

- one **subscription** on `extraction-events` (proposed `extraction-worker`) with
  dead-lettering on expiry, a lock duration the SDK can renew, and
  `max_delivery_count` **strictly above** the application's `MaxAttempts`;
- the connection as a Key Vault secret → container-app secret handle → env var, on
  **both** hosts (the API publishes, the Worker consumes);
- the worker app's missing `AiGateway__*`, `AZURE_CLIENT_ID` and
  `ConnectionStrings__Storage` (§1.5.2);
- worker `min_replicas ≥ 1` — a scale-to-zero worker cannot hold a subscription
  open, and the scale rule is cloud-architect's cost call.

## 2. NW-61 — the completeness signal the aggregates must return

Two of the three defects the requirements list resolve themselves once NW-27
makes the server row appear inside 2 s. What is left for this seat is the part no
client fix can supply: **the server must say "not ready yet" instead of letting a
screen infer it.** That is ADR-012's w14 provenance rule generalised — a client
must not infer a state it can be told — and it is also a live grounding defect.

### 2.0 There are four incompatible definitions of "ready" in the product today

| # | Definition | Where |
|---|---|---|
| 1 | `document.ProcessingStatus == Completed` on a linked document — **canonical**, and ADR-026 §D2's | `PortfolioQueryService.cs:238-247` (SQL `EXISTS`), `:190-193` (in-memory) |
| 2 | `Contract.Status != "completed"` — a free-text column whose bootstrap value is the literal `"processing"` | `AskCopilotService.cs:790-792` |
| 3 | `portfolio.Items.Count` / `TotalCount`, **unfiltered**, passed to a parameter named `validatedContractCount` | `AskCopilotService.cs:159, 178, 191, 200, 259`; `RoutingContext.cs:41` |
| 4 | `processingStatus ∈ {Uploaded, Processing}`, client-side | `../web/src/routes/documents/useDocumentsList.ts:105-108` |

**#3 is a defect against ADR-024, not a style difference.** Ask's routing gate
counts *every* contract row, including the bootstrap shell a still-processing
document created, and `RoutingContext.ValidatedContractCount` is documented as
the switch that decides whether Ask offers an answer or the upload action
(`RoutingContext.cs:29-31`). So Ask will presently treat a document that has not
passed validation as a validated contract — the exact "never a fabricated fact"
promise A15-3 exists to protect. **Decision: #1 is the only definition; #2 and #3
are deleted and call ADR-026 §D2's `CountValidatedContractsAsync`.** #4 becomes a
render of a server field (§2.1).

### 2.1 `GET /api/documents` gains a server-computed `counts` object

```
GET /api/documents            200 -> { items[], page, pageSize, totalCount,
                                       counts: { all, needsAttention, processing, rejected } }
```

- `all` — every document **except** `Rejected` (this is the "All documents · N"
  number, and it is what preserves the design's *never counted* rule as a server
  fact, §1.4);
- `needsAttention` — `NeedsReview` + `Failed`, the definition the client's
  attention filter already applies, moved to the server rather than re-invented;
- `processing` — `Uploaded` + `Processing` (non-terminal);
- `rejected` — `Rejected`.

**The counts are tenant-wide, never page-wide.** The list is paged and the client
currently fetches `pageSize = 100` and buckets locally
(`useDocumentsList.ts:18, :121-123`); a page-scoped count would be a new lie at a
higher page. `DocumentQueryService.ListAsync` today issues one
`CountAsync` over the filtered set (`DocumentQueryService.cs:100`) and has no
`GroupBy(ProcessingStatus)` anywhere — the counts are **one added grouped query**,
unfiltered by `?status=`, not four round trips.

This single field closes NW-61 defect (2) *and* **NW-10**: `RailNav` stops reading
the dead `sessionStorage` key and reads a number the server computed, exactly as
its sibling `useValidatedContractCount` already does. NW-10 needs no seat and no
ADR — but it needs this field to exist, which is why co-locating it with NW-61
(OQ-w15-008's assumption) is the right call.

### 2.2 Contract 360 gains a top-level readiness fact

Contract 360 **already** carries `tabs.documents[].processingStatus`
(`ContractsEndpointExtensions.cs:288-296`, from `Contract360Document`
at `Contract360Result.cs:185-191`) — so the requirements' "no `processingStatus`
read at all" is true of the *web*, not of the contract. But there is no top-level
signal, no `stage`, and `Contract360QueryService` never queries `ExtractionJobs`.
A contract whose document is mid-pipeline therefore returns **200 with a fully
shaped, entirely empty tab tree** — `products`, `clauses`, `obligations`, `risks`
all `[]` — and the only way to tell that from "extraction found nothing" is to
scan an array client-side. That is precisely the inference ADR-012 forbids.

```
GET /api/contracts/{id}   200 -> { ..., readiness: { state, stage, documentCount, completedDocumentCount } }
```

`state` is derived from definition #1 over the contract's linked documents:
`ready` (at least one `Completed`), `processing` (none `Completed`, at least one
non-terminal), `unavailable` (every linked document terminal and none
`Completed`). `stage` mirrors the Documents list's live string and is null unless
`state = processing`. A single object, so a screen asks one question.

### 2.3 Portfolio and Ask

- `GET /api/contracts` (the portfolio) gains `processingDocumentCount` beside its
  existing envelope (`PortfolioEndpointExtensions.cs:83-104`), so the empty state
  can say "3 documents still processing" instead of "no contracts". No row-level
  field: the screen's need is the *distinction*, not per-row detail.
- **Ask's pre-question off-state** is driven by the documents `counts` (§2.1) —
  `all == 0` is onboarding, `processing > 0 && validated == 0` is the
  `askOffReason` copy already shipped verbatim at `askViewModel.ts:254` from
  `screens-v2.md:25-30`. No new endpoint.
- **Ask's server-side turn** stops grounding on unvalidated contracts by
  replacing #2 and #3 with #1. The no-tools / grounding contract itself is
  untouched — `AnswerPromptV2.cs:33-35` and `GroundingGuard.cs:40-70` stay as they
  are; this changes only what is allowed into the pack.

## 3. NW-67 — where the Graph call sits, and what a failure means

Security-architect owns the permission, the consent and the blast radius;
cloud-architect owns the identity and the Terraform. **Mine is the seam, the
placement, the no-op contract and the failure contract.**

### 3.1 Synchronous, inside the invite request, before the mail

`POST /api/workspaces/{tenantId}/invites` is one interactive action, not a batch —
it carries no 2 s budget and a Graph `POST /invitations` is one sub-second call.
It must be **before** the mail, because a mail whose link leads to a sign-in the
invitee cannot complete is A15-4's failure and not a pass. Asynchronous
provisioning is rejected: A15-7 requires a **named** error on the pane, and an
async outcome would need a read-back endpoint and a polling pane for a
sub-second call.

Order in the handler: guards (unchanged, `WorkspaceInvitesEndpointExtensions.cs:81-124`)
→ **provision the guest** → mint token + write rows → send mail → 201.
The Graph call sits **outside** the database write: a remote call inside a
transaction holds a connection and cannot be rolled back anyway.

### 3.2 A provisioning failure aborts the invitation — it does not create a marked one

This is the load-bearing decision, and it is forced by an index. ADR-026 §D4's
partial unique index `(tenant_id, lower(email)) WHERE accepted_at IS NULL AND
revoked_at IS NULL` means a live invitation row **holds the slot**. If a failed
provisioning left an invitation behind, the Admin could not retry without first
revoking — the exact dead-slot trap ADR-020's second w14 footer already
documented for the `Expired` case. So:

- no guest → **no invitation row, no mail, no token**;
- one audit row (`workspace.guest.provisioning_failed`, free-form, no schema
  change — `AuditEvent.cs:29-31`);
- a **502** with a problem body carrying a stable machine-readable `reason`
  (`consent_missing` | `provisioning_failed` | `directory_unavailable`), so the
  pane picks its copy from a closed set and ux-ui-designer owns the strings;
- the Admin can retry immediately, because no slot was taken.

### 3.3 The seam, and the three-plus-one valued result

```
Raffa.Identity.Workspace/Application/IGuestProvisioner.cs
    Task<GuestProvisioningResult> EnsureGuestAsync(string email, string workspaceName, CancellationToken)
    // Provisioned | AlreadyPresent | NotConfigured | Failed(reason)
```

Exactly the `IInvitationMailer` shape (`IInvitationMailer.cs:16-33`), in the same
folder, for the same reason. `NotConfigured` is the fourth value and it is what
keeps CI and local development honest: gated by
`Invitations__GuestProvisioning__Enabled` (default **false**), the invite behaves
exactly as it does on `main` today — link-only, no directory write — instead of
either lying or failing. This mirrors `invitation_mail_enabled` / `ai_gateway_wired`,
the two-phase wiring already proven on this tenant.

Consequently the 201 gains one **load-bearing** field, `identityProvisioned`
(true for both `Provisioned` and `AlreadyPresent`, false for `NotConfigured`) —
NW-69's pre-send "this person has no account on the tenant yet" state reads it,
and it is a server fact rather than a client inference.

**Idempotency is the implementation's obligation, and the permission follows from
it.** A15-5 requires that inviting an address already in the tenant creates no
duplicate guest. The interface states the requirement; whether it is satisfied by
`User.Invite.All` alone or needs a directory read first is a least-privilege

## 4. NW-68 — the real mailer, and the absolute link

The design is pre-decided in the ADR-005 w14 footer (`:154-219`) and is **not**
re-opened: ACS Email + Azure Managed Domain, `infra/modules/communication`,
Key Vault `acs-connection` → handle `acs-cs`, the four config keys, the
per-environment `invitation_mail_enabled`. What this seat decides is the code
side.

### 4.1 The mailer

`AcsInvitationMailer` replaces `NullInvitationMailer` at exactly one line —
`../backend/src/Raffa.Identity.Workspace/Infrastructure/ServiceCollectionExtensions.cs:61`
is `TryAddScoped`, and its own comment records that a real mailer is "a second
`TryAddScoped` call in a later task". Note the ordering rule the codebase already
relies on: **`TryAdd` means the first registration wins**, so the real mailer must
be registered *before* `AddIdentityWorkspaceModule` — and that module's signature
takes only a connection string (`ServiceCollectionExtensions.cs:34-35`), so the
configuration is bound by the host in the established
`sp.GetRequiredService<IConfiguration>().GetSection(...).Bind(...)` factory shape
(`../backend/src/Raffa.AiGateway/ServiceCollectionExtensions.cs:85-92`), never
`IOptions<T>` — which appears nowhere in `backend/src`.

`Azure.Communication.Email` goes into `Raffa.Api`, authenticating with the Key
Vault connection string. It clears both SDK guards for the same reason as the
Service Bus client (§1.6).

`mailDelivered` is unchanged: it is literally the return of
`IInvitationMailer.TrySendAsync` (`WorkspaceInvitationService.cs:96-103`) and it is
already `required` in the contract (`raffa-api.v1.json:463-470`). No wire change.

### 4.2 The absolute link, and what happens when the base is missing

`AcceptRoutePrefix = "/invite/accept#"` is a private constant
(`WorkspaceInvitationService.cs:58`); the composition site is `:86`. With
`Invitations__AcceptUrlBase` configured, `acceptUrl` becomes
`{base}/invite/accept#{token}`; without it, the site-relative form of w14. **The
fragment stays** — ADR-025 Rule C9 and the ADR-005 second w14 footer, never a
query string, because `staticwebapp.config.json` rewrites the accept path and the
platform logs it.

Per ADR-026 §D6 the binding is optional and must never `?? throw` at startup. So
the misconfiguration "mail enabled, no accept-url base" is handled where it can
be handled honestly: **`TrySendAsync` refuses and returns `false`**, logging one
line. The pane then shows the already-designed "could not be sent" state with the
copyable link. Mailing a relative link nobody can open would be worse, and a
startup crash would violate D6.

**No mail body, no accept URL and no token in any log or audit row** — the rule
`NullInvitationMailer.cs:25-29` already keeps deliberately. The new verbs
`workspace.invitation.mail_sent` / `.mail_failed` are free-form strings and need
no migration (`AuditEvent.cs:29-31`); their exact names are security-architect's.

### 4.3 "Try sending again" necessarily re-mints the link — and the fix is one transaction

A finding the wave should not discover in implementation: **the server cannot
re-send the original link.** The token is stored only as a SHA-256 hash
(`WorkspaceInvitationService.cs:73, :297-300`) and the plaintext exists only on
the `IssueAsync` stack and in the 201 body. So any user-initiated retry after the
response is a **re-issue**, and the old link dies.

- Inside the request, a transient transport failure may be retried once by the
  mailer — that is the only true "send it again".
- After the response, "Try sending again" is revoke-then-invite. ADR-016's second
  w14 footer already contemplates a client-composed `DELETE` + `POST`, which adds
  no server writer.

**I propose one better shape and defer to ADR-025's owner**: make
`POST /api/workspaces/{tenantId}/invites` **replace** a live invitation for the
same address in one transaction (revoke + issue, two audit rows), instead of
returning the 409 the partial unique index produces today
(`WorkspaceMembershipService.cs:142-151, :174-182`). It is atomic where the
two-call sequence is not, it removes the dead-slot trap ADR-020's second w14
footer flagged as having "no legal path as written", and it makes "lost the
link", "it lapsed" and "the mail failed" one affordance with one call. It changes
an accepted lifecycle, so **ADR-025 governs and security-architect must ratify**;
if they refuse, the client-composed sequence is the fallback and no server file
changes. Either way the UI must warn first — ADR-020's rule, unchanged.

## 5. NW-05 — the single identity seam (software half)

ADR-010 is security-architect's and its w14 footer already binds this item.
I supply the shape, the exact sweep, and two corrections.

### 5.1 The sweep is 19 parse sites in 12 files, not "~12 copy-pasted blocks"

Verified: **two** helpers — the canonical `TryResolveTenant`
(`DocumentsEndpointExtensions.cs:556-567`) and a *divergent* one with a third
`out string error` parameter (`ConversationsEndpointExtensions.cs:355-369`) — plus
**17 inline five-line guard blocks**, byte-identical to each other and different
from the canonical helper, in `Contracts` (×4), `Portfolio`, `Insights` (×2),
`Negotiations`, `Quotes` (×3), `Renewals` (×3), `Savings` (×2) and `SavingsKpi`.
Add 12 helper call sites and 7 duplicated error strings in `DocumentsEndpointExtensions`
alone. The requirements' "~12" undercounts; the decomposer must size for 12 files.

The pre-authorised narrowing in `w15-requirements.md` §5 (one task, every endpoint
migrated together) is **right and should be confirmed at the table** — the blocks
are copy-pasted, so they are one edit, not twelve, and splitting them would leave
two identity regimes live at once.

### 5.2 `X-Tenant-Id` is demoted, not deleted — and this contradicts the intake

The requirements say the interim posture retires because "`X-User-Id` **and
`X-Tenant-Id`** stop being inputs". For `X-User-Id` that is exactly right. For
`X-Tenant-Id` it cannot be, and the reason is NW-01: a caller may belong to
several workspaces, so the token subject alone does not name a tenant. Only 6 of
36 routes carry `{tenantId}` in the path; putting it on the other 30 would be a
contract break across the whole API and the generated client, in a wave that has
no room for it.

**Decision: after NW-05 the tenant id is a *selector*, not a credential.** It
stays on the wire in its current form, and on every request the resolved seam
verifies the token subject's **live membership** in it before opening a scope —
so a forged or foreign tenant id yields **404** (ADR-025's rejection contract, not
403, which is a tenant-existence oracle). The header stops being trusted; it stops
being an authorization input; it does not stop existing. Whether the wire form
stays a header or becomes an explicit `workspace` parameter is a client- and
security-seat call; the property that matters is *authorized on every request*.

### 5.3 One seam, one middleware, one `Program.cs` line

`ICallerIdentity` is already the only reader of `X-User-Id`
(`Raffa.Api/Infrastructure/CallerIdentity.cs:58-73`) with 8 consumers, all of
which map absence to 401 and none of which reads a header itself — and
`Program.cs:53-59` already names this class as NW-05's edit point. So the identity
half is one file, as designed.

The tenant half converges on the same seam: it becomes a request-scoped
`ICallerContext` exposing the authenticated subject, the selected tenant, and the
verified role, populated by **one middleware** for `/api/*`. Middleware rather
than a per-route filter because `Program.cs` is contended (§8) and middleware is
one insertion — and the insertion is clean: there is currently **no `app.Use*` call
at all** between `builder.Build()` (`Program.cs:230`) and the first map (`:232`),
so nothing has to be reordered.

The middleware **resolves and never rejects**; rejection happens at the point of
use (`RequireIdentity()` / `RequireTenant()`), because the public routes are real:
`/health`, `GET /api/invites` and `POST /api/invites/accept` (token-bearing, and
`GetInvitationAsync` deliberately does not consume the identity seam),
`POST /api/workspaces` (bootstrap) and `GET /api/workspaces` (discovery, which
must keep taking no tenant input — ADR-026 §D1). Pair it with
`RequireAuthorization()` on the groups that need a token and explicit
`AllowAnonymous()` on those that do not; the shape is security-architect's to
ratify.

`WorkspacePrincipalAuthorization` is already JWT-shaped and has exactly **one**
call site, `AuditEndpointExtensions.cs:30`. See §6.2 — it is not the end state the
code comments claim.

### 5.4 Deploy order is a hard requirement, and one workflow breaks

- **Web before backend, always.** A SPA that attaches a token to an API which
  ignores it is a no-op; an API that requires a token before the SPA sends one
  locks every user out of `dev`. `web.yml` and `backend.yml` are separate
  workflows, so this ordering is delivery-manager's to enforce, not an accident to
  hope for.
- **`reprocess-tenant-documents.yml` breaks.** It authenticates with
  `X-User-Id: github-actions/reprocess-tenant-documents` plus both role headers
  (`:203-206`, `:254-257`) — after NW-05 that identity is not a token and the job
  returns 401. It needs a real non-interactive identity, or it must be retired in
  favour of the enqueue path NW-27 creates (`--max-time 600` per document becomes
  "enqueue N, poll"). delivery-manager and security-architect.
- **The test suite is 34 files and 161 header statements**, but 48 of those call
  sites funnel through four helpers in one file
  (`../backend/tests/Raffa.IntegrationTests/R1EndToEndTests.cs:343-378`), and
  `TestPrincipalStartupFilter` and `TokenIdentityRetirementTests`'
  `TestTokenStartupFilter` already fabricate principals. Reuse them; do not invent
  a third.

### 6.1 NW-07 — conversation `user_id`

There are **two** identity seams, and the second is a live bug independent of
NW-05: `TryResolveUserId` (`ConversationsEndpointExtensions.cs:371-399`, 5 call

membership. `Conversation.UserId` is the *only* thing separating two members of

The data question is the real one and it is bigger than case: NW-05 changes the
identity from an MSAL username to a token subject, which orphans **every**
existing row (`conversation.user_id` is `varchar(200)`, indexed
`(tenant_id, user_id, updated_at)` — `chat.sql:14, :57`). Two honest options,
for W16: (a) a one-time per-tenant normalisation in the established
`backend/scripts/` shape; (b) accept orphaning on `dev`/`demo`, where the rows are
test data. **Not** a case-insensitive read predicate as a permanent rule — it
would let a reassigned address read another person's threads.

### 6.2 NW-08 — `GET /api/audit`

Two corrections to the record. First, the endpoint is **not** "already the end
state": its guard reads both the tenant **and** the role out of claims
(`WorkspacePrincipalAuthorization.cs:56-74`), and ADR-010's w14 footer forbids a
`tenant_id` or `roles` claim as an authorization source. So NW-05 alone does not
fix it — the guard must move to the §5.3 seam (tenant from the selector, role
from membership), which is precisely the "single seam its own comment names".
Second, the route is **absent from the OpenAPI document** (34 paths, `/api/audit`
is not one of them), so no generated client can reach it; adding it is part of the
item. `PATCH /api/savings/{id}` is missing too — same class, not this item.

### 6.3 NW-32 — the unattributed actor

Roster §3 omits this seat from NW-32 while its own §2 block names it; flagged for
the gate, immaterial this wave since the item is W16 overflow.

The shape: `"unattributed"` is declared in **ten** places and used in **thirteen**,
and **not one of the nine service methods accepts an actor parameter at all** — so
this is nine signature changes plus their call sites, not a constant deletion.
Four services already take an actor (`DocumentValidationService`,
`DocumentAdmissionGate`, `DocumentReprocessService`, `DocumentDeleteService`, fed
from `DocumentsEndpointExtensions.ResolveActor:569-573`); they are the pattern to
converge on. The real defect is that one absent header produces **three**
outcomes — 401, 400, and a silent `"unattributed"` audit row — which the §5.3 seam
collapses to one.

### 11.1 The grounding defect is in user-facing copy, not only in routing

`AskCopilotService.cs:294` composes the abstain reply as
`$"Nothing in the {portfolio.Items.Count} validated contract(s) supports a
reliable answer."` — and `portfolio.Items.Count` is the **unfiltered** page count
(definition #3). The sentence therefore **asserts to the user** that N contracts
are *validated* when N includes every bootstrap shell a still-processing document
created. `:159` and `:160` pass the same unfiltered number as the parameter
literally named `validatedContractCount`; `:178`, `:191`, `:259` pass
`portfolio.TotalCount`.

So §2.0 #3 is not merely a gate reading the wrong number: **the product already
states a fabricated fact in shipped copy**, before this wave changes anything.
That moves §2 from "a server field NW-61 would like" to the defect A15-3 is
written against. One swap to ADR-026 §D2's `CountValidatedContractsAsync` fixes
the gate and the sentence together.

### 11.2 `Raffa.Storage` repairs a landmine the code already documents

Two facts, both new to this draft, and they point the same way:

- **The Documents/Contracts module *is* already registered in the Worker.**
  `WorkerServiceCollectionExtensions.AddWorkerHost:66-68` calls
  `AddDocumentsContractsModule` + `AddAuditModule` + `AddRenewalsModule`, and
  `Raffa.Worker/Program.cs:16-34` fail-fasts on all three connection strings. The
  DbContext, the tenant RLS interceptor and the application services are therefore
  **already in the worker's container** — so §1.2's claim-inside-a-tenant-scope
  model needs no new module wiring, only the handler. That is a positive finding:
  the hardest half of "the worker opens its own tenant scope" (ADR-009) is
  already composed.
- **Which is exactly why storage is a blocker, not a chore.** The same method's
  doc comment (`:28-40`) already names this failure mode in the abstract:
  `AddDocumentsContractsModule` "registers that service in *any* host that calls
  it — including this one … the Worker's container would hold a registered
  `DocumentUploadService` whose own dependency graph can never resolve — harmless
  while nothing in this host asks for it (today), but a landmine under any
  host-builder configuration that validates the DI graph eagerly
  (`ServiceProviderOptions.ValidateOnBuild`, on by default whenever
  `DOTNET_ENVIRONMENT=Development`)". It was written about `IAuditWriter` and
  closed by adding `AddAuditModule`. **`IDocumentStorage` is the same landmine,
  still armed** — registered nowhere but `Raffa.Api` — and NW-27 is precisely the
  task that makes this host "ask for it".

The difference is that the `IAuditWriter` case could be closed by calling another
module's `AddXxx`; this one cannot, because the adapter is `internal sealed` to a
**host**. Hence the project move in §1.5.1. Worth saying at the table in the
codebase's own words: this is the repair the previous host-composition task
prescribed, not an invention of this seat.

### 11.3 The worker container app, exactly

`infra/modules/containerapps/main.tf:205-275` — **one** secret, `pg-cs`
(`:224-228`), and five env keys all bound to it:
`ConnectionStrings__DocumentsContracts` (`:240`), `__Audit` (`:245`),
`__Renewals` (`:252`), `__Savings` (`:264`), `__Quotes` (`:269`).
**Absent: `ConnectionStrings__Storage`** (the API's is the separate `st-cs`
secret, `:137-140`), **every `AiGateway__*`**, and **`AZURE_CLIENT_ID`**
(`:145`). §1.5.2 is confirmed precisely: the worker holds the `pg-cs` secret and
nothing else.

Two numbers §1.7 could not cite before — **`min_replicas = 0`, `max_replicas = 1`**
(`:231-232`):

- `min_replicas = 0` is the blocker §1.7 already names: an app scaled to zero
  holds no subscription open.
- `max_replicas = 1` is **not** a blocker, but it is a throughput ceiling nobody
  has costed. A15-1 drops **15 PDFs**; one replica running OCR → classify →
  extract → embed per document drains that batch serially. A15-1 sets no deadline
  for reaching a terminal state ("with the browser closed"), so it **passes as
  written** — but the pilot's felt speed deserves a decided number rather than a
  default. **Appended to §9 as a cloud-architect ask**: the §1.2 claim/lease model
  is safe at any replica count, which is what makes raising it a pure cost
  decision and not a design one.

### 11.4 The NW-05 sweep — an outer bound for the decomposer

`Grep "X-Tenant-Id"` over `backend/src/Raffa.Api` returns **72 occurrences across
15 files**: the 12 with parse sites (§5.1), plus `Program.cs` ×5,
`CapabilitiesEndpointExtensions.cs` ×2, `WorkspaceInvitesEndpointExtensions.cs`
×2, `WorkspaceRoleResolver.cs` ×1, `ChatEndpointExtensions.cs` ×1. Parse sites are
the subset that reads and validates; the **occurrence** count is what the edit
actually touches, because each site carries the header-name constant and its own
error strings.

Either number refutes "~12 copy-pasted blocks" as a sizing input. Size NW-05's
sweep at **one task over 15 files** — which is also why §5.1 endorses the
requirements' pre-authorised narrowing (§5, one task for every endpoint) instead
of a per-family split that would leave two identity regimes live at once.
