## 0. The one problem this wave actually poses

Five of my six items are ordinary CRUD. One is not, and it determines the
shape of the other four.

`GET /api/workspaces` (NW-01) must answer **"which workspaces does this
caller belong to?"**. Every table that could answer it is tenant-scoped and
RLS-guarded, and the guard fails *closed*:

- `TenantRlsConnectionInterceptor` sets `app.tenant_id` only when
  `ITenantContext.Current` is non-null, and `RESET`s it when the connection
  returns to the pool (`../backend/src/Contigo.SharedKernel/Tenancy/TenantRlsConnectionInterceptor.cs:53-57,86,107`).
  Its own doc comment (`:15-16`): *"When `ITenantContext.Current` is null (no
  active scope) the claim is left unset, so RLS denies every tenant-scoped
  row on that connection — fail closed."*
- The policy on all four identity tables is
  `USING (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)`
  with `ENABLE` + `FORCE ROW LEVEL SECURITY`
  (`../backend/src/Contigo.Identity.Workspace/Migrations/Scripts/identity-workspace.sql:143-147,154-158,165-169,176-180`).
- `workspace_user` is itself **tenant-scoped**: the same person in two
  workspaces is two rows, unique on `(tenant_id, email)` and
  `(tenant_id, external_subject_id)`
  (`WorkspaceUserConfiguration.cs:29-30`; SQL `:118,125`).

So the caller's own identity is only discoverable *once you already know the
tenant* — the exact thing the endpoint is asked to find out. And ADR-009
quotes spec §3.2 verbatim: *"No cross-tenant query path is acceptable"*
(`ADR-009-tenancy.md:12-13`), with *"No query may run under
`BYPASSRLS`/superuser in the application path"* in its consequences (`:57-58`).

**This is a genuine architectural fork, not a coding detail**, and it needs an
ADR. NW-02, NW-04, NW-09 and NW-58's accept step all sit downstream of how it
is resolved.

### Options I considered

| # | Option | Verdict |
|---|---|---|
| A | Run the discovery query as `BYPASSRLS` / a superuser role | **Reject** — ADR-009 `:57-58` forbids it outright. Not re-openable at this table. |
| B | Enumerate `workspace`, scope into each tenant, test membership | **Reject** — reading `workspace` unscoped is the same forbidden read, and it is O(all tenants) per sign-in. |
| C | New identity-keyed **directory/projection** table (`identity_key → tenant_id`), outside the tenant axis, written alongside every membership write | **Fallback.** Correct and clean, but it denormalises workspace name + role, adds a dual-write consistency obligation on three code paths (create, accept, remove), and introduces a table whose isolation axis differs from every other table in the system. |
| D | **Second, `FOR SELECT`-only, identity-keyed RLS policy on `workspace_user` alone**, plus per-tenant scoped reads for everything else | **Chosen.** |

### Chosen: D — a second isolation axis on exactly one table

`workspace_user` already carries the two columns that identify a person
(`email`, `external_subject_id`, `WorkspaceUser.cs:26,30`). Give it one extra
**permissive, SELECT-only** policy keyed on a new GUC `app.identity_key`.
Postgres ORs permissive policies, so a connection with `app.identity_key` set
and no `app.tenant_id` sees *only that identity's own rows*, across tenants —
and nothing else in the database becomes visible.

`GET /api/workspaces` then runs in two phases:

1. **Discovery** — with `app.identity_key` set and **no** tenant scope, select
   `tenant_id` from `workspace_user` where the identity matches. Returns the
   caller's candidate tenant set and nothing else.
2. **Projection** — for each candidate tenant, `tenantContext.BeginScope(tenantId)`
   and read normally: the `workspace` row (name, and after NW-24 country +
   currency), the caller's role via the existing membership join, and the
   validated-contract count (NW-09). Every read in this phase is an ordinary,
   fully RLS-scoped read of a tenant the caller has provably been admitted to.

Why this beats C: no denormalisation, no dual write, no new table, one source
of truth. Why it is safe: the widened surface is exactly "a person may read
their own identity rows", `WITH CHECK` is untouched so **no write path widens
at all**, and the policy is `FOR SELECT` only.

**Inclusion is gated on membership, not on the `workspace_user` row.** Phase 1
only *discovers* candidates; phase 2 drops any tenant where the caller holds
zero `workspace_membership` rows. This is what makes NW-58's removal
requirement ("access gone") work: removal deletes the membership row and
keeps the `workspace_user` row for audit, and the workspace disappears from
the list on the very next request — no token expiry, no cache invalidation.

**This is the decision I most need the security seat to rule on.** If
security-architect rejects widening an existing tenant table's policy on
principle, I fall back to option C without changing any endpoint contract —
only the internals of the discovery phase move. I have written the ADR so
that fallback costs one section, not a redesign.

## 1. NW-02 — create workspace also writes the creator's membership

**Today.** `WorkspaceProvisioningService.CreateWorkspaceAsync(name, ct)` adds
`db.Workspaces` + `db.WorkspaceRoles` and nothing else
(`WorkspaceProvisioningService.cs:31-49`, insert at `:44-46`).
`WorkspaceEndpointExtensions.CreateWorkspaceAsync` passes only `request.Name`
(`:36-57`) — no caller identity ever reaches the service. So the creator is a
member of nothing, and `WorkspaceRoleResolver`'s membership branch
(`../backend/src/Contigo.Api/Infrastructure/WorkspaceRoleResolver.cs:104-114`)
returns empty for them — which is the whole of NW-14.

**Decision.**

- `POST /api/workspaces` resolves the caller identity (interim `X-User-Id`;
  see §7 seam) and returns **400** when it is absent. Creating a workspace
  nobody can enter is not a success case.
- `CreateWorkspaceAsync(name, callerIdentity, profile, ct)` inserts
  `workspace` + the five `workspace_role` rows + one `workspace_user` (email =
  caller identity, `external_subject_id` = the same value when it is a subject
  rather than an email) + one `workspace_membership` (Admin) in **one**
  `SaveChangesAsync` inside the **existing single** `BeginScope(workspace.TenantId)`
  at `:42`. One transaction, one tenant claim, RLS `WITH CHECK` satisfied for
  all four inserts because they all carry the new tenant's id.
- Reuse `WorkspaceMembershipFactory.CreateInvitedUser` + `CreateMembership`
  (`WorkspaceMembershipFactory.cs:27,52`) rather than new construction logic —
  `CreateMembership` already enforces the user/role same-tenant invariant
  (`:55-61`).
- **Module**: `Contigo.Identity.Workspace` only. No new project.

**ADR action.** `amend ADR-009` — the creator's membership row is part of
tenant bootstrap, not a later step. **security-architect owns ADR-009 and
writes that footer**; this is my proposed text, not my file. I also propose
`amend ADR-022` for the identity key (§7), likewise security-owned.

**Consequences for the decomposition.**

- Files: `WorkspaceProvisioningService.cs` (signature + inserts),
  `WorkspaceEndpointExtensions.cs:36-57` (identity resolution + 400).
- Migration: **none.** No schema change — the tables already exist.
- Contract: `POST /api/workspaces` gains a required `X-User-Id` header and a
  400; the 201 body gains `role: "Admin"` so the SPA can enter directly
  without a second call. OpenAPI `contigo-api.v1.json:53-119` updated.
- Tests: extend `WorkspaceRlsCrossTenantIsolationTests` (named in
  `WorkspaceMembershipFactory.cs:13-14`); an API test that creates a workspace
  and then deletes a document as the creator — that test *is* NW-14's
  acceptance N9, and it should live in this task, not a separate one.
- **Backfill — an honest gap.** Existing `dev` workspaces have no membership
  row and **cannot be attributed retroactively**: `CreateWorkspaceAsync` never
  recorded who created them, so no column, log or audit row identifies the
  owner. There is no EF data-migration precedent in this repo (every
  `Migrations/**` write is the `__EFMigrationsHistory` trailer). The
  established shape for data changes is a separate idempotent script under
  `backend/scripts/` with `SET app.tenant_id` + fixed ids +
  `ON CONFLICT DO NOTHING`, run by its own workflow — precedent
  `../backend/scripts/demo-fixture-seed.sql:8-10,28-31,48-53,60-67` and
  `../.github/workflows/seed-demo-fixture.yml:135`. So: **one operator job
  taking `(workspace id, admin email)` pairs supplied at HITL**, or the
  operator recreates the `dev` workspaces. I cannot decide which — it is a
  data question, not an architecture one. See **OQ-w14-006** below.

## 2. NW-01 — `GET /api/workspaces` for the signed-in identity

**Today.** `WorkspaceEndpointExtensions.cs:31-32` maps exactly two POSTs and
no GET. `WorkspaceMembershipService` has `InviteAsync` / `LinkSignInAsync`
and no list query. The OpenAPI document confirms it in its own text
(`contigo-api.v1.json:57`) and so does the client
(`../web/src/api/client.ts:96-98`).

**Decision.** `GET /api/workspaces`, implemented per §0 option D.

```
GET /api/workspaces
  headers: X-User-Id (required; 400 when absent — never X-Tenant-Id)
  200 -> { workspaces: [ { id, name, role, contractCount,
                           country, currency, createdAt } ] }
```

- **No `X-Tenant-Id` on this endpoint, ever.** The response is derived
  exclusively from the caller identity. A client-supplied tenant header must
  not be able to widen it — that is acceptance N5 and the reason this endpoint
  takes no tenant input at all. A crafted other-tenant id has nowhere to enter.
- Empty array (200) when the caller belongs to nothing — **not** 404. The SPA
  distinguishes "you have none, create one" from "request failed".
- Ordering: `createdAt` ascending, stable, so the picker does not reshuffle.
- New module service `WorkspaceDirectoryService` in
  `Contigo.Identity.Workspace/Infrastructure/`, exposing
  `ListForIdentityAsync(identityKey, ct)`. It owns phase 1 and phase 2's
  identity-side reads; it does **not** know what a contract is.

**ADR action.** **`new ADR-025 — identity-scoped workspace discovery`**
(provisional number; see §8). Deciders: software-architect (owner) +
security-architect (co-signer, ADR-009 axis). Serves NW-01, NW-02, NW-04,
NW-09 and NW-58's accept step. Records option D, records C as the named
fallback, and states the `app.identity_key` GUC contract.

Plus `amend ADR-009` (security-owned): a second, SELECT-only isolation axis
exists on `workspace_user`; the tenant axis is unchanged on every other table
and `WITH CHECK` is unchanged everywhere.

**Consequences for the decomposition.**

- **New GUC + interceptor change.** `app.identity_key` must be set on the
  connection the same way `app.tenant_id` is. That means a sibling ambient
  context (`ICallerIdentityContext` + `CallerIdentityContext`, mirroring
  `ITenantContext`/`TenantContext.cs:10-38`) and an extension of
  `TenantRlsConnectionInterceptor` to `SET`/`RESET` both GUCs.
  **`TenantRlsConnectionInterceptor.cs` is a shared-kernel file wired into
  every module's DbContext options** (e.g.
  `Identity.Workspace/Infrastructure/ServiceCollectionExtensions.cs:33-35`,
  `Documents.Contracts/.../DocumentsContractsDbContextOptions.cs:38-41`) —
  this is the wave's **highest single-writer risk**. It must be **one task,
  landing before every other NW-01/NW-04/NW-58 task**, and no other task in
  the wave may touch that file.
  `RESET app.identity_key` on connection close is mandatory for the same
  pooled-connection-leak reason the tenant claim is reset (`:78-101`).
- **Identity normalisation.** `app.identity_key` and `workspace_user.email`
  must compare case-insensitively — the existing unique index
  `ix_workspace_user_tenant_id_email` (SQL `:118`) is case-sensitive today, so
  `Luca@x.com` and `luca@x.com` are two rows. Decision: **normalise to
  lower-case on write** in `WorkspaceMembershipFactory.CreateInvitedUser`
  (which already trims, `:30`) and set the GUC from the same normalisation.
  Not `citext` — that would be a column-type change on a table with a live
  unique index, for no benefit once writes are normalised.
- Migration: `AddWorkspaceUserIdentitySelfReadPolicy` in
  `Contigo.Identity.Workspace/Migrations/`. Follow the frozen-table-list
  convention that `20260903084728_AddTenantRowLevelSecurity.cs:24-31` states
  explicitly (a new policy gets its own follow-up migration), emitted via
  `migrationBuilder.Sql(...)` like `:51-61`, with a `DROP POLICY IF EXISTS`
  `Down` like `:67-75`.
- `.sql` script: regenerate `Migrations/Scripts/identity-workspace.sql` with
  `dotnet ef migrations script --idempotent` run from
  `backend/src/Contigo.Identity.Workspace`. **Never hand-edit it** —
  `IdentityWorkspaceMigrationScriptStaleCheckTests` regenerates in-process and
  asserts byte equality, so a hand-edit fails `dotnet test`. The script is
  already in both CI arrays (`../.github/workflows/backend.yml:276-286` and
  `:308-318`), so an appended migration is picked up with **no workflow edit**.
- Tests: `WorkspaceRlsCrossTenantIsolationTests` must be **extended, not
  relaxed** — assert (a) with neither GUC set, zero rows; (b) with only
  `app.identity_key` set, exactly the caller's own `workspace_user` rows and
  no `workspace`/`workspace_role`/`workspace_membership` rows; (c) tenant
  isolation for every other table unchanged; (d) no write succeeds under
  `app.identity_key` alone.
- Contract: new path in `contigo-api.v1.json` under `/api/workspaces` (`:53`),
  `listWorkspaces` in `client.ts`, regenerate via `npm run generate:api`
  from `web/`. See §6 for the generator constraints this shape must respect.

## 3. NW-09 — the picker's contract count

**Today.** Five surfaces disagree, and none of them asks the server:
the picker writes a literal `contractCount: 0`
(`../web/src/routes/signin/WorkspacePickerScreen.tsx:82`, rendered `:173`);
the rail and Portfolio each recompute from a *client-side free-text
heuristic* over page 1 of ≤100 contracts
(`../web/src/components/shell/useValidatedContractCount.ts:41-43,60`,
`../web/src/routes/contracts/contractStatus.ts:17-21`,
`../web/src/routes/contracts/portfolioViewModel.ts:38,87`); `/documents`
counts documents, not contracts.

**The key finding: the canonical count already exists on the server.**
`Contract.Status` is free text (`Contract.cs:22`) whose bootstrap value is the
literal `"processing"` (`StagedExtractionService.cs:157`), so it can never
define "validated". The backend's real rule is
`Document.ProcessingStatus == Completed && ContractId is not null`
(`PortfolioQueryService.cs:160-172,190-193`) — *a contract is validated iff at
least one of its linked documents is `Completed`* — and it is already exposed
as `contractsAnalyzedCount` on `GET /api/savings/kpis`
(`SavingsKpiEndpointExtensions.cs:93`, via
`PortfolioAnalysisCalculator.cs:38-39,77`), which no UI consumes.

**Decision.**

- **One definition, and it is the existing server one**: validated contract =
  a contract with ≥1 linked document in `ProcessingStatus.Completed`. The
  client-side `isValidatedContractStatus` heuristic
  (`contractStatus.ts:17-21`) is deleted as a *definition* — the client-architect
  owns that deletion; my part is guaranteeing the server number it is replaced
  with.
- `contractCount` is a **field on NW-01's payload**, not a second round-trip
  per row. It is computed in phase 2, inside each tenant's own
  `BeginScope(tenantId)`.
- **Composition happens in the host, not in a module.**
  `Contigo.Identity.Workspace` may not reference `Contigo.Documents.Contracts`
  — the architecture test forbids it
  (`../backend/tests/Contigo.ArchitectureTests/DependencyDirectionTests.cs:62-63`,
  `["Contigo.Identity.Workspace"] = ["Contigo.SharedKernel"]`). `Contigo.Api`
  is the one project allowed to see both
  (`PortfolioEndpointExtensions.cs:29-31`). So the endpoint handler calls
  `WorkspaceDirectoryService` and the Documents.Contracts query service and
  joins them in the response projection. Established precedent for exactly
  this shape: `SavingsKpiEndpointExtensions.cs:73-88`.
  **I explicitly reject adding a SharedKernel port for this** — it would be
  legal, but host composition is the house pattern and touches one fewer
  shared file.
- Add a counting method to the Documents.Contracts query service that does a
  real SQL `CountAsync` rather than materialising. Note there is **no**
  `CountAsync` over `Contracts` anywhere today — every contract count is
  `ToListAsync` then `.Count` (`PortfolioQueryService.cs:153,183-200`). This
  task adds the first one; it is a distinct-contract count over documents,
  which is expressible in SQL and should not repeat the materialise-everything
  pattern.

**ADR action.** `none — the count is a field on NW-01's contract (ADR-025);
the "validated" definition is the one already encoded in
PortfolioQueryService and needs no new decision.` ADR-020's screen-1 wording
is unchanged (ux-ui-designer's row).

**Consequences.** N+1 by construction: one count query per workspace the
caller belongs to. For the pilot that is 1–3. I am **not** optimising it into
a single cross-tenant aggregate — that would reintroduce exactly the query
path §0 rejects. If a user ever holds many memberships this becomes a real
cost; recorded as a known limit, not a defect.

## 4. NW-04 — `GET /api/workspaces/{tenantId}/members`

**Today.** No member-list route (`WorkspaceEndpointExtensions.cs:31-32`); the
table is a `sessionStorage` echo of invites made in this tab
(`../web/src/routes/workspace/members/memberStore.ts:57,77`).

**Decision.**

```
GET /api/workspaces/{tenantId}/members
  headers: X-Tenant-Id + X-User-Id
  200 -> { members: [ { id, email, displayName, role, status, invitedAt } ] }
  403 when the caller holds no membership in {tenantId}
```

- Ordinary tenant-scoped read: `BeginScope(tenantId)`, join
  `workspace_user` × `workspace_membership` × `workspace_role` — the join
  already exists at `WorkspaceRoleResolver.cs:104-114` and should be reused,
  not re-written.
- **`status` is derived, not stored**: `WorkspaceUser.ExternalSubjectId is
  null` → `"Invited"`, else `"Active"` (`WorkspaceUser.cs:16-17,30` — the
  column is nullable precisely because "a row exists once a workspace admin
  invites someone by email, before that person has ever signed in"). This
  matches the prototype's `Invited`/`Active` values (`app.jsx:133-134`) with
  **no new column**. Recording it as a stored enum would create a second
  source of truth that `LinkSignInAsync` would have to keep in step.
- **Authorization is membership, not a role header**: any member may read the
  roster (OQ-w14-005's assumption); a non-member gets 403. The caller's own
  role comes from the same join. `X-Role` / `X-Workspace-Role` must **not**
  be consulted here — security-architect's call to confirm.

**ADR action.** `none — tenant-scoped read fully covered by ADR-009; the
read model is ADR-025's.` (The intake suggested amending ADR-009 here; I
think that is unnecessary — nothing about this endpoint is new to ADR-009.
Recording my dissent so the table can settle it.)

**Consequences.** Files: `WorkspaceEndpointExtensions.cs`, a
`ListMembersAsync` on `WorkspaceMembershipService`. No migration. OpenAPI +
`listWorkspaceMembers` in `client.ts`. A user holding two memberships (the
invite flow permits it, `WorkspaceMembershipService.cs:53-54`) appears once
with the highest role, using `WorkspaceRoleClaimResolver`'s existing
precedence rather than a second ordering — the same rule
`WorkspaceRoleResolver.cs:101-103,116-118` already applies.

## 5. NW-58 — invitation lifecycle

The largest item, and the one where my seat's answer has to dovetail with
four others. I own: the entity, the migration, the endpoints, the contract,
and the mailer seam. I do **not** own the token's crypto (security), the mail
transport (cloud), the copy (ux-ui), or whether email is in pilot scope
(product-owner, OQ-w14-002).

**Today.**

- `POST …/invites` → `InviteAsync` writes `workspace_user` (`:80-88`) **and
  `workspace_membership` (`:98-105`) immediately**. No token, no expiry, no
  accept URL.
- `LinkSignInAsync` (`:118-145`) + `WorkspaceSignIn.ResolveSignedInUser`
  (`WorkspaceSignIn.cs:28-44`) implement first-sign-in linking, but **no host
  endpoint calls them** — they exist only in tests.
- No membership `DELETE` anywhere (only `DocumentsEndpointExtensions.cs:87`).
- No mail transport in the repo at all.

### 5.1 A finding the intake did not have

Because `InviteAsync` writes the membership **at invite time**, once NW-01
ships keyed on email, **an invited person gains full access to the workspace
without ever clicking the link** — their `X-User-Id` matches
`workspace_user.email` on the row the invite just created. That silently
contradicts NW-58's own sentence ("clicks it, **signs in**, and **joins**
that workspace") and hands out access to any address an Admin typos.

**Decision: membership moves to accept time.** `InviteAsync` writes the
`workspace_invitation` row only. `workspace_user` + `workspace_membership` are
written by the accept path. This is a **behaviour change to an existing
service with existing tests** (`WorkspaceSignInTests`, and the invite tests
that assert the membership row) — it must be called out in the task, not
discovered during implementation.

### 5.2 The token carries its tenant — so accept needs no second cross-tenant path

Accept is called by someone who is not yet a member of that tenant and holds
only a token. Looking an invitation up by token hash alone would be a *second*
cross-tenant read, and I am not spending §0's exception twice.

**Decision: the token is `{tenantId:N}.{secret}`** where `secret` is 32 bytes
of CSPRNG, base64url. The server splits on `.`, `BeginScope(tenantId)`, then
matches `token_hash` **inside** that scope. The tenant id is not a secret (it
is already in route paths today); the secret half is the entire credential.
`workspace_invitation` is therefore a **completely ordinary tenant-scoped
table with the standard `tenant_isolation` policy** — no new isolation axis,
no exception, nothing for the security seat to re-litigate.

Stored: `token_hash` only (SHA-256 of the secret half), never plaintext.
Single-use via a conditional update on `accepted_at`. Expiry via `expires_at`.
Revocation via `revoked_at`. Signing-key questions (if security prefers an
HMAC over a hash, ADR-011 / Key Vault) are **security-architect's** to settle —
my contract is unchanged either way, and I have kept the column named
`token_hash` so an HMAC fits without a migration.

### 5.3 Schema

`workspace_invitation` (new, tenant-scoped, in `Contigo.Identity.Workspace`):

| Column | Type | Null | Note |
|---|---|---|---|
| `id` | uuid | no | PK, `ValueGeneratedNever` per house style |
| `tenant_id` | uuid | no | RLS axis; plain index, per `WorkspaceUserConfiguration.cs:24` |
| `email` | varchar(320) | no | RFC 5321, matching `workspace_user.email` |
| `role` | varchar(30) | no | enum-as-string, matching `workspace_role.name` |
| `token_hash` | varchar(128) | no | unique with tenant — `(tenant_id, token_hash)` |
| `expires_at` | timestamptz | no | |
| `created_at` | timestamptz | no | |
| `created_by` | varchar(320) | no | the inviting identity |
| `accepted_at` | timestamptz | **yes** | null until accepted |
| `revoked_at` | timestamptz | **yes** | null until revoked |

Indexes follow the established tenant-first composite-unique convention
(`WorkspaceUserConfiguration.cs:29`, `suppliers.sql:37`, `quotes.sql:233`):
`(tenant_id, token_hash)` unique, plus a plain `tenant_id` index, plus
`(tenant_id, email)` **non-unique** — a person may legitimately be invited
again after removal, which is NW-58's own requirement.

Every column is either NOT NULL with a value always supplied, or nullable.
**No NOT NULL column without a default is added to an existing table** — the
`quotes.sql:188` precedent and the warning at `QuoteLineConfiguration.cs:45-49`
(EF backfills a new NOT NULL enum-as-string with `""`, which the converter
then cannot parse) apply to NW-24, not here, since this is a new table.

### 5.4 Endpoints

```
POST   /api/workspaces/{tenantId}/invites          (exists; behaviour changes)
  201 -> { id, email, role, expiresAt, acceptUrl, mailDelivered: boolean }
GET    /api/invites/{token}                        (new, unauthenticated)
  200 -> { workspaceName, email, role, expiresAt }   // nothing else, ever
DELETE /api/workspaces/{tenantId}/invites/{id}     (new, Admin — revoke)
POST   /api/invites/{token}/accept                 (new)
  200 -> { workspaceId, workspaceName, role }
DELETE /api/workspaces/{tenantId}/members/{membershipId}  (new, Admin)
```

- `GET /api/invites/{token}` returns **only** the workspace *name*, the
  invited email and the role. No member list, no counts, no ids beyond what
  the invitee needs to recognise the invitation. A token must not become a
  read primitive for tenant data — security-architect's constraint, and I have
  shaped the response to satisfy it up front.
- `POST /api/invites/{token}/accept` requires `X-User-Id`, verifies the token
  is unexpired/unaccepted/unrevoked, then inside the tenant scope creates or
  reuses the `workspace_user`, calls the **already-written**
  `LinkSignInAsync`/`WorkspaceSignIn.ResolveSignedInUser` path
  (`WorkspaceSignIn.cs:28-44`) to bind the subject, writes the membership,
  and stamps `accepted_at` — one `SaveChangesAsync`.
  Note `ResolveSignedInUser` currently **fails** when no invite row exists for
  the email (`:37-41`); the accept path creates the `workspace_user` first, so
  that guard is satisfied rather than weakened.
- `DELETE …/members/{membershipId}`: **last-Admin guard**. Refuse (409) when
  removing the row would leave the workspace with zero Admin memberships. Per
  house style this is a *pure* function in `Domain` — a
  `WorkspaceMembershipRemoval.CanRemove(...)` beside `WorkspaceSignIn` and
  `WorkspaceMembershipFactory`, provable with in-memory objects and no
  database (`WorkspaceMembershipFactory.cs:10-14` states that convention).
  Removal deletes the `workspace_membership` row and **keeps** the
  `workspace_user` row. Note the FK is `ON DELETE CASCADE` from user to
  membership (`WorkspaceMembershipConfiguration.cs:30-33`; SQL `:61`) — so
  deleting the *user* would silently remove every membership. Delete the
  membership, never the user.
- Re-invite after removal works with no special case: `InviteAsync`'s
  duplicate check is on `(WorkspaceUserId, WorkspaceRoleId)`
  (`WorkspaceMembershipService.cs:90-96`, index at
  `WorkspaceMembershipConfiguration.cs:25`), and once the membership row is
  gone a fresh invitation is legal at the same role.

## 6. NW-24 — workspace currency / region

**Today.** `WorkspaceTenant` has `Name` + `CreatedAt` and nothing else
(`WorkspaceTenant.cs:24-29`); the create form submits `{ name }` only
(`WorkspacePickerScreen.tsx:60-90`); the web type carries a
`currencyRegion?` that is never populated (`workspaceStore.ts:47-55`).

**Decision.** Add to `workspace`:

| Column | Type | Null | Note |
|---|---|---|---|
| `country` | varchar(2) | **yes** | ISO 3166-1 alpha-2 |
| `currency` | varchar(3) | **yes** | ISO 4217 alpha-3 |
| `industry` | varchar(120) | **yes** | optional free text (pilot §2 "industria") |

`QuoteLineConfiguration.cs:45-49`. The API renders a missing value as absent

stored currency (OQ-w14-004's assumption, which I adopt). "Region" in the
prototype's `"CHF · eu-west"` is a *business* region; it does **not** touch
ADR-006 (`northeurope` stays). I read the design string as country/region +
currency, and I am modelling `country`; whether the picker renders `eu-west`
or `CH` is ux-ui-designer's row.

`POST /api/workspaces` accepts the three optional fields; `GET /api/workspaces`
returns them (§2).

**ADR action.** **`amend ADR-003`** — new columns on `workspace`, migration +
regenerated idempotent script. **I own ADR-003 and write this footer.**
ADR-003's existing rule already binds me: *"Database changes MUST be expressed
as EF Core migrations (no hand-edited DDL drift)"* (`ADR-003-data-store.md:53`).

## 7. The identity seam (OQ-w14-001) — my position

The raw file's own order puts W15 (JWT) before W14, with the fallback *"W14
can land membership using `X-User-Id` as an interim if JWT slips."* This run
**is** w14 and NW-05 is queued for W15, so the fallback is in force.

- Regenerate with **`npm run generate:api`** from `web/`

  runs as step 1 of `npm run build`.

  `$ref` nor `oneOf`, only flat `properties`, and it checks `enum` *before*

  wave is the first to add many endpoints at once. **delivery-manager's row** —
  I raise it, I do not own the workflow.

## 11. CORRECTION to §2 and §8.1 — the `app.identity_key` GUC cannot be inlined

Found while verifying this draft against the code (§12). It changes the
implementation of my own option D and it is **not cosmetic**.

`TenantRlsConnectionInterceptor` builds its GUC statement by **string
interpolation**, and its own comment says why that is acceptable
(`TenantRlsConnectionInterceptor.cs:103-107`):

> *"Postgres `SET`/custom GUCs do not accept bind parameters. TenantId wraps a
> Guid, whose "D" format is constrained to hex digits and hyphens, so inlining
> it here carries no injection risk."*

The safety argument rests entirely on **the value being a Guid**. It does not
transfer to `app.identity_key`, whose value is an email or token subject
arriving as free text in the `X-User-Id` header (§7). Extending
`BuildSetCommandText` to the identity key by analogy would emit:

```
SET app.identity_key = '<attacker-controlled string>'
```

**Why this is a tenant-isolation bypass, not a lint issue.** The statement runs
on the same connection that carries `app.tenant_id` — the RLS claim itself. A
header of the form `X-User-Id: x'; SET app.tenant_id = '<victim-tenant-guid>'; --`
would set the connection's tenant claim to another tenant, and every
subsequent RLS-scoped read in that request would return the victim's rows.
That is precisely the "cross-tenant query path" ADR-009 `:12-13` declares
unacceptable. A naive implementation of option D therefore converts a request
header into the exact hole the whole ADR exists to close.

**Normative decision, to be a clause in ADR-025.**

1. Set the identity GUC with a **real bind parameter** via the function form —
   `SELECT set_config('app.identity_key', @identityKey, false)` with a
   `DbParameter` — **never** string interpolation. `set_config` is an ordinary
   function call, so it accepts parameters where the `SET` *statement* cannot.
   This is the reason the two GUCs are written by two different mechanisms, and
   the asymmetry must be commented in the interceptor so a later reader does
   not "tidy" it back into `SET`.
2. Third argument is **`false`** (session-scoped), mirroring `SET`'s existing
   semantics and the reset-on-close model. `true` would be transaction-local
   and would silently vanish for the discovery query.
3. `RESET app.identity_key` in `ConnectionClosing`/`ConnectionClosingAsync`
   alongside the tenant reset (`:78-101`) — same pooled-connection-leak reason.
4. **Defence in depth, not the primary control**: normalise and validate the
   identity key before it reaches the connection — trim, lower-case (§2's
   case-folding decision already requires this), length ≤ 320, reject control
   characters. The bind parameter is what makes it safe; validation is what
   makes it observable.
5. `grep` confirms there is **no existing `set_config` call in `backend/src`** —
   all 116 `current_setting`/`set_config` hits are `current_setting` inside
   policies and tests. This is a new pattern in the codebase and must be
   introduced deliberately, in the interceptor task, with a test.

**Consequence for the decomposition.** The interceptor task (§8.1 risk #1) must
carry an explicit negative test: an identity key containing `'`, `;` and `--`
must not alter `app.tenant_id` on that connection. Without that test this
correction is an assertion, not a guarantee. The task stays ranked first and
stays alone in its phase.

**Reconciliation.** This is my proposal in my own lane, but it lands on the
tenant-isolation boundary that **security-architect owns** (ADR-009). I bring
it to the table as a clause for their ratification; if they prefer it as a
footer on ADR-009 rather than a section of ADR-025, I yield the location and
keep the substance.
