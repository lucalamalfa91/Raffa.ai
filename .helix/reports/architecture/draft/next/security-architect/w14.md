## §0. Findings the intake did not have

All five are read off this checkout and all five are load-bearing.

### F1 — `POST /api/workspaces/{tenantId}/invites` has no authorization at all

`../backend/src/Raffa.Api/WorkspaceEndpointExtensions.cs:59-97`
(`InviteAsync`) takes `string tenantId` from the **route**, an
`InviteRequest`, the `WorkspaceMembershipService` and a `CancellationToken`
— and nothing else. It never receives an `HttpContext`, never calls
`WorkspaceRoleResolver`, never checks a claim, a header or a membership row.
`MapPost` at `:32` attaches no authorization metadata; the host wires no auth
middleware at all
(`../backend/src/Raffa.Identity.Workspace/Domain/WorkspacePrincipalAuthorization.cs:14-17`
states it in prose: "nothing in this codebase wires
`AddAuthentication`/`AddJwtBearer` yet (`Raffa.Api`'s host has no auth
middleware)").

So today: **anyone who can reach the API and knows or guesses a tenant GUID
can invite an arbitrary email address into that tenant as `Admin`** — the
role comes straight from the request body via
`WorkspaceRoleClaimResolver.TryResolve(request.Role, …)` at `:75`, with
`Admin` among the five accepted values (`:78`).
`WorkspaceMembershipService.InviteAsync` then writes a real `workspace_user`
row (`:80-88`) **and a live `workspace_membership` row** (`:98-105`) — an
invite today is an immediate grant, not a pending offer. That is what makes
F1 severe rather than theoretical.

Why it has been survivable and why it stops being survivable **in this
wave**: today an unauthorized membership row is inert, because workspace
discovery is a `localStorage` array in one browser
(`../web/src/routes/signin/workspaceStore.ts:32,88-106`) and
`WorkspaceRoleResolver`'s membership branch is the *third* source consulted.
The moment **NW-02** writes real membership rows and **NW-01** turns
membership into the discovery mechanism, that inert row becomes a **working
cross-tenant join path**: the attacker's own address, self-invited as Admin,
appears in their picker and carries Admin rights over another customer's
contracts.

**Consequence for the wave**: NW-01 and NW-02 must not merge before the
invite endpoint is authorized. This is not a "hardening later" item — it is
created *by* this wave's own success. Rule in §5.1, status matrix in §B,
regression test T3 in §C. If the decomposer cuts scope, this is the one
thing that cannot be cut, and it is cheap: one resolver call and one guard.

### F2 — the RLS tenant claim is set once per **connection open**, not per scope

`../backend/src/Raffa.SharedKernel/Tenancy/TenantRlsConnectionInterceptor.cs:22-35`
sets `app.tenant_id` in `ConnectionOpened`/`ConnectionOpenedAsync`, reading
`ITenantContext.Current` at that instant, and `RESET`s it in
`ConnectionClosing`/`ConnectionClosingAsync` (`:37-49`). It never re-reads
the scope while a connection stays open.

Two consequences that decide NW-01's shape:

1. **No tenant claim ⇒ zero rows, and no insert.** With no active scope the
   claim is left unset (`:53-57`, `:66-70`, documented `:15-16` "fail
   closed"), so
   `tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid`
   evaluates to `tenant_id = NULL` → NULL → not true. Every policy in
   `../backend/src/Raffa.Identity.Workspace/Migrations/Scripts/identity-workspace.sql:143-182`
   denies the row. **A "list the workspaces I belong to" query therefore
   returns nothing under the policies that exist today** — the caller's
   tenant is precisely the unknown the endpoint exists to discover. NW-01 is
   an RLS design decision, not an endpoint task.
2. **A nested `BeginScope` on an already-open connection is silently
   ineffective.** `WorkspaceMembershipService` and
   `WorkspaceProvisioningService` open a scope per call
   (`WorkspaceMembershipService.cs:62,124`,
   `WorkspaceProvisioningService.cs:42`) and are correct only because each
   call opens and closes its own connection. Any code that holds a
   connection open (an explicit transaction, an enumerated-but-not-disposed
   query) and then enters a second tenant's scope keeps running under the
   **first** tenant's claim. That is a cross-tenant read RLS will not catch,
   because the claim it is enforcing is the stale one. Rule in §4.3, test T6
   in §C.

### F3 — ADR-009's own interface contract says **one scope per request**

**New in revision 2, and it governs NW-01.**
`../backend/src/Raffa.SharedKernel/Tenancy/ITenantContext.cs:20-26`:

> "Enters a tenant scope for the remainder of the current async call chain.
> … **ADR-009 expects exactly one scope per request/worker job; nested
> scopes are supported (the previous value is restored on dispose) but are
> not the expected usage.**"

NW-01's chosen shape (§3.2) is a **loop of one scope per candidate tenant**
— N scopes in one request. That is not nesting and it is not unsafe, but it
*is* outside the documented expected usage, and the first reviewer to read
`ITenantContext.cs:23-24` will correctly call NW-01 non-compliant with
ADR-009 unless the ADR says otherwise.

**Consequence**: the ADR-009 amendment must **name the discovery request as
a sanctioned exception** and state its rules (§3.2g), rather than leaving
"one scope per request" as an unqualified expectation the wave then breaks
in silence. An undocumented exception is how the next reviewer learns the
wrong lesson — that the rule is soft. It is not soft; it has exactly one
named exception.

### F4 — the DB already enforces two of the invariants revision 1 asked for

**New in revision 2.** Reading the full migration script rather than the
policy block alone:

- `identity-workspace.sql:90` —
  `CREATE UNIQUE INDEX ix_workspace_membership_workspace_user_id_workspace_role_id
  ON workspace_membership (workspace_user_id, workspace_role_id)`.
  Rule 5.3d demanded "uniqueness enforced by a DB constraint, not only by
  application logic — two concurrent accepts must not both insert". **That
  constraint already exists.** Two concurrent accepts of the same invitation
  produce one row and one unique-violation, with no new migration.
- `identity-workspace.sql:125` —
  `CREATE UNIQUE INDEX ix_workspace_user_tenant_id_external_subject_id
  ON workspace_user (tenant_id, external_subject_id)`. Two `workspace_user`
  rows in one tenant cannot bind the same Entra subject. `external_subject_id`
  is nullable (`:42`) and Postgres treats NULLs as distinct in a unique
  index, so any number of invited-but-not-yet-signed-in rows coexist — the
  constraint binds only once a real subject lands.

This matters beyond bookkeeping: it means the accept path's race safety is a
**property of the schema that exists**, not a new thing to get right, and
the task should assert it rather than re-implement it. `identity-workspace.sql:69`
(`UNIQUE INDEX ix_workspace_tenant_id ON workspace (tenant_id)`) likewise
confirms the "the workspace row *is* the first row of its own tenant"
invariant that §2.2 depends on.

### F5 — a *pending* invitation breaks `LinkSignInAsync` as revision 1 specified it

**New in revision 2. This is a correction, not a refinement — revision 1's
Rule 5.3c would have shipped an accept path that always fails.**

`../backend/src/Raffa.Identity.Workspace/Domain/WorkspaceSignIn.cs:36-41`
(`ResolveSignedInUser`) **fails** when neither an
`existingByExternalSubject` nor an `existingByEmail` `workspace_user` row is
found:

> "no workspace invite was found for this email in this tenant; sign-in
> cannot provision a new workspace user."

Its doc comment (`:23-25`) states the invariant deliberately: "only an
admin's invite … creates a `WorkspaceUser` row; self-service join is out of
this task's scope." That is a **security-positive** property and I want to
keep it.

But NW-58's whole point is that an invitation becomes *pending* — the
invitee "stays a member until an Admin removes them", and "re-adding them
needs a new invite", which only makes sense if invitation ≠ membership.
Revision 1's Rule 5.3c said accept should "bind the Entra subject to the
invited `workspace_user` row via `LinkSignInAsync`". If the new invitation
flow stops eagerly writing `workspace_user`, there is no row to bind and
`LinkSignInAsync` returns `Failure` on **every** accept.

**Decision (Rule 5.3c, corrected).** Invite writes `workspace_user` **with
no membership** plus the new `workspace_invitation` row; membership is
written **only at accept**. Consequences, all of which are wanted anyway:

- `LinkSignInAsync`/`ResolveSignedInUser` keep working **unchanged**, and
  `WorkspaceSignIn`'s "sign-in never provisions a user" invariant stays
  literally true.
- NW-04's `status` column becomes derivable with no extra state: a
  `workspace_user` row with a live invitation and **no** membership renders
  `Invited`; with a membership it renders `Active`. That is exactly the pair
  the design requires (`screens-v2.md` §10, `app.jsx:133-134`).
- The only cost is that an invited-but-never-accepted email exists as a row
  inside that tenant — visible to members only, which is already true today
  and is precisely what the Members table is for (§4.1d bounds it).

The alternative (invitation row only; accept provisions the user) forces a
change to `WorkspaceSignIn`'s contract to permit self-provisioning, which is
a strictly weaker security posture for no product gain. **Rejected.**

## §A. The identity seam (OQ-w14-001 — answered)

**Decision.** In w14 the membership key is the interim `X-User-Id` (the MSAL
account username the web already sends on every call —
`../web/src/api/client.ts:49-54` builds the header and `:1276,1321,1367,1397,1431,1469,1513`
and every other method spread it uniformly), resolved in **exactly one
place** so that NW-05 (W15) replaces it with the token subject by editing one
file.

The seam already half-exists:
`../backend/src/Raffa.Api/Infrastructure/WorkspaceRoleResolver.cs:85-119`
(`ResolveMembershipRoleAsync`) reads `X-User-Id` (`:88-97`) and matches it
against `workspace_user.Email` **or** `workspace_user.ExternalSubjectId`
(`:111`) — exactly the shape that survives the swap, because ADR-010's
`sub`/`oid` lands in `ExternalSubjectId` via
`WorkspaceSignIn.ResolveSignedInUser` and
`WorkspaceMembershipService.LinkSignInAsync:118-145`.

What w14 must add: the four new/changed write paths (create, invite, accept,
remove) need the *identity itself*, not only a role. They must not each read
`Headers["X-User-Id"]` — that is four retirement sites instead of one.

- **Rule A1.** One resolution point returns the caller's identity
  (`ICallerIdentity`/`CallerIdentity.TryResolve`, naming is
  software-architect's). Create, invite, accept, remove, and
  `WorkspaceRoleResolver`'s membership branch all consume it. `Grep` for
  `"X-User-Id"` in `backend/src` after the wave must find it in **one** file
  besides the existing document/conversation readers that NW-05/NW-32
  retire.
- **Rule A2.** The interim identity is never trusted for anything except
  *which membership rows to look up*. It confers no role, no tenant and no
  scope by itself. A request with `X-User-Id: <anything>` and no membership
  row for the target tenant is a non-member (§B).
- **Rule A3 (retirement).** `X-User-Id` is removed by **NW-05 (W15)**. The
  retirement test is written now and skipped/inverted then: with a validated
  token present, the header must be **ignored entirely**, not merely
  overridden — a request carrying token `A` and `X-User-Id: B` acts as `A`
  and never as `B`.

**Assumption in force** (matches OQ-w14-001): W15 has not landed, so the raw
file's own fallback ("W14 can land membership using `X-User-Id` as an interim
if JWT slips") applies. If the operator lands NW-05 first, Rule A1's single
seam is where the two orders meet and nothing else in this draft changes.

## §B. Status-code matrix (the rejection contract)

Endpoint *shapes* are the software-architect's; **which rejection and which
status** is mine. One table so no task invents its own.

| Situation | Status | Why this one |
|---|---|---|
| No identity presented (`X-User-Id` absent or blank) on create / invite / accept / remove | **401** | "Authenticate", not "fix your body". The web must re-run MSAL, not retry. ADR-022 makes the header the identity-presentation mechanism, so absence = unauthenticated. Matches `AuditEndpointExtensions.cs:33-34`, which already maps `Unauthenticated` → 401. |
| Identity presented but malformed | **400** | A well-formed refusal of a malformed input; no auth action would help. |
| Caller is **not a member** of the target tenant (invite / members / remove / any membership-scoped route) | **404** | Deliberate: a 403 on a tenant id you do not belong to is a **tenant-existence oracle**. A non-member must not be able to distinguish "exists, you are out" from "does not exist". |
| Caller **is** a member but lacks the role (invite, remove, `DELETE /api/documents/{id}`, `POST …/reprocess`) | **403** | The caller legitimately sees the tenant; only the action is denied. Preserves today's documented behaviour (`DocumentsEndpointExtensions.cs:53-55`, R-DOC-07/R-DOC-10). |
| Any member reads the roster | **200** | §4.1 (OQ-w14-005). |
| Removing the **last** Admin (including self) | **409** | Well-formed and authorized, but violates a tenant invariant. |
| Accept: token unknown, revoked, or already consumed by a *different* identity | **404** | No oracle for token validity beyond what the holder already knows. |
| Accept: token found but **expired** | **410** | The one disclosure worth making: it lets the UI say "expired — ask your Admin for a new one" instead of a dead end. Safe because the token is 256-bit unguessable, so reaching this branch already proves possession. |
| Accept: token already accepted by **this** identity | **409** | Idempotency signal, not an error state for the user. |
| Accept: signed-in identity's email ≠ invited email | **403** | §5.3. Distinct, non-enumerating reason ("this invitation was issued for a different address"), never echoing the invited address. |
| Crafted `X-Tenant-Id` for a tenant the caller does not belong to, on a **read** | **404** | RLS yields no rows (F2.1) → not found. Satisfies acceptance **N5** ("403/404"). |

- **Rule B1.** No path in this wave returns 403 where the caller is not a
  member. Non-membership is always 404. This is the single sentence a
  reviewer should check every new endpoint against.
- **Rule B2 (why this does not contradict `GET /api/audit`).**
  `AuditEndpointExtensions.cs:30-36` returns **403**, not 404, for a
  role failure — and that is correct there, because its tenant comes from
  the caller's own authorized claim, never from a route or header (its own
  comment, `:25-29`: "a `?tenantId=` here would be exactly the cross-tenant
  query path ADR-009 forbids"). With no caller-supplied tenant there is
  nothing to enumerate and no oracle to open. Rule B1 binds routes that
  **take a tenant id from the caller**; audit does not, and stays as it is.

## §1. NW-14 — Delete and Retry 403 for the workspace creator

**Item**: `w14-requirements.md` → NW-14. Seats: security-architect,
client-architect. Acceptance **N9**.

### 1.1 The rule

Authorization for an Admin-only action resolves from, in order:

1. **Role claims** on an authenticated principal
   (`WorkspaceRoleResolver.cs:50-55`, via `WorkspaceRoleClaimResolver`) —
   the ADR-010 end state.
2. **The `workspace_membership` row** for the caller's identity in the
   target tenant (`:85-119`).

**Nothing else.** `X-Role` and `X-Workspace-Role` (`:37-38`, read at
`:70-83`) are **no longer admissible for an authorization decision**.

### 1.2 Why this is safe to do now, not later

`Grep` over `../web/src` for `X-Role|X-Workspace-Role` returns **zero
matches**: `../web/src/api/client.ts` sends `X-Tenant-Id` and `X-User-Id`
uniformly (`:49-54`, `:1276`ff) and no role header anywhere. Demoting the
header therefore breaks **no** existing client. The only reader that keeps it
is `../backend/src/Raffa.Api/CapabilitiesEndpointExtensions.cs:54`
(`GET /api/capabilities`), which shapes UI affordances and grants no data
access.

That endpoint's own doc comment already draws the exact line this rule
codifies (`:44-48`): it "fails closed on the 'show admin entries' axis
specifically … **never a hard 401/403 the way `AuditEndpointExtensions` is,
since the catalog itself is not sensitive, tenant data**." So Rule 1.2a is a
**restatement of a convention this codebase already holds**, not a new
constraint imposed on it — which is why it costs nothing to adopt and why
letting the header drift into an authz decision would be the actual
regression.

- **Rule 1.2a.** The header role is admissible **only** for
  non-authoritative UI shaping (`/api/capabilities`). It is never consulted
  by `IsAdminAsync` (`WorkspaceRoleResolver.cs:66-68`) or by any endpoint
  guard.
- **Rule 1.2b.** Where header and membership disagree, **membership wins**,
  in both directions: a header claiming `Admin` never grants, and a header
  claiming `Procurement` never revokes a real Admin's rights.
- **Rule 1.2c.** This directly executes NW-14's own raw instruction — "Do
  not 'fix' this by sending a spoofable `X-Role: Admin` from the SPA as the
  product solution."

**Implementation note for the software-architect.** Demoting the header is a
deletion, not an addition: `ResolveAsync`'s middle branch (`:57-60`) is
removed so the order becomes claims → membership. `TryResolveHeaderRole`
(`:70-83`) then has one caller left (`/api/capabilities`) or moves there.

### 1.3 What actually fixes N9

No new backend authorization code. Once **NW-02** writes the creator's
membership row, `ResolveMembershipRoleAsync`'s join (`:104-114`) returns
`Admin` and the existing gate passes. NW-14 is therefore a **proof** task,
not a fix task: an API test that creates a workspace and then deletes a
document as the creator (204) and reprocesses one (200), plus the
Procurement-still-403 regression.

The web half is client-architect's: `isAdmin` comes from the role on NW-01's
payload, not from `resolveWorkspaceRole()`'s `?role=` inference
(`../web/src/components/shell/workspaceRole.ts:36-47`, which mirrors
`?role=` into `sessionStorage` at `:42` and **defaults to `"admin"`** at
`:46` for whoever picked the workspace in this browser). That file's own doc
comment (`:24-28`) confirms the swap is a one-function change: "Once
ADR-010's JWT/claim wiring lands, only this function's body changes." I do
not own the button; I own the fact that the server must not believe it.

### 1.4 Interim mechanism → retirement

| Mechanism | w14 | Removed by |
|---|---|---|
| `X-Role` / `X-Workspace-Role` as authz | **demoted now** (UI shaping only) | NW-31 (W15) deletes the alias and the reader |
| `X-Tenant-Id` as the tenant of a membership route | tenant comes from the **route**, membership verified | NW-05 (W15) |
| `X-User-Id` as identity | §A | NW-05 (W15) |
| ADR-022 fixture/demo auth | unchanged this wave | out of w14 scope |

### 1.5 ADR action

**amend ADR-022** — the interim posture is narrowed: a client-declared role
header is not an authorization source; membership is. ADR-022's body and
`Status: accepted` stay untouched.

## §2. NW-02 — Create workspace writes the creator's membership (Admin)

**Item**: NW-02. Seats: software-architect, security-architect. Acceptance
**N1**.

### 2.1 The rule

- **Rule 2.1a.** `POST /api/workspaces` requires a **presented identity**;
  absent → **401** (§B). This is a change of posture from today's
  deliberately anonymous signup step (`WorkspaceEndpointExtensions.cs:17-18`:
  "Workspace creation is the pre-authentication signup step (nobody has a
  tenant claim yet, by definition)"): the endpoint now writes an
  identity-keyed grant, so it cannot be anonymous. (The intake's task sketch
  says 400; I rule **401 for absence, 400 for malformed**. If the
  software-architect prefers 400 uniformly I will `PROPOSE`, not `OBJECT` —
  the split is a client-behaviour nicety, the *requirement* is that it is
  refused.)
- **Rule 2.1b.** The creator becomes `Admin` **of the tenant they just
  created, by virtue of creating it**. The request body's role, if any, is
  **ignored** — never honoured. There is no self-assignable role anywhere in
  this wave.
- **Rule 2.1c.** Creating a tenant grants no read of any existing tenant.
  The response carries only the new tenant's own id/name/createdAt — which
  is what `:51-56` already returns.

### 2.2 RLS consequence

Three inserts (`workspace`, `workspace_user`, `workspace_membership`) plus
the role catalog must all land **inside one `BeginScope(workspace.TenantId)`
and one `SaveChangesAsync`**. `WorkspaceProvisioningService.cs:42-46`
already opens that scope for the right reason — its doc comment (`:17-21`)
states the invariant: the workspace row *is* the first row of its own tenant
(enforced by `UNIQUE INDEX ix_workspace_tenant_id`,
`identity-workspace.sql:69`), and RLS `WITH CHECK`
(`identity-workspace.sql:145-147`) only accepts a write whose `tenant_id`
equals the connection's claim.

- **Rule 2.2a.** One scope, one save, one transaction. A partial bootstrap
  (workspace without membership) is exactly today's bug; it must not be
  reachable by a failure path either.
- **Rule 2.2b.** No new table. `workspace_user` and `workspace_membership`
  already carry `tenant_id` and already have `tenant_isolation` policies
  with both `USING` and `WITH CHECK` (`identity-workspace.sql:154-158`,
  `:176-180`) — nothing to add, and nothing may be relaxed to make the
  bootstrap fit.
- **Rule 2.2c.** This is the one write path that stays **one scope per
  request** in the strict `ITenantContext.cs:23` sense. F3's exception is
  for discovery reads only; bootstrap does not need it and must not use it.

### 2.3 Backfill of existing `dev` workspaces

Existing `dev` tenants have no membership row. The intake left the choice
open. **Security ruling**: a "claim this workspace" endpoint is a
**tenant-takeover primitive** (whoever calls it first becomes Admin of a
tenant holding another user's uploads) and is refused. The backfill is an
**operator/CI job** that inserts the membership from a known
(tenant id, email) pair supplied by the operator at HITL, audited as
`workspace.membership.backfilled` with the operator as actor. If no pair is
known for a tenant, that tenant stays unclaimed — a stale `dev` tenant is a
smaller problem than a takeover path.

### 2.4 ADR action

**amend ADR-009** — the membership + user rows are part of tenant bootstrap,
written under the new tenant's own claim in one transaction; the "first row
of a tenant is the workspace row" invariant is recorded as the reason.

## §3. NW-01 — `GET /api/workspaces` for the signed-in identity

**Item**: NW-01. Seats: software-architect, security-architect,
client-architect. Acceptance **N2, N4, N5**.

This is the hardest security decision of the wave, because of F2.1: under
the policies that exist, a caller with no tenant claim sees **nothing**, and
the caller's tenant is the unknown being discovered.

### 3.1 Options considered

1. **A cross-tenant directory table without RLS** (keyed on identity
   subject, no `tenant_id`, like ADR-024's `market_embedding`).
   **Rejected**: a second source of truth for membership that RLS does not
   protect, guaranteed to drift from `workspace_membership`, and the drift
   direction is "still listed after removal".
2. **Run the discovery query as a role with `BYPASSRLS`.** **Rejected
   outright** — ADR-009 `:57`, verbatim: "No query may run under
   `BYPASSRLS`/superuser in the [application path]."
3. **Identity-keyed permissive `SELECT` policies on all four workspace
   tables**, each traversing to the identity. **Rejected**: four widened
   tables, a policy on `workspace_membership` that must subquery
   `workspace_membership`, and a predicate no reviewer can hold in their
   head. Clever RLS is how holes happen.
4. **One identity-keyed permissive `SELECT` policy on `workspace_user`
   only, then one tenant-scoped read per candidate.** **Chosen.**

### 3.2 Decision (option 4)

- **Rule 3.2a.** Add exactly **one** new policy, on `workspace_user`,
  `FOR SELECT` only, permissive (Postgres OR-s it with `tenant_isolation`):

  ```sql
  CREATE POLICY identity_self ON workspace_user
      FOR SELECT
      USING (
          nullif(current_setting('app.identity_subject', true), '') IS NOT NULL
          AND (
              lower(email) = lower(nullif(current_setting('app.identity_subject', true), ''))
              OR external_subject_id = nullif(current_setting('app.identity_subject', true), '')
          )
      );
  ```

  Three properties that make it safe, and each is a test:
  - **`FOR SELECT` only, no `WITH CHECK`** → it can never authorize a write.
    Cross-tenant inserts remain impossible.
  - **Fails closed on an empty/absent claim** → the `IS NOT NULL` guard
    means an unset `app.identity_subject` widens nothing (unlike a bare
    equality, where `NULL = NULL` is NULL but a careless `coalesce` would
    match every blank row).
  - **One table, one column pair** → the widening is auditable by reading
    six lines. `workspace`, `workspace_role`, `workspace_membership` keep
    exactly one policy each, unchanged.
- **Rule 3.2b.** A new GUC `app.identity_subject` is set by the same
  interceptor mechanism as `app.tenant_id`
  (`TenantRlsConnectionInterceptor.cs:20`, `:103-107`) and is `RESET` on
  connection close for the same pooled-connection reason (`:78-101`). It is
  set **only** for the discovery read. It must be bound as a value, or
  validated, before interpolation — unlike `TenantId` (a `Guid`, whose "D"
  format is "constrained to hex digits and hyphens, so inlining it here
  carries no injection risk", `:104-106`), an identity subject is
  **caller-controlled text**. Use `set_config('app.identity_subject', $1, false)`
  with a real parameter, never string interpolation. **This is a
  SQL-injection sink if anyone copies the `SET` pattern from the tenant
  claim**, and `BuildSetCommandText` is sitting right there to be copied.
- **Rule 3.2c.** The discovery read returns **candidate tenant ids only**.
  Every tenant *fact* — name, role, contract count, and NW-24's
  currency/country — is then read in a **per-tenant scoped read** under the
  normal `tenant_isolation` policy with that tenant's real claim.
- **Rule 3.2d (the removed-member trap).** A candidate tenant is included
  **only if a live `workspace_membership` row is confirmed in the
  per-tenant read**. A removed member keeps their `workspace_user` row (by
  design — audit continuity, and `LinkSignInAsync` needs it, F5), so a
  `workspace_user`-driven list would still show the tenant to someone who
  was removed. Membership, not user existence, is the grant.
- **Rule 3.2e.** Cap the candidate set (50 is generous for the pilot;
  memberships per identity are 1–2). Beyond the cap: return the cap, audit
  `workspace.list.truncated`. An unbounded loop keyed on caller-controlled
  identity is a DoS shape.
- **Rule 3.2f.** The response never contains a tenant the caller has no live
  membership in — not its name, not its count, not its id. `N5`'s crafted
  `X-Tenant-Id` cannot widen the list: the list is keyed on **identity**,
  and the tenant header is not an input to it at all.
- **Rule 3.2g (the F3 exception, stated so it stays one exception).**
  `GET /api/workspaces` is the **only** request in the product permitted to
  enter more than one tenant scope. Its rules:
  1. Scopes are entered **sequentially, never nested** — each disposed
     before the next is entered.
  2. Each per-tenant read runs on its **own connection** (F2.2), so the
     claim is established at open. No scope change inside an open
     transaction, ever.
  3. The multi-scope region is confined to one named service method, so a
     reviewer can find every scope entry in one file.
  4. Any *other* endpoint entering a second scope is a defect, not a
     precedent. Test T6 defends this; the ADR-009 amendment records it.

### 3.3 The count (NW-09 overlap)

NW-09 is software-architect + client-architect, not me, with one exception I
must state: the "validated contracts" count comes from another module's
RLS'd tables (`Raffa.Documents.Contracts`). **Rule 3.3a**: the count must
be produced by a **tenant-scoped read under that tenant's claim**, never by
a cross-tenant aggregate or a group-by over all tenants. A number is data —
"3 contracts" about a tenant you do not belong to is a disclosure.

### 3.4 Interim mechanism → retirement

`app.identity_subject` is **not** interim — it survives ADR-010, because
after NW-05 it carries the token's `sub`/`oid` instead of the header value.
Only its *source* changes, at the §A seam. That is deliberate: I am not
adding a mechanism that must be torn out. Note the policy already matches on
`external_subject_id` as well as `email` (Rule 3.2a), which is the column
`LinkSignInAsync` populates — so the swap needs no policy change either.

### 3.5 ADR action

**amend ADR-009** — records the `identity_self` policy as the single, named,
`SELECT`-only exception to "one policy per tenant table", its three safety
properties, the per-membership scoped read for every tenant fact, the
live-membership requirement (3.2d), the parameter-binding rule (3.2b), the
**multi-scope discovery exception (3.2g, F3)**, and the restatement that
`BYPASSRLS` stays forbidden.

## §4. NW-04 — `GET /api/workspaces/{tenantId}/members`

**Item**: NW-04. Seats: software-architect, security-architect,
client-architect. Acceptance **N3**.

### 4.1 The rule (OQ-w14-005 — answered)

- **Rule 4.1a.** **Any live member** of the tenant may read the roster
  (`name`, `email`, `role`, `status`). The design shows the roster to
  Procurement with a "request access" state
  (`inputs/design/prototypes/raffa-v2/screens-v2.md` §10), and a team of
  five cannot operate if only Admins can see who is in the workspace.
- **Rule 4.1b.** A **non-member gets 404** (§B, Rule B1) — never 403, never
  an empty 200. An empty 200 is also an oracle ("that tenant exists and is
  empty").
- **Rule 4.1c.** Only an **Admin** may invite (§5.1) or remove (§5.4).
  Read ≠ write.
- **Rule 4.1d (privacy).** Email addresses are personal data and are
  returned **only** to members of that tenant. No endpoint in this wave
  exposes an email to a non-member, and the pre-accept metadata endpoint
  exposes none at all (§5.3e).
- **Rule 4.1e (`status` is derived, not stored).** Per F5: no membership +
  live invitation → `Invited`; membership → `Active`. No third state is
  persisted, so the roster cannot disagree with the grant it describes.

### 4.2 RLS consequence

None new. The roster is a join over `workspace_user` × `workspace_membership`
× `workspace_role`, all three already RLS'd (`identity-workspace.sql:154-158`,
`:165-169`, `:176-180`), read under the route tenant's scope after
membership is confirmed.

- **Rule 4.2a.** The route tenant is entered as the scope **after** the
  caller's membership in it is verified. Verify, then scope, then read — not
  "scope and see what comes back", which turns an authorization question
  into an empty-result question and produces 200-with-nothing instead of
  404.
- **Rule 4.2b.** The `identity_self` policy of §3.2a must not make the
  roster read leak: it is `FOR SELECT` on `workspace_user` and matches only
  the **caller's own** rows, so at worst a caller sees their own user row in
  a tenant they are not scoped to — which the 404 in 4.1b prevents them from
  ever reaching, and which contains only their own address. Test T1c.

### 4.3 The connection-claim rule (F2.2)

- **Rule 4.3a.** A change of tenant scope takes effect only on a
  **connection opened after** the scope was entered
  (`TenantRlsConnectionInterceptor.cs:22-35`). Any code path that reads
  tenant A and then tenant B must let the connection close between the two
  (separate `DbContext`/unit of work per tenant), and must never enter a
  second scope inside an open transaction. NW-01's per-tenant loop (§3.2g)
  is the only sanctioned multi-scope path; NW-04's verify-then-scope stays
  single-scope.
- **Rule 4.3b.** Test T6 makes it a regression, not a convention.

### 4.4 ADR action

**amend ADR-009** — member list is tenant-scoped, verify-then-scope,
non-member is 404; plus Rule 4.3a as a general data-access rule (it is not
specific to this wave and the next new table will need it too).

## §5. NW-58 — Invitations: email + link, login joins that workspace, Admin remove requires a new invite

**Item**: NW-58. Seven seats. Acceptance **N3b**. This is where the new ADR
lives.

### 5.1 Issue an invitation

- **Rule 5.1a.** `POST /api/workspaces/{tenantId}/invites` requires: a
  presented identity (else **401**), live membership in the route tenant
  (else **404**), and the `Admin` role resolved per §1.1 (else **403**).
  **This closes F1 and is the highest-priority security task of the wave.**
- **Rule 5.1b.** The invited role comes from the body and may be any role in
  the catalog **including `Admin`** — an Admin may create another Admin.
  What is forbidden is a **non-Admin** reaching this endpoint at all, and
  any *self*-assignment (the caller's own role is never read from a body).
- **Rule 5.1c.** The tenant is the **route** value, verified against
  membership. `X-Tenant-Id` is not an input to this endpoint (today's
  version reads neither — the route is already right; only the guard is
  missing).
- **Rule 5.1d (F5).** Issuing writes `workspace_user` (if absent) **and the
  invitation row — not a membership**. The membership write moves to accept.
  This is the change that turns today's immediate grant
  (`WorkspaceMembershipService.cs:98-105`) into an offer.

### 5.2 The token

- **Rule 5.2a.** 256 bits from a CSPRNG
  (`System.Security.Cryptography.RandomNumberGenerator`), base64url-encoded.
  Never a GUID, never a counter, never derived from the email.
- **Rule 5.2b.** **Only a SHA-256 hash of the token is stored.** The token
  is not recoverable from the database, a backup, a log or an audit row. A
  read of `workspace_invitation` cannot mint an acceptance.
- **Rule 5.2c.** **No new Key Vault secret is required for the token.** This
  is a deliberate, cheaper choice than the HMAC/signed-token shape the
  intake assumed (`w14-requirements.md` NW-58 → "a signed, single-use,
  expiring token (secret in Key Vault, ADR-011)"). Reasons: (i) no key
  material to provision, rotate or sync across `dev`/`demo`; (ii) a
  self-contained signed token stays valid until expiry unless a revocation
  list is kept anyway — and NW-58 *requires* immediate revocation, so the
  row must exist regardless; (iii) "re-adding needs a new invite" is a
  row-state fact, not a signature fact. ADR-011 `:95` already reserves a
  slot for "signing config" in Key Vault; this design simply does not use
  it, which is a narrowing, not a contradiction. The only new Key Vault
  entry in this item is the **mail transport credential**, if the
  cloud-architect lands a transport (§5.6). The locked rules ("secrets in
  Key Vault, never in source or bundle") are satisfied trivially by a design
  with no key.
- **Rule 5.2d.** Lookup is an index seek on the hash. **No constant-time
  comparison is needed or wanted** — there is no secret-to-secret
  comparison. Recorded so nobody "hardens" it into a table scan.
- **Rule 5.2e.** Expiry **7 days** for the pilot, stored absolute
  (`expires_at`), evaluated server-side against `IClock`.
- **Rule 5.2f (transport hygiene).** The token must **never** appear in a
  URL path or query string, and must never be logged. A query parameter
  lands in web-server access logs, in `Referer` headers to any third party
  the page later contacts, and in browser history. **Constraint**: the
  accept link carries the token in the **URL fragment**
  (`/invite/accept#token=…`) — a fragment is never sent to a server — and
  the SPA reads it, clears it from the address bar, and sends it in a
  **request body or a header**, never as a query parameter. The route and
  the mechanism are client-architect's; the constraint (not in the URL
  server-side, not in logs) is mine.
- **Rule 5.2g.** The API's pre-accept metadata read therefore takes the
  token in a body or an `X-Invitation-Token` header, not in the URL. Shape
  is software-architect's; "not in the URL" is mine.

### 5.3 Accept and join

- **Rule 5.3a.** Accept requires a **presented identity** (401 without). An
  anonymous accept cannot exist: there would be no subject to bind.
- **Rule 5.3b.** The signed-in identity's email must match the invited email
  **case-insensitively**; a mismatch is **403** with a reason that does not
  echo the invited address. Rationale: an unrestricted forwardable link is
  an open door into a customer tenant, and in the pilot there is no other
  gate. Risk accepted and recorded in OQ-sec-002.
- **Rule 5.3c (corrected in revision 2 — see F5).** On success, in **one
  transaction under the invitation's tenant scope**:
  1. resolve the `workspace_user` row the invite created (§5.1d) — it
     exists, which is precisely why `WorkspaceSignIn`'s
     "sign-in never provisions a user" invariant (`WorkspaceSignIn.cs:23-25,
     36-41`) can stay intact;
  2. bind the Entra subject onto it via the already-written, currently
     unrouted `WorkspaceMembershipService.LinkSignInAsync:118-145` /
     `WorkspaceSignIn.ResolveSignedInUser` (`WorkspaceSignIn.cs:28-44`) —
     **unchanged**;
  3. insert the membership at the invited role;
  4. set `accepted_at`.

  Partial acceptance must not be reachable. Revision 1 specified only step 2
  and would have failed at `WorkspaceSignIn.cs:36-41` on every accept
  wherever the invitation had stopped writing the user row.
- **Rule 5.3d (single use).** `accepted_at` is set in the same transaction.
  A second accept → 409 for the same identity, 404 for any other. Race
  safety is **already schema-enforced** (F4): the unique index
  `ix_workspace_membership_workspace_user_id_workspace_role_id`
  (`identity-workspace.sql:90`) means two concurrent accepts produce one row
  and one unique-violation. The task asserts this rather than re-implements
  it, and must translate the violation to 409 rather than 500.
- **Rule 5.3e (pre-accept minimal disclosure).** Before acceptance the API
  returns **workspace name, offered role, expiry — and nothing else**. Not
  the roster, not the inviter, not the member count, not any contract or
  business datum, and **not the invited email** (echoing it turns a leaked
  link into an address-discovery tool). A token holder is not yet a member,
  so §4.1d applies to them.

### 5.4 Remove, and what "immediately" means

- **Rule 5.4a.** `DELETE /api/workspaces/{tenantId}/members/{membershipId}`:
  identity (401) → membership (404) → `Admin` (403) → **last-Admin guard
  (409)**. An Admin may remove themselves **unless** they are the last
  Admin. A tenant with zero Admins is unrecoverable without operator
  intervention, so the invariant is "at least one live Admin membership per
  tenant, always".
- **Rule 5.4b (revocation is immediate because nothing caches
  authorization).** The API resolves membership and role **from the database
  on every request** (`WorkspaceRoleResolver.cs:85-119`), and NW-01/NW-03
  revalidate the current workspace against the caller's list. There is no
  session and no token to revoke, so removal takes effect on the **next
  request** — the strongest form available, and it depends on no expiry.
- **Rule 5.4c (this must survive W15 — and it changes a shipped contract).**
  When ADR-010's JWT lands, the token carries **identity only**. Tenant and
  role are resolved from the database per request; a `tenant_id` or `roles`
  claim in a token is **never** the authorization source.

  **This is not merely forward-binding: it amends an existing contract.**
  `../backend/src/Raffa.Identity.Workspace/Domain/WorkspacePrincipalAuthorization.cs`
  is built on the opposite premise today — `TenantIdClaimType = "tenant_id"`
  (`:35`) and `TryAuthorize` reads the tenant from that claim (`:62-67`) and
  the role from `ClaimTypes.Role` (`:69-70`) — and
  `AuditEndpointExtensions.cs:30-31` consumes it. Left alone, W15 would ship
  a stale-authorization window (a removed member keeps access until token
  expiry) and a last-Admin-guard bypass.

  The remedy is cheap and the code says so: `:32-33` records that "whichever
  task adds it (ADR-010) is free to change this constant, **since every
  caller goes through this one place**." So the ADR-010 amendment binds
  NW-05/NW-08 (W15) to change `TryAuthorize`'s tenant/role resolution from
  claim-reading to database-reading **at that single seam**, keeping its
  fail-closed posture (`:42-44`). Recording it now is what makes W15 a
  one-file change instead of a re-litigation.
- **Rule 5.4d (stale invitations).** Removing a member **revokes that
  email's unaccepted invitations in that tenant** in the same transaction.
  Without this, a still-valid link re-admits them with no new invite —
  breaking NW-58's own "re-adding them needs a **new** invite".
- **Rule 5.4e (re-invite).** After removal the membership row is gone, so
  `WorkspaceMembershipService.InviteAsync`'s "already holds the {role} role"
  refusal (`:90-96`) no longer fires and a fresh invite succeeds. The
  `workspace_user` row **remains** (audit continuity, and the external
  subject stays bound under `identity-workspace.sql:125`) and grants nothing
  on its own — see Rule 3.2d, which is what makes that true.
- **Rule 5.4f (RAG closes too).** A removed member's Ask calls for that
  tenant retrieve nothing. This is already structural under ADR-011
  (authz → tenant scope → retrieval), and w14 **strengthens** it: the tenant
  used for retrieval becomes a *verified membership* fact instead of a
  client-asserted `X-Tenant-Id`. Test T7d makes it explicit, because
  "removed from the workspace but Ask still answers about its contracts" is
  exactly the failure ADR-011 exists to prevent.

### 5.5 RLS consequence for the new table

`workspace_invitation` is a **tenant table like every other**:

- `tenant_id uuid NOT NULL`, indexed, and part of the tenant bootstrap's
  scope rules.
- `ENABLE` + `FORCE ROW LEVEL SECURITY` and a `tenant_isolation` policy with
  **both** `USING` and `WITH CHECK`, byte-identical in shape to
  `identity-workspace.sql:176-180`. It gets **no** `identity_self` policy —
  the pre-accept lookup is by token hash and is served by the application
  under the invitation's own tenant scope, resolved from the hash. (The
  hash-to-tenant resolution is the one read that must happen before a tenant
  scope exists; it is a lookup on a unique index over a 256-bit secret the
  caller already holds, returns only the tenant id, and is the narrowest
  possible form of that unavoidable step. It must be a dedicated,
  single-purpose query — never a general "read invitations" path. It is
  **not** a second instance of the F3 multi-scope exception: it enters no
  scope at all, it selects one column.)
- Columns: `token_hash` (unique), `email`, `workspace_role_id`,
  `invited_by`, `created_at`, `expires_at`, `accepted_at?`, `revoked_at?`.
  **No plaintext token column.**
- A partial unique index on `(tenant_id, lower(email)) WHERE accepted_at IS
  NULL AND revoked_at IS NULL` keeps at most one live invitation per address
  per tenant, so "re-invite" cannot silently accumulate valid links (5.4d
  revokes, 5.4e re-issues one).
- Per ADR-009's decomposition rule, the migration is rejected by CI if the
  policy is missing — the wave must not be the first tenant table to skip
  it. The idempotent `DO $EF$ … IF NOT EXISTS` shape of
  `identity-workspace.sql` is the pattern to copy (ADR-021).

### 5.6 Transport (OQ-w14-002) — my part only

Not my call whether a mail transport lands (product-owner + cloud-architect).
My constraints either way:

- **Rule 5.6a.** If a transport lands: its credential is a **per-env Key
  Vault secret** reached by **managed identity** — ADR-011's chosen Option 1
  (`:49-50`: "one Key Vault per environment (`kv-raffa-dev`,
  `kv-raffa-demo`), accessed via Azure managed identity for the API and
  worker"), never in source, Terraform or a client bundle; delivery-manager
  plumbs it before the feature (ADR-016).
- **Rule 5.6b.** If no transport lands: the Admin is shown a **copyable
  accept link** and the UI **must not** say "Invitation sent."
  (`../web/src/routes/workspace/members/memberViewModel.ts:39`'s
  `INVITATION_SENT_MESSAGE = "Invitation sent."`, rendered unconditionally
  on a 201 at `InvitePane.tsx:93,103`). This is NW-58's own must #1; it is
  also a security statement — claiming an unsent mail leaves an Admin
  believing access was granted when it was not.
- **Rule 5.6c.** Either way the **token is not persisted in the UI, in
  `sessionStorage`, or in `localStorage`**, and the copyable link is not
  written to any client store. It is rendered once, from the 201 response,
  and is gone on reload. A token in `localStorage` is a token in every XSS
  payload's reach.
- **Rule 5.6d.** The mail body (if any) contains the link and the workspace
  name. No contract data, no roster, no member emails other than the
  recipient's own.

### 5.7 Audit (ADR-011)

`AuditEvent` is append-only and DB-enforced (the `AddAppendOnlyEnforcement`

**Never recorded**: the token, the token hash, any `Authorization`/

**Rule 5.7a.** These endpoints require an identity, so the `"unattributed"`

## §C. Tests every task in this wave must carry

Non-negotiable, and each one names the rule it defends. "Another tenant
never appears" and "a spoofed header is rejected" are the two families my
lane brief requires; T1–T3 are those, the rest are the traps this codebase
specifically has.

**T1 — another tenant never appears.** Identity `A` is a live member of `T1`
only; `T2` exists with its own workspace, members and documents.
- **T1a** `GET /api/workspaces` as `A` returns exactly `[T1]`. `T2`'s id,
  name and count appear nowhere in the payload. (Rules 3.2c/3.2f)
- **T1b** `GET /api/workspaces/{T2}/members` as `A` → **404**, and the body
  carries no tenant name. (Rule 4.1b)
- **T1c** With `app.identity_subject` set to `A` and **no** tenant claim, a
  direct read of `workspace_user` returns only `A`'s own rows — never
  another identity's row in any tenant. (Rules 3.2a, 4.2b)
- **T1d** With `app.identity_subject` set to `A`, reads of `workspace`,
  `workspace_role` and `workspace_membership` with no tenant claim return
  **zero** rows. Proves the widening is confined to one table.

**T2 — a spoofed header is rejected.**
- **T2a** A Procurement member of `T1` sending `X-Role: Admin`:
  `DELETE /api/documents/{id}` → **403**; `POST …/reprocess` → **403**;
  `POST /api/workspaces/{T1}/invites` → **403**;
  `DELETE …/members/{id}` → **403**. Repeat each with
  `X-Workspace-Role: Admin`. (Rules 1.1, 1.2a, 1.2b)
- **T2b** Identity `A` sending `X-Tenant-Id: {T2}` on every tenant read →
  **404**/empty, and no `T2` row is read or written. (Rule B1, N5)
- **T2c** `X-User-Id: <an identity with no membership in T1>` on every
  membership route → **404**. (Rule A2)

**T3 — the F1 regression (the one that must exist).**
`POST /api/workspaces/{T1}/invites` with **no** `X-User-Id` → **401**
(today: **201 Created** with a real `Admin` membership row). Then: with an
identity that is not a member of `T1` → **404**. With a `T1` Procurement
member → **403**. With a `T1` Admin → **201**. (Rule 5.1a)

**T4 — creator is Admin, and only that.** Create a workspace → rows in
`workspace`, `workspace_user`, `workspace_membership` (`Admin`) for the
creating identity; `DELETE /api/documents/{id}` as the creator → **204**;
`POST …/reprocess` → **200**; a `role` field in the create body is ignored;
create with no identity → **401**. (Rules 2.1a/b/c, 1.3, N1, N9)

**T5 — RLS fail-closed on the new table.** Outside any tenant scope,
`workspace_invitation` reads return zero rows and an insert is rejected by
`WITH CHECK`. (Rule 5.5)

**T6 — the connection-claim hazard (F2.2/F3).** In one unit of work: enter
scope `T1`, read; enter scope `T2` on the **same** open connection, read →
the second read must **not** return `T1` rows, and must not silently run
under `T1`'s claim. The test fails on today's naive nesting, which is the
point. Paired assertion: `GET /api/workspaces` enters its scopes
**sequentially, each on its own connection** (Rule 3.2g), and no other
endpoint enters more than one.

**T7 — removal is immediate and total.** Remove member `B` from `T1`:
- **T7a** `B`'s next `GET /api/workspaces` no longer lists `T1`, although
  `B`'s `workspace_user` row still exists. (Rules 3.2d, 5.4b)
- **T7b** `B`'s next document read in `T1` → **404**; write → **404**.
- **T7c** Any unaccepted invitation for `B`'s email in `T1` is revoked; the
  stale accept link → **404**. (Rule 5.4d)
- **T7d** `B`'s Ask call scoped to `T1` retrieves nothing from `T1`'s
  corpus. (Rule 5.4f, ADR-011)

**T8 — re-invite after removal.** A fresh invite for `B` at the same role
succeeds (`InviteAsync`'s `:90-96` refusal does not fire) and the new token
differs from the revoked one. (Rule 5.4e)

**T9 — last-Admin guard.** Sole Admin removing self → **409**; sole Admin
removing the only other Admin membership → **409**; with two Admins, either
removal → **204**. (Rule 5.4a)

**T10 — token hygiene.** The stored column is a 32-byte hash, not the token;
the token appears in **no** audit row, **no** log sink, and **not** in the
pre-accept metadata response; the pre-accept response contains only
workspace name, role and expiry — no email, no roster, no counts; the accept
request carries the token in a body/header, never a query string. (Rules
5.2b, 5.2f, 5.3e, 5.7)

**T11 — accept binding (F5).** Email mismatch → **403** and **no**
membership row written; expired token → **410**; unknown/revoked → **404**;
second accept → **409**; two concurrent accepts → exactly one membership row
**and a 409, not a 500** (the unique index at `identity-workspace.sql:90`
does the enforcing — Rule 5.3d). Plus the F5 regression: an invitation
issued through the new path is acceptable end-to-end, i.e.
`LinkSignInAsync` finds the `workspace_user` row the invite wrote and does
not return "no workspace invite was found for this email in this tenant".

**T12 — the ADR-010 retirement test (written now, activated in W15).** With
a validated token present, `X-User-Id` is **ignored**, not merely
overridden: token `A` + `X-User-Id: B` acts as `A`. And a token carrying a
`roles`/`tenant_id` claim does **not** grant that role or tenant — the
database is still consulted, through
`WorkspacePrincipalAuthorization.TryAuthorize`'s single seam. (Rules A3,
5.4c)

## §F. What I will object to at the table

Stated in advance so the other lanes can avoid it:

1. Any design where **`GET /api/workspaces` is answered by removing or
   relaxing a `tenant_isolation` policy**, by a `BYPASSRLS` role, or by a
   second un-RLS'd membership table (§3.1 options 1 and 2).
2. Any design where **`X-Role` grants an Admin action** (§1.1), including
   "the SPA sends the role it got from the server" — the server must not
   believe the client about a role it can look up.
3. Any invite/remove/accept path that is **reachable without an
   authorization check** (F1), or that returns **403 to a non-member**
   (Rule B1 — it is an oracle).
4. Any token that is **stored in plaintext**, **travels in a URL query or
   path**, is **written to an audit row or a log**, or is **kept in
   `localStorage`/`sessionStorage`** (§5.2, 5.6c).
5. Any **role or tenant claim in the ADR-010 token being treated as
   authoritative** (Rule 5.4c) — that is the stale-authorization window
   NW-58's "removal is immediate" forbids, and it would silently reopen in
   W15 if not locked now.
6. A **discovery list driven by `workspace_user` existence rather than live
   membership** (Rule 3.2d) — it shows removed members the tenants they were
   removed from.
7. Any UI that says **"Invitation sent."** when no mail left (Rule 5.6b).
8. **(new)** Any second endpoint entering more than one tenant scope per
   request (Rule 3.2g) — the F3 exception is named and singular, or it is
   not an exception.
9. **(new)** Any invitation design that makes **sign-in provision a
   `workspace_user` row** (F5) — that converts `WorkspaceSignIn`'s explicit
   "self-service join is out of scope" invariant into self-service join.
