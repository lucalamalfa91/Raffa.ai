## NW-74 — hide admin-gated Ask chips from a non-Admin

### The rule (what this seat confirms, and what it refuses)

**Confirmed: chip hiding is presentation, never authorization — and it stays that
way.** Every action behind an admin-gated Ask entry is enforced **server-side by
membership on its own endpoint** (`WorkspaceRoleResolver.IsAdminAsync`, the
401→404→403 ladder of ADR-011 w16 clause 14). Hiding or showing a chip in the SPA
grants and revokes nothing. This is the exact basis on which ADR-022 w16 §3
(S16-11) and w17 §4 deferred the item, and the basis on which two consecutive
deferrals carried **zero security debt**.

**Refused, and the refusal is load-bearing:** this item must **not** be written,
described, accepted or reviewed as a security fix. A year from now the title
alone ("hide admin-gated chips") will invite it. The task text and the acceptance
must say "presentation" — never "control", "gate", "enforce" or "authorize".

### Re-verified on this checkout (not re-cited from the ADR)

- `CapabilitiesEndpointExtensions.cs:31-33` — `GetCapabilities()` takes **no
  parameters at all** and returns `CapabilityCatalog.All` **unfiltered**. The
  response is provably identical for no token, a non-Admin and an Admin. (This is
  the property ADR-022 w17 §4 made load-bearing, and it still holds.)
- `CapabilitiesEndpointExtensions.cs:49` — `roleGate` is serialised as a **wire
  label** (`capability.RoleGate.ToApiValue()`), never a server-side filter.
- `CapabilitiesEndpointExtensions.cs:10-16` — the doc comment states the S16-6a /
  S16-11 posture verbatim: catalog discloses *which admin features exist and
  nothing else*; `roleGate` stays on the wire as presentation, never authorization.
- `web/src/components/shell/AppShell.tsx:82` renders `<GlobalAskBar kbReady={…}
  apiClient={…} />` — **no `role` prop**. `AppShell` holds the server-derived
  `role` (`AppShell.tsx:20,73`) and passes it only to `RailNav`, not to the Ask bar.
- `web/src/components/ask-bar/GlobalAskBar.tsx:7-16,33` — `GlobalAskBarProps` is
  `{ kbReady, apiClient }` only; the component has no `role` in scope and no
  `roleGate` read. Role-blind by construction.
- `web/src/components/ask-bar/askSuggestions.ts:51` key `workspace` →
  `"workspace-members"` is the single Admin-gated catalog key
  (`CapabilityCatalog.cs:244`); `suggestionsFromCapabilityCatalog`
  (`askSuggestions.ts:96-110`) selects by `key` + `exampleQuestions.length`, never
  by `roleGate`. This is the leak the item closes, and it is a **display** leak of
  an *example question*, not of tenancy.

**Conclusion: two role-blind renderers, one server-derived `role` prop already in
hand (`AppShell.tsx:40`). The change is to thread that `role` into the Ask bar
renderers and suppress `roleGate === Admin` chips for a non-Admin. No endpoint, no
header, no token, no membership change.**

### RLS consequence

**None.** No tenant table, no RLS policy, no `tenant_id` is added, changed or read
differently by this item. `GET /api/capabilities` stays tenant-free and un-gated
(S16-6a — w16 took that alternative deliberately; this is the one thing NW-74 must
**not** silently reverse by, e.g., gating the catalog server-side to make the
client's job easier). A non-Admin seeing or not seeing a chip changes **no data any
other tenant or any other user of the same tenant can see**; tenancy is unaffected.

### Interim mechanism status

**Nothing under ADR-022 changes this wave, and nothing revives.** The interim
**identity** posture is already fully retired (ADR-022 w16 §1). The only survivor
relevant here is `X-Tenant-Id` as a **membership-verified authorized selector,
never an assertion** — untouched by NW-74. **NW-74 must not reintroduce `X-Role`
/ `X-Workspace-Role`** (ADR-022 w16 §5, w16 clause 1 is not reopened): the role the
renderer uses must be the **server-derived membership role** already parsed in
`workspaceRole.ts` (`App.tsx:169` → `parseWorkspaceRole`), never client-asserted,
never from `localStorage`, never from a decoded token claim.

**Nothing is scheduled for removal by W18 and nothing revives.** The two conditions
ADR-022 w17 §4 carried to W18 stand unchanged and bind the task:

1. The role passed to the renderers is the **server-derived** membership role —
   never client-asserted, never `localStorage`, never an `X-Role` revival.
2. `GET /api/capabilities` is **not** membership-gated.

### Tests the task must carry

- **Identical-catalog invariant (server, already existing):** the same
  `GET /api/capabilities` response for no token, a non-Admin token and an Admin
  token — reassessed as a regression guard that NW-74 did **not** accidentally gate
  the endpoint. Backend test / `curl`, not a browser case.
- **Role-blind renderer is now role-aware (client, vitest):** a `getAskBarCopy`
  (or the new wrapper) with `role: "Admin"` returns the `workspace-members` chips;
  with `role: "Procurement"` (or any non-Admin) does **not** return the
  `roleGate === Admin` chip(s); the non-admin-gated chips (portfolio, documents,
  renewals, quote-check, ask) are unchanged for both.
- **Another tenant never appears:** the rendered chip set is a function of this
  tenant's server-derived role and the static catalog; no tenant row is read, so
  no cross-tenant surface exists. The test is the negative proof — the renderer
  takes `role` as a parameter and reads **no** `tenant_id`, **no** membership list,
  **no** `X-*` header.
- **Spoofed header rejected (regression, already covered):** no `X-Role` /
  `X-Workspace-Role` reintroduced — grep over `web/src` for
  `X-Role|X-Workspace-Role` returns **zero** (paired assertion with the S16-7 /
  D7 idiom). `role` comes from `parseWorkspaceRole` on the workspace row only.
- **Acceptance A17-S3 (the item's own):** a Procurement member does not see
  admin-gated chips; an Admin does; `GET /api/capabilities` is byte-identical for
  both. This is the only behaviour the item promises, and it is **presentation**.
