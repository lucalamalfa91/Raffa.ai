## §1. NW-07 — one comparison rule for the identity column

**The same predicate — "is this identity this `workspace_user`?" — is implemented four times and they disagree on
two axes.** This is broader than the intake's finding, which names only axis (b).

| Site | Gate it guards | email leg | `oid` leg |
|---|---|---|---|
| `CallerContext.cs:143` | membership → **404** | `Email == identity` (ordinal) | ordinal |
| `WorkspaceRoleResolver.cs:80` | role → **403** | `Email == identity` (ordinal) | ordinal |
| `WorkspaceDirectoryService.cs:104,144` | `GET /api/workspaces` | `Email.ToLower() == lower(id)` | **`ExternalSubjectId == lower(id)`** |
| `identity-workspace.sql:203-204` | RLS `identity_self` | `lower(email)=lower(guc)` | `external_subject_id = guc` |

- **S16-1 — the email leg is deleted from both authorization comparators.** ADR-010's w15 footer (**S15-6**) already
  rules that `oid` is the standing key and email is a *binding aid only*. `CallerContext.cs:143` and
  `WorkspaceRoleResolver.cs:80` never implemented it: membership **and** role can today be granted by a match on
  `workspace_user.Email` — a column an Admin writes at invite time. **Not exploitable on this tree** (the identity is
  always a GUID-shaped `oid`; an email never equals one), so this is a latent divergence, not a live bypass — but it is
  one `workspace_user` row carrying a GUID-shaped `Email` away from being a grant, and that row is creatable through the
  ordinary invite path. Email keeps exactly one job, where ADR-025 D.3b already puts it: the **first bind** at invitation
  accept, through `ICallerIdentity.ResolveEmail()` (`CallerIdentity.cs:84-97`). Nowhere else.
- **S16-2 — `external_subject_id` is compared by ordinal equality, and nothing normalizes the identity before it.**
  `WorkspaceDirectoryService.cs:100` trims+lower-cases, then `:104,144` compare the **`oid`** leg against that value;
  `CallerContext`/`WorkspaceRoleResolver` compare raw. Benign while every stored subject is a lowercase GUID (Entra and
  Graph both emit lowercase) — a **user-visible split** the moment one is not: *the workspace is listed but every route
  404s*, or the reverse. Nothing enforces GUID-ness: the column is `character varying(200)` (`identity-workspace.sql:42`).
  **Fix at the source, not per-site**: `app.identity_subject` stops being lower-cased when set, and each leg normalizes
  itself — which is already what the RLS policy does (`lower(email)=lower(guc)` for email, ordinal for the subject).
  All four comparators then agree by construction. **The shipped `identity_self` policy text is not rewritten** (it is
  already correct, and the migration is applied); the change is in the GUC's source only.
- **S16-3 — pre-w15 conversation rows: record, never silently re-key** (confirms **S15-40**, answers **OQ-w16-001**'s
  security half). A backfill that re-points `conversation.user_id` by matching against `workspace_user.Email` would
  re-point ownership **through the very leg S16-1 deletes** — a cross-user data move performed by the weakest key in the
  system. If product-owner wants the history, the only acceptable form is an explicit `(old key, oid)` pair supplied at
  HITL (the ADR-025 D.2e backfill pattern), one tenant at a time, audited. Orphaned history is a smaller problem than
  mis-attributed history. **My ruling does not depend on which product-owner chooses** — it forbids one mechanism.

**RLS consequence**: no new table, no policy change. S15-50 stays binding — `set_config('app.identity_subject', @identity,
false)` keeps its **bound parameter** (an `oid` looks safe to interpolate; that is exactly the reasoning that opens the
sink), and the negative test (`'`, `;`, `--`) stays green.
**Interim mechanism**: none left here — `X-User-Id` is already read nowhere (intake, re-verified).
**ADR action**: **amend ADR-010** (S16-1…S16-3 — "one comparison rule for the identity column"); **amend ADR-024**
(retire `OQ-askv2-005`, which closes with this item). **ADR-009: none** — no policy changes.

## §2. NW-08 — `GET /api/audit` for a real Admin

Confirms **S15-39** exactly: the guard reads a `tenant_id` claim (`WorkspacePrincipalAuthorization.cs:62-67`) and
`ClaimTypes.Role` (`:69-74`); `Program.cs:128` sets `MapInboundClaims = false` and no `IClaimsTransformation` is
registered, so a real Admin token mints neither and lands on **403**. **It fails closed, which is correct** — the danger
is the repair, not the defect.

- **S16-4 — who may read a tenant's audit trail: a live `Admin` membership in the selected tenant, and nobody else.**
  The ladder is `DocumentsEndpointExtensions.cs:492-509`'s, verbatim, in this order: no validated token → **401**;
  missing/non-GUID `X-Tenant-Id` → **400**; well-formed tenant with no live membership → **404** (never 403 — ADR-025
  Rule B1: a 403 is a tenant-existence oracle); member without the role → **403**; Admin → 200, that tenant's rows only.
  `/api/audit` gets **no bespoke ladder**.
- **S16-5 — `TenantIdClaimType` is deleted, and `WorkspacePrincipalAuthorization` dies with it.** The two tempting
  repairs are both already forbidden: mapping `tid` → `tenant_id` (**S15-7** — both environments share one directory, so
  `tid` is identical for every workspace and can never select a tenant) and minting a role claim (**S15-13**). Deleting
  the constant but leaving the type is not enough: it remains a working claims-based authorizer that any future endpoint
  can pick up, which is how this defect got here. Its only other consumer is test-only
  (`TestPrincipalStartupFilter.cs:27-42`, whose own comment says it is never registered in production).
- **OQ-w16-002 — answered: the swap is not a weakening, and the record must say why.** The route's "no `?tenantId=`"
  comment (`AuditEndpointExtensions.cs:25-29`) defends against a *cross-tenant query*. Under `ICallerContext` the tenant
  is still never trusted — it is a **candidate verified against the token subject's membership before the scope opens**
  (`CallerContext.cs:135-152`). The property survives; its enforcement moves from *the absence of a parameter* to *a
  membership fact*, which is strictly stronger. Recorded explicitly so a reviewer does not read "claim → header" as
  "authorization → client input". **`X-Tenant-Id` is an authorized selector** (S15-11), not an assertion.
- **OQ-w16-003 — I concur with "no web surface", and bound the reversal.** If product-owner rules an audit screen in,
  the response body is *a whole tenant's audit trail* — the most sensitive read in the product. It then needs its own
  ADR-020 row and a re-review from this seat (pagination bounds, and no actor-identifier disclosure beyond what the
  member list already shows). Recorded so it cannot land as "just another screen".

**RLS consequence**: no new table, no policy change — `audit_event` is already `ENABLE`+`FORCE`+`tenant_isolation`
(`audit.sql:54-56`). RLS is the **backstop**; membership is the **gate**. The read must run inside the verified tenant's
scope: today `IAuditQueryService.GetEventsAsync` is handed a *claim-derived* tenant, after the swap a *membership-verified*
one.
**ADR action**: **amend ADR-025** (the audit read joins the membership-guarded set; §I's seam swap is discharged) and
**amend ADR-011** ("who may read the audit trail" is now a membership fact). **ADR-026 is software-architect's**;
**ADR-012 §3 is client-architect's** — my constraint on both is only S16-4's ladder.

## §3. NW-31 — the role headers retire (and what must *not* retire with them)

The one live reader is `CapabilitiesEndpointExtensions.cs:54` (`X-Role`), consumed `:77-80`, gating `:64-67`. Its own
doc comment `:44-48` is load-bearing: the endpoint **deliberately never 401s**, "since the catalog itself is not
sensitive, tenant data", and it takes no tenant at all.

- **S16-6 — retiring `X-Role` must not turn `/api/capabilities` into a tenant-scoped route.** The header stops being
  read. Admin-gated entries appear only when the request carries a validated token **and** a membership in the named
  tenant whose role is Admin; with no token the caller gets the **non-admin catalog at 200, never 401**. The endpoint
  keeps failing closed on the admin axis exactly as today — membership replaces the client's assertion, and nothing else
  changes. *Acceptable alternative if the council prefers a smaller diff*: drop the admin gate entirely (the catalog
  discloses only **which admin features exist**, never tenant data). **Not acceptable**: keeping any client-asserted role.
- **S16-7 — `X-Role`/`X-Workspace-Role` retire; `X-Tenant-Id` does not.** The wave's sweep is phrased "retire the
  headers", and `X-Tenant-Id` is a deliberately-kept **authorized selector** (ADR-022 w15 / S15-11). A task that deletes
  it breaks every tenant-scoped route. Concurrence with delivery-manager D7, which says the same from the CI side.
- **OQ-w16-004 — answered. w16 buys CI no new credential; I reach that from the identity plane independently.**
  delivery-manager's **D1** refutes the "zero-cost re-enqueue" premise on infrastructure evidence
  (`infra/modules/servicebus/main.tf:73-74,91-92` — both roles are on the container-apps workload identity only; CI's
  `raffa-sp-<env>` holds neither). I concur, and the token option fails on my own ground regardless:
  - an **app role on `azuread_application.api` + an app-only token** is precisely the token **S15-1 rejects by design**
    ("this API defines no application role, so no app-only token should exist, and the rejection is what keeps it that
    way"). Such a token carries **no `oid`** → no membership → no tenant, so it would *also* need a bypass of
    `CallerContext`'s gate. That is a second authorization source, built for a CI job. **Refused.**
  - the alternative — a **`workspace_membership` row making a service principal a workspace Admin** — is worse: it puts
    a non-human principal in the table that grants humans, where ADR-025's last-Admin guard and the member list both
    count it.
  - → **ADR-010 / ADR-015: no new identity in w16.** cloud-architect stays on `PASS` from this seat too.
  - **Owed to W17** (delivery-manager D5's bulk job), recorded so it is not re-derived: (a) may a CI principal hold a
    topic-scoped Send right — my inclination is **yes: Send only, topic-scoped, never `Manage`, never a SAS key**
    (S15-46); (b) what actor an operator console writes — **S16-9** below already rules it.
- **Interim mechanism → removed**: after this item `X-Role`/`X-Workspace-Role` are read nowhere in `backend/src`, declared
  nowhere in `web/openapi/`, and sent nowhere in `.github/`. The stale doc comments asserting the retired posture go in
  the same task — they are what makes a grep-based audit return a **false verdict** (the three `unattributed` comment
  hits that are not declarations are the same class of trap).
- **RLS consequence**: none — no table, no policy, no new column.
- **ADR action**: **amend ADR-022** — I own this footer: its named retirement items are discharged and the last interim
  *reader* is gone. **ADR-016 is delivery-manager's**, **ADR-012 §3 client-architect's**, **ADR-027 cited not amended**.

## §4. NW-32 — every write names its actor

Reframing independently confirmed (§0): the defect is a **falsified audit trail**, not an authentication bypass — every
endpoint reaching these nine services sits behind `ICallerContext` and 401s first. An authenticated caller's writes are
attributed to nobody. Live **ADR-011** violation; I concur with the intake's refusal to promote it to `must`.
This **corrects S15-41**, which assumed the placeholder survived on an *identity-absent* branch: it is an unconditional
hardcode on every call, signed or not.

- **S16-8 — an audit row that cannot name its actor is not written.** The actor becomes a **required parameter** on all
  nine service methods with **no default value**, so the placeholder cannot return by omission. `AuditEvent.Actor` stays
  `required string` (`AuditEvent.cs:27`) — the column was never the problem; the only value it may hold becomes a
  resolved subject or S16-9's reserved principal.
- **S16-9 — the two caller-less sites (OQ-w16-007) take the actor as a required parameter too, and write a named
  non-human principal — never a placeholder.** `RagAnswerService.cs:140` and `SavingsOpportunityService.cs:165` have no
  HTTP caller; a default there would resurrect the defect under a new name. Where a write genuinely originates in the
  product (a worker, a scheduled job), the actor is a **reserved, documented principal string** — e.g. `system:worker` —
  that (a) is shaped so **no token can ever produce it**, hence it can never collide with an `oid`, and (b) is greppable.
  **A reserved actor is a fact; `"unattributed"` is a lie** — it means "we did not know". W17's operator console (D5)
  inherits this ruling.
- **S16-10 — the green test pinning the defect is rewritten, never deleted.** `RagAnswerServiceTests.cs:70` asserts
  `Assert.Equal("unattributed", entry.Actor)`. Deleting it removes the only evidence the behaviour changed.
- **RLS consequence**: no new table, no policy change — **but note the append-only trigger** (`audit.sql:85-88`): UPDATE
  and DELETE on `audit_event` are rejected, so the existing `"unattributed"` rows **cannot be corrected and are
  permanent**. That is correct for an audit trail. This item stops the bleeding; it does not clean history. Recorded so
  nobody proposes a backfill that would have to drop the trigger to run — **that trigger is never dropped**.
- **ADR action**: **amend ADR-011** (every audit row names a validated subject or a reserved principal; otherwise the
  write fails) and **amend ADR-022** (its second named retirement item is discharged).

## §5. Tests every task in this wave must carry

Each names the rule it defends. "Another tenant never appears" and "a spoofed header is rejected" are mandatory per my lane.

- **S-T24 (NW-07, S16-1/S16-2)** — *one comparison rule*: (a) a `workspace_user` whose `Email` is set to **another
  member's `oid` string** confers **no** membership (404) and **no** role (403); (b) a subject stored with non-lowercase
  characters resolves **identically** through `GET /api/workspaces`, `CallerContext` and `WorkspaceRoleResolver` — the
  workspace is either listed-and-usable or absent-and-404, **never listed-and-404**; (c) S15-50's injection negative
  (`'`, `;`, `--` in the identity) stays green.
- **S-T25 (NW-08, S16-4/S16-5)** — the ladder, in order: no token → 401; missing/non-GUID `X-Tenant-Id` → 400;
  non-member → **404** with no tenant name, id or count in the body; member-not-Admin → 403; Admin → 200.
  Plus **the deletion proof**: a token carrying `tenant_id` **and** `roles` claims naming a tenant the caller has no
  membership in → **404**, not 200 — proving the claims path is *deleted*, not merely unreachable.
- **S-T26 (NW-08)** — *another tenant never appears*: an Admin of T1 calling `/api/audit` with `X-Tenant-Id: T2` gets
  404 and zero T2 rows in any form.
- **S-T27 (NW-31, S16-6/S16-7)** — *a spoofed header is rejected*: `X-Role: Admin` and `X-Workspace-Role: Admin` on
  `/api/capabilities` confer **no** admin entries with no token, and none with a valid **non-Admin** member's token.
  Paired grep: zero `X-Role`/`X-Workspace-Role` across `backend/src`, `web/`, `.github/`, `web/openapi/` outside
  historical ADR/acceptance records — and **`X-Tenant-Id` unchanged**, asserted positively so the sweep cannot overrun.
- **S-T28 (NW-32, S16-8)** — a **signed** POST on each of the nine paths writes an audit row whose `Actor` equals the
  caller's resolved `oid`; `grep -r unattributed backend/src` returns nothing outside comments the council allows; no
  test asserts the literal (S16-10).
- **S-T29 (NW-32, S16-9)** — the two caller-less sites write the **reserved principal**, and that string is rejected as
  a token subject (it can never be an `oid`), so the two namespaces provably cannot collide.
