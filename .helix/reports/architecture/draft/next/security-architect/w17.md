## NW-73 — Bulk whole-tenant reprocess console

Four rulings. S17-1 and S17-2 discharge what ADR-016 §31 `:781-784` records as
**owed to this seat**. S17-3 is new, and is the one a task can get wrong silently.

### S17-1 — a CI principal may hold a Send right. Adopted, bounded.

**Authorized**: `data.azuread_service_principal.ci_deploy` (`raffa-sp-<env>`) holds
**`Azure Service Bus Data Sender`, topic-scoped**, on the extraction topic only.
**Refused, each for its own reason**:

| Refused | Why |
|---|---|
| `Azure Service Bus Data Receiver` | a receiver **drains the Worker's deliveries** — denial of processing, plus tenant/document ids read out of the envelope. Send cannot do either. |
| `Azure Service Bus Data Owner` / `Manage` | creates/deletes entities; ADR-016 §30 already refuses it. |
| namespace-scoped anything | reaches every topic and queue; the grant must not exceed the one topic. |
| SAS key / connection string | `servicebus/variables.tf:28` and ADR-011 forbid it; `DefaultAzureCredential` only (`MessagingServiceCollectionExtensions.cs:84-87`). |
| an app role on `azuread_application.api` + app-only token | ADR-022 w16 §4 `:239-244` refused it; nothing in w17 changes that. |
| a `workspace_membership` row for the SP | ADR-022 w16 §4 `:245-248` refused it; it would put a non-human in ADR-025's last-Admin count. |

**Why Send is genuinely safe here, and the reasoning is not "it is only one verb"**:
the message is a **pointer**, not content — `ExtractionRequested(tenantId, documentId,
jobId, schemaVersion)` (`ServiceBusExtractionQueuePublisher.cs:24`) — and the Worker
**re-reads all authority from the database under RLS** when it claims the job. A forged
or replayed message therefore cannot make the Worker read a document the sender could
not already read; `MessageId` (`:50`) collapses duplicates. **Send crosses no
confidentiality boundary. Receive would.**

### S17-2 — the actor the console writes

- Per-document rows: the **fixed literal** `system:bulk-reprocess`. ADR-011 w16 §16
  `:593-611` in form (`:` cannot occur in an Entra `oid`, so it can never collide with
  a subject; greppable), and `:611` already says "W17's operator console inherits this
  ruling".
- **No CI-controlled string is ever interpolated into `AuditEvent.Actor`.** The column
  is `varchar(200)` (`AuditEventConfiguration.cs:20`) on a table whose UPDATE/DELETE
  trigger makes every row **permanent and uncorrectable** (ADR-011 w16 §18 `:632-641`).
  A bad actor string is not a bug you fix later; it is a falsified trail forever.
- **Human attribution** rides in `Detail`, which is free text and asserts no identity:
  one run-scoped row before the loop — `document.bulk_reprocess.requested`, actor
  `system:bulk-reprocess`, detail `requestedBy=<github.actor>; run=<run-id>;
  tenant=<id>; count=<n>`. → **OQ-w17-sec-01** (one new action constant).
- `ReprocessAsync` already makes this unskippable: `actor` is a **required positional
  parameter** guarded by `ArgumentException.ThrowIfNullOrWhiteSpace` at
  `DocumentReprocessService.cs:62-65`. The console cannot omit it.

### S17-3 — the RLS binding rule. **A whole-tenant enumerator is the first product code that reads a tenant with no HTTP caller.**

`ReprocessAsync` opens its own scope (`:67`) and is safe by construction. **The
worklist query is not** — it lives in the console, outside any scope the product opens.

- **The trap, in the product's own code**:
  `DocumentsContractsDbContextOptions.Configure(builder, connectionString,
  ITenantContext? tenantContext = null)` wires `TenantRlsConnectionInterceptor`
  **only when the third argument is supplied** (`:50-66`). The two-argument form is
  what migrations and tests use — and is exactly what an implementer would copy from
  `TenantRlsMigrationCheckTests.cs:32`. **The console must call the three-argument
  form.**
- **What the two-arg form does**: `app.tenant_id` is never set → the policy's
  `nullif(current_setting('app.tenant_id', true), '')::uuid` is NULL → every comparison
  is NULL → **zero rows**. It fails *closed*, which is right — but it reads as "this
  tenant has no documents" and the console exits **green having done nothing**. That is
  the same class of honest-looking lie ADR-016 §30 names for psql-inserted jobs.
- **Rules**:
  1. DbContext via the three-argument `Configure`; the worklist runs inside
     `tenantContext.BeginScope(tenantId)`.
  2. **Never** a raw `NpgsqlConnection`, a hand-written `SET app.tenant_id`, or `psql`.
     The GUC is the interceptor's to write (`TenantRlsConnectionInterceptor.cs:40`).
  3. **One tenant per run**, from an explicit `--tenant <guid>` parsed as a GUID.
     **No all-tenants mode, no wildcard, no "every tenant in the table" loop** — the
     console never holds more than one tenant's scope in a run.
  4. **Zero rows is an error, not a success**: a syntactically valid tenant with an
     empty worklist exits **non-zero** ("no documents visible for this tenant — check
     the tenant id and the RLS scope"), never a green no-op.
  5. The connection is the **same `postgres-connection` secret the app uses**
     (`verify-tenant-corpus.yml:112`) — nothing more privileged. The console must not
     run as a superuser or a `BYPASSRLS` role; `FORCE ROW LEVEL SECURITY` binds the
     table owner but **not** `BYPASSRLS`, which is the only way left to escape it.

### S17-4 — what the console may print

A CI log is a retained disclosure surface. Permitted: tenant id, document ids, counts,
processing statuses, job ids — and file names **only** because
`verify-tenant-corpus.yml:143` already prints them for the same tenant into the same
sink, so nothing new is disclosed. **Never**: chunk text, extracted field values,
document bytes, any Key Vault value (`::add-mask::` stays, `:122`).

### Tests every NW-73 task carries

- **Another tenant never appears**: scoped to tenant A, a document id belonging to
  tenant B resolves to `null` (the `:73-76` branch) — no publish, no audit row.
- **The trap is pinned**: a test that builds the console's DbContext the way the
  console builds it and asserts `app.tenant_id` **is set** on the open connection.
- **Fail-closed is loud**: an empty worklist under a valid tenant exits non-zero.
- **No forbidden right**: no `Receiver`/`Manage`/namespace-scoped assignment and no SAS
  key in `infra/`; no `X-*` identity header anywhere in the console or its workflow.
- **The audit row**: one row per document, actor exactly `system:bulk-reprocess`;
  `grep` finds no `unattributed` on this path.

## NW-71 — auto-accept at ≥ 90 %

### S17-5 — the audit row

Actor `system:extraction` — the write originates inside the product with no HTTP caller
(ADR-011 w16 §16). **One row per document per extraction run**, not one per field.
Content rule: **field names, never values.** Precedent already in the product:
`DocumentValidationService.cs:124-135` comma-joins field names. Confidence numbers are
permitted (quality metadata about extraction, not contract content); **a field's value
never enters the audit trail**, and the table is append-only, so a value written once
cannot be removed.

### S17-6 — the RLS consequence of the new per-field decision state

- **Cheapest safe shape**: a column on `extraction_evidence`, which is already
  `ENABLE` + `FORCE` + `tenant_isolation` (`documents-contracts.sql:798-800`) and is
  already keyed per field (`ix_extraction_evidence_contract_id_field_name`, `:770`).
  **A column adds zero new isolation surface.** Shape is software-architect's call;
  the isolation consequence is mine.
- **If a new table is chosen**, all four are required in the same migration:
  1. `tenant_id uuid NOT NULL`;
  2. **the entity derives from `TenantScopedEntity`** — `TenantRlsMigrationCheckTests.cs:37-44`
     discovers the table list **from the EF model by that base type**. An entity that
     does not derive is **never checked, and the suite stays green**: the "guards the
     guard" assert at `:46-49` only catches an *empty* list, not a missing member.
     **This is the silent-escape path and the task must carry it as a test.**
  3. `ENABLE` + `FORCE ROW LEVEL SECURITY` + `CREATE POLICY tenant_isolation …
     USING (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
     WITH CHECK (same)` — the exact shape already used;
  4. the deployable script check (`TenantRlsDeployableScriptCheckTests.cs:78`) covers
     it too, since `.sql` and migrations are separately asserted.

### S17-7 — authorization: NW-71 adds none, and must not

- The decision is **server-computed**. In the contract it is **read-only**: a
  client-supplied decision on the validate/PATCH path is **rejected with 400** and
  never persisted. A client must not be able to assert "accepted" for a field the
  server scored below the bar — that would make a display band an authorization
  decision, which is the same error ADR-022 §3 forbids on the other screen.
- **Manual override keeps exactly today's gate** — the membership-verified tenant
  selector plus whatever the existing endpoint already enforces. No new role, no new
  privilege, no Admin-gating of review. A human override is attributed to the caller's
  resolved subject; an auto-accept to `system:extraction`. **The trail must always
  distinguish the two.**

### Tests every NW-71 task carries

- Another tenant never appears: the decision state is invisible cross-tenant (the
  guard test covers the table; a scoped read for tenant B returns none of A's rows).
- A client-asserted decision is rejected (400) and does not change stored state.
- The audit row names fields, **contains no field value** (assert on a value string).
- Auto-accept rows carry `system:extraction`; a human validation carries a subject.

## NW-74 — hide admin-gated Ask chips

### S17-8 — the one line the roster asks for

**Confirmed: still not a control, and the catalog stays un-gated.** Verified directly —
`GetCapabilities()` takes **no parameters at all** and returns `CapabilityCatalog.All`
unfiltered (`CapabilitiesEndpointExtensions.cs:31-33`), so the response is provably
identical for no token, a non-Admin and an Admin. ADR-022 §2a `:213-220` and §3
`:222-230` already rule it; every action behind an admin-gated entry is enforced
server-side on its own endpoint. Two conditions on the task:

1. the role passed to both renderers is the **server-derived** membership role
   (`workspaceRole.ts:37-39`, least privilege) — **never** client-asserted, never read
   from `localStorage`, never an `X-Role` revival;
2. `GET /api/capabilities` is **not** membership-gated (w16 took that alternative
   deliberately) and the item/PR text **must not** be written as a security fix.

**ADR action: `none` — ADR-022 §2a/§3 already cover it; this seat confirms.**

## Interim mechanisms (ADR-022) — w17 neither revives nor retires any

The identity posture is already fully retired (`ADR-022:194-195`); what remains is the
fixture seed, which is data and is untouched. `X-Tenant-Id` stays a
**membership-verified selector**, not an assertion (§5 `:256-266`) — NW-73 must not
reintroduce it as a console argument, NW-74 must not reintroduce `X-Role`. **Nothing
interim is scheduled for removal by w17, and nothing revives.** No new identity,
federated credential, app role or Key Vault secret: the wave's whole identity delta is
**one topic-scoped Send assignment** — zero under OQ-w17-sec-02.
