## §1. NW-05 — API JWT (ADR-010) replaces spoofable headers

**Status today, verified.** There is no authentication. Identity is `X-User-Id` through
one seam (`CallerIdentity.cs:58-73`, trimmed and lower-cased at `:70-71`) and `X-Tenant-Id`
through 74 sites. `WorkspaceRoleResolver.cs:129` matches that string against
`workspace_user.Email` **or** `ExternalSubjectId`, so `-H "X-User-Id: <a known Admin's
address>"` returns that Admin's real role. This is full impersonation and it is the single
largest open exposure in the product.

### 1.1 Validation parameters (who is authorized, from which claim)

- **S15-1 — delegated user tokens only.** The API accepts a **v2 access token** issued to
  the public-client registration for this environment's API registration. An **id token**
  is not an access token (its `aud` is the public client's id) and is rejected by audience
  validation. An **app-only** token (no `scp`, `idtyp=app`) is rejected: this API defines
  no application role, so no app-only token should exist, and the rejection is what keeps
  it that way. Both are **401**.
- **S15-2 — audience is `api_client_id`, never the `api://` URI, never unvalidated.**
  `identity/main.tf:75` sets `requested_access_token_version = 2`, so `aud` is the API
  application's **client id** (`outputs.tf:13`, verbatim: "the default `aud` claim on v2
  access tokens issued for this environment's API"). `api_identifier_uri` (`outputs.tf:18`)
  is the *alternate resource identifier a client requests*, not the audience a v2 token
  carries. A task that wires `api_identifier_uri` as the audience will see every token
  rejected and the tempting repair is `ValidateAudience = false`. **`ValidateAudience` is
  `true`, always, with `api_client_id` as the only accepted value.** A second accepted
  audience is a new decision, not a fix.
- **S15-3 — issuer is pinned to this environment's concrete tenant issuer.**
  `identity/outputs.tf:25-28` already emits
  `https://login.microsoftonline.com/<tid>/v2.0`. `ValidateIssuer = true` against that
  literal. **`common` / `organizations` / `consumers` are never accepted**, and the API
  does not derive the issuer from the token. (The runtime-config validator,
  `write_web_runtime_config.py:80-83`, checks the *prefix* only, so `…/common` passes it
  today — defence in depth on the API side is therefore mandatory, not optional. Extending
  that validator to reject the three multi-tenant segments is a cheap, welcome addition and
  is delivery-manager's file.)
- **S15-4 — the rest, fail-closed.** `ValidateIssuerSigningKey` and `RequireSignedTokens`
  true, keys from the environment's OIDC discovery document (JWKS, auto-refreshed — never
  a pinned key, never a shared secret: ADR-010 `:84-85`, "the API does **not** store or
  share client secrets"). `ValidateLifetime` true, `ClockSkew` ≤ **2 minutes** (the 5-minute
  default is a 5-minute stale-authorization extension for free). A token whose `ver` is not
  `2.0` is rejected — v1 tokens carry a different `aud` shape and a different claim map.
- **S15-5 — a missing `scp` denies; a present `scp` grants nothing.** `Raffa.Read` /
  `Raffa.Write` (`identity/main.tf:79`, `:90`) are **client capability**, not user
  authorization: they say the browser was allowed to ask, never that the caller may touch a
  given tenant. Absent required scope → **403**. Present scope → the request proceeds to
  the membership check, which is the only grant. Recorded because "the token has
  `Raffa.Write`" is the most natural wrong reading of a scope.

### 1.2 Which claim is the identity (the load-bearing choice)

- **S15-6 — `oid` is the identity; `email` is a binding aid, never the standing key.**
  The membership match runs on `workspace_user.ExternalSubjectId = oid`. An email address
  is **mutable and re-assignable inside a directory** — matching a standing membership on
  email means a re-assigned alias silently inherits someone's grant. Email keeps exactly
  two jobs: (1) the **first** bind of a subject to an invited address
  (`WorkspaceMembershipService.LinkSignInAsync`, unchanged — ADR-025 Rule D.3c step 2),
  and (2) the invitation email match (ADR-025 Rule D.3b). After the bind, `oid` is the key.
- **S15-7 — `tid` is the Entra directory, never the Raffa workspace tenant.** This is the
  rule NW-05 exists to protect, because NW-05 is the wave that first puts Entra claims in
  front of the application. A v2 token carries `tid` (the directory GUID). It is **not**
  `WorkspacePrincipalAuthorization.TenantIdClaimType` (`:35`, `"tenant_id"`), and mapping
  one to the other to "make `GET /api/audit` work" (NW-08) would ship exactly the
  stale-authorization window ADR-010's w14 footer clause 2 and ADR-025 §I forbid. Both
  environments use the **same** directory (`identity/main.tf:63`, `:118`), so `tid` is
  *identical* for `dev` and `demo` and for every customer workspace — it can never select a
  tenant. **No Raffa code reads `tid` for any purpose.**
- **S15-8 — the `#EXT#` UPN is never parsed into an email for an authorization decision.**
  A B2B guest's UPN in the resource directory is mangled
  (`luca_gmail.com#EXT#@<tenant>.onmicrosoft.com`). ADR-025 Rule D.3b matches the
  signed-in identity against the invited address by case-insensitive equality
  (`WorkspaceInvitationService.cs:187`, `:197`) — against a mangled UPN that comparison
  **fails**, and A15-4 fails at its last step with the invitee signed in and locked out.
  The de-mangling "fix" (replace the final `_` before the domain with `@`) is ambiguous for
  addresses containing `_` and must not be a grant basis. The resolution order is:
  **`oid` bound at invite time by NW-67 (§3.3) → the `email` claim → refuse (403) and tell
  the Admin to re-invite.** Never the UPN.
- **S15-9 — the `email` optional claim must be requested, in Terraform.** S15-8's second
  branch only exists if the access token carries `email`. That is an
  `optional_claims { access_token { name = "email" } }` block on
  `azuread_application.api` (`identity/main.tf:57-105`) — a small addition to the same
  Terraform change NW-05 already needs (hazard 2: an API env var arrives only through
  Terraform + an HCP apply). Cloud-architect owns the file; this seat owns the requirement.
- **S15-10 — nothing about a token's shape is asserted as proven until one interactive
  sign-in on deployed `dev`.** ADR-010's w14 footer clause 4 already requires this for the
  identity plane, and it fails *after CI is green, in the browser*. The NW-05 task's
  acceptance names the claims it observed (`ver`, `aud`, `iss`, `oid`, `scp`, `email`) in
  the runbook. This is the honest form of every Entra claim statement in §1.2.

### 1.3 What the interim mechanism becomes, and when it is removed

| Mechanism | Today | After NW-05 | Proof |
|---|---|---|---|
| `X-User-Id` | the identity, one seam (`CallerIdentity.cs:58-73`) | **not read at all.** `HeaderCallerIdentity` is replaced by a token-subject implementation; the class and its `UserIdHeaderName` constant (`:60`) are deleted, not kept "for compatibility" | S-T1 |
| `X-Tenant-Id` | a caller-asserted tenant, read at **74 sites / 17 files** | **not an authorization input.** A caller-supplied tenant id is a **selector**: membership of the token subject in it is verified *before* any scope is entered (ADR-009 w14 clause 7). A non-member gets **404** | S-T2 |
| `X-Role` / `X-Workspace-Role` | UI shaping only (ADR-022 w14 footer) | retired by **NW-31 (W16 head)** — the constants at `WorkspaceRoleResolver.cs:48-49` and the unreferenced `TryResolveHeaderRole` (`:89-102`) go with NW-06 (§2) | S-T3 |
| `"unattributed"` actor | 4 endpoint paths + 9 service defaults | unreachable on the API surface (absent identity is 401) — the **deletion** is NW-32 (W16 head) | §6.3 |

- **S15-11 — a caller-supplied tenant id is a selector, not an assertion.** This
  generalizes ADR-022 w14 footer clause 3 from membership routes to every route. Whether it
  travels as a route segment or a header is software-architect's shape; that it is verified
  against the **token subject's** membership before `BeginScope`, and that failure is
  **404** and never 403, is this seat's.
- **S15-12 — revocation stays immediate; nothing caches authorization.** ADR-025 Rule D.5b
  holds *because* role and tenant are read from the database per request. The token caches
  **identity** for its lifetime and nothing else. **No membership cache, no role cache, no
  session cookie, no claims transformation that materializes a role.** A removed member's
  token still authenticates — and gets 404 everywhere, which is the correct answer.

### 1.4 Rejection contract (extends ADR-025 §B; no row is changed)

| Situation | Status |
|---|---|
| No `Authorization` header, or a token failing S15-1…S15-4 | **401** |
| Valid token, required scope absent (S15-5) | **403** |
| Valid token, caller is not a member of the selected tenant | **404** (never 403 — ADR-025 Rule B1, unchanged) |
| Valid token, member, wrong role | **403** |
| Forged `X-User-Id` / `X-Tenant-Id` with **no** valid token | **401** — A15-8 verbatim |
| Valid token `A` **plus** `X-User-Id: B` | acts as `A`; the header is **not read** (ADR-025 Rule A3 / T14) |

**ADR action**: amend **ADR-010** (S15-1…S15-12) and **ADR-022** (the retirement table and
its proofs). ADR-010's Decision outcome — four registrations, PKCE, per-env `iss`/`aud` — is
unchanged; the amendment records the validation parameters and the two claims that are never
authorization.

## §2. NW-06 — workspace role from membership / claims, never a client assertion

**Status today, verified.** `WorkspaceRoleResolver.ResolveAsync` (`:55-71`) has two sources:
a claims branch (`:60-65`) and the membership read (`:70`, `:104-137`). `:67-69` records, in
the code, that the header branch was **deleted** in w14. The claims branch has **never
executed** — there is no authenticated principal in this host (§0).

### 2.1 The finding: NW-05 turns a dead branch into a cross-tenant escalation

`ResolveAsync(httpContext, tenantId, …)` takes a `tenantId` and the claims branch
**ignores it entirely**: it returns `claimRole` for *any* tenant, before the tenant-scoped
membership join at `:122-132` ever runs. Today that is harmless because the branch is
unreachable. The moment NW-05 wires JWT, an Entra **app role** named in a way
`WorkspaceRoleClaimResolver` accepts — assigned once, in the directory, by a directory
admin, for the whole environment — would resolve to that role in **every workspace the
caller can name**, bypassing `workspace_membership` completely. `IsAdminAsync` (`:74-76`)
is the gate for `DELETE /api/documents/{id}` and `POST …/reprocess` (R-DOC-07/R-DOC-10), so
the failure mode is cross-tenant destructive access, not just visibility.

### 2.2 Decision — delete the claims branch; membership is the only source

- **S15-13 — the claims branch is deleted, not enabled.** ADR-025 §E lists claims first as
  "the ADR-010 end state"; ADR-010's own w14 footer clause 1 and ADR-025 **§I**, written
  later in the same wave, override it: *"the token carries identity only … a `tenant_id` or
  `roles` claim is **never** the authorization source."* Where §E and §I touch one
  mechanism, §I governs — it is the section ADR-025 wrote specifically to bind this wave.
  So NW-06's ruling is the opposite of "prove the claims branch live": `ResolveAsync`
  collapses to `ResolveMembershipRoleAsync`, `WorkspaceRoleClaimResolver` keeps its
  remaining non-authorization caller (`GET /api/capabilities`, until NW-31), and the two
  header constants (`:48-49`) plus `TryResolveHeaderRole` (`:89-102`, zero call sites) are
  deleted in the same edit.

  This is strictly cheaper than the alternative: reviewing and tenant-scoping a claims
  path costs a design, a Terraform app-role, an assignment story and a permanent second
  authorization source. Deleting it costs six lines and removes a class of bug.
- The membership read (`:104-137`) is unaffected by NW-05 **except** that `identity` becomes
  the token's `oid` (S15-6). The join already matches `user.ExternalSubjectId == identity`
  (`:129`), so the swap needs no query change — exactly what ADR-025 Rule F.2c promised.

**ADR action**: amend **ADR-022** (this is the last interim reader to go) and record the
§E/§I reconciliation in the **ADR-010** amendment, so a reviewer reading §E alone does not
conclude the claims branch survives. ADR-025's body is **not** rewritten.

## §3. NW-67 — Raffa provisions the invitee's Entra B2B guest at invite time (Graph)

An invitation stops being a database row and becomes a **write into the company
directory**. That is a new trust boundary and it is this seat's decision.

### 3.1 The permission, and its blast radius

- **S15-14 — `User.Invite.All`, application permission, on the existing per-environment
  workload identity.** Confirms **OQ-w15-005**'s assumption in force. It is the least
  privilege that satisfies Graph `POST /invitations`.
  - **Rejected: `User.ReadWrite.All`** — read, update and delete of *every* user object in
    the directory, to create a guest. Not proportionate; not proposed.
  - **Rejected: delegated `User.Invite.All` via on-behalf-of.** Better attribution (the
    invite runs as the human Admin) but requires an OBO exchange, a confidential-client
    credential the design deliberately does not have (ADR-010 `:84-85`), and the inviting
    Admin to hold the directory's *Guest Inviter* role — which a customer's Procurement
    Admin will not. Recorded as the correct shape for a future enterprise tenant, not for
    the pilot.
  - **No new secret** — managed identity, so **ADR-011 gains no Key Vault entry for
    NW-67** (ADR-011 w14 footer clause 1's zero-key posture holds for this item).
  - Admin consent is a **one-time operator act** at the ADR-016 gate (delivery-manager),
    not a CI credential — hence **ADR-015 action: none**.
- **S15-15 — blast radius, stated so it is owned.** The API container app can now invite any
  external address into the company directory. Bounds, all enforceable:
  1. **One call site.** The Graph client is constructed and called in exactly one type. A
     `Grep` for the Graph client symbol in `backend/src` finds **one** file. Any second
     call site is a defect.
  2. **Reachable only behind ADR-025 Rule D.1a** — identity (401) → membership in the
     **route** tenant (404) → `Admin` (403). The directory write happens *after* all three,
     never before.
  3. **The invited address comes from the authenticated Admin's request body and nowhere
     else** — never a claim, never a header, never an `X-Forwarded-*` value.
  4. **A per-tenant cap on live (unaccepted, unrevoked) invitations**, default **100**,
     audited as `workspace.invitation.cap_reached` when hit, mirroring ADR-025 Rule F.1f's
     posture. ADR-025 §F.4's partial unique index already prevents accumulating links for
     the *same* address; the cap bounds *distinct* addresses, which is the directory-spam
     shape. The product-owner may change the number; the mechanism does not change.
- **S15-16 — `sendInvitationMessage: false`, and the redeem URL is radioactive.** Graph
  returns an `inviteRedeemUrl`. It is a credential-shaped URL that redeems the guest
  **directly**, with no Raffa invitation row, no token, no email match (ADR-025 D.3b) and
  **no `workspace_membership` write**. An invitee who used it would become a directory
  guest inside a customer's Entra tenant while belonging to no workspace.
  **The `inviteRedeemUrl` is never mailed, never returned to any client, never stored,
  never logged, never audited.** It is consumed nowhere. Raffa's own
  `/invite/accept#<token>` (`WorkspaceInvitationService.cs:58`, `:86`) remains the one and
  only accept channel.

### 3.2 Ordering — guest first, invitation row second

- **S15-17 — provision the guest *before* the invitation row is committed.** The two
  failure modes are not symmetric:
  - *Row first, Graph fails* → a **live 256-bit token** exists for an identity that cannot
    sign in. That is precisely A15-7's defect — "a 'ready' link that cannot be used" — and
    the token is a credential sitting in a database for seven days.
  - *Graph first, row fails* → an **orphan B2B guest** with no `workspace_user` and no
    `workspace_membership`. Under S15-18 that guest can see **nothing**, in any workspace,
    in either environment. It is inert, and it is reconciled by the next invite for the
    same address (the already-present no-op, A15-5).
  An inert artefact beats a live credential. Where the Graph seam *sits* (API or Worker) is
  software-architect's; the **ordering** is this seat's.
- **S15-18 — directory presence is not a grant.** ADR-025 Rule F.1d already says membership,
  not `workspace_user` existence, is the grant. NW-67 extends the same sentence one level
  out: **a B2B guest object grants nothing.** A guest who signs in with no membership row
  sees 404 on every tenant-scoped route and an empty `GET /api/workspaces` (ADR-025 Rule
  F.1g — the list is keyed on identity and returns only tenants with a live membership).
  This is the rule that makes S15-17, S15-19 and S15-20 all safe at once.

### 3.3 The bind that makes A15-4 pass

- **S15-19 — store the Graph-returned guest object id in `workspace_user.ExternalSubjectId`
  at invite time.** Raffa issues the Graph call, so it receives the created (or existing)
  guest user's `id` — the `oid` that will appear in that person's token. Binding it at
  invite time means accept matches on **`oid`**, exactly (S15-6), and the mangled `#EXT#`
  UPN never enters an authorization decision (S15-8). Without this, NW-67 + NW-05 together
  break ADR-025 Rule D.3b's email equality and A15-4 fails at the last step.
  ADR-025 Rule D.3c step 2 (`LinkSignInAsync`) is **unchanged** — it becomes a confirmation
  of an already-bound subject rather than the first bind. This is the item's highest-value
  detail and the decomposer must carry it verbatim.

### 3.4 Failure, no-op, and the two answers the caller may see

- **S15-20 — the provisioning outcome has exactly two externally-visible values.**
  `provisioned` (covering *both* "newly created" and "already present in the directory")
  and `failed` (a **fixed enumeration** of named reasons). The invite form must not become a
  **directory-enumeration oracle**: a workspace Admin is not a directory admin, and
  "this address already exists in your company tenant" is a fact about the directory, not
  about the workspace. A15-5's no-op must therefore be *indistinguishable* from a fresh
  provision in the response.
- **S15-21 — a Graph error body is never surfaced or logged verbatim.** It can carry
  directory configuration, tenant policy detail and other users' data. The response carries
  a named code from S15-20's enumeration; the audit row and the log carry that code plus the
  Graph `request-id` (an opaque correlation value). Never the raw response, never the
  `inviteRedeemUrl` (S15-16).
- **S15-22 — a failed provisioning never yields a link the pane presents as ready.** The
  invitation row may exist so the Admin can retry, but the 201 body must make the failure a
  **server fact** the pane renders (NW-69's job — this is the security half of A15-7). The
  pane never infers it.

### 3.5 Removal, and the shared directory

- **S15-23 — removing a workspace membership never deletes or blocks the Entra guest.**
  Confirms **OQ-w15-007**'s assumption in force. The guest may belong to other workspaces or
  to the tenant's own business; deleting a directory object because one workspace removed a
  member is a destructive act far outside Raffa's mandate, and it is **unnecessary** —
  ADR-025 Rule D.5b already makes removal immediate (nothing caches authorization) and
  S15-18 makes the surviving guest inert. **No directory-deletion path is built, in this
  wave or later, without a new ADR.** ADR-025 Rule D.5c (removal revokes that email's live
  invitations in the same transaction) is unchanged and still carries the whole revocation.
- **S15-24 — one directory across `dev` and `demo` is acceptable, and here is why.**
  Confirms **OQ-w15-005**'s second half. Both registrations are `AzureADMyOrg` in the same
  directory (`identity/main.tf:63`, `:118`), so a guest provisioned from `dev` is visible in
  `demo`. That is *already* the accepted isolation model — ADR-010 isolates by
  **registration**, and `identity/main.tf:61-62` states it verbatim: "dev/demo isolation is
  by distinct registration, not by separate Entra tenants". It is acceptable **only**
  because S15-18 holds: a `dev`-provisioned guest signing into `demo` has no
  `workspace_user` and no `workspace_membership` in any `demo` tenant and gets 404
  everywhere. **S-T18 proves it rather than assuming it.**
  Recorded residual, accepted: the invitee's address becomes visible to whoever can read
  the company directory (the tenant's own admins) — not to another customer, and not to
  another workspace. Gating provisioning per environment was considered and **rejected**:
  it would mean a `demo` invite could not provision at all (same directory, same object),
  buying nothing that S15-18 does not already give.

### 3.6 Audit (extends ADR-011 w14 footer clause 4 / ADR-025 §G — additive, no schema change)

`AuditEvent.Action` is a free-form string (`../backend/src/Raffa.Audit/Domain/AuditEvent.cs:29`)
and every existing verb is an inline literal, so these are additive:

| Action | Actor | ResourceType / ResourceId | `Detail` may carry |
|---|---|---|---|
| `workspace.guest.provisioned` | inviting Admin | `WorkspaceInvitation` / invitation id | invited email, role, guest object id |

## §4. NW-68 — Raffa sends the invitation email (ACS Email)

The ADR-005 w14 footer's design (ACS Email, Azure Managed Domain, `infra/modules/communication`,
`acs-connection` → `acs-cs`, the four config keys, `data_location = "Europe"`) is **accepted
and not re-opened**. This seat rules on the secret, the link, and the logs.

### 4.1 The credential

- **S15-26 — whichever credential form ships, these three bind.** (a) It exists **only** in
  this environment's Key Vault, reached by the workload managed identity (ADR-011 Option 1,
  unchanged); (b) it never appears in source, a client bundle, Terraform source, a workflow
  file or a container image layer; (c) it is never logged, never echoed in an error, never
  put in an audit row.
- **S15-27 — proposal (not an objection): prefer managed-identity auth to ACS over a
  connection string.** Azure Communication Services accepts an Entra `TokenCredential` on
  the Email client. Using the workload identity there removes the secret **entirely** —
  no `acs-connection` vault entry, no `acs-cs` container-app secret handle, no rotation
  story, no per-environment drift. That is strictly stronger than the connection-string
  form and costs a role assignment instead of a secret. **ADR-005 is cloud-architect's
  ADR** and its w14 footer already names `acs-connection`; I raise this as a `PROPOSE` at
  the table, not an `OBJECT` — it weakens nothing either way, and S15-26 binds the
  connection-string form if that is the ruling.

### 4.2 The link — `Invitations__AcceptUrlBase` is a security control

- **S15-28 — the accept base is configuration, never a request value.** The base is
  `https://` + **this environment's own SPA host**, supplied by Terraform (the value already
  exists: `containerapps/main.tf:188-193` builds CORS from `var.spa_host_name`, declared
  `containerapps/variables.tf:59`, wired from `module.staticwebapp.default_host_name`). It
  is **never** derived from `Host`, `Origin`, `X-Forwarded-Host` or any other request
  header. A host-header-injected accept base means Raffa **mails a live invitation token to
  an attacker-controlled origin** — the invitee clicks a Raffa-branded mail and hands the
  token over. This is the single reason `Invitations__AcceptUrlBase` cannot be "computed".
- **S15-29 — fail closed at startup.** If `Invitations__Mail__Enabled` is true and
  `Invitations__AcceptUrlBase` is absent, not `https://`, or not a well-formed absolute URI,
  the API **fails to start**. It does not fall back to the site-relative constant and mail a
  fragment with no origin, and it does not disable mail silently. If
  `Invitations__Mail__Enabled` is false the seam stays `NullInvitationMailer`
  (`ServiceCollectionExtensions.cs:61` today) — there is no third state where a mailer is
  registered but unconfigured.
- **S15-30 — Rule C9 survives the transport, and is now load-bearing for a new reason.**
  ADR-025 Rule C9 puts the token in a URL **fragment** (`AcceptRoutePrefix = "/invite/accept#"`,
  `WorkspaceInvitationService.cs:58`). A fragment is never transmitted to any server —
  which is exactly what makes it safe to put this link in an **email**, where it will pass
  through mail gateways, archivers and click-protection / link-rewriting services that
  fetch or rewrite URLs server-side. A token in a query string would be handed to every one
  of them. The absolute base changes the origin and **nothing else**: the token stays after
  the `#`, and Rule C10 / C10a / C10b / T15 are unchanged.
- **S15-31 — one recipient, no other headers.** The mail goes to the invited address only.
  No CC, no BCC, no distribution list, and no `Reply-To` pointing at a Raffa-operated
  mailbox that could receive a forwarded token. The invited address is not echoed into any
  other tenant's mail.

### 4.3 Logs, audit, and what `mailDelivered` may claim

- **S15-32 — no mail body, no recipient content, no rendered link in any log sink.** This
  is the locked ADR-011 posture applied to a new sink. `NullInvitationMailer.cs:25-29`
  already models the discipline exactly — the `acceptUrl` parameter is in the signature and
  is **deliberately never interpolated into the log statement**. The real mailer must keep
  that property: it may log the recipient address, the ACS operation id and a named outcome;
  never the body, never the subject's rendered content, never the URL.
- **S15-33 — two new audit verbs, additive.** `workspace.invitation.mail_sent` and
  `workspace.invitation.mail_failed`, actor = the inviting Admin, `ResourceType` =
  `WorkspaceInvitation`, `ResourceId` = the invitation id. `Detail` may carry the invited
  email (ADR-025 §G already allows it), the ACS operation id, and a named failure reason.
  **Never** the accept URL, the token, the body, or a raw ACS error payload.
- **S15-34 — `mailDelivered: true` means *accepted for delivery*, not *delivered*.** It
  stays the server fact `WorkspaceInvitationService.cs:99-101` already returns — the bool
  from `IInvitationMailer.TrySendAsync`. It is set only when ACS accepted the message. It is
  never a delivery receipt, never inferred by the client (ADR-012's provenance rule), and
  never optimistically `true` on a queued-but-unconfirmed send. A15-6's failure path
  (`false` + the ADR-020 copy + the link still works) is the honest answer and must stay
  reachable.

**ADR action**: amend **ADR-011** (the `acs-connection` secret — or its managed-identity
replacement, S15-27 — plus S15-28…S15-33's never-log list; this is the concrete instance of
ADR-011's w14 footer clause 2, "if a mail transport lands later"), amend **ADR-025** (§J
gains S15-28…S15-31, because the accept link's integrity is the invitation lifecycle's).
ADR-005 / ADR-007 / ADR-016 actions are cloud-architect's and delivery-manager's;
**ADR-026** (absolute `acceptUrl`) is software-architect's shape with S15-28 binding it.

## §6. Forward rules for the W16 head (roster names me; not at this table)

NW-07, NW-08 and NW-32 are **queued** by §5 and carry no `w15` task. They are recorded here
because **NW-05 changes their behaviour whether or not W16 has run**, and the W16 intake
must not re-audit them.

### 6.1 NW-08 — `GET /api/audit` after NW-05 (the one that must not "just work")

`AuditEndpointExtensions.cs:22-36` calls `WorkspacePrincipalAuthorization.TryAuthorize`,
which demands an authenticated principal (`:56-60`), a **`tenant_id`** claim (`:35`,
`:62-67`) and a `ClaimTypes.Role` claim (`:69-74`). After NW-05 a real Entra token supplies
none of those two claims, so the endpoint **stays 401/403 — it fails closed, and that is
correct.** The danger is the repair: mapping `tid` → `tenant_id` (S15-7) or minting a role
claim (S15-13) to make it work would ship the stale-authorization window and the
last-Admin-guard bypass ADR-025 §I names by ID.

- **S15-39 (binds W16).** NW-08's fix is the **§I seam swap**: `TryAuthorize`'s tenant and
  role resolution moves from claim-reading to **membership-reading**, at the one place
  `WorkspacePrincipalAuthorization.cs:32-33` says every caller goes through. `TenantIdClaimType`
  is deleted with it. `GET /api/audit` keeps **403** for a member without the role — ADR-025
  Rule B2 is unchanged, because its tenant never comes from a caller-supplied value
  (`AuditEndpointExtensions.cs:25-29`). Who may read a tenant's audit trail: **a live
  `Admin` membership in that tenant, and nobody else.** The read stays tenant-scoped; the
  route gains no `?tenantId=`.

### 6.2 NW-07 — conversation `user_id`

The live bug is independent of NW-05: `HeaderCallerIdentity` lower-cases
(`CallerIdentity.cs:71`) while `ConversationsEndpointExtensions.TryResolveUserId` does not,
so one person can be split across two keys by a case difference in their UPN.

- **S15-40 (binds W16).** After NW-05 the conversation key is the token `oid` (S15-6) —
  case-invariant by construction, which dissolves the normalization bug rather than patching
  it. Per-user isolation is the property: a caller reads only conversations whose `user_id`
  is their own subject, **inside** their tenant scope. Rows written under the old
  header-derived key are **not silently re-keyed** — a migration that re-points conversation
  ownership by string matching is a cross-user data move; either migrate on an explicit
  `(old key, oid)` pair supplied at HITL (the ADR-025 Rule D.2e backfill pattern) or leave
  them orphaned. Orphaned pilot chat history is a smaller problem than a mis-attributed one.

### 6.3 NW-32 — the `"unattributed"` actor

- **S15-41 (binds W16).** After NW-05 an absent identity is **401** everywhere, so the three
  divergent behaviours (401 / 400 / a silent `"unattributed"` audit row) collapse to one.
  The nine service-layer defaults would nevertheless survive as the value written to
  `CreatedBy`/`CorrectedBy` and to audit rows, so NW-32 is a **deliberate deletion**: the
  constant goes, the resolved identity is threaded in, and an audit row that cannot name its
  actor becomes unwritable rather than unattributed. ADR-011's audit posture requires it —
  an audit trail whose actor column can hold a placeholder is not an audit trail. ADR-025
  §G Rule G1 already closed the workspace surface; this closes the rest.

## §7. Rules I place on items where I am **not** rostered

I am not on NW-27 or NW-61 and I claim **no decision row** for either — those are
software-architect's, cloud-architect's, product-owner's and ux-ui-designer's. But NW-27's
own touchpoint list names **ADR-009**, which only this seat may amend, and no other seat can
write that footer.

### 7.1 NW-27 — the Worker's tenant scope (ADR-009)

ADR-009's "Implications for the decomposition" already binds this, verbatim: *"Background
worker jobs … must carry `tenant_id` from the queue message and set the same connection
claim — a job derived from tenant A's document must never run in tenant B's context."*
NW-27 is the first wave to actually build that path, so the rule needs its mechanism.

- **S15-42 — a Service Bus message body is untrusted input.** Anyone holding Send rights on
  the namespace can enqueue one. So the message's tenant id gets **exactly the ADR-025 Rule
  C4 treatment**: `Guid.TryParseExact(…, "N")` **before** `ITenantContext.BeginScope`; a
  parse failure dead-letters the message and enters no scope. This is the same discipline
  that keeps `TenantRlsConnectionInterceptor.BuildSetCommandText`'s "the tenant is always a
  parsed Guid" justification true, now applied to the second caller-controlled value that
  reaches it.
- **S15-43 — the first statement inside the worker's scope is the job-row match** (ADR-025
  Rule C5, reused). The worker reads **nothing** — not the document, not the blob, not a
  count — until the `ExtractionJob` row identified by the message is found *in that tenant*.
  A miss disposes the scope and dead-letters. Without this, a forged message is a read
  primitive against an arbitrary tenant.
- **S15-44 — one scope per message, and a message is a job.** ADR-009 w14 clause 4's "two
  named exceptions, and only two" is unchanged: the Worker is **not** a third exception. One
  message, one tenant, one scope, one unit of work; the connection closes between messages
  (ADR-009 w14 clause 5 / ADR-025 Rule F.3a — a scope change takes effect only on a
  connection opened after it, and a pooled connection carrying a stale claim is a
  cross-tenant read RLS cannot catch).
- **S15-45 — the message carries ids only.** No contract text, no extracted facts, no
  personal data, no file bytes, no blob SAS. A queue — and especially its **dead-letter
  queue**, which retains bodies for operator inspection — is a log-like sink readable by
  anyone with Listen rights, and ADR-011 forbids raw contract content in a log sink.
- **S15-46 — no shared-access-key connection string for Service Bus, anywhere.** Managed
  identity + Azure RBAC: **`Azure Service Bus Data Sender`** on the identity the API uses,
  **`Azure Service Bus Data Receiver`** on the identity the Worker uses, and **no** `Manage`
  right on either. The fully-qualified namespace is non-secret config. ADR-011's locked
  "managed identity" row makes this the default; recorded because
  `RootManageSharedAccessKey` + a Key Vault secret is the obvious shortcut, and it would
  hand any holder both send and receive on every queue in the namespace. **ADR-011 gains no
  Service Bus secret.**
- **S15-47 — if NW-27 adds any table** (an outbox, a job-claim table, a rejection record),
  it is an **ordinary tenant table** under ADR-009 §8: `tenant_id` not null and indexed,
  `ENABLE` + `FORCE ROW LEVEL SECURITY`, a `tenant_isolation` policy with **both** `USING`
  and `WITH CHECK`, shipped **in the same migration as the table** (`TenantRlsDeployableScriptCheckTests`
  fails the build otherwise). No identity-keyed policy — the ADR-025 §F.1 widening stays
  confined to `workspace_user`.
- **S15-48 — a `Rejected` document row is a tenant row like any other.** If OQ-w15-004's
  assumption holds and the admission gate moves to the Worker, the refused file becomes a
  **persisted row inside a tenant**. Two consequences: it must never be retrievable by Ask
  (ADR-011's two-corpora footer already forbids embedding a document that has not passed
  validation — a `Rejected` row must produce **no** embedding rows, and if the gate now runs
  post-persistence the "rejected files are never stored" sentence in ADR-011's ADR-024
  footer needs the amendment software-architect and product-owner are writing); and the
  stored artefact is a file a tenant uploaded, so it carries the same `tenant_id`-prefixed
  blob path rule as any other (ADR-009 "Implications", object paths tenant-prefixed, never a
  client-supplied raw blob URL).

### 7.2 NW-61 — the completeness signal

- **S15-49.** The "still processing" signal on Contract 360, Portfolio and Ask is a
  **count/status about tenant data**, so it is produced by a **tenant-scoped read under that
  tenant's own claim** — never a cross-tenant aggregate or a group-by over all tenants
  (ADR-025 Rule F.5, verbatim: *"A number is data"*). And Ask's gate must remain
  authz-before-retrieval: the off-state is decided **after** the caller's tenant is a
  verified membership fact, and a document that has not passed validation contributes
  neither an answer nor a fact (ADR-011, ADR-024). Today's gate is *inferred* client-side
  (`askViewModel.ts:250-261`); replacing an inference with a server fact strengthens
  ADR-011, and no client heuristic may re-introduce it.

## §13. Verification pass (this lane turn, baseline `3720543`)

This draft pre-existed my turn. Per the harness's verify-or-write rule I kept it and
re-read every load-bearing citation against the tree rather than defend an unread line at
the table. **Result: every citation in §0–§12 holds, with one correction (13.1) and four
refinements.** Corrections are marked **[C]**, refinements **[R]**; each names the rule it
touches so the table and the decomposer can act on it without re-reading the file.

### 13.1 [C] S15-47 names a test that does not exist

S15-47 (and §11) cite **`TenantRlsDeployableScriptCheckTests`**. There is no such type.
The real guard is **`backend/tests/Raffa.Tenancy/TenantRlsMigrationCheckTests.cs`** —
`:19`, `:29` `Every_tenant_scoped_table_has_forced_row_level_security_and_a_policy`. Its
own doc comment (`:9-12`) is the sentence to quote: it "runs as part of the normal
`dotnet test` step in `.github/workflows/backend.yml`, migrates a disposable Postgres
instance, and fails the build if any tenant-scoped table is missing `ROW LEVEL SECURITY`,
`FORCE ROW LEVEL SECURITY`, or an actual policy."

**Read S15-47 with that name.** A task told to satisfy a non-existent test finds nothing,
concludes the guard is absent, and ships the table without the policy — the exact omission
ADR-009 `:57-58` ("every new table added later must opt in to the same policy — **a
migration-time check**") created the check to prevent.

### 13.2 [R] The RLS guard is conditional, and NW-27's new table may fall outside it

This is the substantive half of 13.1 and it changes what S15-47 must *require*.
`TenantRlsMigrationCheckTests:37-44` discovers its table list **dynamically from the EF
model — every `TenantScopedEntity` subclass — of `DocumentsContractsDbContext` alone**
(`:31-34`). Automatic coverage therefore holds **only** when a new table's entity
subclasses `TenantScopedEntity` **and** lives in that context.

The tree already proves the gap: `workspace_invitation` (w14) lives in
`IdentityWorkspaceDbContext`, so w14 had to hand-write
**`WorkspaceInvitationRlsTests.cs`** for it, and its doc comment (`:12-21`) says so —
"the same shape `TenantRlsCrossTenantIsolationTests` and
`WorkspaceRlsCrossTenantIsolationTests` already proved for the four pre-existing tables,
applied here to the new one."

**S15-47 gains a clause**: if NW-27 adds an outbox, a job-claim table or a rejection
record, the task must **either** put it in `DocumentsContractsDbContext` as a
`TenantScopedEntity` (automatic coverage) **or** ship a hand-written per-table RLS test
on the `WorkspaceInvitationRlsTests` pattern. "The migration check covers it" is an
assumption a decomposer will otherwise make for free, and it is false half the time.

### 13.3 [R] A new RLS test written against the default container role passes vacuously

`WorkspaceInvitationRlsTests:23-25` states the trap outright: every assertion runs
"through a dedicated, deliberately unprivileged Postgres role — see
`TenantRlsCrossTenantIsolationTests`'s own doc comment for why a superuser connection
would make this pass vacuously." `:29-30` shows the mechanism (`raffa_invitation_app`).

Testcontainers hands you a **superuser** by default, and RLS does not constrain a
superuser or a table owner. A new-table RLS test written the obvious way is **green and
worthless**. Any hand-written test under 13.2 must create its own unprivileged role.
This binds NW-27's task and is not visible from ADR-009's text alone.

### 13.4 [R] The code — not ADR-025 §E — carries the instruction S15-13 overrules

§2.2 attributes "the ADR-010 end state" to ADR-025 §E. Verified: §E is at
`ADR-025:395` and is about a **client-declared role** (headers). The phrase is in the
**source**: `WorkspaceRoleResolver.cs:20-22` describes the claims branch as *"the ADR-010
end state, and the only source that survives past this wave."*

This makes **S15-13 stronger, not weaker**. An implementer opening the file to wire NW-05
reads a doc comment instructing them to keep and enable the claims branch — and the branch
is the cross-tenant escalation §2.1 describes, now re-confirmed on disk:
`ResolveAsync(httpContext, tenantId, …)` returns `claimRole` at `:60-65` **without ever
referencing its `tenantId` parameter**; only `:70` is tenant-scoped. So the deletion must
take the **doc comment with it**, or the next wave restores the branch from its own
documentation. ADR-025 §I (`:658-677`, read in full) is unambiguous and governs: *"the
token carries identity only … a `tenant_id` or `roles` claim is **never** the
authorization source"*, remedied at the one seam `WorkspacePrincipalAuthorization.cs:32-33`
names.
