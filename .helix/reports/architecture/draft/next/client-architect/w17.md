## NW-72 — Savings realized amount (head, epic-20)

- **Decision**: the KPI renders **currency-grouped money from the server**, and
  the client **never sums across currencies** (a cross-currency total is a
  fabricated number). Absent → the existing `—` idiom (`KpiRow.tsx:49`), never
  a fabricated `0`.
- **No new cell shape is needed.** `KpiCell.lines` is already `string[]` and
  `savingsViewModel.ts:91` already renders currency buckets
  (`annualSpendAnalyzed.map(bucket => formatCurrencyAmount(...))`). Realized
  money follows that exact idiom. Whether it is a 4th cell or a second line in
  "Savings identified" is ux-ui-designer's (screens-v2 §8 has no money slot).
- **Generated client must expose**: realized money as an array of
  `{currency, amount}` on the **existing** `GET /api/savings/kpis` body,
  mirroring `annualSpendAnalyzed`. **Not** the PATCH-only `realizedAmount`
  (`schema.ts:614`) — per OQ-w17-006 that stays PATCH-only.
- **⚠ §5 constraint 7 narrows**: if the field rides the existing KPI body (a
  re-exported generated type), **NW-72 is not a `client.ts` writer** and NW-63
  owns that file alone. The decomposer must confirm the KPI body is generated,
  not hand-declared, before assigning two writers.
- **Sweep**: `savingsViewModel.ts:92` carries a stale comment — "Realized KPI
  stays a count (clause 29)". Same task, same sweep as the backend comments.
- **e2e**: `w17-savings.spec.ts` — A17-S1, in the shape `invite.spec.ts:196`
  already uses: record an outcome → money appears grouped by currency →
  **reload and a second browser agree**.
- **ADR action**: `none` from this seat — ADR-001/ADR-028's money fence is
  product-owner's to lift; I record only the no-cross-currency-sum rule.

## NW-71 — Auto-accept ≥ 90 % (`must`, epic-22) — **the flagship read-back**

- **Decision**: the web **renders the server's persisted per-field decision and
  never recomputes it** (OQ-w17-002's assumption adopted). `semantics.ts`
  becomes **label-only**: `getConfidenceTag` paints a confidence *label*; it no
  longer decides acceptance. `isConfidenceBlocking` (`reviewViewModel.ts:294`)
  must read the server decision, not `< 80`.
- **The store this replaces, and the endpoint that replaces it**:
  `acceptedThisSession` — `useReviewSession.ts:92` — a `useState<Set<…>>` folded
  into the rows at `:145`. **`accept()` already has two branches and they are
  not equal**: `:177-182` does a real `PATCH` + `load()` read-back, while `:184`
  is pure React state with **no network at all**. Two kinds of "accepted",
  rendered identically; on reload the second kind vanishes. NW-71 adds a
  **third** (server auto-accept). One screen, three durabilities, one paint —
  this is exactly the cache-instead-of-a-GET my lane forbids.
- **The read-back path already exists**: `useReviewSession.ts:124` already calls
  `getContractEvidence` on every `load()`. If the per-field decision is a column
  on `extraction_evidence`, the review screen reads it back with **zero new
  endpoints and zero new fetches**. (security-architect reaches the same table
  from isolation — already `FORCE`-protected, per-field keyed. Two seats, two
  reasons, one answer — worth recording at the table.)
- **Binding rule**: a row's accepted state renders from the **server's**
  decision. A session-only acceptance may exist for a decision not yet written,
  but must be **visibly distinct** (pending), never painted as a persisted one.
- **Generated client must expose**: a per-field decision enum (e.g.
  `decision: "auto_accepted" | "needs_review"`) on the evidence body. The
  **threshold itself is never on the wire as a client rule** — the number is the
  server's; the client learns only the outcome.
- **Precedent**: NW-10 already did this once — `navItems.ts:85-90` records the
  `sessionStorage` tracker retired in favour of `useDocumentCounts`. Same move.
- **Seed**: `stash@{2}`'s web half is presentation-only under this ruling; take
  its band collapse, **drop its rounded `>=` comparison** (OQ-w17-002).
- **e2e**: `w17-review.spec.ts` — A17-1…A17-4: a ≥90 % field shows Accepted
  **without a click**, and **survives reload** (template: `v2.spec.ts:757`).
- **ADR action**: **amend ADR-012** (client renders server decisions; the
  read-back rule named against `acceptedThisSession`). ADR-019's bands are
  ux-ui-designer's; ADR-003/ADR-011 software/security.

## NW-62 — 360 answers (`must`, epic-21)

- **Decision**: **consume the server's answer; never compose a second one in the
  view model** (OQ-w17-005 adopted). `buildAnswers`
  (`contract360ViewModel.ts:160-199`) maps a server answer; it does not compute.
- **The cost is already paid.** `contract360/index.tsx:115-119` already runs
  three parallel GETs after the 360 and `:48-50` documents the rule: an optional
  source that fails "degrades its own answer to an honest 'not yet' rather than
  failing the screen". Adding `getContractStrategy` (already generated,
  `schema.ts:724`) to that `Promise.all` needs **no new loading architecture**.
- **The line that matters for N16**: `SAVINGS_NOT_YET_AVAILABLE` /
  `LEVER_NOT_YET_AVAILABLE` (`:150-152`) survive **only** as the
  absent/failed state of a real source — never as the steady state of a source
  that is never called. That is the whole defect today.
- **One source, not two.** If software-architect composes the answer into the
  360 payload instead, the band reads that and **does not** call `/strategy`.
  Either shape is acceptable; two sources on one screen is not.
- **Generated client must expose**: `getContractStrategy` — already present; no
  new hand-written glue, so **NW-62 is not a `client.ts` writer**.
- **e2e**: `w17-answers.spec.ts` — N16: both cells concrete with citations on a
  contract whose facts are in the file; and an explicit case that the constants
  appear **only** when the source is genuinely absent.
- **ADR action**: `none` from this seat (ADR-024's payload is software's); the
  one-answer-source rule goes in the **ADR-012** amendment.

## NW-63 — Document viewer (`must`, epic-22) — **OQ-w17-001**

- **The split is right, and it costs no dependency.** I adopt the assumption in
  force (W17 ships the viewer over real pages; bbox overlays + editable phrases
  head W18) — and add the reason no seat has priced: **because NW-26 rasterises
  server-side, the viewer renders PNG pages, so no PDF library is needed at
  all** — not this wave, and not for the W18 remainder (a bbox overlay is
  absolutely-positioned DOM over an `<img>`). `package.json:19-25` stays at five
  runtime dependencies. **ADR-012's dependency fence is not breached.**
- **This must be recorded, not just done**: an implementer handed "document
  viewer" adds `react-pdf` reflexively. The ADR-012 footer says why not.
- **The real client risk is object-URL lifetime.** `getDocumentPreviewUrl`
  (`client.ts:2082-2113`) returns `URL.createObjectURL(blob)` — an
  **authenticated** fetch (`X-Tenant-Id` + bearer, `:2086`), so a plain
  `<img src="/api/…">` **cannot work**. `client.ts:423-426` already states the
  contract: "the caller must `URL.revokeObjectURL(objectUrl)` once done … this
  client does not track outstanding object URLs itself" — and the grep shows
  **zero callers today**. The viewer is its first consumer: an N-page document
  paged without revoking leaks one blob per page. **Binding**: every page fetch
  revokes in a `useEffect` cleanup; the viewer holds at most the current page
  (plus optional neighbours) alive.
- **Route** — `/documents/:documentId/viewer?page=N&clause=<id>`, one new line
  in `ShellRoutes` (`WorkspaceShellApp.tsx:64-97`). Reasons: (a) the
  `?clause=&page=` pair is **already** the citation-landing convention
  (`contract360/index.tsx:52,65-67,113`) — reuse it, do not invent a second;
  (b) **the current page lives in the URL, not React state**, so reload and a
  deep link land on the same page (the persistence rule); (c) the viewer is a
  *state reached from a citation*, not a rail destination — same call the V2 IA
  made for Review (`navItems.ts:18`), so **`navItems.ts` gets no new row and has
  zero writers this wave**.
- **Owed by software-architect, one phase earlier**: a **per-page** preview
  route (today `GET /api/documents/{id}/preview` has no page parameter,
  `client.ts:2085`) **and** `pageCount` on the document body (`page_count` is
  already persisted, `documents-contracts.sql:834`). Without both, the viewer
  has exactly one page and the item's "uploaded pages" is unmet.
- **Generated client must expose**: `getDocumentPreviewUrl(tenantId, id, page)`
  — a new parameter on hand-written glue ⇒ **NW-63 owns `client.ts`** (§5-7).
- **e2e**: `w17-viewer.spec.ts` — N17: open a validated PDF's viewer, see
  **that file's page** (not the FILE placeholder), page forward, and **deep-link
  `?page=3` straight into page 3 after a reload**.
- **ADR action**: **amend ADR-012** (why no new runtime dependency; the
  object-URL rule) and **amend ADR-018** (the viewer route in the V2 map).
