## 0. The one rule this wave is really about

`client-architect-lane` and the raw file both carry the same rule: **a client
cache never stands in for a missing GET.** Four caches in this SPA exist only
because an endpoint was missing, and each one says so in its own header
comment:

| Store | Key | Storage | Stands in for | Item |
|---|---|---|---|---|
| `web/src/routes/signin/workspaceStore.ts:32,88-106` | `raffa.signin.knownWorkspaces.<homeAccountId>` | `localStorage` | `GET /api/workspaces` | NW-01 |
| `web/src/routes/signin/workspaceStore.ts:33,117-145` | `raffa.signin.currentWorkspace` | `sessionStorage` | "which tenant am I in" | NW-03 |
| `web/src/routes/workspace/members/memberStore.ts:25,54-86` | `raffa.workspace.members.<tenantId>` | `sessionStorage` | `GET …/members` | NW-04 |
| `web/src/components/shell/workspaceRole.ts:30,36-47` | `raffa.shell.workspaceRole` + `?role=` | `sessionStorage` | "what is my role" | NW-14 |

All four verified line-exact. The decision for all four is the same and it is
not "sync them better": the cache is **deleted or demoted**, and when the
server read fails the screen shows ADR-018's error state — quoted verbatim
from `ADR-018:117`, "2px accent left rule + h4 + plain endpoint/job name +
secondary Retry" — never a stale local answer. A fallback-to-cache would
reproduce exactly the bug each item reports: a client that disagrees with
Postgres and is confident about it.

Corollary the decomposer must not soften: **there is no "keep the old list as
a fallback" task.** If `GET /api/workspaces` is down, the picker is in an
error state.

## NW-01 — `GET /api/workspaces` for the signed-in identity

### Client decision

`loadKnownWorkspaces` / `rememberWorkspace` / `KNOWN_WORKSPACES_KEY_PREFIX`
are **deleted** from `workspaceStore.ts`. `WorkspacePickerScreen.tsx:36`
stops seeding state from `localStorage` and fetches
`apiClient.listWorkspaces()` on mount; `:78-85` stops writing a
`WorkspaceSummary` after a create (the POST response is no longer a cache
seed — the list is re-read, or the created row is entered directly as it is
today at `:91`).

`WorkspaceSummary` stops being a hand-written interface with client-side
inferences in it. Two of its fields are inventions that die with the store:
`contractCount` ("Always 0 from this screen", `:39-45` → NW-09) and
`roleLabel` ("Client-side inference, not a server-issued claim", `:56-64` →
NW-14). Its replacement is the generated row type.

**The picker screen has no `useEffect` today** — `:36-41` are all
`useState` initialisers. NW-01 introduces the first network read on this
screen, which is what forces the two new states below.

> **F8 — the method name is not my invention.** `client.ts:22-24` already
> names the missing call: "there is no matching `listWorkspaces()`/
> `getWorkspaces()` call here: no such backend endpoint exists yet". I adopt
> the name the codebase already reserved.

> **F1 — the row needs one field fewer than revision 1 assumed.** Two
> wire→label mappers already exist: `navItems.ts:32-35`
> (`WORKSPACE_ROLE_LABEL`, "Display labels, matching the backend enum names")
> and `memberViewModel.ts:84-88` (`memberRoleLabel`, `"Admin"` → `"Workspace
> Admin"`). The picker's role tag (`WorkspacePickerScreen.tsx:177`) is
> therefore derived from `role`, **not** a server-sent `roleLabel`. The NW-01
> row carries `role` only; no `roleLabel`, and no new copy decision for UX.

### Route / state change

None. `/signin` keeps its shape (ADR-018 route map; ADR-024 lands on `/ask`).
Only the source of the list changes. The three states of the screen —
"No workspaces yet" (`:151-159`), the list (`:161-181`), and the entered state
(`:100-137`) — all survive; a fourth (loading skeleton) and a fifth (error +
Retry) are added because a network read now sits in front of them.

### What the generated client must expose

`listWorkspaces(): Promise<ListWorkspacesResult>` in `client.ts`, anchored to
`paths["/api/workspaces"]["get"]["responses"][200]["content"]["application/json"]`.

Four hard constraints on the OpenAPI entry, from
`web/scripts/generate-api-client.mjs` — generator facts, not preferences, and
the software seat needs them **before** it writes the contract:

1. **`operationId` is mandatory** — `:125-130` throws without one
   ("every operation must declare one"). Use `listWorkspaces`.
2. **The row schema must be flat scalars.** `renderSchemaType`'s `object`
   case (`:97-113`) renders a *flat property map* only; a property whose
   value is itself an object renders `unknown`, and there is no `$ref` /
   `oneOf` support (`:114-119`, `default: return "unknown"`). So the 200 body
   is `array` → `object` of `id, name, createdAt, role, contractCount`
   (+ `currency`, `country` if NW-24 lands) — every member a string, number
   or enum. No nested `owner {}`, no `$ref`.
3. **Enums become literal unions** (`:63-65`), which is what we want for
   `role` — so `RequireRole` and `canManageMembers` keep compiling against a
   real type. Arrays of unions are parenthesised correctly (`:95-96`), so an
   array-of-rows body is safe.
4. **Only `responses` are generated** (`renderOperation`, `:132-146`). Neither
   `requestBody` nor `parameters` is parsed, so path parameters and request
   bodies stay hand-written in `client.ts` (`:17-21` states this). Unchanged
   convention this wave.

### Which e2e case proves it

`day1.spec.ts:33-41` currently asserts the opposite of what NW-01 delivers —
verbatim: *"A stock Playwright browser context (no reused `storageState`)
therefore always starts from 'No workspaces yet' and must create its own
workspace — it has no way to discover the ADR-022 fixture-seeded tenant"*.
After NW-01 that paragraph is false and must be rewritten in the same task
(`v2.spec.ts:70-75` carries the same premise — see NW-03).

New case, acceptance **N2**: sign in with the test account in a **fresh**
browser context (no `storageState`) and assert `.workspace-row` is present
with no create step — discovery survives a cleared profile. That is the one
assertion the `localStorage` cache could never pass.

### ADR action

`amend ADR-012` — introduces the persistence rule and the generated-client
contract for workspace discovery. One footer, shared with NW-03/NW-09/NW-14.

> **C4 — the footer *introduces*, it does not restate.** A grep of ADR-012 for
> `persistence|sessionStorage|localStorage|read-back|cache` returns **zero
> matches**: the persistence rule is in my lane skill and the raw file, never
> in the ADR. The footer's anchor is ADR-012`:53` ("A change to the API
> surface must regenerate/update a shared OpenAPI/TypeScript client … no
> hand-written divergent DTOs"), which it extends from *shape* discipline to
> *provenance* discipline. ADR-012 has no amendment footer yet; mine is the
> first, and `## Decision outcome` (`:25-29`) stays untouched above it.

## NW-03 — Current workspace is a server fact, not `sessionStorage`

### Client decision

`raffa.signin.currentWorkspace` **stays as a key** but is demoted from
source of truth to a **session hint**. `loadCurrentWorkspace()` /
`selectCurrentWorkspace()` / `clearCurrentWorkspace()` keep their signatures;
what changes is that nothing trusts the value without checking it against the
server list.

Resolution order on every mount, once `GET /api/workspaces` has resolved:

| List | Hint | Result |
|---|---|---|
| empty | any | create form (`No workspaces yet`) |
| 1 row | any | **enter it** — no picker (`percorso-pilota-v1.md` §2 step 1, "Se ne ha uno, entra") |
| ≥2 rows | hint ∈ list | enter the hint |
| ≥2 rows | hint ∉ list or absent | picker |

The `hint ∉ list` branch is the client half of NW-58's removal requirement:
a member an Admin removed loses the workspace on their next mount, because
the id they cached is no longer in their server list. No extra endpoint, no
polling — revalidation is the mechanism.

### Route / state change — the real one

This is not a store swap, it is a change to the app's top-level gate.
`App.tsx:49` calls `loadCurrentWorkspace()` **synchronously during render**
and `:91` branches on it immediately (`if (!account || !workspace)`): today
`App` renders either `SignInRoute` or `WorkspaceShellApp`, with nothing in
between. Making the workspace a server fact inserts an inherently async step,
so `App` needs a third state:

```
no account            -> SignInRoute (unchanged)
account, resolving    -> NEW: loading state (ADR-018:115 skeleton contract)
account, list empty   -> SignInRoute (create form)
account, resolved     -> WorkspaceShellApp
```

The "resolving" state must not flash the sign-in screen; that would look like
a logout on every reload. Treat `App.tsx` as one task's file, not two.

> **F7 — the render-time read is load-bearing elsewhere.** Because `:49` is
> non-reactive, `selectCurrentWorkspace()` cannot re-render `App` — which is
> exactly why `WorkspacePickerScreen.tsx:124` is a hard `<a href="/">` and why
> its own comment (`:117-123`) justifies that with "no router is mounted
> anywhere above this component". NW-58's router hoist **falsifies that
> premise**. Nothing breaks (a hard navigation still works), but the comment
> becomes a lie and the flow keeps a full page reload it no longer needs. The
> task that hoists the router updates that comment, or converts the `<a>` to a
> `navigate()`. Flagged because it is invisible in a diff of `App.tsx` alone.

Two further consumers read the hint directly and must be revalidated through
the same resolved value, not their own `loadCurrentWorkspace()` call:
`useValidatedContractCount.ts:54` (whose effect keys on `workspace?.id`,
`:76`) and `MembersRoute` (`index.tsx:36`, with its own `!workspace` empty
state at `:82-89`).

### What the generated client must expose

Nothing new — NW-03 consumes NW-01's `listWorkspaces`. This is a dependency,
not a second contract: **NW-01 lands one phase before NW-03**.

### Which e2e case proves it

Acceptance **N4**: close tab / reopen → same tenant with one membership.
In Playwright terms: complete the flow, `page.reload()` with `sessionStorage`
cleared but the MSAL account intact, assert the shell mounts on `/ask` with
`.shell-rail-workspace-name` unchanged (the selector `day1.spec.ts:132`
already uses) and no picker.

**Blocking e2e consequence — flag for delivery-manager.** `v2.spec.ts` pins
the fixture tenant by writing `raffa.signin.currentWorkspace` directly
(`:68-79`, `:118-119`) and calls it "the documented seam, not a mock"
(`:78`). That seam **survives** NW-03 — the key still exists and is still
honoured — but only for a tenant the caller is a **member** of. Under the
`hint ∉ list` rule a non-member's pin is discarded and the whole V2 suite
stops walking the fixture tenant.

> **F6 — this is now a certainty, not a risk.** No membership row exists
> anywhere today: `WorkspaceProvisioningService` writes none (NW-02's own
> evidence) and `InviteAsync` is the only writer, so only invited users have
> one. I checked the seed path: `seed-demo-fixture.yml` greps clean for
> `invite|membership` — its only workspace reference is a table-existence
> check (`:126,128`). Nothing has ever made the e2e account a member of
> `RAFFA_E2E_TENANT_ID`. So `v2.spec.ts` goes **red** at NW-03 unless a
> membership seed lands with it. OQ-w14-c2 is upgraded from assumption to
> verified fact, and the seed is a **prerequisite task**, not a follow-up.

### ADR action

`amend ADR-012` — same footer as NW-01 (resolution order; the session key is
a hint, never the source of truth).

## NW-14 — Delete and Retry upload 403 for the workspace creator

### Client decision

`resolveWorkspaceRole()` (`workspaceRole.ts:36-47`) is **deleted as the
product path** — both halves: the `?role=` query override (`:40-44`) and the
`sessionStorage` mirror that **defaults to `"admin"`** (`:46`) for whoever is
looking. `App.tsx:113` stops calling it and passes the `role` field from the
resolved workspace row (NW-01) into `WorkspaceShellApp`.

**The SPA sends no role header, ever.** This is the raw file's own guard ("Do
not 'fix' this by sending a spoofable `X-Role: Admin` from the SPA as the
product solution") and it is a client-architecture commitment, not a backend
one. Verified: a grep for `X-Role|X-Workspace-Role` across **all** of
`web/src` returns **zero hits** — the client sends `X-Tenant-Id` (`:1276` and
21 further call sites) and `X-User-Id` (`userIdHeaders`, `:52-55`) and nothing
else. So this rule costs nothing today and is purely a commitment not to
regress. The role travels server-side from `workspace_membership`; the
client's copy is **presentation-only** — it decides which affordances render,
never what is permitted. The 403 is the authority; the button state is a
courtesy.

> **F2 — the parse rule, and why it is not a detail.** The wire vocabulary is
> **wider than the nav's**: `memberViewModel.ts:9-11` records that the backend

> `WorkspaceRole` is `"admin" | "procurement"` only (`navItems.ts:29`) and
> NW-54 (those roles as first-class nav) is **DEFERRED**. So `role` from the
> wire may be a value the nav does not model, and the mapping needs a
> documented fallback.
>
> **That fallback must be least-privilege, never `"admin"`.** Today's default
> *is* `"admin"` (`workspaceRole.ts:46`) — the precise reason a non-Admin sees
> Admin affordances. Carrying that default into the new parse would
> re-introduce NW-14's bug for Legal/Finance/ReadOnly members while "fixing"
> it for Procurement. One line, and it is the whole point of the item.
>
> **Where it lives:** `parseWorkspaceRole(wire)` replaces
> `resolveWorkspaceRole()` **in `workspaceRole.ts`** — the file NW-14 already
> rewrites. Not in `navItems.ts`, which keeps NW-09 as its single writer.
> The display direction already exists (`WORKSPACE_ROLE_LABEL`,
> `navItems.ts:32-35`) and is untouched.

> **F3 — this settles a standing ADR-018 assumption rather than contradicting
> it.** ADR-018`:133-135` assumes "Entra ID will return role/permission claims
> usable client-side to gate `/workspace/members` (**otherwise the non-admin
> 'request access' state must be server-driven**)". ADR-010's claims are not
> wired and NW-05 is queued for W15, so the stated alternative is the one in

### Route / state change

`RequireRole` (`WorkspaceShellApp.tsx:67-74`) and `canManageMembers`
(`navItems.ts:43-45`) keep their exact shape — only the provenance of the
`role` value changes. **`navItems.ts` is not written by this item**, keeping

### What the generated client must expose

### Which e2e case proves it

## NW-58 — Invites are email + link; login joins that workspace; remove requires a new invite

The largest item and the only one that changes the route map.

### Client decision — 1: a new public route

**`/invite/accept?token=…`** is new. Verified absent from ADR-018's route map
(`:89-102`, headed "**Route map (locked)**") and from ADR-024's V2 map. A
locked map is exactly why this is a genuine amendment, not an interpretation.

### Client decision — 2: the router must move (structural)

Every existing route lives **inside** `WorkspaceShellApp`, and
`BrowserRouter` is only mounted once `account && workspace` are both true
(`App.tsx:91,108`; `WorkspaceShellApp.tsx:81-87`). An invitee arrives
**signed out** and **with no workspace** — precisely the state in which no
router exists today. So the accept route cannot simply be added to
`ShellRoutes`.

Decision: **hoist `BrowserRouter` into `App.tsx`.** `WorkspaceShellApp` drops
its own `BrowserRouter` (`:81-87`) and `App` mounts one router with a public
branch:

```
<BrowserRouter>
  <Routes>
    <Route path="/invite/accept" element={<InviteAcceptRoute …/>} />   // public, outside AppShell
    <Route path="*" element={…existing account/workspace gate…} />
  </Routes>
</BrowserRouter>
```

`ShellRoutes` is already exported separately (`WorkspaceShellApp.tsx:41`)
precisely as a testing seam, so this is a supported change rather than a
rewrite. Two files, one task: `App.tsx` + `WorkspaceShellApp.tsx`. It
composes with NW-03's new "resolving" state, which is why **NW-03 and NW-58's
route task must not run concurrently on `App.tsx`** — and it carries F7's
comment fix at `WorkspacePickerScreen.tsx:117-123`.

### Client decision — 3: the accept flow

| State | Client behaviour |
|---|---|
| signed out | stash the token, `loginRedirect`, return to `/invite/accept` |
| signed in | `POST /api/invites/{token}/accept` → response carries `{ tenantId, name }` → select that workspace → land on `/ask` (ADR-024) |
| invalid / expired / used / revoked | ADR-018`:117` error state, plain reason, "ask your admin for a new invite" — **no tenant data** |

The pre-accept `GET /api/invites/{token}` returns the **workspace name only**
(security's rule: a token must not leak tenant data before acceptance), which
is exactly enough to render "You have been invited to *X*".

**On stashing the token across the OIDC redirect**: one `sessionStorage` key,
cleared on first use *and* on failure, **never `localStorage`** — a
`localStorage` token would outlive the browser session and survive an account
switch on a shared machine. This is not a violation of §0: a one-shot token in
flight across a redirect is transient flow state, not a cache standing in for
a GET. Stating the boundary so the rule stays enforceable.

### Client decision — 4: "Invitation sent." (the copy contract)

`InvitePane.tsx:101-105` renders `INVITATION_SENT_MESSAGE`
(`memberViewModel.ts:39`, "Invitation sent.") whenever `sent && error ===
null`, and `MembersRoute` sets `sent` unconditionally on a 201
(`index.tsx:78`). NW-58's must #1 is that the UI may not claim a mail was sent
unless it left.

Client seam: **the server tells the client what happened.** The invite 201
body carries a delivery discriminator — `delivery: "sent" | "link-only"` —
plus `acceptUrl` when it is `link-only`. Concretely the client's `sent:
boolean` prop becomes `delivery: "sent" | "link-only" | null`; the client
renders UX's copy for whichever value arrives and **never infers "sent" from a
201**. The 201 body already returns a member object (`index.tsx:69-71` reads
`result.member.{id,email,role}`), so this is an additive change to an existing
shape.

This is the decision that makes OQ-w14-002 (is a mail transport in scope?)
**not a client-blocking question**: the SPA is correct either way, and needs no
second change when a transport lands later. Recommend the table adopt it
regardless of how the PO and cloud seats rule on the transport. UX owns the
two strings; I own only the fact that there are two.

### Client decision — 5: member writes go to the server

Remove → `DELETE /api/workspaces/{tenantId}/members/{membershipId}` →
re-read the list (NW-04). No optimistic local removal: the last-Admin guard is
a server rule, so the server's answer is the one that renders.

### What the generated client must expose

- `inviteWorkspaceMember` — extended 201 body: `+ delivery`, `+ acceptUrl?`
  (both scalars → generator-safe).
- `getInvitePreview(token)` → `{ workspaceName }`.
- `acceptInvite(token)` → `{ tenantId, name }`.
- `removeWorkspaceMember(tenantId, membershipId)`.

Request bodies and path parameters hand-written as usual (constraint 4); every
operation needs an `operationId`; every response body flat scalars.

## Consequences for the decomposition

1. **Endpoint before consumer, one phase later.** NW-01's endpoint (software
   seat) ships in phase *n*; the picker rewrite in phase *n+1*. Same for
   NW-04 and each NW-58 operation. A web task that consumes an endpoint
   landing in its own phase is a broken chain.
2. **Membership backfill is a hard prerequisite of NW-01's web task, not a
   follow-up.** Existing `dev` workspaces have no membership row (NW-02's own
   sketch; F6 confirms none exist anywhere). The moment the picker reads the
   server list, every pre-existing `dev` workspace **disappears** for its
   creator until backfilled — a user-visible regression at deploy time. The
   client must not soften it by keeping the `localStorage` list as a fallback
   (§0). Operator backfill or a "claim this workspace" path lands with, or
   before, the web task.
3. **The e2e fixture account needs a membership** on `RAFFA_E2E_TENANT_ID`
   or the V2 suite goes red at NW-03 (F6 — verified, not hypothetical).
4. **A second Entra test account, on the same email domain** (F5), is a
   prerequisite for NW-58's and NW-14's full acceptance. Not blocking the
   code; blocking the proof.
5. **Two e2e header comments assert the opposite of this wave** and must be
   rewritten by the tasks that falsify them: `day1.spec.ts:33-41` and
   `v2.spec.ts:68-79`. A spec whose documented premise is false is a trap for
   the next reader even while it passes.
6. **Five new client states** enter screens that today have none: picker
   loading, picker error+Retry, App "resolving", members loading, members
   error+Retry. They are ADR-018`:112-119`'s IA-level contract ("The
   decomposer must not treat empty/error as 'nice to have'"), not polish; the
   UX seat owns their copy.
7. **Mobile**: untouched. ADR-013 stays a non-gating scaffold; no w14 item
   reaches it.
