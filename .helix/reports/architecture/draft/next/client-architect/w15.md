## 0. Three rules this wave turns on

**Rule A — a client must not *infer* a server state it can be told.**
ADR-012's w14 footer clause 1 forbids a client store standing in for a missing
GET. This wave hits the sibling defect: three surfaces guess a server state
from a proxy value. `ask/index.tsx:103` sets `hasAnyDocument` from
`totalCount > 0` — documents **in any state** — and `askViewModel.ts:250-261`
then tells the user the document "is still processing or waiting for review",
which is a **lie for a tenant whose only document failed**. `RailNav.tsx:72-75`
infers a badge from a dead session key. `useDocumentsList.ts:123` computes
`allCount` as `documents.length`, the fetched page. Inference is the same
defect as a cache: a client confidently disagreeing with Postgres.

**Rule B — the header shape that ships today cannot carry a token.**
`client.ts:48` declares `GetUserId = () => string | null` — **synchronous** —
and `userIdHeaders` (`:55-58`) is spread inline into **37 separate
`await fetch(` call sites**, one per operation (`:1336 … :2726`, 36 methods
plus `/health`). Token acquisition is asynchronous. NW-05 therefore cannot be
a find-and-replace across 37 header literals; 37 literals are 37 chances to
omit one, and after NW-05 an omitted header is a 401 with no fallback. This is
the one structural client change in the wave (§NW-05).

**Rule C — the contract file is single-writer per phase, and its enums are
load-bearing.** `web/scripts/generate-api-client.mjs` regenerates
`web/src/api/generated/schema.ts` **wholesale** on every `npm run build`
(`package.json:13`, generator `:21-23`, `:193`). ADR-012 w14 clause 3's four
constraints were re-verified line-exact on this tree: `operationId` mandatory
or throw (`:125-130`); ~~flat scalars only, nested object → `unknown`~~, no
`$ref`/`oneOf` (`:97-119`) — **CORRECTED at the table, see §9: nesting *is*
supported; only `$ref`/`oneOf` renders `unknown`**; enums → literal unions (`:63-65`); **only
`responses` are parsed** (`:132-146`). One consequence is new and binding on
this wave: the `enum` branch (`:63-65`) is evaluated **before** the
nullable-union branch (`:72-76`), so a schema that is both nullable and
`enum` **silently loses its `null`** — the contract already records this
against `stage` (`raffa-api.v1.json:982`). See §3 for what that forbids.

## NW-61 — upload feels instant; details only when the document is ready

Seats: client-architect (me), ux-ui-designer, software-architect,
product-owner. My half is the read-back contract, the poll, the optimistic-row
hand-off, the request deadline, and the counts.

### What is already right, and must not be "fixed"

The client half of R-DOC-09 is built and correct, and a task must not rebuild
it: the optimistic row exists before the request starts
(`useDocumentsList.ts:131-134`), the progress bar renders the **server's**
stage and never a client timer (`DocumentStatusTable.tsx:151`,
`ProcessingPipeline.tsx:4-6`, `documentTable.ts:51-55`), and the 2 s poll
exists (`useDocumentsList.ts:13`, `:110-119`). The intake is right that NW-27
resolves defects (1) and (2) of its own accord: on a 201 the hook calls
`load()` (`:141`), the server row arrives `Uploaded`, `hasNonTerminalRow`
(`:105-108`) turns true and the interval starts. **No change to the poll
predicate is needed**, and I withdraw the intake's implied one.

### Client decision 1 — the optimistic row is handed off on *evidence*, not on a timer

New finding, and it is a regression **NW-27 creates**. `useDocumentsList.ts:140-141`
drops the local entry and *then* calls `load()`, so the row is absent between
those two moments. Today the POST takes tens of seconds and the gap is one
invisible RTT at the end; once the POST returns in under 2 s the gap becomes a
**visible flicker on every file of a 15-file batch**, which is precisely the
"all 15 rows exist" claim A15-1 makes.

Decision: the `"admitted"` branch records the **server id from the 201**
(`schema.ts:199` — the 201 body already carries `id` and `processingStatus`)
on the local entry, and the local entry is dropped only when a server row with
that id is present in `documents`. Never on a timer, never on an optimistic
assumption that `load()` will succeed. If `load()` fails, the local row stays
and the list shows ADR-018 `:117`'s error state — the row does not vanish.

### Client decision 2 — both counters are the server's number

ADR-012 w14 clause 7 ("a count has one definition and it is the server's")
already binds, and the documents screen violates it twice:
`useDocumentsList.ts:123` `allCount = documents.length` is the **fetched
page**, capped at `LIST_PAGE_SIZE = 100` (`:15-18`), and `attentionCount`
(`:122`) is a client filter over that same page (`documentTable.ts:141-143`).
`result.page.totalCount` is fetched and **never read** here — its only reader
in the whole app is `ask/index.tsx:103`.

Decision: `allCount` reads `result.page.totalCount`. `attentionCount` becomes
a **server** number on the same response envelope — it must not be a second
client predicate, and it must not be a second round-trip.

**Contract ask (software seat)** — `listDocuments`' 200 envelope, which
already carries `page` / `pageSize` / `totalCount`
(`raffa-api.v1.json:906-911`), gains two non-nullable integers: a count of
documents needing attention, and a count of documents **not yet terminal**.
Both plain `integer`, no `enum`, no nullability (§3). Naming is the software
seat's. One envelope, one call, one definition — and it is what makes the next
three decisions cheap rather than three new endpoints.

### Client decision 3 — the completeness gate reads a server fact on three screens

A15-3's promise ("never an empty contract or a fabricated fact") is a
**product** rule; my half is where the fact comes from.

- **Ask.** `ask/index.tsx:256` gates on `kbReady`, and the off-copy branches
  on `hasAnyDocument = totalCount > 0` (`:103`) — any state, including
  `Failed`. Decision: the off-state branches on the **not-yet-terminal** count
  from the envelope above, not on `totalCount`. This creates a third off-state
  the product does not have today — *documents exist, none is in flight, none
  validated* — whose **copy is the UX seat's** (ADR-020). I record only that
  the state is now distinguishable and must not be collapsed back into the
  "still processing" sentence, which would re-ship the lie under a server
  number.
- **Ask must re-read while it is off.** `useValidatedContractCount.ts:42-50`
  states it in its own comment: fetched once per shell mount, **no re-poll**.
  So a user sitting on `/ask` while a document completes never sees the gate
  flip. Decision: while the off-state is showing *and* the in-flight count is
  non-zero, Ask re-reads on the **same 2 s cadence and the same predicate
  shape** `useDocumentsList.ts:110-119` already uses — reusing the existing
  `listDocuments(pageSize: 1)` call at `ask/index.tsx:102`, not a new endpoint
  and not a poll of `GET /api/workspaces`. It stops the moment it flips.
- **Portfolio.** `contracts/index.tsx:130-139` renders "Nothing to triage yet"
  with no processing read at all. Decision: it makes the same one-row
  `listDocuments` call and, when the in-flight count is non-zero, shows the
  processing state instead of the reroute — **copy UX's**.
- **Contract 360.** `contract360/index.tsx` reads no `processingStatus`
  anywhere (the only read in the feature is a per-row tag,
  `contract360ViewModel.ts:449`). It is **contract**-scoped, so the workspace
  envelope cannot answer it. **Contract ask (software seat)**: the
  `getContract360` aggregate carries a per-contract "documents still
  processing" signal. If it is nullable it **must not** carry `enum` (§3).

I explicitly do **not** propose a client-side derivation for any of the four.
Deriving "still processing" by fetching every row and testing it is exactly the
heuristic ADR-012 clause 7 deleted for contract counts.

### Client decision 4 — the upload POST gets a client-owned deadline, and it is a safety net

`client.ts:1726` has no `signal`; `uploadPipeline.ts` has no `AbortController`
(verified: zero matches for `AbortController|AbortSignal|signal:|timeout` in
`client.ts`). The only deadline in the path is the Container Apps ingress
default (~240 s), which `infra/modules/containerapps/main.tf:179-194` does not
declare — it is implicit and undocumented (intake, NW-27 evidence).

Decision: **one** client-owned deadline on `uploadDocument`, configured in one
place, never per call site. An abort maps to the existing `"failed"` branch
(`uploadPipeline.ts:127-132`, which already handles `statusCode === null`), so
the user gets Raffa's retryable message rather than an opaque platform 502.

Two honest constraints on the number, which I do **not** invent:
1. It must exceed the time to *send* a legitimate body. `MAX_FILE_BYTES` is 50 MB
   (`uploadPipeline.ts:19`); 50 MB on a slow link is minutes, so a tight
   "2 s budget" deadline would break large uploads on exactly the network where
   they matter. `fetch` + `AbortController` cannot express
   "time-to-first-response-byte after the body is sent", so the deadline is
   necessarily absolute.
2. It must sit **below** the platform ceiling, or it never fires.

**Reconcile with cloud-architect**: the ceiling is currently implicit. If they
pin it on the ingress for NW-27, my deadline is derived from that number; if
they do not, the decomposer ships a default **below 240 s** with the
derivation recorded in the task. Assumption in force: 120 s. This is a safety
net — the *mechanism* that makes upload feel instant is NW-27, not this.

## NW-69 — invite pane: honest delivery and identity state

Seats: ux-ui-designer (copy and states, owner of ADR-020), client-architect
(me). My half is one sentence of structure and two rules.

### Client decision — the discriminant becomes a server string, and the pane renders it

`memberViewModel.ts:166-173` is a discriminated union on the server boolean:

```ts
export type InviteOutcome =
  | { mailDelivered: true; email: string }
  | { mailDelivered: false; email: string; acceptUrl: string; expiresAt: string };
```

Its own doc (`:166-170`) already anticipates this wave: *"not a third, invented
state; the transport wave that needs a third value owns that change"*. ADR-020's
w14 footer (`:283`) settled the same point from the copy side — a failure needs
**"a third value, not a second boolean"**.

Decision: the discriminant becomes the **server's outcome string** on the
invite 201. Not a second boolean, not two booleans the client combines, not a
client inference from a status code — `members/index.tsx:118-120` already
records why (*"this fallback used to claim a mail had gone out on this same
failure path"*). Four outcomes are now expressible: sent · mail failed ·
guest provisioning failed · (created, no transport configured).

### Client decision — the link renders only when it is usable

A15-7's whole point is *"never a 'ready' link that cannot be used"*. So the
`acceptUrl` / `expiresAt` arm is **not** keyed to "mail did not go out" but to
"the link is the usable path":

- mail failed → link **shown** (it is the only way in), plus the pre-decided
  ADR-020 copy and "Try sending again";
- guest provisioning failed → link **suppressed**, named error only — a link
  to a sign-in the invitee cannot complete is the defect, not the remedy;
- sent → no link (`acceptUrl` plaintext exists only on the 201 anyway —
  ADR-020 `:520-524`, ADR-026 `:227-230`).

### No client change for NW-68's absolute link

`composeAcceptLink` (`memberViewModel.ts:175-179`) is
`new URL(acceptUrl, origin).toString()` and its own comment already states it
accepts a site-relative **and** an absolute value unchanged. When
`Invitations__AcceptUrlBase` lands, **the client does not change**. Recorded so
no task is written for it.

### Generated client

The invite 201 gains the outcome as a **non-nullable `string` with `enum`** —
unlike `role`, which ADR-026's w14 footer clause 3 keeps a bare string because
role names are per-tenant rows, this vocabulary is a closed server-side set, so
a literal union is correct and it is what makes the pane's branch exhaustive
under `tsc --noEmit`. **Non-nullable is not a preference**: a nullable `enum`
silently loses its `null` in this generator (§3). Field name and values are the
software seat's (ADR-026).

### e2e / unit

The pane's three outcomes are vitest cases (they run in CI today,
`web.yml` → `npm test`), not browser cases. The browser case is N3b (NW-58r),
which is not mine.

### ADR action

**`none` from this seat on ADR-020** — the states and the copy are the
ux-ui-designer's and the failure copy is already pre-decided in their w14
footer. The two rules above go into my ADR-012 w15 footer (§4). **Reconcile
with ux-ui-designer**: if they want the outcome vocabulary to differ from the
software seat's wire values, the mapping lives in `memberViewModel.ts` and is
theirs to name — the pane still renders one server fact.

## NW-67 — the invitee's Entra B2B guest (client half)

Seats: security (owner), cloud, software, client-architect (me), delivery,
product. My half is exactly two things: accept completing without a second
click, and what the popup's return actually lands on.

### Client decision — one gesture, and it is the one already on the screen

Verified current flow: the token is read from the **fragment** and the address
bar cleared in a lazy `useState` initializer (`invite/accept/index.tsx:57-68`,
`:101`) — before first paint, satisfying ADR-025 Rule C10b's intra-route
ordering. The only effect (`:126-134`) is mount-only and calls the **GET**,
never the accept. `handleContinueWithEntra` (`:172-183`) calls `loginPopup`
and **handles success by doing nothing** — `useMsal()`'s `accounts` re-render
flips the CTA from "Continue with Microsoft Entra ID" (`:233-238`) to "Join"
(`:224-232`). So today A15-4 fails on a second, mandatory click.

Decision: `handleContinueWithEntra` **awaits** its own `loginPopup` promise and
continues into the accept on resolution. Deliberately **not** a `useEffect` on
`accounts`:

1. It is the *same* user gesture — one click, and the consent the button
   already carries is consent to join.
2. It fires only on the transition **this screen initiated**. A visitor who was
   **already signed in** on arrival still gets ADR-020 **state 3** and its
   explicit "Join {workspace}" button. An effect on `accounts` would auto-join
   them too, silently removing the one consent step state 3 exists for.
3. An effect keyed on an MSAL account array can fire for reasons that are not
   this sign-in.

Ordering inside the chain: if the GET has not resolved when the popup does,
the accept waits for the offer — `handleJoin`'s existing guard
(`:137-139`, `state.phase !== "offer"`) must not be weakened into a race.
Popup-blocked / popup-failed keeps its current landing (`:175-177` → ADR-020
state 5), which ships regardless and is why no `must` depends on the popup
(ADR-012 w14 second footer clause 4).

Nothing else on this route changes: not the 8-phase state union (`:70-80`), not
the fragment rule, not the storage rule. `acceptInvitation` (`client.ts:1653`)
sends no body and needs none.

### Finding — a B2B guest's `username` is not guaranteed to be the invited address

**This is the client-architecture reason for the wave's ordering constraint,
and it is not in the intake.** The accept operation binds identity from
`X-User-Id` (`client.ts:1093`, *"binds the signed-in identity (`X-User-Id`,
required — absent is 401)"*), whose value is the MSAL account `username`
(`main.tsx:70-73`). The server matches that string, case-insensitively, against
the invited email (`WorkspaceInvitationService.cs:187`, `:197` — intake).

For a freshly provisioned **B2B guest**, the directory `userPrincipalName` is
the `…#EXT#@<tenant>.onmicrosoft.com` form, and what MSAL surfaces as
`username` is the identity provider's `preferred_username` — **provider-defined
for an email-OTP guest**, not something this seat can assert. If it is not the
plain invited address, the match yields **403 → ADR-020 state 6
"wrong account"** — the exact failure A15-4 exists to remove, arriving *after*
the mail, the guest and the passcode all worked.

I am not guessing which it is. The decision that removes the guess is that the
accept must bind to a **server-verified** identity — the token subject and the
claim set the API validates — not to a client-supplied string. That is NW-05,
and it is why the intake's ordering constraint *"NW-67 with or after NW-05"* is
load-bearing rather than tidy.

**Assumption in force**: NW-05's validation lands before or with NW-67's accept
path, and the server matches the invitation on the verified email/UPN claims
rather than on `X-User-Id`. **Reconcile with security-architect** (owner of
ADR-010 / ADR-025): if NW-05 slips inside the wave, A15-4 must be walked
against a **real** B2B guest before the wave is called done, because a passing
walk with an existing member's account proves nothing about this path.

### Generated client / e2e

**No new generated surface** on the accept path. The invite 201's provisioning
outcome is NW-69's field (above). e2e is N3b (NW-58r) — not my item; my only
input is that NW-67 removes the *missing second account* cause of its skip, and
the **passcode** cause remains (OQ-w15-006).

### ADR action

**`none`** on ADR-012's route and storage clauses — nothing about the fragment,
the memory-only token or T15 changes. The auto-continue rule is one clause of
my ADR-012 w15 footer (§4). ADR-010 / ADR-025 actions are the security seat's;
I supply the finding above as input to theirs.

## NW-05 — API JWT replaces spoofable headers (client half)

Seats: security (owner), software, client-architect (me), cloud, delivery.

### Verified starting state

- **The SPA already asks for the API scopes and throws the token away.**
  `buildLoginRequest` (`msalConfig.ts:80-84`) requests
  `appConfig.oidcApiScopes`; grep over all of `web/src` returns **zero**
  `acquireTokenSilent` / `acquireTokenPopup` / `acquireTokenRedirect` and
  **zero** `Bearer`. The three `Authorization` hits are prose.
- **No new SPA runtime config key is needed.** `oidcApiScopes` is already a
  declared field (`appConfig.ts:34`), validated as a non-empty array of
  non-empty strings (`:75-82`) and assigned (`:91`). The web half of NW-05
  needs **no Terraform and no CI change** — unlike the API half, which cannot
  receive authority/audience except through Terraform + an HCP apply
  (hazard 2). Worth stating plainly so the decomposer does not put the client
  task behind the infra phase.
- **MSAL's cache is `sessionStorage`** (`msalConfig.ts:36`, deliberately, for a
  narrower XSS blast radius) and `navigateToLoginRequestUrl: false` is
  **already set explicitly** (`msalConfig.ts:70-72`, applied `main.tsx:56`) —
  ADR-025 Rule C10a shipped in w14. Neither is re-opened.
- **37 fetch call sites, no choke point** (Rule B).

### Client decision 1 — one authorized-fetch choke point

`createApiClient`'s identity parameter becomes an **async** token accessor, and
a single internal helper attaches `Authorization: Bearer` to every request.
Each method keeps its own `X-Tenant-Id` / `X-Invitation-Token` — those are
per-call facts — but **no method builds the identity header any more**.

`userIdHeaders` (`client.ts:55-58`) and the `X-User-Id` header are **deleted**,
not made conditional. ADR-010's w14 footer clause 3 is explicit that the header
must *stop being read*, and precedence is not enough; the client half is that
it stops being **sent**. `GetUserId` and `main.tsx:70-73`'s closure over
`getAllAccounts()[0]?.username` go with it.

**This supersedes one sentence of ADR-012's w14 footer clause 4** — *"Headers
are attached per method in `client.ts`, never by a global wrapper"* — which was
a description of the mechanism, not a rule. Clause 4's two **rules** stand
unchanged and are re-affirmed: **the SPA declares no role to the API, ever**,
and **a route that carries `{tenantId}` gets no `X-Tenant-Id`**.

### Client decision 2 — how the token is obtained, and what it never touches

`acquireTokenSilent({ scopes: appConfig.oidcApiScopes, account })`, with
`InteractionRequiredAuthError` → `acquireTokenPopup`. **Never a redirect from
inside a request**: a redirect unloads the page, losing in-flight state and —
on `/invite/accept` — the in-memory invitation token (ADR-012 w14 clause 6;
ADR-020 state 5). Popup blocked → the ADR-018 `:117` error state with a
sign-in affordance, never a silent retry loop.

**The SPA never stores the access token.** It is read from MSAL's own cache per
request and never copied into React state, a module variable, `sessionStorage`
or `localStorage`. Corollary, recorded so a task does not "harden" the wrong
thing: **ADR-025 T15 is about the invitation token**, and MSAL's own
`sessionStorage` cache is not a violation of it. `localStorage` remains
unwritten anywhere in `web/src` (verified).

A **401 after a successful silent acquisition** is a server rejection, not a
stale-token case: do not retry silently. One place surfaces sign-in.

### Client decision 3 — `X-Tenant-Id` stays the *selection*, and the e2e seam survives

The client keeps sending the selected workspace on tenant-scoped routes; what
changes is that the server validates it against the **token subject's
membership** instead of trusting it. Consequence I am claiming: the
`raffa.signin.currentWorkspace` hint and the e2e seam built on it
(`v2.spec.ts:68-85`) **survive unchanged**, and a forged tenant becomes a
403/404 instead of data.

**Reconcile with security-architect and software-architect — say this now, not
in the decomposition.** If they instead move tenant selection into the route
path, that is a change to **every tenant-scoped method** in `client.ts` plus
every call site, and it is a different task size. My lane's position: the
header is a *selector*, validated against membership; ADR-022's w14 rule that
a membership route takes its tenant from the path is untouched.

### Client decision 4 — no client contract change

The generator parses **only `responses`** (`generate-api-client.mjs:132-146`),
so headers are hand-written by construction: NW-05 is a **zero-edit item on
`web/openapi/raffa-api.v1.json` and `schema.ts`**. It does not contend for the
contract file (§3).

### e2e / unit — the check that actually runs

The 37-call-site risk needs a check that runs in CI, and one exists: a
**vitest** case that enumerates the `ApiClient` surface (`client.ts:1021`, 36
methods) and asserts **every** method attaches `Authorization`. `web.yml` runs
`npm test` today, so this is a real gate this wave, not a deferred one. The
browser evidence is that the whole `v2.spec.ts` walk still passes against
deployed `dev` after the switch. A15-8's forged-header assertion is a `curl` /
integration check and belongs to the backend seats — a browser cannot forge a
header it does not send.

**Risk to state out loud (delivery-manager's ordering):** this is the change
that can lock everyone out of `dev`. The client task must not merge ahead of
the API's validation config, and the scope literal in `web.yml:204-205` is a
rename risk that fails **in the browser after CI is green** (ADR-010 w14
clause 4).

### ADR action

## 3. Constraints I place on other seats' contract edits

These are consequences of the generator, verified on this tree, not preferences.

1. **`processingStatus` is a closed `enum` in seven places** in
   `web/openapi/raffa-api.v1.json` (`:733`, `:967`, `:1096`, `:1287`, `:1389`,

   They must be **one task or different phases**. NW-05 does **not** contend

## 9. Correction found at the table (2026-09-13) — nesting is supported; `$ref` is not

Promoting §NW-61's contract ask required me to state the generator's object rule
precisely enough for another seat to build on. Reading it that closely showed
**Rule C and §3 were wrong, and so is ADR-012's own w14 clause 3 — which this
seat wrote.** Marked in place above rather than rewritten; the correction is
here and in the ADR-012 w15 footer §9.

**What is false.** "A nested object renders `unknown`." `renderSchemaType`'s
`object` case renders every property with `renderSchemaType(propSchema)`
(`generate-api-client.mjs:110`), which **re-enters the same `object` branch** at
`:97`. A nested object declared inline with `properties` therefore renders as a
nested inline type literal.

**Proved by existence, not by re-reading the code** — which matters, because a
code reading is what produced the error in the first place:

| Evidence | What it shows |
|---|---|
| `raffa-api.v1.json:3103-3105`, `:5253-5261` | the contract **already** nests an object three deep (`items` → object → `components` → object) |
| `web/src/api/generated/schema.ts:646` | the **rendered** result is on disk today: `renewalUrgency: { score: number; …` |
| `raffa-api.v1.json:3910` | the contract's own comment names the **real** limit: a shape is *"duplicated here, not `$ref`'d (web/scripts/generate-api-client.mjs has no `$ref` support)"* |
| grep `\$ref\|oneOf\|anyOf\|allOf\|"components"` over the contract | 7 hits, and **none is a real `$ref`** — two are prose in descriptions, one is that comment, four are a *property named* `components` (score components). **No `components` section exists.** |

**What genuinely renders `unknown`** is narrower and unchanged: an `object`
schema with **no `properties`** (`:107`), and any schema the `type` switch never
reaches (`:114-118`) — which is every **`$ref`, `oneOf`, `anyOf`, `allOf`**,
because a `$ref` object declares no `type` at all. The misleading source is the
generator's own comment at `:98-106`, which describes the contract *as it stood
when the case was written* and invites an extension that is not needed.

**Why this was worth catching rather than shipping.** ADR-027 §D7–§D9 and the
NW-61 row promote `counts` on `listDocuments` and `readiness` on
`getContract360` and record — **on the strength of my clause 3** — that they
"are nested objects rendered `unknown`". Left standing, that belief has three
outcomes and **two are defects**: the fields get flattened to dodge a limit that
does not exist; the generator is extended for a case it already handles; or —
the likeliest, because it is the smallest edit sitting in front of an `unknown`
— the client **hand-writes the type in `client.ts`**, which is the "no
hand-written divergent DTOs" prohibition of ADR-012 `:53`, the one rule this ADR
has held since it was accepted. My own §NW-61 asked for **flat integers on the
envelope** for the same wrong reason; that ask is withdrawn.

**The binding rule that replaces the false one** (ADR-012 w15 footer §9): every
schema this wave adds is declared **inline** with `type`, `properties` and
`required` — **no `$ref`, no `oneOf`/`anyOf`/`allOf`, at any depth**. Nesting is
free; referencing is what breaks. §3's other three constraints stand exactly as
written, including §3.2 (nullable + `enum` drops the `null`), which is what
makes `readiness.stage` nullable-**without**-`enum` and NW-69's outcome
**non-nullable**-with-`enum`.

**Also settled at the table, so this draft is not read against a stale
question**: OQ-w15-ca-03 is **resolved** — `X-Tenant-Id` stays a header,
demoted to a membership-verified selector (security-architect's NW-05 ruling),
so §NW-05 decision 3 is decided rather than proposed and the `v2.spec.ts:68-85`
