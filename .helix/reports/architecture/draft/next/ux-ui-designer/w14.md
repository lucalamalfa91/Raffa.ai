## 1. NW-24 — workspace currency / region (screen 1)

Oracle: `screens-v2.md` §1 (`:13-21`); anchors `markup.html:52-57` (create form)
and `markup.html:62-64` (pick row). Today: `WorkspacePickerScreen.tsx:189-212`
is a one-field form labelled "Workspace name" (`:192`), and `:172-175` renders
`{contractCount} contracts` plus a `currencyRegion` that is never populated
(`workspaceStore.ts:46-55` says so in its own comment).

### D-24.1 — Create form: adopt the prototype's three fields and its copy

`markup.html:52-57` is `Create your workspace` / "A workspace is your tenant.
Contracts uploaded here never leave it." / **Company** · **Industry** ·
**Country** / `Create workspace`. Adopt it whole, in that order.

- The label is **Company** (`:54`), not today's "Workspace name"
  (`WorkspacePickerScreen.tsx:192`) — the prototype's word, and what the user
  actually types.
- Keep the tenancy sentence (`:53`). It is the only place in the product that
  tells a user their contracts stay in their tenant, and it is the copy that
  earns the first upload. Today's form has no such sentence.
- **Country** is required: it derives currency (D-24.2). **Industry** is
  optional (OQ-w14-004).

**Correction to revision 1 (C1).** Revision 1 specified the Industry select
"with a leading *Not specified* option". `markup.html:55` has **no such
option** — it ships exactly five: Food & beverage · Manufacturing · Financial
services · Software · **Other**. An invented empty option would have been an
unnamed divergence, which is the one thing this seat may not do. Decision:
**ship the export's five options verbatim and treat `Other` as the "not
specified" case.** An optional field needs no empty sentinel when the export
already provides a catch-all, and this keeps the create form 1:1 with the
prototype. Industry is stored as free text behind a closed list, so widening
the list later is copy, not a migration.

### D-24.2 — Currency is derived from country, not asked

The create form asks Country (`markup.html:56`) and **never asks currency**, yet
the pick row prints `CHF` (`:63`). The only consistent reading is that currency
is derived. Decision: `country` is the input; `currency` is derived at creation
and stored as its own column, so it stays correctable later without a schema
change — which is why OQ-w14-004 keeps both first-class.

**Verified support (new, F-country).** `markup.html:56`'s option list is exactly
**Switzerland · Italy · Germany · Austria**. The derivation CH→CHF and
IT/DE/AT→EUR is therefore **total over the prototype's own list** — w14 needs no
fallback branch and no "unknown country" state. That removes the only real risk
in deriving rather than asking, and it is why no currency picker ships in w14.

The form shows the derived value inline under the Country select as a
micro-meta line: **"Amounts are shown in CHF."** so a wrong guess is catchable
*before* the workspace exists.

Boundary to product-owner: a workspace currency is a **display default only** and
never overrides a contract's own stored currency (OQ-w14-004, assumption in
force). Screen 6's `pfSummary` already prints a currency ("N validated contracts
· **CHF X annual** · K notice deadlines within 45 days", `screens-v2.md:118-120`),
so the workspace default has a second consumer on day one — worth naming
because it is where an override, if the PO ruled one, would first be visible.

### D-24.3 — The pick-row meta line is a segment list that degrades

Anchor `markup.html:63`:
`{{ seededCount }} validated contracts · CHF · eu-west`. Render up to three
segments joined by ` · `; a null segment is **dropped**, never rendered as an
empty gap, a dash, or a placeholder:

| # | Segment | Copy | When null |
|---|---|---|---|
| 1 | count | `N validated contracts` / `1 validated contract` / `No validated contracts yet` | never null |
| 2 | currency | the ISO code — `CHF` | omit the segment |
| 3 | region | the **country name** — `Switzerland` | omit the segment |

A workspace created before this wave renders `No validated contracts yet` alone
and stays legible. That is the state the prototype never shows — `app.jsx:138`
hardcodes `seededCount:3` — and the one that will actually occur on `dev` on day
one, because every existing workspace has null profile columns and, per NW-02,
no membership row either.

Today the row renders **two** segments, not three:
`WorkspacePickerScreen.tsx:173-174` prints the count and then appends
`currencyRegion` as one pre-joined string. Splitting it into two real fields is
part of this item, not a refactor a task may skip.

### D-24.4 — The pick row also carries a role tag, and it currently lies

**New (C2/F5) — revision 1 missed this entirely.** The pick row is not just a
meta line. `markup.html:62` is a two-cell grid and `:64` renders
`<span class="tag tag-accent">{{ roleLabel }}</span>` — the caller's **role in
that workspace** (`app.jsx:140`). It is already implemented at
`WorkspacePickerScreen.tsx:177`.

It is also the third frozen field on this screen, beside `contractCount: 0`:

- `WorkspacePickerScreen.tsx:83` hardcodes `roleLabel: "Workspace Admin"` on
  create;
- `workspaceStore.ts:56-64` types the field as the **string literal**
  `roleLabel: "Workspace Admin"` — the type system itself encodes "every
  workspace in this list is one where you are Admin", with the comment at
  `:57-62` conceding it is "Client-side inference, not a server-issued claim".

Consequence, and the reason this belongs to w14 rather than W15: the moment
NW-58 lands, an invited **Procurement** member signs in and screen 1 tells them
they are a **Workspace Admin**. That is a false claim in the product's first
screen after sign-in, produced by this wave's own feature.

Decision: the role tag renders the **server role from NW-01's payload**, and the
literal type widens to the real role set. Copy is `INVITE_ROLE_LABEL`
(`memberViewModel.ts:18-21`) — "Workspace Admin" / "Procurement" — so no new
string is invented and the picker agrees with the members table.

This also corrects `waves/w14.md:45`, which records NW-14's design ref as
"none — no visual change beyond the affordance's real enabled state". There
**is** a visual surface for the wrong-role bug and it is on screen 1. The
authorization decision stays with security-architect and client-architect; the
row on screen 1 is mine, and I will propose that row change at the table.

### D-24.5 — `eu-west` is not shipped (divergence)

The prototype's third segment is a **cloud-region slug**. The product pins its
Azure region to `northeurope` (ADR-006) and makes no data-residency promise on
this screen. Printing `eu-west` directly under "Contracts uploaded here never
leave it" reads as a residency claim the product has not made — and contradicts
ADR-006 besides. Render the **business country the user chose**
(`Switzerland`), never a cloud-region slug. OQ-w14-004 already rules region a
business region; this makes that ruling visible in the copy instead of leaving
it in an open question.

## 2. NW-58 — invitation copy and member states (screen 10)

Oracle: `screens-v2.md` §10 (`:147-154`); anchors `markup.html:388` (table),
`:392-399` (invite pane), `:403` (non-admin), `app.jsx:133-134,170`.

### D-58.1 — The invite result has four outcomes: one validation, three deliveries

Anchor to replace: `memberViewModel.ts:39`
`INVITATION_SENT_MESSAGE = "Invitation sent."`; render site
`InvitePane.tsx:101-105`, set by `index.tsx:78` `setSent(true)` on a 201. That
is a claim about a **mail**, made from a **database write**. The raw file's must
#1 is exactly this: "UI must not say 'sent' unless the mail left." (In the
export it is weaker still — `app.jsx:170` sets `inviteSent` from a **regex**,
with no request at all.)

**Correction (C-error, F11).** The word "sent" also appears in the *failure*
path: `index.tsx:63` falls back to "The invitation could not be sent." A sweep
of this pane must catch that string too, not only the success one.

The pane renders one of three **terminal delivery** states, selected by an
outcome the API **returns** — never inferred from the status code:

| Outcome | Copy | Extra affordance |
|---|---|---|
| `delivered` | **"Invitation sent to {email}."** | — |
| `link_only` (no transport configured) | **"Invitation ready for {email}."** + micro-meta "Send them this link. It expires {date} and can be used once." | accept URL in a readonly `.input` + `.btn-secondary` **"Copy link"** |
| `failed` (invitation created, transport errored) | **"Invitation created, but the email could not be sent."** | same copy-link block + `.btn-secondary` **"Try sending again"** |

The `delivered` copy keeps the prototype's sentence and adds the address, so a
typo is catchable at the moment it is made. In `link_only` the word "sent"
appears nowhere on the screen.

The `failed` copy must **not** tell the Admin to invite again: the invitation
already exists, and re-inviting the same email at the same role is precisely
what fails today (`WorkspaceMembershipService.cs:93-96`, "already holds the
{role} role in this workspace"). This is the state everyone forgets and the one
that quietly destroys trust.

Two constraints this places on other seats' contracts:

1. software-architect — the invite response carries a **delivery discriminator**
   and the **accept URL**.
2. The `sent` prop is typed `boolean` (`InvitePane.tsx:17-18`). Three outcomes
   means it becomes a discriminated union; that is a signature change, not a
   copy edit, and the task must say so. Keep `role="status"` on the success
   block (`:101-105`) and `role="alert"` on the error block (`:96-100`) — the
   accessibility semantics are already right and must survive the change.

If the council rules no transport for w14 (OQ-w14-002), only `link_only` ships —
the other two copies are decided now anyway, so W15 does not re-open a settled
string.

### D-58.2 — The domain rule is a fourth invite state, and it currently blocks the wave's own acceptance

**New, and the most consequential find of this pass (F1/F2).** Revision 1 did
not mention the domain rule at all.

`screens-v2.md:150` states it as a design rule — the invite email "**must match
the workspace domain**". It is fully implemented:

- `memberViewModel.ts:69-82` `validateInviteEmail` rejects a mismatch **before
  any request**, with `formatDomainError` (`:58-61`) → "Use an @{domain}
  address." — the real-domain version of `markup.html:398`;
- the domain comes from `index.tsx:45`
  `workspaceDomainFromEmail(userLabel)` — **the signed-in Admin's own email**;
- `memberViewModel.ts:64-67` documents why: "There is no tenant-domain field on
  `WorkspaceTenant` — the honest proxy is the signed-in Admin's own email
  domain."

Two consequences the table must take:

1. **It is a UX state, and it is not a delivery outcome.** It fires pre-submit,
   it is recoverable, and it must not be conflated with the three outcomes of
   D-58.1. Copy stays as implemented; it is the export's own sentence with the
   real domain substituted.
2. **It gates N3b.** NW-58's acceptance requires inviting a second identity and
   having them land in that workspace. If the second Entra account is on a
   different email domain, the invite is refused **client-side**, before any
   endpoint exists to be tested. This is a design rule blocking a backend
   acceptance, so it must be decided now rather than discovered in the fan-out.

Decision I bring to the table: **keep the rule** (it is a real safeguard against
inviting the wrong outsider into a tenant) and make it honest —

- the domain becomes a property of the **workspace**, not of whoever is signed
  in. `memberViewModel.ts:64-67` names the missing column; **NW-24 is the item
  that adds workspace profile columns**, so `domain` should be decided in the
  same breath as `country` / `currency` / `industry`. That is a cross-item link
  neither item's block records, and it costs one column now versus a migration
  later.
- until that column exists the current proxy stays, and the copy stays.
- the acceptance prerequisite is explicit: **the second Entra test account must
  share the first's email domain.** If the operator cannot provide one, the
  alternative is an Admin-only override, which I would rather not design this
  wave — it weakens a safeguard to satisfy a test.

This is my input to OQ-w14-004's field set and to N3b's wording; the transport
half stays with product-owner and cloud-architect.

### D-58.3 — Status set is Active · Invited · Expired; "removed" is not a status

Anchors: the **type** is `memberStore.ts:14`
`MemberStatus = "Active" | "Invited"`; the **tag** is
`memberViewModel.ts:91-93` `getMemberStatusTag`; the export is
`app.jsx:133-134`.

| Status | Tag | Source |
|---|---|---|
| `Active` | `.tag-neutral` | unchanged (`app.jsx:133`) |
| `Invited` | `.tag-accent` | unchanged (`app.jsx:134` `tag-accent`) |
| `Expired` | `.tag-outline` | **new** |

`Expired → outline` is not a new idea — it is this system's existing "needs your
decision" treatment, verified in four places: ADR-019:104 (`Status needs_review`
→ `.tag-outline`), `semantics.ts:75-76` (the same mapping in code),
`semantics.ts:44` (`Review · N%` → outline), and the export's own
`app.jsx:12`/`:73`. An expired invitation is exactly that. It also preserves
ADR-019's one-accent rule: `Invited` and `Expired` are told apart by **label and
row action**, never by a second colour (ADR-019:124-125, "No colour-only
semantics").

Two precise anchor notes for the decomposer:

- `getMemberStatusTag` (`:91-93`) is a **binary ternary** — it structurally
  cannot express a third case. Both it and the `MemberStatus` union at
  `memberStore.ts:14` change. `memberStore.ts` is deleted by NW-04
  (client-architect), so the union moves rather than being edited in place; the
  **vocabulary** is mine either way.
- The row model already carries `lastActiveAt` (`memberStore.ts:22`), unrendered.
  An `Expired` row needs a date to be actionable ("It expires {date}"), so the
  temporal field the payload needs is not a new concept on this screen.

A **removed** member is not a row. This table answers "who can get in", not
"who ever could"; removal deletes the row. An audit trail belongs to
`/api/audit` (NW-08, queued W15), not to this screen.

`Expired` rows carry the row action **"Send a new invitation"** — the same POST.
Flag to software-architect: that POST must succeed for an email whose previous
invitation expired or was revoked; today `WorkspaceMembershipService.cs:93-96`
rejects it.

### D-58.4 — One person may hold two roles; the roster must say which it shows

**New (F6).** `WorkspaceMembershipService.cs:52-55` documents that a second
invite at a **different** role "adds a second membership instead of erroring".
So one email can hold Admin *and* Procurement simultaneously, and NW-04's
roster would render **two rows for one person** — with two different `Remove`
buttons and an ambiguous last-Admin count.

This is a data-shape question with a visible surface, so I record the design
constraint and hand the payload decision to software-architect and
security-architect: **the roster is one row per person.** If multiple
memberships exist, the row shows the **highest** role and removal removes the
person, not one grant. Anything else makes D-58.5's confirm ("They lose access
immediately") false, because removing one of two memberships does not remove
access.

### D-58.5 — Remove is a fourth column, Admin-only, with a consequence-bearing confirm

The prototype has **no** remove affordance at all: `markup.html:388` is a
three-column table (Member · Role · Status), verified in the export and in
`MembersTable.tsx:23-29`. Pure gap; requirements win.

- A fourth `Actions` column renders **Remove** as `.btn-ghost` per row,
  **only when the caller is Admin** — from the server role on NW-01's payload,
  never from a client-declared `?role=` (that is NW-14's rule and it applies
  here identically; a spoofable header must not gate a destructive action).
- Removal is destructive and not undoable without a new invitation, so it is a
  **two-step inline confirm on the row**, not a modal: the `Actions` cell swaps
  to the question, two buttons, and the consequence line —

  > **Remove {email}?**  [Yes, remove] [Cancel]
  > They lose access immediately. To bring them back you will need to send a new invitation.

  Inline rather than a dialog on purpose: ADR-019:78 marks `--shadow-*` "dialogs
  only (avoid in-app)" and the locked component catalogue (ADR-019:87-94) has no
  dialog. This needs nothing the catalogue does not already have — `.btn-ghost`
  and a micro-meta line.

### D-58.6 — The last-Admin guard is a visible disabled control, not a 403

OQ-w14-005: an Admin may not remove the last Admin. The pattern is already
encoded twice — ADR-019:119-121 ("the CTA is `disabled` until gating is met,
**with a visible reason, not a hidden control**") and, in code,
`semantics.ts:15-17` ("pair `isConfidenceBlocking` with … **a disabled CTA +
`.hint`**"). Applied: on the only Admin's row, `Remove` renders `disabled` with
a `.hint`:

> This is the last Workspace Admin. Invite another Workspace Admin first.

("Invite", not "promote" — there is no role-change affordance in w14 and the
copy must not point at one.) Hiding the button would make the Admin think the
product is broken; letting the click 403 would teach them it is unreliable.

Honest scope note: ADR-019:119-121 states the principle for one named CTA
("Mark as validated"). Applying it to `Remove` is a **generalisation**, not a
quotation — which is exactly what an amendment footer is for, and why this is
recorded as an ADR-019 action rather than assumed.

### D-58.7 — Removing yourself

Permitted when another Admin exists. The confirm changes to:

> **Remove yourself from {workspace}?**
> You will lose access immediately and will need a new invitation to return.

The table already knows which row is yours — `MembersTable.tsx:35,40` marks it
"You" — so this needs no new data. On success the app returns to `/signin`: it
must not sit in a shell for a tenant the user no longer belongs to, which is
also NW-03's revalidation rule. Named because the alternative is an unhandled
403 storm on the next render.

### D-58.8 — Procurement's read-only roster: resolving a contradiction, not overriding the prototype

**Correction (C4/C5) — revision 1 got the shape of this decision wrong.** It
presented a read-only Procurement roster as a fresh divergence from
`markup.html:403`. Three facts change that framing:

1. **ADR-018:107-108 already decided it**: "**Procurement** — all routes except
   member management (sees a 'request access' / **read-only** state on that
   surface)." `ia-v2.md:13-15` agrees ("Members screen is read-only with
   'request access'").
2. **The export contradicts its own IA doc.** `markup.html:403` hides the table
   outright: the entire grid (`:386-401`) sits inside `<sc-if isAdmin>`
   (`:384`), and the non-admin branch is only the explanation block plus an
   inert `Request access` button.
3. **It already ships, as a route guard.** `WorkspaceShellApp.tsx:70` wraps the
   route in `<RequireRole role={role} allow="admin">`, and
   `index.tsx:28-29` records that the component "only renders for Workspace
   Admin".

So the decision is not "override the prototype" — it is **which of two existing
readings is in force**, now that NW-04 makes a real roster available for the
first time. I side with ADR-018 and `ia-v2.md`: Procurement gets the table,
read-only — no `Actions` column, no invite pane — with the explanation block
beneath it.

`RequireRole.tsx:20-26` makes this the *documented follow-up* rather than a new
idea: it records that the prototype's "Admins: Marta Keller, Jonas Frei"
sentence was **deliberately generalised** because "this app has no backend 'list
members' endpoint yet to look up a real [admin]". NW-04 is that endpoint, this
wave. The generalised clause can now become the real Admin addresses.

**Boundary, verified in the ADR itself.** ADR-018:125-126 states that "Route
guards for admin-vs-procurement nav items are a thin API/claims concern **handed
to client-architect** (not re-decided here)." Showing Procurement the roster
changes what `RequireRole` gates. **The states and the copy are mine; the guard
change is client-architect's**, and I will put it to them at the table rather
than assert it. If they keep a hard guard, my copy still applies to the block
that remains.

`Request access` has no endpoint and must not ship as a dead control — it is
inert today (`RequireRole.tsx:41`, a `<button>` with no handler). Render it as
`<a class="btn btn-secondary" href="mailto:…">` to the workspace's Admin
addresses, subject prefilled `Workspace Admin access — {workspace}`. Real,
honest, zero backend. (Both roles are inside the same tenant and the roster
above already shows emails, so no address is exposed that the screen does not
already show.) If the table prefers to drop the button, the block still reads
correctly without it — a dead button is the one option that is not available.

### D-58.9 — The member row shows an email, and the role summaries are D8's, not the prototype's

**New (F3/F4) — two decomposer traps of the same shape, both live in the
