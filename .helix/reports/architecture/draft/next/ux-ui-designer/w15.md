## NW-27 — the document states contract once the gate runs on the Worker

**The design question, exactly**: `w15-requirements.md` OQ-w15-004 puts the
admission gate on the Worker, which makes a refused file a **terminal `Rejected`
row**. `screens-v2.md:72-75` calls the "Not added" card ***session-only, never
counted***, and the code enforces that premise verbatim —
`documentTable.ts:74-79` ("no `Rejected` server-side — rejected files are a wholly
separate, session-only concept"), `UploadResultCard.tsx:10-19`
("a rejected file was never stored, has no id, and is never counted"),
`uploadPipeline.ts:54-61` (`RejectedFileOutcome`, "never persisted"). The council
needs the states ruling before the migration is written.

### A1 — The premise of the session-only rule is gone, so the rule goes with it

`UploadResultCard.tsx:16` gives the rule its own reason: *"a rejected file was
never stored, has no id"*. With the gate on the Worker the file **is** stored
before the gate can run — the gate parses and OCRs it
(`DocumentAdmissionGate.cs:110-112`) and calls Foundry `classify` (`:136-138`),
neither of which can happen on bytes nobody kept. A refusal therefore arrives
**seconds or minutes after the drop, possibly with the browser closed**, which is
the one thing a session-only card cannot survive.

**Decision**: a refused file **is a row**, with a terminal server status. A card
that vanished on reload would hide a durable server fact — the exact shape ADR-012's
w14 footer forbids ("a client store never stands in for a missing GET"), and it
would silently lose files against A15-1's own promise that every dropped file
"survives a reload and a second browser". **This is a named divergence from
`screens-v2.md:72-75`, and the requirements win.**

**What survives of the oracle's instinct, and it is the important half**: *never
counted*. A refused file is never counted as a document Raffa **holds** (§A4).

### A2 — The wire value is `Rejected`; the screen says **Not added**

No new word enters the product. The row's status tag is the string already
shipped on the card — `UploadResultCard.tsx:24`
`<span class="tag tag-outline">Not added</span>` — and the treatment is the one
already on it.

| Wire (`DocumentProcessingStatus`) | `RowStatus` | Tag variant | Label |
|---|---|---|---|
| `Rejected` (new) | `"rejected"` (new) | `.tag-outline` | **Not added** |

This is the same wire-value → label translation the grid already performs
(`NeedsReview` → "Needs review", `semantics.ts:67-68`). **`.tag-outline`, not
`.tag-accent`**: the accent is reserved for `failed`, a Raffa-side failure the user
can retry (`semantics.ts:69-70`; ADR-019 `## Semantic mapping` `:105`). A refused
file is not a failure — it is a decision about the file, and `.tag-outline` is
already this system's "this row is about a decision" treatment (ADR-019 w14
clause 1's own derivation for `Expired`). The **one-accent rule** holds and
`## Accessibility baseline`'s no-colour-only rule is satisfied by the text label.

**Anchors a web task must cite**: `web/src/styles/semantics.ts:52` (`DocumentStatus`
union), `:61-72` (`getStatusTag`), `web/src/routes/documents/documentTable.ts:79`
(`RowStatus`), `:81-93` (`getRowStatus`), `:97-99` (`getRowStatusTag`).

### A3 — The reason is the row's `hint`; the card is retired

The three refusal sentences are requirement copy and stay word for word after the
lead-in: `uploadPipeline.ts:39-46` (`not_a_contract`, `no_readable_text`) and
`:50-52` (`getOversizedCopy`). They become a server field on the row and render in
the **existing** hint slot under the filename — the slot
`DocumentStatusTable.tsx:138` already uses ("Not yet linked to a contract").

**One copy edit, made here so a task does not make it silently**: the `"Not added: "`
lead-in is **dropped** when the sentence sits beside the tag, because the tag is the
lead-in. The remainder is verbatim — e.g. *"This looks like a recipe, not a contract.
Raffa only keeps contracts, order forms, quotes and the documents around them. Drop
the signed agreement or the supplier's proposal."* (initial capital restored). The
oversized sentence keeps its filename: *"{fileName} is larger than 50 MB. Raffa
accepts files up to 50 MB."*

**`UploadResultCard.tsx` is deleted, not kept beside the row.** `screens-v2.md:76`
is *"one row per file, per-file outcome"*; a card **and** a row for the same file is
two surfaces for one fact, and the card is the one that cannot survive a reload.

**Next step on a `Rejected` row: none.** The action cell is empty
(`documentTable.ts:117-134` `getRowAction` returns `null`, as it already does for a
processing row). There is nothing to review, ask or retry — re-dropping the same
file would be refused again. The Admin's existing `Delete` column
(`DocumentStatusTable.tsx:184-208`) is the only way to clear it, which needs no new
endpoint and no new copy. **No "Dismiss" affordance**: a durable row cannot be
dismissed client-side without a client store standing in for the server (ADR-012).

### A4 — What each number counts (the rule NW-10's task also needs)

Four counters read the same list and they do **not** all mean the same thing. This
table is the contract:

| Surface | Anchor | Counts `Rejected`? | Why |
|---|---|---|---|
| "All documents · N" | `AttentionFilter.tsx:25-27`; `useDocumentsList.ts:123` | ~~**yes**~~ → **no — WITHDRAWN at the table, see §9.1** | It is a *filter* label — `getFilterHint` promises "Everything, including validated documents" (`documentTable.ts:166`). Hiding a row from "All" is a lie, and A15-1 reads "All documents · 15" after 15 files |
| "Needs your attention · N" | `AttentionFilter.tsx:22-24`; `useDocumentsList.ts:122`; `documentTable.ts:141-143` | **no** | `isAttentionStatus` must exclude `Rejected` as well as `Completed`. Nothing is pending on a refused file; leaving it in inflates the default filter and the rail badge **forever** |
| `kbSummary` "N documents · M askable · K waiting for your review" | `documentTable.ts:154-160` | **no** | This is the **corpus** line — what Raffa holds. This is the surviving half of the oracle's *never counted* rule |
| Rail **Documents** badge (`N to review` / `N docs`) | `ia-v2.md:25`; `navItems.ts:99-107`; `RailNav.tsx:67,72-75` | **no** | `N to review` is the attention count; `N docs` is the corpus count. Both exclude `Rejected` |

No new segment is added to `kbSummary`. A user who wants to see refused files
switches to **All documents** — the filter the hint already points at.

### A5 — "Queued" is the honest pre-stage reading, and it is a named divergence

The six stage strings are **untouched**: `screens-v2.md:65-66` =
`app.jsx:76` `stageLabels` = `documentTable.ts:56-63` = `DocumentProcessingStageMap.cs:20-39`.
`getStagePercent(null)` stays 0% (`documentTable.ts:68-72`).

What changes is the reading of `stage: null`. Today `DocumentStatusTable.tsx:155`
renders `(item.stage ?? "Uploading") + "…"`, and that is true in a synchronous
product because the row and the upload are the same act. Once `POST /api/documents`
returns at `processingStatus: "Uploaded"`, the file **is stored** and the row is
waiting for a Worker — a window the prototype never had (`app.jsx:46-48` creates the
row at `stage:0` and ticks to stage 1 after 700 ms) and one that A15-2 deliberately
makes long (restart the Worker mid-batch).

| Row | `stage` | Reads |
|---|---|---|
| local, pre-201 (`localUploads`) | — | **"Uploading…"** (unchanged — the file genuinely is in flight) `DocumentStatusTable.tsx:97,105` |
| server, `Uploaded` | `null` | **"Queued…"** |
| server, `Processing` | one of six | the stage string, verbatim |

**Divergence named**: `app.jsx:46` has no queue wait, so the export cannot answer
this. "Queued" is one plain word that fits the 13px cell, and it is the only reading
that does not claim an upload that already finished. A row stuck at "Uploading…"
for a minute is indistinguishable from a stuck upload — which is precisely the
defect A15-2 exists to catch.

### A6 — Screen 3's state inventory, restated

`screens-v2.md:77-79` becomes, for the product (the export line is unchanged on

> completed · failed (retry) · **not added (a row, terminal)** · attention-empty ·
> list error

`rejected (not added)` moves from a session card to a row; `queued` is new.

## NW-61 — "still processing" on three screens that have no such state

**The gap, precisely.** The client half of the progression is already built and
correct (`useDocumentsList.ts:132-134` optimistic row, `DocumentStatusTable.tsx:151`
server stage, `documentTable.ts:67` "never a client timer"). What is missing is
downstream: **Contract 360, Portfolio and Ask cannot tell "nothing here" from "still
processing"**, so a user who has dropped fifteen contracts is told to upload one.

### B1 — The states contract gains a fourth state: **not ready yet**

This is the IA-level decision and it is the one that generalises.

ADR-018 `## Empty / error / loading (IA-level contract)` (`:112-119`) names three
states. A surface whose content derives from **validated contracts** has **two**
zero states, and they are not the same thing:

| State | Means | Treatment | Copy shape | CTA |
|---|---|---|---|---|
| **empty** | nothing has been uploaded | h3 + one sentence + primary action (unchanged, `:116-117`) | "…Upload one to start." | **Upload a contract** → `/documents` |
| **not ready yet** (new) | something is in flight or awaiting review | **the same block** — h3 + one sentence + one action. **Not** the error treatment: nothing has failed | "…still being processed." | **Go to Documents** → `/documents` |

Two rules bind it:

1. **The distinction is a server signal, never a client heuristic.** The surface is
   told; it does not infer. This is ADR-012's w14 provenance rule extended one step
   — *a client must not infer a server state it can be told* — and it is why NW-61
   asks software-architect for a completeness signal on the aggregates rather than
   a second client count.
2. **An empty state must never tell a user to do a thing they have already done.**
   "Upload a contract" shown to someone whose fifteen files are mid-pipeline is the
   product forgetting what the user just did.

It binds every tier surface, including the two this wave does not build: **Ask**
(§B2), **Portfolio** (§B3), **Contract 360** (§B4), and — same shape, no task
required this wave — **Renewals** (`screens-v2.md:125-127`) and **Quote check**
(`:141-144`). Stating it once in ADR-018 means those two inherit it without a
second decision.

### B2 — Ask: the copy is already right; the **predicate** is wrong

`screens-v2.md:25-30` already ships both variants and the product already renders
them verbatim (`askViewModel.ts:250-261`, the "still processing" sentence at
`:253-255`). **No copy change. None.**

The defect is which variant is chosen. `hasAnyDocument` is `totalCount > 0` over
documents **in any state** (`ask/index.tsx:93`, `:99-105`, `:254-257`), so a tenant
whose only documents are `Failed` — or, after NW-27, `Rejected` — is told *"Your
document is still processing or waiting for review"*, which is false.

**Decision**: the sentence's own two clauses are the predicate.

| Variant | Shown when | Copy (`screens-v2.md:28-30`, verbatim) | CTA |
|---|---|---|---|
| still processing | ≥1 document is `Uploaded` · `Processing` · `NeedsReview` | "Your document is still processing or waiting for review. Ask only answers from facts that passed validation — so it never guesses." | **Go to Documents** |
| nothing yet | otherwise (including "every document is `Failed` / `Not added`") | "Upload a contract first. Raffa extracts the facts, you sign off the weak ones, and Ask switches on." | **Upload a contract** |

A tenant holding only refused files is told "Upload a contract first" — true: they
have no contract. **No third string is invented**, and the first clause of the
shipped sentence ("still processing **or waiting for review**") maps exactly onto
the three statuses above, which is the evidence that the copy was written for this
predicate all along.

**Anchors**: `web/src/routes/ask/askViewModel.ts:250-261`, `web/src/routes/ask/index.tsx:93`,
`:99-105`, `:254-257`.

### B3 — Portfolio: one new variant of the block that already exists

Today one zero state, verbatim from `markup.html` `kbOff` and `screens-v2.md:116-117`
(`contracts/index.tsx:130-139`).

| Condition | h3 | Sentence | CTA |
|---|---|---|---|
| 0 validated **and** nothing in flight (today) | "Nothing to triage yet" | "The portfolio lights up from validated contracts. Upload one to start." | **Upload a contract** |
| 0 validated **and** ≥1 document in flight (new) | **"Nothing to triage yet"** (unchanged — it is true either way) | **"Your documents are still being processed. The portfolio lights up from validated contracts."** | **Go to Documents** |

The h3 is unchanged, the second half of the sentence is the export's own words, and
the CTA label is already in the product's vocabulary (`screens-v2.md:30`,
`askViewModel.ts:256`). **No new vocabulary.**

**Anchor**: `web/src/routes/contracts/index.tsx:130-139` (`.screen-reroute`).

### B4 — Contract 360: a fifth state, because the alternative is an empty contract

`screens-v2.md:112` lists screen 5's states as `open · in negotiation · assigned ·
not uploaded (empty)`; the code has `loading | not-found | error | ready`
(`contract360/index.tsx:21-25`, `:140-157`). Once NW-27 creates a `contractId`
before extraction finishes, `ready` renders an aggregate with no clauses, no spend
and no dates — **"an empty contract"**, which is the product promise NW-61 is
written to protect.

**Decision — screen 5 gains `still processing`**, per §B1:

> h3 **"This contract is still being prepared."**
> "Raffa is still extracting the facts. It will open here once they pass validation."
> `.btn-secondary` **"Go to Documents"** → `/documents`

Driven by the aggregate's own completeness signal (software-architect's), **never
inferred** from an empty clause array — an empty array is also what a genuinely
factless contract returns, and the two must not share a screen.

Two smaller consequences of the same rule, stated so a task does not guess:

- **Details ▾ › "documents in family"** (`screens-v2.md:103-104`): a document that
  is not yet validated renders **with its row status tag** (§A2's vocabulary),
  never silently omitted. A family that hides its own in-flight members is the same
  lie one level down.
- The **back label** and every other chrome element are unchanged.

**Anchors**: `web/src/routes/contracts/contract360/index.tsx:21-25` (`FetchState`),
`:72-117` (load), `:140-157` (loading / not-found), `:229-255` (render).

### B5 — What NW-61 does **not** change

The optimistic local row (`useDocumentsList.ts:132-134`), the stage rendering
(`DocumentStatusTable.tsx:151-155`), the progress bar, the six stage strings, the
attention filter's default, `justValidated`'s hook (`screens-v2.md:70-71`). The poll
predicate (`useDocumentsList.ts:105-108`), the request timeout and the read-back
contract are **client-architect's**, not this seat's.

### ADR action — NW-61

- `amend ADR-018` — §B1: `## Empty / error / loading (IA-level contract)` gains the
  **not-ready-yet** state and its two rules; it binds Ask, Portfolio, Contract 360,
  Renewals and Quote check.
- `amend ADR-020` — screens **2** (§B2, predicate only, copy confirmed unchanged),
  **5** (§B4, a fifth state), **6** (§B3, a second zero-state variant).

## NW-68 — the delivery copy is confirmed; the **email itself** is the unowned surface

### C1 — Everything the pane says about delivery is already decided

ADR-020's w14 footer 10.1 pre-decided the whole set *"so it is not re-opened"*
(`ADR-020:280-287`). This seat **confirms it verbatim** and re-opens nothing:

| Fact | Copy | Status |
|---|---|---|
| `mailDelivered: true` | "Invitation sent to {email}." | shipped, `InvitePane.tsx:118` — **unchanged** |
| `mailDelivered: false` | "Invitation ready for {email}." + the link + `.micro-meta` "It expires {date}, can be used once, and is not shown again." | shipped, `InvitePane.tsx:124-138`, `memberViewModel.ts:194-196` — **unchanged** |
| delivery **failed** (the third value 10.1 reserved) | "Invitation created, but the email could not be sent." + **"Try sending again"** | pre-decided `ADR-020:282-284`; becomes reachable this wave — see NW-69 §D2 |

The absolute accept link (`Invitations__AcceptUrlBase`) needs **no copy change**:
`composeAcceptLink` already accepts a site-relative or an absolute `acceptUrl`
unchanged (`memberViewModel.ts:175-179`), by design.

**ADR-020 action for the pane under NW-68 is therefore `none` — already decided in
the w14 footer.** The outcome *set* changes, and that change belongs to NW-69.

### C2 — The invitation email has no design owner, and that is how a task invents one

NW-68 ships "a Raffa-branded mail". **There is no email anywhere in any export** —
`inputs/design/` holds screens, `markup.html`, `styles.css`, `app.jsx`, and nothing
that leaves the browser. ADR-019's system is a *web* system (flat, 0 radius, one
accent, `styles.css` custom properties) and **none of its mechanism survives an
email client**: no external stylesheet, no CSS custom properties, no web font.

Leaving this to the implementing task produces branded HTML nobody reviewed, on the
first message the product ever sends to a person outside the tenant. So this seat
decides it now.

**Decision — the invitation email is *surface 12* of ADR-020**: not a screen, but a
user-visible surface with a state set and an owner. (If a second message ever ships,
a later wave may lift it into its own ADR; one message does not earn one.)

**Form.**

- **Plain text is the body of record**; an HTML part may be added but must carry the
  same words in the same order and read correctly if it is stripped.
- One column, left-aligned, **no images, no logo file, no web font, no external
  stylesheet**. Any colour is an inline literal of an ADR-019 token value
  (`--color-accent` `#ec3013`, `--color-accent-700` `#ae1800` for text,
  `--color-text` `#201e1d`), never a variable reference. This is ADR-019's
  *"consume tokens, do not fork them"* honoured in the only way an email allows.
- The accept link is a **plain visible absolute URL** as well as an anchor — a
  forwarded or text-only copy must still be usable.

**Copy — verbatim, and deliberately the same words as the screen the link opens.**

> **Subject**: You've been invited to {workspace} on Raffa
>
> **Join {workspace}**
>
> You have been invited as {role}.
>
> [ Open your invitation ]   ← the absolute accept link
>
> Signing in uses your email address — Microsoft will send you a one-time code.
>
> This link expires {date} and can be used once.
>
> If you were not expecting this, you can ignore this message.

Line 2 and line 3 are ADR-020 screen 11 state 2 **verbatim** (`ADR-020:397`):
`h2` "Join {workspace}" and "You have been invited as {role}." The mail and the
landing page must say the same thing or the invitee thinks they clicked the wrong
link.

**Three rules, each closing a real failure.**

1. **The mail carries the workspace name, the offered role and the expiry — and
   nothing else.** No validated-contract count, no member list, no supplier names.
   The same leak guard as ADR-020 `:422-425`, and stronger: a mail can be forwarded
   by anyone, forever.
2. **The one-time-code line is not decoration.** With NW-67 the invitee's first
   sign-in issues an Entra **email one-time passcode** — a *second* message, from
   Microsoft, that they did not expect. The raw file names this exact abandonment
   ("today the first signal is Microsoft's error inside the popup, where Raffa
   cannot intervene"). One sentence in Raffa's own mail turns a suspicious second
   email into an expected step. **The same sentence appears on screen 11 and on the
   invite pane** — one string, three surfaces (NW-69 §D3).
3. **The mail never claims an account was created.** It says signing in uses their
   email address. "We created an account for you" is both alarming and, from the
   invitee's side, untrue — nothing exists for them to manage.

**Anchors a task must cite**: `IInvitationMailer.cs:16-33` (the seam),
`NullInvitationMailer.cs:16-38` (which deliberately never interpolates the URL —
the new implementation is the first thing in the product allowed to),
`ADR-020:397` (the two sentences quoted), `memberViewModel.ts:175-179`
(absolute-vs-relative already handled client-side).

### ADR action — NW-68

- `amend ADR-020` — **surface 12, the invitation email**: §C2's form, copy and three
  rules. The pane's delivery copy is recorded as **confirmed, unchanged**
  (`none — already decided in the w14 footer 10.1`).
- ADR-019: **none** — no token, no component, no semantic row. The email consumes
  token *values* inline precisely because it cannot consume the system.

## NW-69 — the invite pane grows from one boolean to four outcomes

### D1 — One boolean cannot carry what NW-67 and NW-68 produce

Today: two states from one flag — `InvitePane.tsx:116-120` (`true`) and `:122-140`
(`false`), typed as a **binary union** at `memberViewModel.ts:171-173`, mapped from
the 201 at `index.tsx:127-131`. With `NullInvitationMailer` always `false`
(`NullInvitationMailer.cs:30-36`) only the second is reachable, which is why an
"Invitation sent to …" on `dev` is recorded as a defect.

This is the same shape of defect ADR-020 10.3 already named for `MemberStatus` —
*a binary type that a third case is about to arrive at*. It is named here before it
ships, not after.

### D2 — Four states, in a precedence order: **identity first, delivery second** — **state 1 RETIRED at the table, see §9.2**

The two new facts (guest provisioned? mail sent?) are not independent in what the
Admin must **do**. A delivered mail whose link leads to a sign-in the invitee cannot
complete is worse than no mail at all — that is A15-4's failure and the whole reason
A15-7 exists. So the pane speaks about identity first and only then about delivery.

| # | Server outcome | Copy | Affordance | Link shown? |
|---|---|---|---|---|
| 1 | guest provisioning **failed** | **"Invitation created, but {email} cannot sign in yet."** + `.micro-meta` **"Raffa could not add them to your company directory, so the link will not work yet. A tenant administrator has to approve Raffa's permission to invite guests."** | `.btn-secondary` **"Try sending again"** | **no** |
| 2 | guest ok · mail **sent** | **"Invitation sent to {email}."** (10.1, unchanged) + §D3's `.micro-meta` | — | no |
| 3 | guest ok · mail **failed** | **"Invitation created, but the email could not be sent."** (10.1's pre-decided third value, verbatim) | `.btn-secondary` **"Try sending again"** + the link block | **yes** |
| 4 | guest ok · **no transport configured** | **"Invitation ready for {email}."** (10.1, unchanged) + expiry `.micro-meta` | the link block | **yes** |

Blocking pre-creation failures (format, 400, 409) are unchanged
(`InvitePane.tsx:110-114`).

**State 1 withholds the link, and that is the decision this item exists for.** Both
environments authenticate against a **single** Entra tenant
(`identity/main.tf:63`, `:118`) and `write_web_runtime_config.py:80-82` forbids a
`common`/`organizations` authority — so an address the tenant does not know
**literally cannot sign in**. Rendering a copyable link there would be exactly the
"'ready' link that cannot be used" the raw file names as the defect. The word
**"sent"** appears nowhere in state 1 or state 3 (10.1's rule, extended).

State 1's `.micro-meta` names **what someone must do next**, not what the stack did
— ADR-019 w14 clause 2's rule for a visible reason. It says "a tenant
administrator", not "you", because the Admin of a Raffa workspace is usually not

### D4 — **"Try sending again" must not mint a new invitation**

ADR-020's second w14 footer gives `Invited` and `Expired` rows the action **"Send a
new invitation"**, whose consequence line is *"**The link you already shared stops
working.**"* (`ADR-020:539-546`). "Try sending again" is a **different act** and the
two must not be quietly merged:

> **"Try sending again" retries the transport (or the provisioning) for the
> invitation that already exists. It does not mint a new one, so it does not kill a
> link the Admin may already have copied, and it therefore carries no consequence
> line and no inline confirm.**

**If the implementing seats cannot offer that** — if the only available mechanism is
revoke-then-invite — then the button's **label becomes "Send a new invitation"** and
it takes that row action's inline confirm and consequence line, unchanged. One or
the other. **Never "Try sending again" with re-issue semantics**: an Admin who is
told "try again" and silently loses the link in someone's inbox was misled by this
seat's own copy. The mechanism is software-architect's (ADR-026 `:234`/`:226`, or one
server-side operation); the label follows the mechanism, and this footer binds both
branches so no task has to choose.
